# 联合环

联合环是 Scarlet/Violet 中最多可容纳 4 名玩家共享地图字段的会话。其代码将其称为团队圈（`TeamCircle`），而蓝莓任务（BBQ）则称为 `bbmission`。pokeldn 以嘉宾身份加入控制台本地的联合环，报告完成蓝莓任务的清除（这些清除会为房主授予 BP，并释放 Snacksworth 的传说宝可梦），并在房主玩家周围生成野生宝可梦（参见[野外遭遇](#overworld-encounters)）。本应用的两个联合环工具位于[应用指南](gui.md#union-circle)中。

以下 Lua 代码是 Scarlet 4.0.0（`main.blua`，SHA-256
`c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815，[太晶团体战](sv_raid.md)的 chunk）的 chunk `be21e65463b9a98f`，除非另有说明为 `main_dynamic`。`0.N` 表示该 chunk 主函数的原型 N（从 0 开始计数）。这些原型编号与公开的 3.0.1 反编译版本（Martmists-GH/SV-Script-RE）相同。尖括号中的名称来自其哈希列表；其他名称仍为哈希值。

## 获取 Lua 代码

该 chunk 位于 `arc/data.trpfs` 中的 `script/lua/bin/release/main/main.blua`，以 Oodle 压缩存储。4.0.0 更新所需的虚拟 RomFS 需要基础游戏的支持：`arc/data.trpfd` 的一部分位于基础游戏中。

    ./.venv/bin/python tools/switch/nso_read.py main main.bin
    ./.venv/bin/python tools/switch/trpfs_read.py --update UPDATE.nsp --base BASE.nsp --keys prod.keys \
        --image main.bin --extract script/lua/bin/release/main/main.blua --out-dir OUT

`--image` 运行 `main` 的 `OodleLZ_Decompress`（`0xcc8750`）。该 chunk 是 Lua 5.4 字节码，包含 30,829 个顶层原型；`main_dynamic`（`script/lua/bin/release/main_dynamic/main_dynamic.blua`）保存事件脚本，并以相同方式提取。

## BBQ

任务进度是原生的，位于 Lua 模块 `c5137FC87` 中。Lua 游戏事件通过 `C00099C1DFBF96B11.S110BDDB84DEB4379`（`0.7064`）报告到其中，它将（任务类型、两个值、计数）传递给 `c5137FC87.f4246D9CA`；例如，一次进化报告类型 28，计数为 1。圈子的一侧任务是另一个原生模块 `c4D400AC0`。

每个任务都有一个等级，即其 `MissionInfo` 行在俱乐部数据（`arc/worlddataclubMissionDifficultyWeightAdvanced.bin.trpak`）中的 `mission_grade`：0 普通，1 奖励，2 团队。Snacksworth 将团队任务称为团队任务。一次清除事件会携带其任务的等级。

该包的任务表是一个 FlatBuffer，包含 64 个 `MissionInfo` 结构：类别（1 战斗、2 领域、3 摄影）、`mission_type`、`mission_id`、目标、奖励 BP、重新加载 BP（用于更换任务）、释放类型、等级、难度（0 新手至 2 高级）和权重。任务 ID 在每条消息中是其行的 `mission_type`；`mission_id` 用于区分同类型行，它们在等级、难度、目标或 BP 上有所不同。BBQ 列表通过一对值（`0x29de0f4`）查找任务。另一个表 `MissionSettings` 提供每种类型的文本变体（宝可梦类型、生物群落、口味），位于 `club_bbmission` 中。任务表使用的类型：

当 BBQ 管理器创建时（`0.7062`），它会向原生侧提供 getter。`c16FE4B25` 获取玩家自己的字段（`f61488ABA`，存档的 `currentFieldId`）和成员的字段（`f45B80F87`，站点索引的 110 值）。`c5137FC87` 获取玩家是否在野外（`f01FF34BD`）以及两个俱乐部等级标志 `FSYS_CLUB_BBMISSION_LVUP_01` 和 `_02`。

每帧，管理器的 `PreUpdate`（`0.7069`）处理三个原生队列：

| 队列 | 来源 | Lua 执行的操作 |
|---|---|---|
| `c5137FC87.fB8D11637` / `f35493666` | 玩家自己的清除 | 在 `c4D400AC0.f5770F782` 保持时，将每个清除交给 `c4D400AC0.fAC449469`。在圈子中完成的奖励清除（`c4D400AC0.f48603105`）会发送至 `c4D400AC0.f263D7D28` 和 `f07578A96`（房主处），而嘉宾对其不获得任何积分。其他清除则排队等待 BP |
| `c4D400AC0.fD7C6549F` / `f37737462` | 其他成员的清除 | 显示每条清除为通知；除非是奖励清除，否则排队等待 BP |
| `c4D400AC0.fD961BFD2` / `f541C4B17` | 来自圈子的 BP 授予 | 将每个授予排队等待 BP |

`0.7075` 将排队的事件合并为同等级的一个，并将它们的 BP 相加（`fBCA6AEB8`）。`0.7076` 将排队的总数添加到货币管理器，`0.7077` 显示 BP 消息。管理器的添加（`0.15120`）将玩家的 BP 限制在 0 至 9,999,999 之间（`0.15128`），因此一次清除最多计 9,999,999 BP，尽管其 BP 是 s32。

Lua 不检查任何条件：成员的普通或团队清除直接从第二个队列支付给房主，而奖励清除仅通过原生圈子模块放入第三个队列的授予支付。

## 原生模块

以下地址位于 Scarlet 4.0.0 的 `main` 中。

原生模块和函数名称是 `main` rodata 中的普通字符串；每个模块都有一个 `{name, function}` 对的 `luaL_Reg` 样式表，位于 `.data` 中：`c4D400AC0` 位于 `0x442e500`（22 个函数），`c5137FC87` 位于 `0x4420630`（45 个）。清除事件是 userdata（方法位于 `0x441dc50`）：`fBCA6AEB8` 返回 BP（s32，偏移 `+0x10`），`f0C278E84` 返回等级（s8，偏移 `+0xd`）。`0x29dd878` 根据任务行构建它：任务 ID（u16，偏移 `+0x0`）、`0x4` 处的 u32、等级和 BP。

`c4D400AC0` 的函数作用于一个圈子对象，这是一个惰性构建的单例，位于 `0x4739410`：

| 函数 | 功能 |
|---|---|
| `f5770F782` | 圈子是否就绪（`0xa0d038`） |
| `f48603105`、`fE8E53DDE` | 玩家是否在圈子中，以及是否为房主（`0xa0e9ac`） |
| `fAC449469` | 发送玩家的清除作为消息 3（`0xa0db20`） |
| `f263D7D28` | 在房主处，发送奖励清除作为消息 5（`0xa0dcf4`） |
| `f07578A96` | 在房主处，为其自己的奖励清除记分（`0xa0df34`，然后是授予推送 `0xa0e164`） |

圈子在其自己的通道上发送这些消息（对象的 `+0x70`）：游戏密钥 0x0048 在 0x80 端口 0 上，消息类型在 kind 字节中。每条消息都是游戏标记格式（`0xb9`，18 个字段，由 `0xa17694` 读取）的清除事件，然后是发送者的消息序列（`+0xb8`）。消息 3 还携带发送者的 BBQ 状态记录（`0xa0f37c`，由 `0xa17170` 读取）。在标记格式中，-64 至 127 的整数是其自己的字节，更宽的整数放在带符号标签（0x84 至 0x86）之后，浮点数放在 0x88 之后。

清除事件的字段：

| 字段 | 值 |
|---|---|
| 0 | 任务 ID |
| 3、11 | 任务的槽位 |
| 4 | 等级 |
| 5 | BP |
| 6 | 发送者的站点 ID 元组（u64，标签 0x83） |
| 7 | 任务的 `MissionInfo` 行 |
| 12、13 | 占据该槽位的任务及其行 |

其他字段为零或空行。清除前 0.1 秒，房主发送 kind 2：任务、-1、-1、其进度（1.0）、其序列和状态记录。

### BBQ 状态记录

每个玩家的 BBQ 管理器在其 `+0x40` 处保存状态记录；圈子将其（`0xa0f37c`）写入消息 1、2 和 3 中。消息 1（kind 1）是发送者的消息序列和状态记录本身。玩家在圈子开始时发送一条（步骤 1），然后发送一个无载体的 kind 4（`480004`），然后步骤 2，房主在每次成员清除后再发送一条。该记录是一个 11 元组：

| 元素 | 记录偏移 | 值 |
|---|---|---|
| 0 | `+0x0` | 每条记录中都为 1：管理器在 `+0x40` 处的字节 |
| 1 至 3 | `+0x4`、`+0x50`、`+0x9c` | 玩家的三个任务槽 |
| 4 | `+0xe8` | 每条记录中都为 1 的单字节字符串 |
| 5、6 | `+0xec`、`+0x138` | 两个额外槽，在所有观察到的记录中均为空 |
| 7 | `+0x184` | 带符号字节，等于元素 9 在所有记录中 |
| 8 | `+0x185` | 玩家距离下一次授予的奖励清除次数 |
| 9 | `+0x188` | 单人总分（管理器的 `+0x1c8`） |
| 10 | `+0x18c` | 团队总分（管理器的 `+0x1cc`） |

槽（`0xa0fa18`）占 0x4c 字节，其中记录携带任务 ID（u16，0 表示为空）、其进度（float）、其文本变体（`MissionSettings` 的变体，0 表示无）和行的 `mission_id`。成员的主机第五槽如果命名的任务与自己的不同，则采用主机的槽（`0xa14290`）。

`circle.bbq_record` 读取以消息 1、2 或 3 结尾的状态记录。

零售主机的槽保存其任务类型的新手普通行（`mission_id` 0：20 BP，目标为 10 次击败用于任务 1，其他任务为 1），进度为 0，直到报告完成其中一个；其余槽保持为空，奖励计数为 0。

### 成员在主机任务上的进度

成员通过消息 2（kind 2，0x80 端口 0）报告进度来完成主机的一个任务：任务、两个值（-1、-1 表示无变体）、计数、其消息序列和自己的状态记录。主机回复其显示进度的记录，然后自己的消息 3：信用成员站点 ID（字段 6）的清除、BP、槽位和任务。其单人总分增加 1。

消息 2 携带 Lua 的进度报告（`c5137FC87.f4246D9CA`）传递的内容：任务、其两个值和计数。主机的接收处理器将这四个值（带上成员标志和发送者）交给与其自身报告相同的原生进度分发器（`0x29dc838`，其自身报告到达 `0x29dc6b0`）。因此，主机将成员的进度计为自己的进度，完成任务并自己清除它，并且该清除像任何自己的清除一样计入其单人总分。

`circle.progress_message` 构建消息 2。一次 Snacksworth 运行（参见[加入](#joining)）会向主机的三个槽依次发送最新记录显示的任务，计数为 500（普通行的最大目标），并将槽的变体作为第一个值，无变体则为 -1；零售主机会清除每个任务。

## 主机如何处理成员的通关

接收处理程序 (`0xa13b00`) 通过跳转表 `0x3c5b7a4` 进行类型分发。对于消息 3，主机：

1. 将成员的 Bonus 次数存储在其 BBQ 状态中对应成员槽位；
2. 在自己的 BBQ 列表 (`0x29de0f4`，按任务 ID 和 `+0x4` 的 u32 查找) 中查找该任务。只有匹配到主机自己的 Bonus 任务时，通关才计入主机自己的统计，并且只有此时主机才会为其排队自己的通知。在步骤 4 中的标志之外，结果不决定以下任何内容；
3. 将通关排队作为成员的通知（`fD7C6549F` 队列）；
4. 如果通关是 Bonus，则将事件的 `+0x7c` 设为 min(3, 主机自己的 Bonus 次数加上三个成员槽位)，将 `+0x80` 设为步骤 2 是否匹配，将其发送给每个成员作为消息 5，并通过授予推送将事件作为接收到的方式授予自己；
5. 如果通关是 Team 清关且主机的 BBQ 管理器处于活动状态，则将 1 添加到主机的 Team 总计（如下所述）。

只有在此之后，主机才会比较消息的序列号与成员最后一次的序列号，并且序列号仅作为成员的状态记录的门控。

收到消息 5 的成员通过相同的授予推送授予事件，除非其序列号早于主机最后一次看到的序列号。

主机支付的是成员消息中命名的内容：不会检查 `+0x10` 的 BP 或任务是否存在。普通或 Team 清关由 Lua 立即支付。Bonus 清关通过授予推送，仅此而已。它逐个准备每个事件，并仅当其 `+0x7c` 比上一个已释放事件的 `+0x7c` 大 1，或小 2，或两者均为 0 时，才将其释放到授予队列（对象的 `+0x108`）中。该值由槽位构建，因此成员的下一个 Bonus 清关必须报告一个比上一次大 1 的计数。

## Snacksworth

BBQ 管理器维护两个运行总计，由 `c5137FC87.f6ED7C9B6` (`+0x1c8`) 和 `fECB0EBF0` (`+0x1cc`) 读取：

| 总计 | 上升条件 | 也被读取于 |
|---|---|---|
| 单人，`+0x1c8` | 玩家自己的普通或 Bonus 清关 (`0x29dda40`) | 俱乐部的 BBQ 等级提升事件，15 和 45 时 |
| Team，`+0x1cc` | 玩家自己的 Team 清关，以及在主机上每个成员的 Team 清关（消息 3，`0xa14918`） | |

Snacksworth 是事件 `s2_sub_012`，他的 25 个传说宝可梦是事件 `s2_sub_013` 到 `s2_sub_037`，每个事件的状态存储在 `WEVT_S2_SUB_0NN_STATE` 中。该事件在 `main_dynamic` 中的类（原型 `0.1995` 到 `0.2032`）通过 `0.2019` 读取单人总计，通过 `0.2020` 读取 Team 总计。当玩家与他对话时，`0.2002` 在单人总计（减去已在单人路线上释放的 `missionReleaseCount`）达到 `missionReleaseCount` 后释放下一个单人路线的传说宝可梦；`0.2003` 对 Team 路线使用 Team 总计和 `teamMissionReleaseCount` 做相同的处理。这两个计数都来自事件的配置表 (`s2_sub_012.ReleaseConfigTable`，位于 `arc/worlddataeventcommandcommand_data_rootcommand_data_root.bin.trpak`)。该包中唯一的该形状的表保存 10 和 1。

`s2_sub_012.ReleasePokeTable` 将每个传说宝可梦放置在四条路线中的两条上：两条单人路线 (`MissionA`, `MissionB`) 和两条 Team 路线 (`TeamMissionA`, `TeamMissionB`)：

| 在 | 传说宝可梦 |
|---|---|
| 两条单人路线 | 急冻鸟、雷鸟、火鸡、梦云宝 |
| 两条 Team 路线 | 烈空座、凯路夏、诺诺亚 |
| 每条各一条 | 其他 18 只 |

脚本向 `CA4C5F9FA83D2AF80.SDF0C255E6E08D740` 询问玩家当前处于哪一对路线：A 路线或 B 路线；朱离子版位于 A 路线（一次 Team 清关释放了 Zekrom，仅在 `TeamMissionA` 上）。每对路线将 25 只传说宝可梦分为两组，没有共享：单人路线上有 13 只，Team 路线上有 12 只。一次对话最多释放一个 snack，优先尝试 Team 路线。每条路线在尚未释放的传说宝可梦中随机选择 (`0.2007`)。一条路线的下一次释放需要其总计达到其计数乘以（已在其上释放的传说宝可梦数量加 1）。因此，所有 25 只需要单人总计达到 130，Team 总计达到 12，以及 25 次对话。

没有消息命名一个 snack：脚本将主机自己的总计与配置进行比较。每次携带 Team 清关的消息 3 都会将 1 添加到主机的 Team 总计，没有检查该任务是否是主机拥有的 Team 任务，也没有对重复进行序列检查；每次 `teamMissionReleaseCount` 为 1 时，每次都是一个 Team 路线的 snack。主机的每个任务由成员完成（[成员在主机任务上的进度](#a-members-progress-on-the-hosts-quests)）都会将 1 添加到其单人总计，从而支持单人路线上的 13 只。

## 加入

`bin/sv_join.py --union-circle` 以与团体战嘉宾加入团体战的方式加入一个控制台所主持的圈子 (`pokeldn.sv.circle`)。它占据座位，发送其身份记录，镜像主机在 0x7C 端口 1 上的频道表，并在 `--hold` 期间（默认为整个 `--seconds`）保持座位。它不发送大厅消息，并且在控制台离开时不会担任主机角色。当主机的场地升起时，它会将自己的玩家放置在上面 (`circle.Member`, [The field](#the-field))。它打印用户跟随的内容；`--verbose-circle` 添加其发送的每个圈子消息和区域搜索的每个步骤，`--capture` 文件也会保留这些内容。

    ./.venv/bin/python bin/sv_join.py --union-circle --code 3707 --hold 540 --capture circle.jsonl

零售版 Scarlet 4.0.0 在 Link Code 下主持一个圈子时，广告场景 5，最多四名参与者，以及交易的应用程序数据：密码中的代码和游戏字节中的代码，其长度为 +0x24。游戏字节中还保存有 `aa 08 3e` 在 +0x21，搜索中的控制台将其保持为零。

它以与 Link Trade 或 Tera Raid 主机相同的方式为嘉宾座位：加入响应、车站列表、频道表（键 0x007B、0x0132、0x0232 和 0x0332）、两个流的打开、时钟应答及其身份记录。然后嘉宾等待直到主机的玩家开始圈子。

## 启动圈子

在启动时，主机发送 Net 0x50，其中包含其广告的成员计数、0x80 端口 2 上的类型 7 公告（以及接受每个成员的类型 9），以及在 0x80 端口 0 上的圈子消息。

圈子消息是 Lua 的网络消息。每条都是一个游戏消息（处理器键、种类、步骤，然后是序列化器头；[Tera Raids](sv_raid.md#the-lobby)），位于键 0x0132，其种类是 Lua 消息 ID。团体战的“加载中”和“已加载”（0x0132，种类 0x6E 和 0x73）是同一接收者的消息 110 和 115。一些负载是 FlatBuffer 表，其他的是固定结构；104 和 106 是 LZ4 压缩的（序列化器压缩 2）。

| 消息 | 来自 | 负载 | 由 `TeamCircleUI` 处理 |
|---|---|---|---|
| 100 | 主机，在启动时 | 一个 u32 表，始终为 12345678 | 启动音效；嘉宾的启动标志 |
| 101 | 每个车站，主机在其 100 之后，成员在主机的 100 上 | 32 字节：车站所处的位置（场地 ID、三个宝可梦中心标志） | 每个车站 |
| 103 | 每个车站 | 一个 u32 表，同步点的 ID | 1 和 2 发送给 UI（启动演示已加载、已结束），其他所有 ID 发送给同步对象 |
| 111 | 主机 | 5916 字节：四个零字节，然后是一个包含两个向量表的 FlatBuffer（30 和 10） | 仅一个标志；内容原生读取 |
| 104 | 主机 | 一个表：游戏时间、实时时间及其经过的秒数（浮点数）、天气种子（u64）、彩票的长度及其当前和下一个天气的 {类型、持续时间} 对 | 时钟和天气，进入游戏时间管理器和 `WeatherManager.Sync` |
| 102 | 主机 | 两个 u32：成员所传送到的飞行点 | 传送 |
| 106 | 每个车站 | 300 个六字节槽位，其 Tera Raid 晶石；`ffffffff0000` 表示空槽 | 每个车站 |

主机按照表的顺序发送它们，在其 101 之后发送三条键为 0x0048 的消息，在启动后的两秒内完成。

每个车站都达到同步点 2215，等待每个车站的 101，发送其 106，并等待其他所有人的 106 (`IsGemInfo`)；启动演示的 103，ID 为 1 和 2，也以相同的方式等待。当每个成员都发送带有其 ID 的 103 时，达到同步点 (`CEEE8D2836ABEDE23`)。

零售版控制台会将超过 1395 字节的消息分割为片段，并将未分段的更长消息保持未确认状态，因此 106 会进行 LZ4 压缩，主机自己的也是如此。

一旦所有 106 就绪，主机传送到其 102 的飞行点并发送 115（1，0）。

## 字段

主机玩家随后进入字段。它打开 14 个更多的信道键（低字节 0x1E 至 0x2A，其中一些带子信道 0 和 1），并向每个成员发送 0x7C 端口 1 的更新，经 zlib 压缩。零售成员也以相同方式将相同的更新发回。主机发送键 0x0024 类型 1 步骤 1，无主体，从此开始发送其玩家：

| 内容 | 方式 |
|---|---|
| 动画状态 | 可靠，0x80 端口 0，键 0x001E 类型 5，状态名称 (`Top/pc_field/move/defaultwait01`)，每 3 至 7 秒一次 |
| 变换 | 不可靠协议 0x68（网格寻址如 0x80），键 0x011E 类型 4，38 个浮点数，约每秒 20 次；类型 6 和 7 各一次 |

在构建开始演示之前，主机等待 (`F9FFADFE613D572B7`) 直到其他每个站点的玩家对象在其字段上存在。未发送玩家的成员将停留在黑色的「通信中」屏幕上。主机通过原生模块 `c2A8846F6`（其 `f6BD530B6` 在等待之前即执行）生成成员为 `playables.Player` 对象。

玩家对象在字段键之后，通过 0x7C 端口 0 在每个成员与主机之间传输：

| 键 | 消息 | 内容 |
|---|---|---|
| 0x001F | id (u16), 类型 (u16) | 控制台声明其自身的一个对象 |
| 0x001E | 类型 0, 0, id (u16) | 控制台请求另一个声明的对象 |
| 0x001E | 类型 1, 2 或 3, 0, id (u16), 状态 | 回答：对象的状态，由对象在声明中的位置决定的类型 1、2 或 3 |

每个控制台声明四个对象（类型 0、1 或 2、3 和 10），id 从站点索引开始每次递增 4。一个控制台请求另一个声明的所有对象；没人回答类型 10 对象的请求。状态为 70 字节（类型 2）或 214 字节（类型 1 和 3），经 zlib 压缩：句柄、缩放、旋转、位置；类型 1 是玩家，携带一个 FlatBuffer。主机在成员的类型 1 回答后半秒开始其演示。

成员随后通过键 0x0025 向主机询问 u64 id 列表，主机以标志回答每个列表（参见[野外遭遇](#overworld-encounters)）。

键 0x0048，即 BBQ 模块的（参见[原生模块](#native-modules)），位于主机的第一个信道表中。在其端口 2 公告附近，主机发送类型 1 步骤 1，一个无主体的类型 4 (`480004`)，以及类型 1 步骤 2，两个步骤都携带其状态记录（参见[BBQ 状态记录](#the-bbq-status-record)）。

`circle.Member` 执行以下操作：
- 它用主机自身的 101 的副本回答主机的 100，因此客人的玩家站在主机的位置。
- 它回显主机发送的每一个 103。
- 它用 300 个空槽回答主机的 106，经 LZ4 压缩：一个没有水晶的世界。
- 它发送主机发送的每一个 110 和 115 的副本作为自己的，跟随主机的字段。
- 一旦 `sv_join` 发送了字段键回来，它声明站点 1 的四个对象并请求主机的每一个。它用客人 id 下主机自身该类型对象的状态回答主机的每一个请求，因此客人的玩家站在主机的位置。

使用 `--follow-host`，客人的玩家也随主机一起移动：主机的每一帧在 0x68 上以及键 0x001E 上的对象消息都在客人的匹配对象下发送，在客自己的 60 Hz 时钟上，延迟 0.3 秒重放主机（主机的变换大约每秒到达 27 次）。客人在主机 5 米范围内停留，面向主机，并将主机的移动混合按自己的步伐缩放。

使用 `--circle-task`，客人的玩家在任务完成后离开圆圈，运行结束：
- `snacksworth` 从其第一个状态记录中读取主机的单人和团队总分。从开始演示结束（其 id 为 2 的 103）后，每秒发送一次，团队清除其团队总分缺少 12，然后报告完成主机的任务直到其单人总分为 130（参见[成员在主机任务上的进度](#a-members-progress-on-the-hosts-quests)），然后再清除一次团队任务当其团队总分仍缺少任何（参见[Snacksworth](#snacksworth)）。每次团队清除都是从游戏绘制团队任务的方式绘制的团队任务（`circle.TEAM_QUESTS`，每个任务及 BP 带其概率）并获得该任务的 BP。它打印其进度随着主机总分上升，停止当它们在连续 20 次发送中没有上升时。
- `bp` 在开始演示结束后一秒发送一次，一次普通清除任务 29，获得 `--bbq-clear` BP，1 至 9,999,999。

每次清除都是一条带有 BP、客人的站点 id 和客人的状态记录的消息 3。

零售主机支付每一次这样的清除，无需客人发送消息 1；通知和 BP 显示一次其玩家关闭 BP 侧边栏后。一次团队清除，无论哪个任务，释放下一个团队路线传说宝可梦（参见[Snacksworth](#snacksworth)），无论主机在蓝莓学院内还是外。

## 野外遭遇

圆圈中的每个控制台从自己的游戏版本生成围绕自己的玩家的野生宝可梦，并将每个广播给其他人，因此成员可以捕捉到其他版本的专属宝可梦（Scarlet 主机在区域零生成 dev id 982，Violet 成员生成 992）。没有版本交换，主机没有特殊作用。

共享的宝可梦在 0x80 端口 0 和不可靠协议上传输，由其所有者广播；只有请求一个和拒绝请求发送到单个站点，在 0x7c 端口 0：

| 键 | 消息 | 内容 |
|---|---|---|
| 0x0026 | 类型 1, 其 96 字节记录作为字节字符串 | 所有者生成的实体（站点, n) |
| 0x0026 | 类型 2, (站点, n) | 实体消失 |
| 0x0026 | 类型 5, ((站点, n), (站点, n)) | 控制台向所有者请求实体进行战斗，采用请求者自己的 id；在 0x7c 端口 0 发送给所有者 |
| 0x0026 | 类型 6, 相同对 | 所有者拒绝；返回请求者 |
| 0x0026 | 类型 7, 相同对 | 实体现在属于第二个 id 的站点，进行战斗；有一次在该实体的类型 2 之前 15 秒 |
| 0x0126 | 类型 3, (站点, n), (一个浮点数, 0.0, 0.0, 0, 0 或 1) | 实体的状态，每 0.2 秒（成员）至 0.5 秒（主机）；最后一个元素是其状态 |
| 0x011E | 类型 4 在 0x68 上, 按对象 id | 实体的变换，如玩家 |

实体的对象 id 是站点 + 4n，打开其记录的 u16。一个控制台只与玩家站在其附近的成员分享其实体。每个 id 是一对无符号整数（调度器 `0x1dbd4b0` 不读取有符号标签）。

一个控制台将另一个的实体标记为未解决（状态 1）并拒绝战斗它（`BattleStartWait`），直到一个状态命名状态 0。走向已解决的实体时，它显示「!」并向所有者询问（`0x1972664`）：它为实体获取一个新的 id，存储该对和一个回调，并其管理器更新（`0x1593884`）向发送实体记录的站点发送类型 5。遭遇（`GameEventEncount`, NetInitWait）随后等待，无超时，直到所有者的回答命名相同的对（`0x1dbdd70`）。当它是其自身的一个且没有其他控制台持有时，所有者交出实体（`0x1dbdc20`，然后更新的广播在 `0x15934c8`），否则拒绝（`0x1593914`）。交出后，每个控制台将实体重命名为请求者的 id（`0x1595a1c`）并标记为已参与；请求者将其标记为自己的并开始战斗。当它战斗自己的实体时，一个控制台广播一次类型 7，相同对重复两次。

记录为 96 字节。`EncountManager.UpdateNetworkSpawn` 通过 Lua 模块 `c4CF1D719` 绑定的 getter 将其字段复制到 `pml.pokepara.InitialSpec` 中（原生 `0x90e344` 至 `0x90e588`），然后在宝可梦本身上设置勋章、Tera 种类和 Alcremie 的装饰。每个捕获的记录都符合此布局：

| 偏移 | 位 | 字段 |
|---|---|---|
| 0x00 | u16 | 对象 id |
| 0x04 | u64 位 0-10 | dev 种属 |
| | 11-22 | 持有物品 |
| | 23-30 | 缩放 |
| | 31 | 性别 (1 为母性) |
| | 32 | 异色；当设置时生成异色 |
| | 33-37 | 形态 |
| | 38-44 | 等级 |
| | 45-52 | 勋章 (标记)，当不为 0 时应用 |
| | 53-57 | 性格 |
| | 58-62 | Tera 种类 |
| 0x0C | u32 位 0-3 | Alcremie 装饰 |
| | 8-27 | IV HP、攻击、防御、速度，各 5 位 |
| 0x10 | u16 位 0-9 | IV 特攻、特防 |
| | 10-11 | 能力槽 |
| 0x24 | s32 | -1；在唯一见到的 Ditto 和 Zorua 中为 0 |
| 0x30 | 3 个浮点数 | 位置 |
| 0x40 | 4 个浮点数 | 旋转，每个样本都是单位矩阵 |

其他字节为 0（零售记录在 0x02、0x28 和 0x54 保存有陈旧内存）。在其记录之前，所有者在 0x68 上发送实体的帧：类型 6 无父节点 (`00000000 00000000 0000003f 0000003f 00000000 0000003f 0000003f`) 和类型 7 缩放 1.0。`circle.Spawner` 以相同方式发送客人的自身生成（参见[精心制作的遭遇](#crafted-encounters)）。

`UpdateNetworkSpawn` 仅从记录构建宝可梦；异色位设置稀有度字（`+0x18`）为 `0x2ffffffff` 或 `0x1ffffffff`，因此所有者决定是否异色。记录不含招式、PID 或加密常量；一次捕获会添加捕获者的训练师、球、位置、日期和等级。

游戏接受任何记录；PKHeX (Core 26.8.26) 将捕获判断为野外遭遇在捕获位置：

| 字段 | PKHeX 接受 |
|---|---|
| 种属、形态、等级 | Scarlet / Violet 野外槽在捕获位置具有该种属和形态且等级范围包含等级的；从不接受 shiny 锁定或静态专属如 Rayquaza |
| Tera 种类 | 种属自身的类型之一，除非分布爆发覆盖该种属在此处 |
| 性别 | 在种属的比例范围内 |
| 标记 | 不为 Mightiest 或 Titan；Jumbo 仅当缩放 255，Mini 仅当缩放 0；天气标记仅当槽命名该天气 |
| 异色、性格、IV、能力槽（含隐藏）、缩放、持有物品 | 任意 |

PKHeX 列出每个 Scarlet / Violet 野外槽在两个版本下，因此其他版本的专属是合法的，时间段槽不限制已存储的宝可梦。记录的种属是内部索引 (`gen9.national` 提供国家图鉴编号）。

字段的其余部分：

| 内容 | 键 |
|---|---|
| 主机的爆发 | 0x0029 类型 1，字段打开时每个爆发广播一次 |
| 主机自身的状态 | 0x0024 类型 1 和 0x002A 类型 3 至 5，几个小整数 |
| 成员的 id 查询 | 0x0025，仅成员到主机 |

两个游戏都在每个地图上提供一个遭遇表 (`world/data/encount/pokedata/pokedata*_array.bin`)，包含两个版本的行；字段 28 命名行所属的版本。

爆发消息是一个元组：中心（三个浮点数，来自 `world/data/encount/point_data/outbreak_point_data`），附近的第二个点，种属，0，形态，0，90 至 110 的计数，地图（0 帕尔迪亚，1 北上，2 蓝莓）和 0。

键 0x0025 是周期性成员到主机的查询：类型 1 列出 u64 id，类型 3 回答每个 `((id,), 标志)` 为 0 或 1，类型 2 列出成员放弃的 id。id 的顶部五位是类别；成员遍历类别 1、2、3、4、5、9、10、13 和 16 大约每九秒一次。

## Crafted encounters

`sv_join --spawn SPECIES:LEVEL` 以成员身份加入联合环，并在主持人的玩家周围生成三个由用户精心构造的宝可梦；使用 `--follow-host` 时，访客的玩家跟随主持人的玩家。`--spawn-*` 标志设置记录所携带的内容：形态、异色、太晶属性、性格、性别、能力槽位、体型、携带物和 IV 数值。若省略其中某项，则该项会像主持人的野生宝可梦那样随机生成：体型随机、性格随机、每个 IV 随机、能力槽位为 0 或 1、不携带物品。每个生成的宝可梦距离主持人的玩家 15 至 25 米。当主持人战斗（其 ask 被移交）、移除（一种以命名为 2 的方式）或走开超过 50 米时，该宝可梦会被放弃，并有另一个靠近主持人。

使用 `--spawn-legal` 时，PKHeX 决定合法性：辅助工具的 `wild_areas` 命令按位置列出朱／紫的野生插槽，`wild_legal` 对从每个插槽捕获的精心构造宝可梦运行 PKHeX 的合法性分析，每次按太晶属性检查一次。PKHeX 在任意位置接受的生成将停止运行。

然后这些生成等待主持人的区域（`wild.Locator`）。主持人主机分享的每只野生宝可梦（键 0x0026，类型 1，一旦访客的玩家靠近）缩小位置范围至包含该物种、形态和等级的插槽。一旦所有剩余的位置都被 PKHeX 接受，该区域即视为已找到；无需全部都被接受。随后生成出现，并且当主持人走开超过 50 米远离该区域被找到时的位置时，它们全部消失；查找重新开始。在此之前，查找也会在主持人距离其加权的生成超过 100 米时重新开始，以及从无法匹配任何剩余位置的生成开始。无法被任何野生插槽容纳的生成（如团体战的、活动的）将被排除。

在零号区域中，主持人主机不会发送其玩家的变身信息。若 2 秒内无变身信息，则主持人会被放置在其最近 30 秒内六个最新生成的中间；若没有生成，则不会出现新的宝可梦。距离变身起点 10 米以内的变身永远不会放置主持人。

该搜索以 id 为 `zone` 的 `[panel]` 状态卡片显示在应用程序中。
