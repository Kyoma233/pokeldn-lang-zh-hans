# 联合环

联合环是《朱／紫》中最多四名玩家共享场景的会话。其代码称它为队伍圈（`TeamCircle`），而蓝莓任务（BBQ）则是 `bbmission`。pokeldn 以访客身份加入一台主机的本地联合环，上报蓝莓任务完成，从而向房主支付 BP 并解锁 Snacksworth 的传说宝可梦，还会在房主玩家周围生成野生宝可梦（[旷野遭遇](#overworld-encounters)）。应用的两个联合环工具见[应用指南](gui.md#union-circle)。

下面的 Lua 是 Scarlet 4.0.0（`main.blua`，SHA-256 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`，[太晶团体战](sv_raid.md)所在的代码块）中的代码块 `be21e65463b9a98f`，除非另注明为 `main_dynamic`。`0.N` 表示该代码块主函数的第 N 个原型，从 0 起算。这些原型编号与公开的 3.0.1 反编译（Martmists-GH/SV-Script-RE）一致。尖括号中的名称来自其哈希列表；其他名称仍是哈希。

## 获取 Lua

该代码块是 `arc/data.trpfs` 中的 `script/lua/bin/release/main/main.blua`，以 Oodle 存储。4.0.0 更新版的虚拟 RomFS 需要基础游戏的对应部分：`arc/data.trpfd` 的一部分位于基础游戏中。

    ./.venv/bin/python tools/switch/nso_read.py main main.bin
    ./.venv/bin/python tools/switch/trpfs_read.py --update UPDATE.nsp --base BASE.nsp --keys prod.keys \
        --image main.bin --extract script/lua/bin/release/main/main.blua --out-dir OUT

`--image` 运行 `main` 的 `OodleLZ_Decompress`（`0xcc8750`）。该代码块是 Lua 5.4 字节码，含有 30,829 个顶层原型；`main_dynamic`（`script/lua/bin/release/main_dynamic/main_dynamic.blua`）保存事件脚本，提取方式相同。

## 蓝莓任务

任务进度在原生侧，位于 Lua 模块 `c5137FC87` 中。Lua 游戏事件通过 `C00099C1DFBF96B11.S110BDDB84DEB4379`（`0.7064`）向它报告，后者将（任务类型、两个值、计数）传给 `c5137FC87.f4246D9CA`；例如一次进化会报告类型 28，计数为 1。任务在联合环一侧则是第二个原生模块 `c4D400AC0`。

每个任务都有一个等级，即俱乐部数据（`arc/worlddataclubMissionDifficultyWeightAdvanced.bin.trpak`）中其 `MissionInfo` 行的 `mission_grade`：0 普通、1 奖励、2 团队。Snacksworth 把团队任务称为团体任务。完成事件会携带其任务的等级。

该包的 quest 表是一个包含 64 个 `MissionInfo` 结构体的 FlatBuffer：类别（1 战斗、2 场地、3 拍照）、`mission_type`、`mission_id`、目标、奖励 BP、重掷 BP（用于换掉任务）、解锁类型、等级、难度（0 初级到 2 高级）和权重。每条消息中任务的 id 都是其行的 `mission_type`；`mission_id` 用于区分同一类型的各行，这些行在等级、难度、目标或 BP 上有所不同。BBQ 列表通过这一对值（`0x29de0f4`）查找任务。第二个表 `MissionSettings` 在 `club_bbmission` 中按变体（宝可梦属性、生物群落、口味）给出某种类型的文本。任务表使用的类型如下：

BBQ 管理器创建时（`0.7062`）会把 getter 交给原生侧。`c16FE4B25` 获取玩家自己的场景（`f61488ABA`，存档中的 `currentFieldId`）和成员的场景（`f45B80F87`，对应站点索引的 110 值）。`c5137FC87` 获取玩家是否在场景中（`f01FF34BD`）以及两个俱乐部等级标志 `FSYS_CLUB_BBMISSION_LVUP_01` 和 `_02`。

|---|---|---|

| `c4D400AC0.fD7C6549F` / `f37737462` | 其他成员的完成 | 将每个完成显示为通知；除非是奖励完成，否则排队等待发放 BP |
| `c4D400AC0.fD961BFD2` / `f541C4B17` | 联合环的 BP 发放 | 将每笔发放排队等待计入 BP |

Lua 不做任何校验：成员的普通或团队完成会直接从第二个队列向房主支付，而奖励完成只会通过原生联合环模块放入第三个队列的发放来支付。

## 原生模块

以下地址位于 Scarlet 4.0.0 的 `main` 中。

原生模块和函数名是 `main` 的 rodata 中的普通字符串；每个模块在 `.data` 中都有一个 `luaL_Reg` 风格的 {名称, 函数} 对表：`c4D400AC0` 位于 `0x442e500`（22 个函数），`c5137FC87` 位于 `0x4420630`（45 个）。完成事件是 userdata（方法位于 `0x441dc50`）：`fBCA6AEB8` 返回 BP（s32 位于 `+0x10`），`f0C278E84` 返回等级（s8 位于 `+0xd`）。`0x29dd878` 根据任务行构建它：任务 id（u16 位于 `+0x0`）、`+0x4` 处的 u32、等级和 BP。

`c4D400AC0` 的函数作用于同一个联合环对象，这是一个在 `0x4739410` 处惰性构建的单例：

| 函数 | 作用 |
|---|---|
| `f5770F782` | 联合环是否就绪（`0xa0d038`） |
| `f48603105`、`fE8E53DDE` | 玩家是否在联合环中，以及玩家是否是房主（`0xa0e9ac`） |
| `fAC449469` | 将玩家的完成作为消息 3 发送（`0xa0db20`） |
| `f263D7D28` | 在房主上，将奖励完成作为消息 5 发送（`0xa0dcf4`） |
| `f07578A96` | 在房主上，将自身的奖励完成计入（`0xa0df34`，然后是发放推送 `0xa0e164`） |

联合环会在自己的通道（对象的 `+0x70`）上发送这些消息：游戏键 0x0048 在 0x80 端口 0，消息类型放在 kind 字节中。每条消息先是游戏 tagged 格式的完成事件（`0xb9`，18 个字段，由 `0xa17694` 读取），然后是发送者的消息序号（`+0xb8`）。消息 3 还携带发送者的 BBQ 状态记录（`0xa0f37c`，由 `0xa17170` 读取）。在 tagged 格式中，-64 到 127 的整数本身就是一字节，更宽的整数放在有符号标签（0x84 到 0x86）之后，浮点数放在 0x88 之后。

完成事件的字段：

| 字段 | 值 |
|---|---|
| 0 | 任务 id |
| 3、11 | 该任务所在槽位 |
| 4 | 等级 |
| 5 | BP |
| 6 | 发送者站点 id 组成的元组（u64，标签 0x83） |
| 7 | 任务的 `MissionInfo` 行 |
| 12、13 | 占用该槽位的任务及其行 |

其他字段为零或空行。在完成前十分之一秒，房主会发送 kind 2：任务、-1、-1、其进度（1.0）、其序号及其状态记录。

### BBQ 状态记录

每个玩家的 BBQ 管理器将其状态记录保存在自己的 `+0x40`；联合环会把它（`0xa0f37c`）写入消息 1、2 和 3。消息 1（kind 1）只包含发送者的消息序号和状态记录。玩家在联合环启动步骤 1 时发送一条，然后发送无正文的 kind 4（`480004`），再发送步骤 2，而房主在每个成员完成后会再发送一条。该记录是一个由 11 个元素组成的元组：

| 元素 | 记录偏移 | 值 |
|---|---|---|
| 0 | `+0x0` | 每条记录中都为 1：管理器在 `+0x40` 处的字节 |
| 1 到 3 | `+0x4`、`+0x50`、`+0x9c` | 玩家的三个任务槽位 |
| 4 | `+0xe8` | 一字节的字节串，每条记录中都为 1 |
| 5、6 | `+0xec`、`+0x138` | 两个额外槽位，在所见的每条记录中为空 |
| 7 | `+0x184` | 一个有符号字节，在每条记录中都与元素 9 相等 |
| 8 | `+0x185` | 玩家距离下一次发放的奖励完成数 |
| 9 | `+0x188` | 单人总次数（管理器的 `+0x1c8`） |
| 10 | `+0x18c` | 团队总次数（管理器的 `+0x1cc`） |

一个槽位（`0xa0fa18`）为 0x4c 字节，其中记录携带任务 id（u16，为空时为 0）、其进度（浮点数）、其文本变体（`MissionSettings` 变体，没有则为 0）以及该行的 `mission_id`。如果房主的第五个槽位指定了与成员自身不同的任务，该成员会采用房主的槽位（`0xa14290`）。

`circle.bbq_record` 读取结尾为消息 1、2 或 3 的记录。

零售主机上的房主槽位保存其任务类型的初级普通行（`mission_id` 0：20 BP，任务 1 的目标为 10 次打倒，其他任务为 1），进度为 0，直到有报告完成其中一个；额外槽位保持为空，奖励计数为 0。

### 成员在房主任务上的进度

成员通过消息 2（kind 2，0x80 端口 0）报告某个房主任务的进度来完成它：任务、两个值（没有变体的任务为 -1、-1）、计数、其消息序号以及自己的状态记录。房主先用自己的记录回复，显示该进度，然后发送自己的消息 3：将功劳记给该成员站点 id（字段 6）的完成、BP、槽位以及占用该槽位的任务。房主的单人总次数增加 1。

消息 2 携带 Lua 进度报告（`c5137FC87.f4246D9CA`）所传递的内容：任务、其两个值和计数。房主的接收处理程序将这四个值连同成员标志和发送者一起交给同一个原生进度分发器（`0x29dc838`），房主自己的报告也是到达这里（`0x29dc6b0`）。因此房主会把成员的进度当作自己的进度来计数，自行完成任务并完成它，这次完成与房主自己的完成一样计入其单人总次数。

`circle.progress_message` 构建消息 2。Snacksworth 运行（[加入](#joining)）会按最新记录所显示的三个房主槽位，依次向每一个槽位发送消息，计数为 500（普通行的最大目标），并把该槽位的变体作为第一个值，没有变体则为 -1；零售主机上的房主会完成每个槽位。

## 房主如何处理成员的完成

接收处理器（`0xa13b00`）通过位于 `0x3c5b7a4` 的跳转表按类型分发。对于消息 3，房主会：

1. 将该成员的 Bonus 计数存储到该成员在其 BBQ 状态中的槽位；
2. 在自己的 BBQ 列表中查找该任务（`0x29de0f4`，按任务 id 和 `+0x4` 处的 u32）。只有与自己的某个 Bonus 任务匹配时，这次完成才会计入房主自己的总数，而且只有这时房主才会为它排队一条自己的通知。除了第 4 步中的一个标志外，这个结果对下文没有任何决定作用；
3. 将这次完成作为成员通知排队（`fD7C6549F` 队列）；
4. 如果这次完成是 Bonus，就把事件的 `+0x7c` 设为 min(3，房主自己的 Bonus 计数加上三个成员槽位)，把事件的 `+0x80` 设为第 2 步是否匹配，把它作为消息 5 发送给每个成员，并通过 grant push 以该事件作为已接收来给自己记账；
5. 如果这次完成是 Team 完成且房主的 BBQ 管理器处于活动状态，就给房主的 Team 总数加 1（见下文）。

只有在这些之后，房主才会把消息的序列与成员的上一序列比较，而序列只会决定成员状态记录是否更新。

收到消息 5 的成员会通过同样的 grant push 计入该事件，除非其序列比上一次从房主那里看到的更旧。

房主会按照成员消息指定的内容进行结算：没有任何地方检查 `+0x10` 处的 BP 或任务是否存在。Normal 或 Team 完成由 Lua 立即结算。Bonus 完成经过 grant push，这是唯一的排序机制。它会先暂存每个事件，并且只有在其 `+0x7c` 比上一个已释放事件的大 1、小 2，或两者都为 0 时，才把它释放到 grant 队列（对象的 `+0x108`）。这个值由槽位构建，因此成员下一次 Bonus 完成必须报告比上一次多 1 的计数。

## 史纳克斯沃斯

BBQ 管理器会维护两个运行总数，分别由 `c5137FC87.f6ED7C9B6`（`+0x1c8`）和 `fECB0EBF0`（`+0x1cc`）读取：

| 总数 | 增加条件 | 也被读取者 |
|---|---|---|
| solo，`+0x1c8` | 玩家自己的 Normal 或 Bonus 完成（`0x29dda40`） | 社团的 BBQ 升级事件，在 15 和 45 时 |
| Team，`+0x1cc` | 玩家自己的 Team 完成，以及房主在消息 3 中收到每个成员的 Team 完成（`0xa14918`） | |

Snacksworth 是事件 `s2_sub_012`，他的 25 只传说宝可梦是事件 `s2_sub_013` 到 `s2_sub_037`，每个事件的状态都在 `WEVT_S2_SUB_0NN_STATE` 中。`main_dynamic` 中该事件的类（原型 `0.1995` 到 `0.2032`）通过 `0.2019` 读取 solo 总数，通过 `0.2020` 读取 Team 总数。当玩家与他交谈时，一旦 solo 总数减去每只已在 solo 路线上释放的传说宝可梦对应的 `missionReleaseCount` 后达到 `missionReleaseCount`，`0.2002` 就会释放下一只 solo 路线传说宝可梦；`0.2003` 对 Team 路线使用 Team 总数和 `teamMissionReleaseCount` 执行相同逻辑。两个计数都来自事件的配置表（`s2_sub_012.ReleaseConfigTable`，位于 `arc/worlddataeventcommandcommand_data_rootcommand_data_root.bin.trpak`）。该包中唯一具有这种形状的表保存的是 10 和 1。

同一包中的 `s2_sub_012.ReleasePokeTable` 把每只传说宝可梦放到四条路线中的两条上，两条 solo（`MissionA`、`MissionB`）和两条 Team（`TeamMissionA`、`TeamMissionB`）：

| 出现路线 | 传说宝可梦 |
|---|---|
| 两条 solo 路线 | 急冻鸟、闪电鸟、火焰鸟、熊徒弟 |
| 两条 Team 路线 | 烈空坐、酋雷姆、奈克洛兹玛 |
| 各一条 | 其余 18 只 |

脚本会询问 `CA4C5F9FA83D2AF80.SDF0C255E6E08D740` 玩家处于哪对路线，是 A 路线还是 B 路线；朱在 A 路线（一次 Team 完成释放了捷克罗姆，它只在 `TeamMissionA` 上）。每对路线会把 25 只传说宝可梦分开，没有任何共享：solo 路线上 13 只，Team 路线上 12 只。一次交谈最多释放一个零食，并会先尝试 Team 路线。每条路线会在其尚未释放的传说宝可梦中随机选择（`0.2007`）。某条路线的下一次释放需要其总数达到其计数乘以该路线上已释放的传说宝可梦数量加一。因此全部 25 只需要 solo 总数为 130、Team 总数为 12，以及 25 次交谈。

没有任何消息会指明某个零食：脚本会比较房主自己的总数与配置。每条携带 Team 完成的消息 3 都会给房主的 Team 总数加 1，不会检查该任务是否是房主拥有的 Team 任务，也不会针对重复进行序列检查；由于 `teamMissionReleaseCount` 为 1，所以每条消息就是 Team 路线的一个零食。房主的任务每被成员完成一个（[成员在房主任务上的进度](#a-members-progress-on-the-hosts-quests)），就会给其 solo 总数加 1，这会给 solo 路线上的 13 只提供来源。

## 加入

`bin/sv_join.py --union-circle` 会以团体战嘉宾加入团体战的方式加入由主机开设的联合环（`pokeldn.sv.circle`）。它会占住座位、发送自己的身份记录、在 0x7C 端口 1 上镜像房主的频道表，并按 `--hold` 保持座位，默认保持整个 `--seconds`。它不发送任何大厅消息，当主机离开时也不会接替房主角色。当房主的场地开放时，它会让自己的玩家出现在场地上（`circle.Member`，[场地](#the-field)）。它会打印用户可以跟随的内容；`--verbose-circle` 会额外打印它发送的每条联合环消息和区域搜索的每一步，而 `--capture` 文件无论如何都会保留这些内容。

    ./.venv/bin/python bin/sv_join.py --union-circle --code 3707 --hold 540 --capture circle.jsonl

零售版朱 4.0.0 在通过 Link Code 开设联合环时，会广播 scene 5、最多四名参加者，以及交换应用数据：密码和游戏字节中包含该代码，其长度在 +0x24。游戏字节在 +0x21 还保存着 `aa 08 3e`，正在搜索的主机会将其留为零。

它让嘉宾入座的方式与连接交换或太晶团体战房主相同：加入响应、站点列表、频道表（键 0x007B、0x0132、0x0232 和 0x0332）、两个流打开、时钟应答及其身份记录。然后嘉宾会一直等待，直到房主的玩家开始联合环。

## 开始联合环

开始时，房主会发送 Net 0x50，其中包含统计成员数量的广播、0x80 端口 2 上的 type-7 公告（以及接受每个成员的 type 9），以及 0x80 端口 0 上的联合环消息。

联合环消息是 Lua 的网络消息。每条都是键 0x0132 下的游戏消息（处理器键、种类、步骤，然后是序列化器头；[太晶团体战](sv_raid.md#the-lobby)），其种类就是 Lua 消息 id。团体战的“loading”和“loaded”（0x0132，种类 0x6E 和 0x73）是同一接收器的消息 110 和 115。有些负载是 FlatBuffer 表，其他是固定结构；104 和 106 使用 LZ4 压缩（序列化器压缩 2）。

| 消息 | 来源 | 负载 | 由 `TeamCircleUI` 处理 |
|---|---|---|---|
| 100 | 房主，开始时 | 包含一个 u32 的表，始终为 12345678 | 开始音效；嘉宾的开始标志 |
| 101 | 每个站点，房主在其 100 后立即发送，成员在收到房主的 100 后发送 | 32 字节：站点所站的位置（场地 id、三个宝可梦中心标志） | 每个站点 |
| 103 | 每个站点 | 包含一个 u32 的表，即同步点 id | 1 和 2 传给 UI（开始演示已加载、已结束），其他所有 id 传给同步对象 |
| 111 | 房主 | 5916 字节：四个零字节，然后是包含两个表向量的 FlatBuffer（30 和 10） | 仅一个标志；内容由原生代码读取 |
| 104 | 房主 | 一个表：游戏时间、真实时间及其经过秒数（浮点数）、天气种子（u64）、抽签的长度以及当前和下一次天气的 {类型，持续时间} 对 | 时钟和天气，输入游戏时间管理器和 `WeatherManager.Sync` |
| 102 | 房主 | 两个 u32：成员传送到的飞行点 | 传送 |
| 106 | 每个站点 | 300 个六字节槽位，即其太晶团体战结晶；`ffffffff0000` 表示空槽位 | 每个站点 |

房主会按表格顺序发送它们，并在其 101 之后、开始后两秒内发送三条键 0x0048 消息。

每个站点都会到达同步点 2215，等待每个站点的 101，发送自己的 106，并等待其他每个站点的 106（`IsGemInfo`）；开始演示中 id 为 1 和 2 的 103 也以同样方式等待。当每个成员都发送了带有其 id 的 103 后，同步点即视为达到（`CEEE8D2836ABEDE23`）。

零售主机会把超过 1395 字节的消息拆分为片段，并让未拆分的较长消息不被确认，因此 106 会使用 LZ4 压缩，房主自己的 106 也是这样。

一旦所有 106 都收到，房主会传送到其 102 的飞行点，并发送 115 (1, 0)。

## 场地

房主的玩家随后进入场地。它会用 0x7C 端口 1 向每个成员发送更新，其中打开 14 个更多频道密钥（低字节 0x1E 到 0x2A，其中一些带子频道 0 和 1），并经 zlib 压缩。零售版成员以同样方式发送相同的更新回来。房主发送无正文的密钥 0x0024 类型 1 步骤 1，之后不断发送其玩家：

| 内容 | 方式 |
|---|---|
| 动画状态 | 可靠传输，0x80 端口 0，密钥 0x001E 类型 5，状态名（`Top/pc_field/move/defaultwait01`），每 3 到 7 秒 |
| 变换 | 不可靠协议 0x68（像 0x80 一样以网状寻址），密钥 0x011E 类型 4，38 字节浮点数，约每秒 20 次；类型 6 和 7 各一次 |

在构建开场演示之前，房主会等待（`F9FFADFE613D572B7`），直到其他各个站点的玩家对象都存在于其场地上。不发送玩家的成员会让它停留在黑屏“通信中”画面。房主通过原生模块 `c2A8846F6` 将成员生成为 `playables.Player` 对象（其 `f6BD530B6` 就在等待之前运行）。

玩家对象在场地密钥之后通过 0x7C 端口 0 在成员与房主之间传输：

| 密钥 | 消息 | 内容 |
|---|---|---|
| 0x001F | id (u16)、type (u16) | 一台主机声明自己的一个对象 |
| 0x001E | 类型 0、0、id (u16) | 一台主机请求对方声明过的某个对象 |
| 0x001E | 类型 1、2 或 3、0、id (u16)、状态 | 应答：对象的状态，其类型 1、2 或 3 由对象在声明中的位置决定 |

每台主机声明四个对象（类型 0、1 或 2、3 和 10），ID 从站点索引开始按 4 递增。一台主机请求对方声明的每个对象；没有人应答对类型 10 对象的请求。状态为 70 字节（类型 2）或 214 字节（类型 1 和 3），经 zlib 压缩：句柄、体型值、旋转、位置；类型 1 是玩家并携带 FlatBuffer。房主在成员的类型 1 应答后半秒开始其演示。

然后，成员用密钥 0x0025 向房主询问 u64 ID 列表，房主用标志来应答每个列表（[野外遭遇](#overworld-encounters)）。

密钥 0x0048 是蓝乐活模块（[原生模块](#native-modules)）的，位于房主的第一个频道表中。在其端口 2 通知前后，房主发送类型 1 步骤 1、一个无实体的类型 4（`480004`）和类型 1 步骤 2，两个步骤都携带其状态记录（[蓝乐活状态记录](#the-bbq-status-record)）。

`circle.Member` 会执行以下操作：
- 它用房主自己的 101 的副本来应答房主的 100，这样访客的玩家就会站在房主玩家所在的位置。
- 它会回显房主发送的每个 103。
- 它用 300 个空槽位来应答房主的 106，经 LZ4 压缩：一个没有晶体的世界。
- 它把房主发送的每个 110 和 115 的副本作为自己的发送，跟随房主的场地。
- 一旦 `sv_join` 发回场地密钥，它就声明站点 1 的四个对象并请求房主的每个对象。它用访客 ID 下房主自己同类型对象的状态来应答房主的每个请求，这样访客的玩家就站在房主玩家所在的位置。

使用 `--follow-host` 时，访客的玩家也会跟随房主的玩家移动：0x68 上的每一帧房主数据以及密钥 0x001E 上的对象消息都会在访客对应对象下发出，使用访客自己的 60 Hz 时钟，延迟 0.3 秒重放房主（房主的变换大约每秒到达 27 次）。访客与房主保持 5 米以内，面向房主，并按自己的速度缩放房主的移动混合。

使用 `--circle-task` 时，任务完成后访客的玩家会离开联合环，该次运行结束：
- `snacksworth` 从房主的第一个状态记录中读取其单人和团队总数。从开场演示结束（其 id 为 2 的 103）起，它每秒发送团队通关，补足其团队总数还缺少的 12 个，然后报告完成房主的任务，直到其单人总数达到 130（[成员在房主任务上的进度](#a-members-progress-on-the-hosts-quests)），然后在其团队总数仍缺任何数量时再发送一个团队通关（[Snacksworth](#snacksworth)）。每个团队通关都是按游戏抽取团队任务的方式抽取一个团队任务（`circle.TEAM_QUESTS`，每个任务和 BP 都按其概率），并支付该任务的 BP。它随着房主总数的增长打印进度，并在连续 20 次发送总数都没有增长时停止。
- `bp` 在开场演示结束一秒钟后发送一个 29 号任务的普通通关，支付 `--bbq-clear` BP，范围为 1 到 9,999,999。

每次通关都是消息 3，带其 BP、访客的站点 ID 和访客的状态记录。

零售版房主无需访客先发送消息 1 就会支付每次这样的通关；一旦其玩家关闭 BP 侧栏，通知和 BP 就会显示。一次任何任务的团队通关，都会释放下一只团队路线传说的宝可梦（[Snacksworth](#snacksworth)），无论房主在蓝莓学园内还是外。

## 野外遭遇

联合环中的每台主机都会从自己的游戏版本中在自己的玩家周围生成野生宝可梦，并把每只广播给其他主机，因此成员可以捕获另一版本的独占宝可梦（《朱》房主在第零区生成 dev id 982，《紫》成员生成 992）。不会交换版本，房主也没有特殊作用。

共享的宝可梦通过 0x80 端口 0 和不可靠协议传输，由其所有者广播；只有对某只的请求及其拒绝会发送给单个站点，通过 0x7c 端口 0：

| 密钥 | 消息 | 内容 |
|---|---|---|
| 0x0026 | 类型 1，其 96 字节记录作为字节串 | 所有者生成的实体（站点，n） |
| 0x0026 | 类型 2，(站点，n) | 该实体已消失 |
| 0x0026 | 类型 5，((站点，n)，(站点，n)) | 一台主机请求所有者把该实体交给它进行战斗，使用请求者自己的 ID；通过 0x7c 端口 0 仅发送给所有者 |
| 0x0026 | 类型 6，同样的一对 | 所有者拒绝；返回给请求者 |
| 0x0026 | 类型 7，同样的一对 | 该实体现在属于第二个 ID 的站点，该站点与它战斗；有一个在该实体的类型 2 前 15 秒到来 |
| 0x0126 | 类型 3，(站点，n)，(一个浮点数、0.0、0.0、0、0 或 1) | 该实体的状态，每 0.2 秒（成员）到 0.5 秒（房主）；最后一个元素是其状态 |
| 0x011E | 0x68 上的类型 4，按对象 ID | 该实体的变换，和玩家的变换一样 |

实体的对象 ID 是站点 + 4n，这个 u16 会打开其记录。主机只与玩家站在自己玩家附近的成员共享其实体。每个 ID 都是一对无符号整数（调度器 `0x1dbd4b0` 不读取有符号标记）。

主机把另一台主机的实体记录为未安定（状态 1），并拒绝与它战斗（`BattleStartWait`），直到某个状态指明状态 0。走进一个已安定的实体时，它会显示“！”并请求所有者（`0x1972664`）：它为实体取一个新的自己的 ID，存储这对 ID 和一个回调，然后它的管理器更新（`0x1593884`）向发送该实体记录的主机发送类型 5。遭遇（`GameEventEncount`、NetInitWait）随后无超时地等待所有者的应答，应答中要指明同样的一对（`0x1dbdd70`）。当该实体是所有者自己的且没有其他主机持有它时，所有者将其移交（`0x1dbdc20`，然后是 `0x15934c8` 处的更新广播），否则拒绝（`0x1593914`）。移交时，每台主机都会将该实体重命名为请求者的 ID（`0x1595a1c`）并标记为已交战；请求者将其归档为自己的并开始战斗。当一台主机与自己的实体战斗时，它会广播类型 7，并将同样的一对连续发送两次。

记录为 96 字节。`EncountManager.UpdateNetworkSpawn` 通过 Lua 模块 `c4CF1D719` 绑定的 getter（原生 `0x90e344` 到 `0x90e588`）将其字段复制到 `pml.pokepara.InitialSpec` 中，然后在宝可梦本身上设置奖章、太晶属性和霜奶仙的装饰。捕获的每条记录都符合此布局：

| 偏移 | 位 | 字段 |
|---|---|---|
| 0x00 | u16 | 对象 ID |
| 0x04 | u64 位 0-10 | dev 物种 |
| | 11-22 | 持有物 |
| | 23-30 | 体型值 |
| | 31 | 性别（1 为雌性） |
| | 32 | 异色；设置时生成物为异色 |
| | 33-37 | 形态 |
| | 38-44 | 等级 |
| | 45-52 | 奖章（证章），非 0 时应用 |
| | 53-57 | 性格 |
| | 58-62 | 太晶属性 |
| 0x0C | u32 位 0-3 | 霜奶仙装饰 |
| | 8-27 | 个体值 HP、攻击、防御、速度，各 5 位 |
| 0x10 | u16 位 0-9 | 个体值特攻、特防 |
| | 10-11 | 特性槽 |
| 0x24 | s32 | -1；在仅见过的百变怪和索罗亚中为 0 |
| 0x30 | 3 个浮点数 | 位置 |
| 0x40 | 4 个浮点数 | 旋转，所有样本中均为恒等 |

其他字节为 0（零售版记录在 0x02、0x28 和 0x54 处残留有旧内存）。在发送记录之前，所有者会在 0x68 上发送实体的帧：类型 6 无父级（`00000000 00000000 0000003f 0000003f 00000000 0000003f 0000003f`）和类型 7，体型值为 1.0。`circle.Spawner` 以同样方式发送访客自己的生成物（[定制遭遇](#crafted-encounters)）。

`UpdateNetworkSpawn` 仅从记录构建宝可梦；异色位将稀有度字（`+0x18`）设为 `0x2ffffffff` 或 `0x1ffffffff`，因此由所有者作出决定。记录不包含招式、PID 或加密常数；捕获时会加入捕获者的训练家、球、地点、日期和等级。

游戏接受任何记录；PKHeX（Core 26.8.26）会将该捕获判定为在捕获地点发生的野外遭遇：

| 字段 | PKHeX 接受条件 |
|---|---|
| 物种、形态、等级 | 捕获地点存在《朱／紫》的野外槽位，物种和形态一致，且等级范围包含该等级；像烈空坐这样锁异色或仅定点出现的物种永远不会 |
| 太晶属性 | 该物种自身拥有的一种属性，除非配信大量出现覆盖了该地点的该物种 |
| 性别 | 符合该物种的性别比例 |
| 证章 | 不是最强之证或宝主之证；大个子之证仅在体型值为 255 时，小不点之证仅在体型值为 0 时；天气证章仅在槽位指定该天气的地方 |
| 异色、性格、个体值、特性槽（也包括隐藏特性）、体型值、持有物 | 任意 |

PKHeX 把《朱／紫》的每个野外槽位都列在两个版本之下，因此另一版本的独占宝可梦是合法的，时段槽位不会限制已存储的宝可梦。记录中的物种是内部索引（`gen9.national` 给出全国图鉴编号）。

场地的其余部分：

| 内容 | 密钥 |
|---|---|
| 房主的大量出现 | 0x0029 类型 1，场地打开时每个大量出现广播一次 |
| 房主自己的状态 | 0x0024 类型 1 和 0x002A 类型 3 到 5，几个小整数 |
| 成员的 ID 查询 | 0x0025，仅成员到房主 |

两款游戏每个地图都附带一张遭遇表（`world/data/encount/pokedata/pokedata*_array.bin`），其中含两个版本的行；字段 28 指定某行会在哪些版本中抽出。

大量出现消息是一个元组：中心点（三个浮点数，来自 `world/data/encount/point_data/outbreak_point_data`）、其附近的第二个点、物种、0、形态、0、90 到 110 的数量、地图（0 帕底亚、1 北上、2 蓝莓）和 0。

密钥 0x0025 是周期性的成员到房主查询：类型 1 列出 u64 ID，类型 3 用 0 或 1 应答每个 `((id,), flag)`，类型 2 列出成员放开的 ID。ID 的高五位是类别；成员大约每九秒遍历类别 1、2、3、4、5、9、10、13 和 16。

## 定制遭遇

`sv_join --spawn SPECIES:LEVEL` 以成员身份加入联合环，并在房主玩家周围维持三只由用户定制生成的宝可梦；使用 `--follow-host` 时，访客玩家会跟随房主玩家。

`--spawn-*` 标志设置记录包含的内容：形态、异色、太晶属性、性格、性别、特性槽位、尺寸、携带物品和个体值。未设置的项会按房主自己的野生宝可梦那样抽取：尺寸、性格和各项个体值随机，特性槽位为 0 或 1，无携带物品。每只生成宝可梦出现在房主玩家 15 到 25 米处。当房主与某只对战（its ask，handed over）、将其移除（用 kind 2 命名它）或离开它超过 50 米时，该只被放走，另一只会来到房主附近。

使用 `--spawn-legal` 时，由 PKHeX 判定：辅助工具的 `wild_areas` 命令按位置列出朱／紫的野生槽位，`wild_legal` 对从每个槽位捕获的定制生成宝可梦运行 PKHeX 的合法性分析，每个太晶属性一次。若某只生成宝可梦在任何位置都不被 PKHeX 接受，运行便会停止。

这些生成宝可梦随后等待房主的区域（`wild.Locator`）。房主主机共享的每只野生宝可梦（key 0x0026 kind 1，访客玩家靠近后）会将候选位置缩小到那些具有与其物种、形态和等级相匹配的槽位的位置。当剩余每个位置都是 PKHeX 接受该生成宝可梦的位置时，区域即算找到；位置无需是单个。之后生成宝可梦会出现；当房主从找到区域时所站的位置走开超过 50 米时，它们会全部消失，寻找会重新开始。在那之前，当房主距离它权衡过的生成宝可梦，或距离没有任何剩余位置能容纳的生成宝可梦超过 100 米时，寻找也会重新开始。没有野生槽位能容纳的生成宝可梦（团体战的、活动的）会被略过。

在第零区，房主的主机不会发送其玩家的 transform。如果 2 秒内没有 transform，房主会被放置在过去 30 秒内其六个最新生成宝可梦的中间位置；若一个都没有，则不会有新的生成宝可梦出现。距离原点 10 米以内的 transform 永远不会放置房主。

搜索会在应用中显示为 id 为 `zone` 的 `[panel]` 状态卡片。
