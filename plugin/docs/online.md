# 在线交换

一次在线交换连接两名远隔的玩家：每个板载设备上运行一场本地交换，两款应用通过公共 Nostr 中继传递各自提供的宝可梦，而中继只会看到加密后的事件。代码：`pokeldn/online/`；启动器标志 `--online` 和 `--online-code`。

## 房间

当两款应用运行相同的游戏且使用相同的代码时，它们会相遇：

    room = sha256("pokeldn online 1|<game>|<code or 'open'>")     64 个十六进制数字

配对版本共享一个游戏键（`frlg`、`sv`）。代码是游戏拥有链接码时的控制台自己的链接码。一张桌子上的两个控制台直接找到彼此；要在一张桌子上测试，请为每个控制台分配自己的本地码，并使用 `--online-code` 将两个板载设备放入同一房间。

## 中继

每个事件都是 NIP-01 的临时类型 21059 事件，带有标签 `["t", <room>]`，以及对于其中一款应用，`["p", <its signing key>]`。每款应用订阅从其开始前 10 秒开始的类型 21059 事件，使用房间的标签，发布到所有中继并丢弃重复的事件 ID。每个会话使用新的 secp256k1 密钥签名（BIP-340，`pokeldn/online/schnorr.py`）。

| 中继 | 8 个事件，每个 2 秒一个 |
|---|---|
| relay.primal.net, relay.snort.social, offchain.pub, relay.nostr.net, nostr.oxtr.dev, nostr-pub.wellorder.net | 8 个已送达；默认集合 |
| relay.damus.io | 4 个已送达，然后封禁该地址一段时间 |
| nos.lol, nostr.mom | 无（速率受限） |
| nostr.wine | 拒绝（付费） |

`POKELDN_RELAYS`（逗号分隔的 URL）替换默认集合。offchain.pub 拒绝来自未知密钥的突发请求，并接受节流的事件。两款应用在第二个到达后 0.4 秒配对；一条 344 字节的记录大约需要 0.15 秒穿过。

### 存储的事件

在 relay.primal.net、relay.nostr.net、nostr.oxtr.dev、nos.lol、nostr.mom、offchain.pub 和 nostr-pub.wellorder.net 上测试：

| 事件 | 结果 |
|---|---|
| 来自新密钥 | 接受并返回 |
| 带有 NIP-40 `expiration` 的 30402 | 在过期前提供，之后不再 |
| 带有相同 `d` 重新发布的 30402 | 一分钟内只提供更新的那个 |
| 命名 30402 的类型 5 | 一分钟内只提供类型 5 |
| 仅通过 `a` 地址命名被替换的 30402 的类型 5 | 被五个丢弃；nostr.oxtr.dev 和 nostr-pub.wellorder.net 保留它，直到类型 5 命名其自身的 ID |
| 无 `expiration` 的 30402、类型 5 和类型 1059 | 17 天后仍全部提供 |
| 命名类型 1059 的类型 5 | 被所有提供 1059 的六个丢弃 |
| 通过 `p` 键读取类型 1059 | 被六个提供；relay.nostr.net 要求 AUTH 并拒绝 |

## 相遇

每个事件的内容是 AES-256-GCM 加密的，密钥为 `sha256("pokeldn room key|" + room)`。

| 消息 | 发送 | 内容 |
|---|---|---|
| `here` | 每 2.5 秒发送到房间 | 协议 1，X25519 密钥，训练家名称，应用版本，忙碌状态 |
| `invite` | 发送给一款应用 | 训练家名称 |
| `yes` / `no` | 回答 | 训练家名称 |
| `bye` | 发送给非伙伴 | 原因 |

一款应用只邀请最长时间空闲且签名密钥大于自身的应用，一次邀请一次，最多 6 秒，同时拒绝其他邀请。被拒绝或未回应的邀请会跳过该应用 10 秒。伙伴的第一条频道消息计为其 `yes`。

## 频道

伙伴之间的消息在房间密钥层之内携带发送者的 X25519 密钥，以及内层 AES-GCM 加密的内容：

    sha256("pokeldn pair|" + room + "|" + sorted("<signing key>:<x25519 key>" of both) + shared secret)

每条消息携带 `s`（其编号）和 `a`（按顺序收到的最高编号）。未确认的消息每 2 秒重发一次；确认在抵达后 0.3 秒发送；心跳每 4 秒一次。静默 45 秒的伙伴被视为丢失，并在尚未提供任何内容时被替换。

| 消息 | 意义 |
|---|---|
| `hello` | 训练家名称和应用版本，一次性 |
| `offer` / `withdraw` | 交易 *r*：本地控制台提供此记录（base64），或撤回 |
| `accept` / `unaccept` | 交易 *r*：本地控制台确认，或撤回 |
| `refused` | 交易 *r*：接收方拒绝发送方的记录，并说明原因 |
| `done` | 交易 *r*完成；下一个是 *r* + 1 |
| `ping`, `bye` | 保持连接；离开 |

## 传输内容

仅传输提供的记录和交易的状态。在控制台看到记录之前，PKHeX 会对其进行检查（`pokeldn.online.session.checker`）：

| PKHeX 发现 | 记录 |
|---|---|
| 不可解析、校验和错误、游戏中缺少的物种或形态、超出游戏表格的 ID | 拒绝，并向发送方显示原因 |
| 未发布的物品或技能（剑的物品以 1607 为止） | 拒绝 |
| 其他任何非法标志 | 提供，向接收方显示标志 |

## 在启动器中

带有 `--online` 的主机启动器提供伙伴控制台的记录。本地控制台的提供以 `offer` 发出；伙伴的记录提供给本地控制台；启动器仅在两个控制台都确认后才确认；`done` 开始从箱子中启动下一个交易。

| 标题 | 启动器的提供 | 控制台撤回其提供 | 启动器撤回其提供 | 启动器的确认 |
|---|---|---|---|---|
| 火红 / 叶绿 | 伙伴的队伍块（200 字节×3，邮件 220，斩纹 40），每个块在控制台自己的抵达时发送；带有伙伴光标的 `SET_MONS_TO_TRADE` | `READY_CANCEL_TRADE`（回答 `PLAYER_CANCEL_TRADE`），`REQUEST_CANCEL` | `PLAYER_CANCEL_TRADE` | `START_TRADE` |
| 去吧！皮卡丘／去吧！伊布 | 带有伙伴 232 字节记录的类型 2，回答控制台的步骤 | 撤回的投票（状态 2），离开（状态 4） | 无 | 提供的副本上的 2，尾随字移动到 2 |
| 剑 / 盾 | 带有箱子命令 1 的 20030；0x84 快照的队伍槽保留控制台自己的宝可梦 | 箱子命令 2（提供），5（确认） | 箱子命令 2 | 箱子命令 4 |
| 晶灿钻石 / 明亮珍珠 | 0x13 回答控制台的 | 0x45 `{1}` | 0x45 `{1}` | 0x21 `{0, 2}`；安全阶段保持自动 |
| 传说 阿尔宙斯 | 在计数器之下回答控制台的选择器 4；选择器 2 的显示一旦知道伙伴的记录即回答 | 选择器 6 | 无 | 控制台选择器 5 的镜像 |
| 朱 / 紫 | 带有伙伴 348 字节主体的类型 2 | 类型 4 `8000040100` | 类型 4 | 类型 3 |
| 传说 Z-A | 伙伴选择的预览，然后 0.5 秒后选择 | `0103` | `0103` 在下一轮下 | `0102`，然后 `0104` |

火红和叶绿交换整个队伍。每位主机在伙伴的控制台发送相同的配对之前，都保留自己的块；控制台在没有计时器的情况下等待 [trade.c:1478]。只有当 PKHeX 读取块中的每一个宝可梦时，该块才会到达控制台。在记录之前，光标以 `pick` 的形式传递。

离开或在 45 秒内静默的伙伴计为撤回，除非交易已过了不可撤销的点。一只火红或叶绿的控制台，其伙伴离开后会收到 `PLAYER_CANCEL_TRADE` 用于每个选择 [trade.c:1712]；未完成的队伍交换以空队伍结束。在剑上，交换的记录是内容 50 的 ([剑的交易](swsh_trade.md))。

## GTS

GTS 在从不同时在线的玩家之间交易银行中的宝可梦：一位玩家从 [银行](gui.md#the-bank)中列出一个宝可梦，要求最多三个想要的物种、一个等级范围，以及可选的异色；另一位玩家用自己的宝可梦回应，列出人的应用在下次打开时进行交易。代码：`pokeldn/online/gts.py`，`pokeldn/app/gts.py`，应用的 GTS 页面。

| 事件 | 类型 | 签名者 | 内容 |
|---|---|---|---|
| 列表 | 30402（NIP-99），`d` 为随机 ID | 每列表一个密钥 | JSON：协议 1，游戏，宝可梦如 PKHeX 读取的，记录的 SHA-256，`wants` 和 `also`（如下），训练家名称，状态，获胜报价 |
| 报价 | 1059，`p` 为列表密钥 | 每报价一个密钥 | 密封：列表的 `d`，游戏，记录，训练家名称 |
| 回答 | 1059，`p` 为报价密钥 | 列表密钥 | 密封：报价 ID 和被列出的记录，或拒绝及原因 |
| 删除 | 5（NIP-09） | 被命名事件的密钥 | 无 |

列表带有标签 `pokeldn-gts`、`pokeldn-gts-has-<species>` 和 `pokeldn-gts-wants-<species>` 用于每个想要的物种，携带 NIP-99 的 `title`、`summary`、`status`、`published_at`，并在 30 天后过期（NIP-40）。密封的内容是 AES-256-GCM 加密的，密钥为 `sha256("pokeldn gts|" + x)`，x 为 ECDH x 坐标（`schnorr.shared_x`）。每个存储事件的 ID 和签名都会被检查。

一个想要是 `{"species", "name", "min_level", "max_level"}`，当只接受异色时额外包含 `"shiny": true`。`wants` 保存第一个；`also` 仅在多于一个时存在，最多保存另外两个，任何一个匹配的报价都会回应。两个字段都是对协议 1 的扩展：来自 0.40.0 或更早版本的应用会忽略它们，将列表显示为仅询问第一个想要物种，发送的报价若不符合异色要求会被列出人的应用拒绝并返回。

| 步骤 | 发生什么 |
|---|---|
| 存款 | 宝可梦必须合法；它离开银行并发布列表 |
| 报价 | 合法且匹配一个想要物种、等级和异色要求；它离开银行，密封给列表密钥；一款应用为每个列表保存一个等待的报价，保持向其他玩家的报价开放，直到列出人的应用回应；页面用时钟标记它 |
| 列出人的应用打开 | 存储的报价按时间顺序回应；第一个有效的被交易，其余被拒绝 |
| 交易 | 回答携带被列出的记录；列表被重新发布为已交易；收到的记录被存入银行 |
| 报价人的应用打开 | 记录与列表的 SHA-256 进行检查并存入银行；拒绝、失去竞赛或撤回的列表返回自己的宝可梦；它删除自己的报价 |
| 列表结束 | 30 天后宝可梳返回；报价的返回一次在中继发送完所有存储的回答后一个小时 |
| 被删除 | 重新发布为已撤回；宝可梳返回；之后的报价被拒绝 |

每个列表和报价都是 `Documents/pokeldn/GTS`（当设置 `POKELDN_DATA/GTS` 时）中的一个文件夹，包含 `state.json`（密钥、已签名事件、已发送回答）和记录。回答在发布前写入，并且每个活跃的事件都会重新发送到每个连接的中继。完成的文件夹在 60 天后删除。一轮大约需要 30 秒。

中继是 [存储的事件](#stored-events) 中的；`POKELDN_GTS_RELAYS` 替换它们。修改后的应用可能会保留提供的宝可梦或列出不拥有的宝可梳；SHA-256 只会在之后显示出来。没有受信任的第三方的公平交换是不可能的（Pagnia 和 Gaertner，1999）。

## 未解决

- 中继在 24 小时后或没有过期时间的事件保留多长时间。
- 控制台如何回应主机撤回其提供的同时还持有它：剑的箱子命令 2（主机剑在确认屏幕上开始 4 秒后离开命令 1 然后 2），朱的类型 4，Z-A 的 `0103`，晶灿钻石的 0x45 在控制台的选择之后。去吧！皮卡丘／去吧！伊布 和传说 阿尔宙斯 保持。
- Z-A 是否接受没有预览的选择，以及传说 阿尔宙斯 是否接受第二个选择器 4。
- 零售控制台在箱子上等待伙伴多长时间，超过一分钟。
