# 神秘礼物菜单的本地无线分支

剑盾版的神秘礼物菜单通过本地无线接收神秘卡片：一个分发器广告宣传一个 LDN 网络，其广告数据以片段形式携带卡片。地址为盾 1.3.2 的 `main`，除非标记为剑；空中行为与零售主机进行比较。

## 菜单

接收方式选择器 `StateSelectReceiveDataBase` 有一个子类对应每个菜单按钮 (`L_mystery_top_btn_00` .. `_04`)：

| 状态 | 方式 |
|---|---|
| `StateSelectReceiveDataInternet` | 通过网络 |
| `StateSelectReceiveDataSerial` | 串行码或密码 |
| `StateReceiveDataLocal` | 本地无线 |
| `StateReceiveDataFromBall` | 精灵球 Plus |
| `StateReceiveDataRankMatch` | 排位对战奖励 |

接收状态包括 `StateReceiveBase`、`StateReceiveInternet`、`StateReceiveSerial`、`StateReceiveLocal` (`0x01004938`，其自身代码仅引用其进度条布局)、`StateReceiveFromBall`、`StateReceiveRankMatch`、`StateReceiveNews` 和 `StateReceiveComplete`。播放记录键 `fushigi_net`、`fushigi_serial` 和 `fushigi_p2p` 分别统计每个通道的接收次数，以及 `yy_battle_single_p2p` / `_net`。

本地无线按钮位于 `/bin/message/<lang>/common/mystery.dat` 的第 69 行；第 9 行为搜索消息，第 11 行为“未找到礼物”。

### 应用程序的状态机

调度器 `0x00FE6F80` 读取位于 `app+0x718` 的请求对象：就绪标志位于 `+0x60`，下一个状态 ID 位于 `+0x64`。当标志被设置且 ID 不大于 16 时，它通过 `0x020641A4` 跳转并构建该状态。`SetNextState(id)` 是 `0x00FF0DE0`，拥有 63 个调用点。

| id | 状态 | id | 状态 |
|---|---|---|---|
| 0 | TopMenu | 9 | SelectReceiveDataSerial |
| 1 | ReceiveMenu | 10 | SelectReceiveDataRankMatch |
| 2 | ReceiveLocal | 11 | SelectReceiveDataFromBall |
| 3 | ReceiveInternet | 12 | ConfirmGift |
| 4 | ReceiveSerial | 13 | ReceiveNews |
| 5 | ReceiveRankMatch | 14 | ReceiveComplete |
| 6 | ReceiveFromBall | 15 | ConnectPalma |
| 7 | SelectReceiveDataLocal | 16 | (默认，TopMenu) |
| 8 | SelectReceiveDataInternet | | |

本地无线是状态 2，搜索，然后是 7，从分发器提供的礼物中选择；状态 7 不触碰任何网络，其列表在进入前就已填充。推进 2 到 7 的机制尚不清楚。`0x00FE700C` (`mov w8, w21`) 是调度器的跳转表索引。该类的主虚函数表是 `0x025737C8`；`main` 中没有任何内容指向该应用程序，因此通过扫描堆来查找虚函数表。该镜像没有神秘礼物协议缓冲模块。

## 礼物界面的网络

在本地无线屏幕上，主机广告宣传其始终开启的本地游玩网络：本地通信 ID `0x0100ABF008968000`（两个标题），版本 4，场景 ID 65535（连接交换为 60001），接受策略为 ALL，`NodeCountMax` 为 2，广告数据为 384 字节，密码 CRC 为零。游戏在加载后 16 至 31 秒内创建一次该接入点；进入或离开神秘礼物不会发出 LDN 调用。礼物屏幕仅设置其广告数据并激活 Pia 加入过滤器。

在该屏幕上，游戏以每分钟约 40 次的频率调用 `nn::ldn::Scan`，交替调用 `SetAdvertiseData` 和 `GetNetworkInfo`，从不调用 `Connect` 或 `CreateNetwork`。扫描在 802.11 层是被动的（不发送探测请求）。其过滤器仅匹配本地通信 ID 和网络类型；`SessionId` 和 `SceneId` 不被过滤。

### 模式字节

`session_config+0x70` 是本地游玩模式。`0x01096730` 通过跳转表 `0x02066C14` 将其映射到 Pia 场景 ID 和参与者数量；`0x010961a8` 通过 `0x02066C40` 将其映射到广告数据字节 `0x97`（广告为 `0xAF`；游戏的数据从 `0x18` 开始）：

| 模式 | 场景 ID | 参与者 | 广告数据 `0x97` |
|---|---|---|---|
| 0 | 无，创建者在 `0x01096764` 返回 false | | 0xFF |
| 1 | 60021 | 2 | 0x01 |
| 2 | 60001 | 2 | 0x0D |
| 3 | 60002 | 2 | 0x0E |
| 4 | 60003 | 2 | 0x0F |
| 5 | 60004 | 4 | 0x10 |
| 6 | 60005 | 2 | 0x1E |

连接交换是模式 2；礼物屏幕运行模式 0，不会创建会话。进入应用程序时保存模式于 `app+0xFE8` 并设为 0（`0x01022f08`）；离开时恢复（`0x01023198`）。一名极巨化冒险的主持者广告 `0x11`，不在该表中。唯一其他因屏幕而异的广告字节是 `0xB9`（0x00 礼物，0xAA 交易），含义未知。

## 礼物屏幕上的 Pia 网格

该屏幕上的网格不允许任何加入者；卡片使用 [信标广告数据传输](#the-card-travels-in-beacon-advertise-data)。一个加入者在 0x14 上完成站点握手，其在 0x18 上的网格加入请求被拒绝：

    02 00 ff ff 01        JOIN_RESPONSE, refused, reason 1

`ProcessJoinRequestJob` 运行 `InitialStep`、`CheckApprovalJoin`、`SendJoinRefused`、`SendJoinResponse`、`WaitResponseAck` 和 `JoinSucceeded`。原因 1 仅来自应用程序回调；其他原因来自传输检查。

| | 剑 | 盾 |
|---|---|---|
| `CheckApprovalJoin` | `0x01553d20` | `0x017cc450` |
| reason-1 存储 | `0x01553d58 strb w9, [x19, #0xbc]` | `0x017cc59c strb w9, [x19, #0xba]` |
| `MeshProtocol+0x60` 处的 Pia 跳板 | `0x0157fcfc`, 全局 `0x04c4b848` | `0x018414b0`, 全局 `0x02616a30` |
| `SendJoinRefused` | `0x01553d80` | |
| 传输检查 | `0x0154806c` | `0x017bb2e0` |

该跳板在其对象的 `+0xb0` 为空时批准，否则尾调用它。游戏在 `0x006b47b0` 设置它为加入过滤器 `0x006b41c0`，并在 `0x006b5340` 清除它，两者均来自模式切换 `0x006a9af0`。

### 加入过滤器 0x006b41c0

`manager` 是 `[0x02610000 + 0x4b0]`，`session` 是 `[manager+0x58]`。按顺序的四个门，以及礼物屏幕的值：

| 顺序 | 位置 | 测试 | 值 | 判定 |
|---|---|---|---|---|
| 1 | `0x006b4204` | 屏蔽列表启用 (`manager+0x21C`) 且非空 (`+0x1C0`) | 启用，空 | 通过 |
| 2 | `0x006b8260` | Pia 站点计数 `pia_obj+0x1A8` 低于 `session+0x1F0` | 计数 1，最大值 0 | 拒绝 |
| 3 | `0x006b827c` | 允许列表标志 `session+0x4f5`；设置，遍历 `session+0x4c0` 的列表 | 0 | 批准 |
| 4 | `0x006b4248` | 身份 `+0x10` 处的半字（地址字节 8，IPv4 为零） | 0 | 批准 |

`session+0x1F0` 的最大值仅由 `0x006b9900` 写入，该函数从极巨化冒险匹配 (`0x00bd9b30`) 和 Max Raid 洞穴 (`0x01031c74`) 进入：礼物屏幕为 0，主持连接交换为 2，主持 Max Raid 为 4。在礼物屏幕上将其设为 8 会允许加入，但座位场景不会发送任何应用程序负载，也不会在 0x84 上打开任何内容。

### 传输检查

`0x017bb2e0` 在回调之前运行，返回 `0xFF` 或原因字节。其对象是 `read_u64(read_u64(main + 0x0262F7B0))`。

| 字段 | 宽度 | 内容 |
|---|---|---|
| `+0xA8` | u16 | 最大站点计数 |
| `+0xAA` | u8 | 启用字节；为零则在其他任何测试之前返回 2 |
| `+0xAB` | u8 | 选择计数读取的掩码字 |
| `+0xAC` | u8 | 计数遍历的掩码位数 |
| `+0xC4` | u32 | 占用掩码，当 `[0xAC] == [0xAB]` 时读取 |
| `+0xC8` | u32 | 否则的占用掩码，唯一一个自由槽搜索读取的掩码 |

| 位置 | 当返回 0 时 |
|---|---|
| `0x017bb380` | 计数（1 加每个设置位） `>=` 最大值，或无自由槽 (`0xFD`) |
| `0x017bb498` | `mesh_obj+0x370` 处的表满对 `read_u64(main + 0x02616710) + 0x70` 处的 u16 或其容量 `table+0x48` |
| `0x017bb4d4` | `mesh_obj+0x132` 处的字节，由类型为 0x18 的事件设置 |

当类型为 0x19 的事件设置 `mesh_obj+0x131` 时返回 4。

## 接收任务和导入器

gfl 网络管理器是 `read_u64(read_u64(main+0x0261CBA8))`（虚函数表 `0x025819A0`）；空的全局是每个发送存根上的无会话保护。它在 `+0xD0`/`+0xD8` 没有条目数组。进入本地无线情况时，`StateReceiveLocal` 的驱动 `0x01004C80`（对 `state+0x2A0` 的情况机器）通过 `0x010B7100` 构建接收任务（构造函数 `0x010B73E0`，虚函数表组 `0x0257DD88`，轮询 `0x010B74D0`），将其链接在 `manager+0x68`，并在 `state+0xB0` 安装接收委托（`0x0100504C` 组）。

该任务持有数据接收器在 `job+0x60`（目标 `0x01005BC0`），进度回调在 `job+0xE0`（`0x01005C70`），以及其消息源，即会话对象在 `job+0x08`（虚函数表 `0x0250DAE0`）。它在搜索屏幕打开时出现，并在屏幕关闭时释放。陷阱：重新进入屏幕会在新地址处重建任务和接收器的对象。

接收器尾调用 `0x00FF0E00` -> `0x00FF1FB0` -> `0x00FF2170`，即导入器，它拒绝不是 0x2D0 字节记录（720 字节，PKHeX 的第 8 代神秘卡片大小；`0x00ff22f4`）整数倍的主体。每个记录通过 [记录必须携带的内容](#what-a-record-must-carry) 的检查（`0x00FF2354`），被 `0x01449820` 过滤，并由 `0x00FF3EC0` 实例化。

导入器的第二个参数是路由；它成为卡片 `+0x64` (`0x00FF3F5C`)，以及当 `route != 0` 时，表头 `+0x0E` (`0x010B5FAC`)。每个调用者都是接收状态虚函数表槽 16 中的一个 lambda：

| 状态 | 路由 | 调用点 |
|---|---|---|
| `StateReceiveLocal` | 0 | `0x01005bf8` |
| `StateReceiveInternet` | 1 | `0x01011588`, `0x010115f0` |
| `StateReceiveSerial` | 2 | `0x0100a268`, `0x0100a2d0` |
| `StateReceiveFromBall` | 2 | `0x0100fc78`, `0x0100fce0` |
| `StateReceiveRankMatch` | 3, 4 | `0x01012458`, `0x010124c0` |

任何非 0 路由都会覆盖记录的日期 ([卡片的日期](#the-cards-date))。路由 3 和 4 还会在块 `0xa83021c1` 和 `0xce07d358` 中设置字节 (`0x00ff24e0..0x00ff26d4`)；路由 0 不会触碰任何一个。

## 卡片通过信标广告数据传输

分发器不加入任何网络。它广告宣传一个网络，其广告数据携载卡片，接收器则从其 `Scan` 结果中重新组装。

礼物是 gflnet3 核心的消费者，独立于交易同步泵。核心管理器 `read_u64(read_u64(main+0x02616B80))` 命名自己为 `BeaconCommunication` (`0x02068858`)，并驱动 `nn::ldn::Scan`、`GetNetworkInfo`、`SetAdvertiseData` 和 `OpenAccessPoint`（包装函数 `0x017978F0`、`0x01794C3C`/`0x01799BE0`、`0x017961B0`、`0x01794CF0`）。Pia 网格加入对其没有任何影响。

## 信标主体帧

LDN 广告数据的 0x180 字节由信标核心框架的 0x18 字节头和 0x168 字节主体组成。

| 主体偏移 | 大小 | 字段 |
|---|---|---|
| `+0x00` | 2 | 覆盖 `body[2:0x168]` 的 CRC-16/ARC，初始化为 0，无最终异或 |
| `+0x02` | 12 位 | 网络 ID，低 8 位在 `body[2]`，高 4 位在 `body[3]` 的低半字节 |
| `+0x03` 高半字节 | 4 位 | 每次捕获均为零 |
| `+0x04` | 1 | 每次捕获均为零 |
| `+0x05` | 至多 0x163 | 应用程序负载 |

神秘礼物、连接交换和 Max Raid 屏幕上的网络 ID 均为 `0xD70`。负载边界检查为 `cmp x2, #0x163` 位于 `0x006c2174`。

校验例程是 `0x0065dcb0`（由 `0x0065def0` 构建的表），反射 CRC-16/ARC，多项式 `0xA001`。

构建函数 `0x006c1fa0` 清零主体，调用位打包写入器 `0x006c1830` 将网络 ID 写入 `body+2`，将负载复制到 `body+5`，并在 `body+0` 存储覆盖 `body+2` 的 0x166 字节的校验和；缺失或过大的负载会存储 `0xFFFF` 代替 (`0x006c21d4`)。

## 接收到的信标通过的大门

`0x006c1be0` 返回 1 以接受一个条目。接收到的广告（`0x006bb9d4`、`0x006c4b38`、`0x006ca0dc`）仅在其接受时才到达存储 `0x006c53b0`。任何失败的测试都会拒绝：

1. `0x02616b80` 后面的核心对象存在；
2. `body+0` 等于对 `body[2:0x168]` 重新计算的校验和；
3. body 的网络 ID 与 `0x02616b88` 后面的半字不同，核心缺失时的构建器回退值；
4. 网络 ID 与核心自身的 nibbles 逐一一致（`0x006c1cf0`）：低 nibble 必须相等；不同第二个 nibble 接受；否则第三个 nibble 必须相等。

带有陈旧校验和的信标会被扫描但从不存储。

陷阱：0x480 字节的 `NetworkInfo` 扫描结果槽（包括 `pia_obj+0x3C0`）会完整复制 0x180 字节的任意 body，无论其校验和；该标记仅证明接收。

`0x006c53b0` 仅在条目为新时才将其追加。一个存储器的数组位于 `+0x40`，计数位于 `+0x48`，容量位于 `+0x50`（0x32），互斥锁位于 `+0x60`；一个条目为 0x180 字节，一个虚函数表指针紧跟其后，body 位于 `+8`。两个存储器通过 `0x006c5300` 交替使用。

`0x010f6600` 遍历一个存储器，通过 `0x006c1d50` 读取网络 ID，通过 `0x006c1f80` 读取 payload（返回 `body+5`；唯一调用者 `0x010f66c4`），并将 payload 传递给 `0x010f8cf0`，后者将其存储在消息对象中，供 `[gfl_job+0x68]` 虚函数表 `+0x38` 的处理程序使用。接收者的站点信息结构就是这个 payload，因此其偏移位于广告数据的 0x1d 字节处。

## 投票重组的消息

Payload 的第 0 字节是消息类型。`0x010f6600` 为每种已知类型构建一个类型化视图，指向 `payload+1`：

| 类型 | 视图 | 发送至 |
|---|---|---|
| 0 | `0x010f8730` | `0x0110f270`，以及 `0x02610958` 后面的对象；接收者自己的信标（站点信息） |
| 1 | `0x010f8830` | `[manager+0x68]` 的 job，虚函数表槽 `+0x38` |

在礼物屏幕上，该 job 是接收 job，槽 `+0x38`（`0x0257dd88+0x48`；虚函数表指针是该组加 0x10）是它的投票 `0x010b74d0`，因此类型 1 的 payload 会馈送给导入器。

投票读取 `payload+1` 处的十字节头部，通过 `0x010f7bf0`（字段访问器 `0x010F7A40..0x010F7A80`；发送端在 `0x010F7C08` 布局）；片段紧随其后：

| 偏移 | 大小 | 含义 |
|---|---|---|
| `+0` | 4 | 零值，或投票立即返回 |
| `+4` | 2 | 总消息长度 |
| `+6` | 1 | 分片数量 |
| `+7` | 1 | 本分片的索引，除非小于分片数量否则拒绝 |
| `+8` | 2 | 重组消息的 CRC-16/ARC（`0x0065dcb0`） |

0x88 字节的重组上下文（每个正在传输的消息一个）位于 `job+0x160` 和 `job+0x168` 之间，匹配所有头部字段但不包括索引（`0x010f7550`）。`0x010f7100` 将分片复制到 `index * 300`；超出缓冲区的索引或已设置的位会被丢弃。一条消息最多为 65535 字节和 256 个分片；一张 720 字节的卡片被分为 300、300 和 120 字节的分片。

当 `0x010f7610` 报告所有位均已设置时，`0x010f7680` 比较 `context+0x18` 与 `0x010f71e0`（通过 `0x0065dcb0` 的缓冲区），若不匹配则返回 null。投票在 null 时跳过接收端（`0x010b77fc`），并无论结果如何在一次投票内擦除上下文。

陷阱：带有错误校验和的消息不会留下任何痕迹，空的上下文列表也是已完成消息所留下的痕迹。

## 记录必须携带的内容

| 偏移 | 大小 | 字段 |
|---|---|---|
| `+0x00` | 8 | 日期（参见[卡片的日期](#the-cards-date)） |
| `+0x08` | 4 | 卡片 ID，u16，作为整个字比较：`+0x0A..+0x0B` 必须为零 |
| `+0x0C` | 2 | 无用 |
| `+0x0E` | 2 | 游戏版本掩码 |
| `+0x10` | 1 | 标志：第 0 位跳过单次卡片表，第 2 位单次卡片日期 |
| `+0x11` | 1 | 礼物种类，1 至 5 |
| `+0x12` | 1 | 单次卡片限制 |
| `+0x13` | 1 | 单次卡片标签 |
| `+0x15` | 1 | 标题索引 |
| `+0x1C` | 1 | 保存在头部 `+0xf` |
| `+0x20` | | 种类的 payload |
| `+0x2CC` | 2 | 记录的 CRC-16/CCITT-FALSE，本字段清零后计算 |

版本掩码：导入器调用 `0x007d4270`（盾：`mov w0,#0x2d; ret`）并测试 `1 << 1` 与掩码，当值为 `0x2D` 时，否则测试 `1 << 0`（`0x00ff2330..0x00ff2358`）。盾版本占第 1 位；`0xFFFF` 通过任一版本；零值被跳过。

单次卡片表：当 `+0x13` 非零（`0x00ff236c`），`0x01449820` 拒绝该记录，若表中位于相册 `+0x1660` 的条目（块 `0x112D5141` 偏移 `0x1600`；五十四字节条目，一个半字卡片 ID 和一个字节）与 `+8` 处的卡片 ID 和 `+0x13` 处的字节匹配。保留时，`0x00ff1544` 在 `+0x12` 非零且 `+0x10` 的第 0 位清除时（`0x00ff152c`）调用 `0x014494a0(album, record)`：它将五十个条目下移，追加 `{card id, +0x13}` 到 `+0x1724`，并当该 ID 的条目中非零字节达到 `+0x12` 时，在前 49 个条目中清零它们。当 `+0x13` 或 `+0x12` 为零或 `+0x10` 的第 0 位被设置时，卡片每次都会被导入。

最后接收表：`+0x10` 的第 2 位使保留路径调用 `0x01449560(album, record)`（`0x00ff1548`、`0x00ff1558`）：十个 16 字节条目位于相册 `+0x15c0`，第 `+0` 处为 u64 日期，第 `+8` 处为 u16 卡片 ID。持有该 ID 的条目会取记录的日期（`0x01449650`）；否则第一个日期更旧的条目（`0x016cc1f0`，无符号）会取 ID 和日期（`0x01449804`、`0x0144980c`）。空条目会被取用，因为其零日期更旧。

被接受的记录被复制到一个 0x338 字节的结构中（记录位于 `+0x68`，`0x00ff2380`），并交给验证器 `0x010b5de0`，它清零 `+0x2CC` 并在所有 0x2D0 字节上运行 CRC-16/CCITT-FALSE（多项式 `0x1021`，初始化 `0xFFFF`，`0x010b5e60`、`0x010b5f54`）。它返回 `0x80000000` 表示空指针或长度不为 `0x2D0`，返回 `0x80000001` 表示校验和不匹配（导入器将其映射为 1，`0x00ff23d0`），否则返回 0，包括种类在 1..5 之外的情况。它填充 0x68 字节的头部：卡片 ID 到 `+8`，`+0x15` 到 `+0xa`，`+0x11` 到 `+0xc`，`route != 0` 到 `+0xe`，`+0x1C` 到 `+0xf`。卡片对象为 0x3A8 字节，结构保存在 `+0x70`。

卡片 ID：`0x00ff2f50` 比较记录 `+0x08` 处的 u32（`0x00ff30c0`）与 16 位 ID，因此 `+0x0A` 或 `+0x0B` 处的任何非零值都无法匹配，导入器报告 2（无法在本游戏中获得的礼物）。`+0x0C` 从未被读取。

标题：`+0x15` 索引标题表，PKHeX 将其作为 `text_wondercard8_<lang>.txt` 提供，在卡片被接受前显示在列表中。构建器使用的索引：1 宝可梦蛋，3 道具名称，21 "{species} (Gigantamax Pokemon)"，34 口袋钱，36 服装，39 战斗点数。索引 0 是物种名称单独；索引 11 是 "{species} de {original trainer}"。

种类：1 至 5 通过 `0x02067620` 分发；其他任何值返回成功但不构建任何内容。种类 3 和 5（`0x010b5fd8`）保留 `+0x20` 处的字到头部 `+0x30`，并不构建任何内容。种类 1 到 `0x010b58f0`，种类 2 复制其道具对，种类 4 到 `0x010b5bb0`。

语言索引来自 `0x02067650` 的表（游戏语言到 0..8）。标记字节发送到 `0x00775d50`；超过 127 的索引不设置任何内容。带有零标记字节的记录会命名标记 0 三十二次：用 `0xFF` 填充列表。

解析器不读取等级或相遇等级；这两个偏移都来自声明的卡片。

等级 0：构建器绘制 `r = random & 0x7f` 直到 `r <= 99`，并取 `r + 1`，在 1..100 范围内均匀分布（`0x010b6218`），相遇等级为 0。一个蛋无论如何获得等级 1（`0x010b6400`）。经验值匹配物种的成长组。

IV：构建器按顺序测试六个字节 HP、攻击、防御、特攻、特防、速度；第一个在 `0xFC..0xFE` 范围内的存储完美数量 `byte - 0xFB`（1 至 3）到 `[sp+0x110]`，并将所有六个物种 IV 设为 `0xFFFF`，丢弃其余（`0x010b6300..0x010b63c4`）。否则，32 或以上的字节变为 `0xFFFF`，低于 32 的字节保留。`0x00766660` 将等级上限设为 100，并在该等级的不同随机位置写入 31（`0x00766a50..0x00766b04`）；仍为 `0xFFFF` 的每个 IV 都会被滚动 0..31（`0x00766de8`）。因此，任何 IV 字节中的 `0xFC`、`0xFD` 或 `0xFE` 会给出恰好 1、2 或 3 个随机 31 的 IV。

留在零的记录会给出一个雄性、固执性格、第一能力和 IV 为 0 的宝可梦。`pokeldn.swsh.wc8.pokemon_card` 写入性别 3、性格 `0xFF`、能力 3 和每个 IV 字节 `0xFF`，除非该字段被指定，否则游戏会随机生成每个值。

性别 3 在每次构建时滚动一次，声明构建两次：展示 `0x00fe3720`（`0x00fe3a50`）和赎回 `0x010159d0`（`0x01015a0c`），因此展示时可能显示与队伍接收到的性别不同的宝可梦。性别 0、1 或 2 跳过滚动（`0x00766d94`）。应用程序和 `bin/swsh_gift_host.py` 在卡片构建时绘制性别一次（当 `r + 1 < ratio` 时为雌性，`r` 低于 253）；`--set gender=3` 恢复游戏自己的滚动。

## 通过信标传递的卡片，端到端

从一个合成信标发送的 720 字节记录，分为三个分片，到达未修改控制台上的导入器。导入器的结果位于 `bound+0x2C0`，`bound` 是 `job+0x80`；`0x00ff1fb0` 在其非零时返回它，否则当卡片列表为空时返回 2（版本掩码为 0 会返回 2，"无法在本游戏中获得"；错误校验和返回 1，"接收礼物失败"）。一个密封的种类 3 记录带有零日期，显示为 2070 年 1 月 1 日。

## 通过礼物卡发送到零售主机

`bin/swsh_gift_host.py` 通过 LDN 协议将各种类型的礼物卡发送到零售版的剑／盾主机。主机仅在 LDN 协议版本 1 上列出礼物卡，且广告数据需以 Pia 协议的自身礼物广告标头开头（参见[Sword 会话](swsh_session.md)）：随机网络 ID、零密码 CRC、系统通信版本 5、标头大小 0x18、随机会话参数以及八个零字节。场景 ID 和应用程序版本不做过滤。标题仅从 `+0x15` 获取，无论卡片类型；卡片类型决定了具体发送的内容。

类型 2 的记录仅需类型、物品配对和数量。解析器从记录 `+0x20..+0x37` 复制恰好六个 ID/数量配对到标头 `+0x30..+0x47`（`0x010b6024..0x010b6080`），并将标头 `+0x0D` 设置为非零数量的个数（`0x010b6084..0x010b60e4`）；兑换时对每个非零数量的配对调用 `Bag::AddItem`（`0x01015d00..0x01015dd0`）。1.3.2 版本的物品表共有 1607 条目；其中名称以 `★` 开头的条目为虚拟物品（其中包括 1279 到 1578）。PKHeX 将 1607 个 ID 中的 51 个标记为 `???`；应用程序的物品选择器列出 `ItemStorage8SWSH.GetAllHeld()` 返回的 817 个 ID，这也是卡片检查所接受的集合。

类型 4 为服装（参见[服装](#clothing)）。类型 3 和类型 5 在状态对象 `[[0x2610798]+0x208]` 中的 clamped 计数器上加上 `+0x20` 处的单词：

    类型 3  0x01015e00   [status+0x17c] = min(old + amount, 9999)                  0x014390fc
    类型 5  0x010160b0   [status+0x64]: 超过 9,999,999 的金额设为 9,999,999；
                         否则为 old + amount， clamped 到 9,999,999              0x01438f2c

`status+0x64` 是口袋里的钱（`AddPocketMoney_` `0x014ad5e0`，`GetPocketMoney_` `0x014ad700`）。
两种兑换方式都从记录 `+0x20` 读取金额。

类型 1 的兑换 `0x010159d0` 构建宝可梦（`0x010b6110`；null 返回 0）并提供给队伍（`0x01015b78`，虚拟 `+0x28`）。如果队伍拒绝，则询问箱子存储 `[[0x2610798]+0x220]` 是否有空位（`0x01408000`，`0x01015bd0`），并仅当存在空位时才放置（`0x01406b00`，`0x01015c08`）。其结果从未被测试；一张无法通过房间测试的卡片永远不会到达这里（参见[菜单拒绝的内容](#what-the-menu-refuses)）。

`Bag::AddItem`（`0x01420790`；bag, id, count, new-flag）从物品字段 14 获取口袋（`0x00788c50(id, 14)`，物品字节 `+0x11 & 0xF`），找到持有该 ID 的槽位或第一个空槽位，并写入 `id | min(count + n, 999) << 15`；槽位已满 999 时拒绝。每个槽位为一个 u32：ID 在第 0-14 位，数量在第 15-29 位，第 30 位为新物品标志。保存块由 `0x0141fae0` 注册，键为 `0x1177C2C4`，大小为 `0x12F8` 字节。口袋从 `bag+0x1358` 开始：

|---|---|---|
| 0 | Medicine | 60 |
| 1 | Balls | 30 |
| 2 | Battle | 20 |
| 3 | Berries | 80 |
| 4 | Items | 550 |
| 5 | TMs | 210 |
| 6 | Treasures | 100 |
| 7 | Ingredients | 100 |
| 8 | Key | 64 |

## 作为礼物信标的棋盘

`bin/swsh_gift_host.py --save-to-board`（应用程序中的“Keep it on the board”）将卡片的广告周期存储到 ESP32 开发板上并退出。从任何 USB 充电器供电后，开发板将在 `--dwell` 指定的时间内独立广告发送卡片的三个分片，直到有主机打开它（参见[便携信标](hardware_esp32.md#portable-beacon)）。每次上电使用相同的网络和密钥；广告 nonce 每次随机初始化。零售主机从开发板单独接收卡片的情况尚未测量。

### Pokemon HOME

该组包含 EventsGallery 中的 `HOME Simulated WCs`（卡片 ID 9000 及以上，PKHeX 的 `WC8.IsHOMEGift`），每张卡片都与 PKHeX 的事件数据库中保存的卡片逐字节一致，标题来自 projectpokemon。卡片 9000 到 9007 的初始版本将所有 PID 固定为 0；第二版（保留版本）则由游戏随机生成。

从其中一张卡片获得的宝可梦不带 HOME tracker，但 PKHeX 要求礼物卡中的宝可梦必须带有 HOME tracker：由于主机自行生成宝可梦，PKHeX 会在任何 HOME tracker 设置下标记缺失的 tracker（参见[HOME tracker 设置](gui.md#the-home-tracker-setting)），而 Pokemon HOME 目前仍会接受。应用程序会用琥珀色轮廓标出这些卡片并说明情况。

`+0x10` 处的标志决定主机获取卡片的频率（参见[菜单拒绝的内容](#what-the-menu-refuses)）：

| 位 2 | 13 | 每日最多十次，按卡片日期限领一次 |
| 均无 | 46 | 每次都可领取 |

有两张宝可梦卡片带有版本掩码 1 或 2，另一版本的主机会跳过这些卡片。

## 服装

类型 4 的记录从 `+0x20` 开始包含十二对 u32：类别和索引。前六对（`+0x20..+0x4F`）适用于玩家状态字节 `+0x105` 为零的情况，后六对（`+0x50..+0x7F`）适用于其他情况。该字节由 `0x01424c20` 在状态对象 `[[0x2610798]+0x1e8]` 上读取。PKHeX 的 `MyStatus8` 在块偏移 `0xA5` 处保存玩家性别，`0x60` 为其下偏移；该对象是否在 `+0x60` 保存该块尚未验证。

解析器 `0x010b5bb0` 将玩家的六对数据复制到标头 `+0x30..+0x5F`，并将索引不为 `0xFFFFFFFF` 的配对数量写入标头 `+0x0D`。兑换函数 `0x01015eb0` 再次读取记录中的配对（通过相同测试 `0x01015f14`；记录 `+0x20` 为标头与记录的 `+0x88`），并对每个索引不为 `0xFFFFFFFF` 的配对调用 `0x0143a450(wardrobe, category, index, 1)`，作用在衣柜 `[[0x2610798]+0x218]` 上。该设置函数拒绝类别大于 14 或索引大于 1023 的输入，否则设置位 `index & 7` 在字节 `wardrobe + 0x68 + category * 0x80 + index / 8` 上。配对 `(0, 0)` 会设置类别 0 的第 0 位；跳过索引为 `0xFFFFFFFF` 的槽位。

## 菜单的拒绝

在兑换选定的卡片之前，`0x01014a60` 读取卡片种类 `card[+0x7c]`（`0x01014bcc`）、`w25 = 0x00ff1750(card) - 1`（`0x01014bd4`、`0x01014be4`）以及记录标志位 `[card+0xe8]` 的第 2 位（`0x01014be8 ubfx w24,w8,#2,#1`），并对种类 1 执行房间检测 `0x013adee0`（`0x01014d68`）。顺序如下：

    0x00ff1750 返回 1、2 或 3    消息 7、0x10 或 0x11     0x01014d9c cmp w25,#3; 表 0x02065360 = 7, 16, 17
    种类 1 且无房间               消息 8                   0x01014c14 mov w21,#8
    标志位 2 已设置               消息 0xF、然后状态 3     0x01014d38 mov w1,#0xf; 续接 0x010156f0
    其他情况                     状态 3、兑换             0x01014e70

`0x02064f80` 保存 `mystery.tbl` 的标签哈希，每条消息索引对应一个 u64；从 `0x01000718` 初始化的例程将第 k 项解析为 `owner+0x5f8+8k`，并由 `0x01002da0` 读回。来自 1.3.2 英文版 `mystery.dat`：

| 消息 | 标签 | 文本 |
|---|---|---|
| 7 | `msg_o_mystery_win_13` | You can't get that gift, since you've already received the same gift before. |
| 8 | `msg_o_mystery_win_14` | There's no room for another Pokémon. Make room in your party or Pokémon Boxes, and then try again. |
| 0xF | `msg_o_mystery_win_34` | You can receive this gift just once a day. Once you've received it, you can't claim another one until the next day. |
| 0x10 | `msg_o_mystery_win_35` | You can only receive this gift once per day. You've already claimed the one for today, so check in tomorrow for your next chance. |
| 0x11 | `msg_o_mystery_win_36` | You can only receive 10 gifts per day. You've already claimed 10 gifts today, so check in tomorrow to be able to claim more. |

一次拒绝的续接 `0x01015740` 在 `+0x80` 存储 0，即菜单的第一个状态。被拒绝的卡片既不被放置也不被保留，一旦原因消失即可再次领取。

`0x013adee0` 在箱子存储没有空位时返回 1（`0x013adfb4 cset w20,eq`），并报告队伍已满（队伍虚函数表 `+0x60`，槽位 12，`0x013adfc4`；`0x013adfd0 and`）。

`0x00ff1750`，仅从 `0x01014bd4` 调用，是领取检测。当 `[card+0x60]` 或 `[card+0x68]` 为零时立即返回 1（`0x00ff1750..0x00ff1770`）；对于路线 0 到 2，继续通过 `0x00ff17b4` 到 `0x00ff1a30`：

    data = album+0x60 (0x014480e0)
    记录标志位 0 置位，且卡片 ID 的比特位在 data+0x1450 的位图中设置（album +0x14b0）   -> 1
    记录标志位 2 清除 (0x00ff1ab0)                                                       -> 0
    记录的日期无效 (0x00ff1b84)                                                          -> 3
    从 data+0x1560（album +0x15c0）的十个 0x10 字节条目，0x00ff1b88..0x00ff1c70:
        条目 ID == 卡片 ID 且卡片日期 <= 条目日期 (0x016cc210, cset ls)                 -> 2
        卡片日期 > 条目日期 (0x016cc1f0, cset hi): 一个空闲条目
    一个空闲条目                                                                        -> 0
    全部                                                            -> 3

位图读取取字节 `id >> 3`（`0x00ff1a8c ubfx x9, x23, #3, #0xd`），无边界检查：位图为 0x100 字节（ID 0 到 2047），因此具有标志位 0 且 ID 大于等于 2048 的记录会读取超出范围，ID 大于 13000 的记录会读取超出 0x17B8 字节的块。具有标志位 0 清除的记录从不读取它。该比特位在领取时设置，其写入者未知。

这些条目仅由 `0x01449560` 写入，其唯一调用者 `0x00ff1558` 位于 `[card+0xe8]` 的 `0x00ff154c tbz w8,#2` 之后，它们存储记录自己的日期（`0x01449570`、`0x01449648`），而非领取时间。具有标志位 2 的卡片按卡片日期最多一次，且每天最多十次；若日期未变重新发送，则会被消息 0x10 拒绝，而其条目依然保留。

保留路径 `0x00ff13f0`（唯一调用者为 `0x01014f74`，在宝可梦放置之前）更新上述表格，为路线 1 到 4 将领取时间写入 `card+0x70`（或路线 0 的记录日期），并归档卡片（`0x014480f0`）。它不检查合法性。

构建和兑换均不检查招式、重学招式、性格、球、携带物或形态 against 种族。构建器 `0x010b6110` 只有一个出口且无拒绝：它原样存储四个招式和四个重学招式（`0x77bfb0`、`0x77b9a0`；存储于 `0x770c7c`），招式 ID 大于 826 仅改变 PP 查找（`0x00781490`）。兑换 `0x010159d0` 仅检测种类字节、非空构建结果以及队伍是否有空间（`0x7840f0` 拒绝种族 0 或队伍已满）或箱子是否有空位（`0x1406b00` 需要一个空槽）。

唯一的种族检测在宝可梦参数构造函数 `0x777f40`（`0x778118..0x778148`）中：其个人数据条目第 0x21 字节第 6 位清除的种族（`0x764990`、`0x77f530`）会获得记录 `+0x04` 字的坏蛋位 2（`0x76eb40`），之后所有访问器读取静态替身种族 0x383（`0x776c50`），命名为 "Egg"。菜单路径上没有任何拒绝：卡片在菜单中按种族名称列出并显示，队伍接收一个空白的 "Egg"。种族大于 898 读取个人数据条目 0，存在且不被标记。永远不要发送剑盾中不存在的种族；桌面应用的 PKHeX 检测会拒绝之。

性别是构建器唯一修正的字段（`0x777490`，个人数据字段 0x14 在 `0x7774a4` 读取）：比率 0、254 和 255 分别强制为男性、女性和无性别（表 `0x1c4d2d0`）；其他任何比率下请求的 2 变为 0（`0x7774d8`）。构建器将记录性别 3 转换为 0xFF，即随机（`0x010b62ac`）。

## 卡片的日期

记录的前八个字节是相册显示的日期，一个小端序 u64 位域，表示绝对 UTC 时间。没有公开的映射名称它；PKHeX 的 `WC8.cs` 从卡片 ID `+0x08` 开始。

| 位 | 字段 |
|---|---|
| 0-5 | 秒 |
| 6-11 | 分 |
| 12-16 | 时 |
| 17-21 | 日 |
| 22-25 | 月，1 到 12 |
| 26-39 | 年，绝对值 |

`0x016cc5e0` 通过 days-from-civil 算法（其中的 `146097`、`1461` 和除以 100 的常量都在其中）将其转换为 posix 时间，并在值等于 `main+0x2616900` 之后的哨兵值时返回 0。相册绘制 `0x00ffbaa0` 将其传递给 `nn::time::ToCalendarTime`（`0x00ffbaf0`），因此应用控制台的时区，回退到 `ToCalendarTimeInUtc`。年份以两位数字显示。

零日期显示为 01/01/2070。

只有本地无线卡片保留其日期。其他所有路线都会用 `nn::time::StandardNetworkSystemClock::GetCurrentTime`（`0x00ff3f8c` -> `0x01449ca0`；PLT `0x01900050`，GOT `0x0260fbb8`）覆盖这八个字节，由 `0x016cbfd0` 和 `0x016cc1d0` 打包。

分发器在发送前用计算机当前的 UTC 时间填充空日期并重新密封校验和；非零日期被保留，导出的文件保留其原始日期。宝可梦的相遇日期与相册日期分离。

## 相册如何存储卡片

相册是存档块 `0x112D5141`（PKHeX 的 `KMysteryGift`），`0x17C8` 字节，由 `0x01447eb0` 加载到相册对象 `+0x60`，并由 `0x01449d90` 写回。它存储一个重新编码的头部，从不存储 720 字节的传输记录或其字符串。`tools/switch/swsh_save.py` 将 `main` 读入其块中（PKHeX 的 SwishCrypto：对文件使用静态 xorpad，每个块使用 XorShift32 流由其密钥播种，以及在两个常量之间的加密体进行 SHA-256）；`--key 112d5141 --out FILE` 输出该块，`--patch KEY OFF HEX --write OUT` 修改块的字节并重新密封文件。

    0x0000  50 个 0x68 字节的槽，最新在槽 0；插入会将每个槽下移一位
            (0x01449880 索引它们，cmp w1, #0x31；槽在使用中时其 +0x0C 非零)
    0x1450  0x378 字节，在每次存档读取时为零；最后一次领取表为 0x1560..0x15FF
            (album +0x15c0) 和每张卡一次表为 0x1600..0x16C8 (album +0x1660)

一个槽是导入器从记录中填充的 0x68 字节头部：

    +0x00  8    记录的日期位域（零值绘制为 2070 年 1 月 1 日）
    +0x08  u16  卡片 ID
    +0x0A  u16  记录在 +0x15 的字节（宝可梦卡为 0，种类 3 为 1，道具卡为 3）
    +0x0C  u8   种类：1 宝可梦、2 道具、3 空种类
    +0x0D  u8   种类 2：六个道具数量中非零的个数；否则为 0
    +0x0E  u8   1 表示卡片通过任何路线而非本地无线到达
    +0x0F  u8   记录在 +0x1C 的字节（种类 3 卡片为 1）
    +0x12  u16  等级（种类 1）
    +0x30  u32  种族（种类 1）；种类 2：道具对（u16 ID、u16 数量），如记录 +0x20
    +0x38  4 x u32  招式（种类 1）
    +0x48  26   昵称，UTF-16（种类 1）
    +0x62  u8   3 在每个宝可梦卡上

清零槽的 `+0x0C..+0x62` 会从相册中移除该卡片；它所交付的道具仍留在 `MyItem`（`0x1177C2C4`）。

## 每帧更新耗尽存储的函数

`0x010f65a0` 是 gfl 网络管理器的每帧更新（管理器来自 `0x0261cba8`）：它通过 `0x006c5300` 排空 `manager+0x60` 的接收器，遍历条目，并在每次找到非空存储时在 `manager+0x80` 盖上戳。其唯一调用者是位于 `0x00f1df30` 内部的 `0x01109240`，通过一个注册的回调到达。

陷阱：在某些会话中，存储永远不会被耗尽，`manager+0x80` 保持不变；在读取任何信标结果之前，请先确认它在前进。原因未知。
