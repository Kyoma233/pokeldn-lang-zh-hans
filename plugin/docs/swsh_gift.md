# 神秘礼物菜单

《剑／盾》的神秘礼物菜单通过本地无线接收神秘卡片：分发者广播一个 LDN 网络，其广播数据以片段携带卡片。地址为《盾》1.3.2 的 `main`，除非标记为《剑》；空中行为以零售主机为基准。

## 菜单

接收方式选择器 `StateSelectReceiveDataBase` 为每个菜单按钮（`L_mystery_top_btn_00` .. `_04`）设置一个子类：

| 状态 | 方法 |
|---|---|
| `StateSelectReceiveDataInternet` | 通过网络 |
| `StateSelectReceiveDataSerial` | 序列号或密码 |
| `StateSelectReceiveDataLocal` | 本地无线 |
| `StateSelectReceiveDataFromBall` | 精灵球 Plus |
| `StateSelectReceiveDataRankMatch` | 排位对战奖励 |

接收状态包括 `StateReceiveBase`、`StateReceiveInternet`、`StateReceiveSerial`、`StateReceiveLocal`（`0x01004938`，其自身代码只引用进度条布局）、`StateReceiveFromBall`、`StateReceiveRankMatch`、`StateReceiveNews` 和 `StateReceiveComplete`。游玩记录键 `fushigi_net`、`fushigi_serial` 和 `fushigi_p2p` 按渠道统计接收次数，此外还有 `yy_battle_single_p2p` / `_net`。

本地无线按钮位于 `/bin/message/<lang>/common/mystery.dat` 的第 69 行；第 9 行是搜索消息，第 11 行是“未找到礼物”。

### 应用的状态机

调度器 `0x00FE6F80` 读取 `app+0x718` 处的请求对象：`+0x60` 处的就绪标志，`+0x64` 处的下一状态 id。当标志置位且 id 不超过 16 时，它通过 `0x020641A4` 跳转并构建该状态。`SetNextState(id)` 为 `0x00FF0DE0`，有 63 处调用点。

| id | 状态 | id | 状态 |
|---|---|---|---|
| 0 | TopMenu | 9 | SelectReceiveDataSerial |
| 1 | ReceiveMenu | 10 | SelectReceiveDataRankMatch |
| 2 | ReceiveLocal | 11 | SelectReceiveDataFromBall |
| 3 | ReceiveInternet | 12 | ConfirmGift |
| 4 | ReceiveSerial | 13 | ReceiveNews |
| 5 | ReceiveRankMatch | 14 | ReceiveComplete |
| 6 | ReceiveFromBall | 15 | ConnectPalma |
| 7 | SelectReceiveDataLocal | 16 | （默认，TopMenu） |
| 8 | SelectReceiveDataInternet | | |

本地无线是状态 2，即搜索，然后是状态 7，即从分发者提供的内容中选择；状态 7 不接触网络，其列表在进入前已被填充。从 2 推进到 7 的过程未知。`0x00FE700C`（`mov w8, w21`）是调度器的跳转表索引。该类的初级 vtable 是 `0x025737C8`；`main` 中没有任何内容指向该应用，因此要通过扫描堆中的 vtable 来找到它。该映像没有神秘礼物的协议缓冲区模块。

## 礼物画面的网络

在本地无线画面上，主机广播其常开的本地联机网络：本地通信 id 为 `0x0100ABF008968000`（两个版本均如此），版本 4，场景 id 65535（连接交换为 60001），接受策略为 ALL，`NodeCountMax` 2，384 字节广播数据，密码 CRC 为零。游戏在加载后 16 到 31 秒创建一次该接入点；进入或离开神秘礼物不会产生任何 LDN 调用。礼物画面只设置其广播数据并启用 Pia 加入过滤器。

在画面上，游戏每分钟调用约四十次 `nn::ldn::Scan`，并与 `SetAdvertiseData` 和 `GetNetworkInfo` 交错调用，从不调用 `Connect` 或 `CreateNetwork`。该扫描在 802.11 层是被动的（无探测请求）。其过滤器只指定本地通信 id 和网络类型；`SessionId` 与 `SceneId` 未过滤。

### 模式字节

`session_config+0x70` 是本地联机模式。`0x01096730` 通过跳转表 `0x02066C14` 将其映射到 Pia 场景 id 和参与人数；`0x010961a8` 通过 `0x02066C40` 将其映射到广播数据字节 `0x97`（广播 `0xAF`；游戏数据从 `0x18` 开始）：

| 模式 | 场景 id | 参与人数 | 广播数据 `0x97` |
|---|---|---|---|
| 0 | 无，创建者在 `0x01096764` 处返回 false | | 0xFF |
| 1 | 60021 | 2 | 0x01 |
| 2 | 60001 | 2 | 0x0D |
| 3 | 60002 | 2 | 0x0E |
| 4 | 60003 | 2 | 0x0F |
| 5 | 60004 | 4 | 0x10 |
| 6 | 60005 | 2 | 0x1E |

连接交换是模式 2；礼物画面运行模式 0，不创建会话。进入应用将模式保存至 `app+0xFE8` 并设置为 0（`0x01022f08`）；离开时恢复（`0x01023198`）。极巨团体战主办方广播 `0x11`，该值不在表中。唯一另一个随画面而异的广播字节是 `0xB9`（0x00 表示礼物，0xAA 表示交换），含义未知。

## 礼物画面上的 Pia mesh

该画面上的 mesh 不接受加入者；卡片使用[信标传输](#the-card-travels-in-beacon-advertise-data)。加入者完成 0x14 上的站点握手，其在 0x18 上的 mesh 加入请求被拒绝：

    02 00 ff ff 01        JOIN_RESPONSE, refused, reason 1

`ProcessJoinRequestJob` 依次运行 `InitialStep`、`CheckApprovalJoin`、`SendJoinRefused`、`SendJoinResponse`、`WaitResponseAck` 和 `JoinSucceeded`。原因 1 只来自应用回调；其他原因由传输检查给出。

| | 剑 | 盾 |
|---|---|---|
| `CheckApprovalJoin` | `0x01553d20` | `0x017cc450` |
| 原因 1 存储 | `0x01553d58 strb w9, [x19, #0xbc]` | `0x017cc59c strb w9, [x19, #0xba]` |
| 位于 `MeshProtocol+0x60` 的 Pia 跳板 | `0x0157fcfc`，全局 `0x04c4b848` | `0x018414b0`，全局 `0x02616a30` |
| `SendJoinRefused` | `0x01553d80` | |
| 传输检查 | `0x0154806c` | `0x017bb2e0` |

当对象的 `+0xb0` 为空时，跳板批准；否则尾调用它。游戏在 `0x006b47b0` 处将其设置为加入过滤器 `0x006b41c0`，并在 `0x006b5340` 处清除，二者均来自模式切换 `0x006a9af0`。

### 加入过滤器 0x006b41c0

`manager` 为 `[0x02610000 + 0x4b0]`，`session` 为 `[manager+0x58]`。四个关卡按顺序排列，并列出礼物画面上的值：

| 顺序 | 位置 | 测试 | 值 | 判定 |
|---|---|---|---|---|
| 1 | `0x006b4204` | 屏蔽列表已启用（`manager+0x21C`）且非空（`+0x1C0`） | 启用，空 | 通过 |
| 2 | `0x006b8260` | Pia 站点数 `pia_obj+0x1A8` 小于 `session+0x1F0` | 计数 1，上限 0 | 拒绝 |
| 3 | `0x006b827c` | 允许列表标志 `session+0x4f5`；置位时遍历 `session+0x4c0` 处的列表 | 0 | 批准 |
| 4 | `0x006b4248` | 身份 `+0x10` 处的半字（地址字节 8，IPv4 为零） | 0 | 批准 |

最大值 `session+0x1F0` 仅由 `0x006b9900` 写入，该函数可从极巨大冒险匹配（`0x00bd9b30`）和极巨团体战巢穴（`0x01031c74`）到达：礼物画面上为 0，主办连接交换时为 2，主办极巨团体战时为 4。在礼物画面将其写为 8 会允许加入，但已入座的场景不会发送任何应用载荷，也不会在 0x84 上打开任何内容。

### 传输检查

`0x017bb2e0` 在回调之前运行，并返回 `0xFF` 或原因字节。其对象为 `read_u64(read_u64(main + 0x0262F7B0))`。

| 字段 | 宽度 | 含义 |
|---|---|---|
| `+0xA8` | u16 | 最大站点数 |
| `+0xAA` | u8 | 一个启用字节；为零时在任何其他测试之前返回 2 |
| `+0xAB` | u8 | 选择计数读取哪个位掩码字 |
| `+0xAC` | u8 | 计数遍历位掩码的多少位 |
| `+0xC4` | u32 | 占用位掩码，当 `[0xAC] == [0xAB]` 时读取 |
| `+0xC8` | u32 | 其他情况下的占用位掩码，也是空闲槽搜索唯一读取的位掩码 |

| 位置 | 满足以下情况时返回 0 |
|---|---|
| `0x017bb380` | 计数（1 加上每个置位加一）`>= max`，或没有空闲槽（`0xFD`） |
| `0x017bb498` | `mesh_obj+0x370` 处的表已满，相对于 `read_u64(main + 0x02616710) + 0x70` 处的 u16 或其容量 `table+0x48` |
| `0x017bb4d4` | `mesh_obj+0x132` 处的字节，在类型 0x18 事件时置位 |

当类型 0x19 事件将 `mesh_obj+0x131` 置位时，它返回 4。

## 接收任务与导入器

gfl 网络管理器是 `read_u64(read_u64(main+0x0261CBA8))`（vtable `0x025819A0`）；空全局变量是每个发送存根上的无会话保护。它在 `+0xD0`/`+0xD8` 处没有条目数组。进入本地无线分支后，`StateReceiveLocal` 的驱动 `0x01004C80`（`state+0x2A0` 上的 case 机）通过 `0x010B7100`（构造函数 `0x010B73E0`，vtable 组 `0x0257DD88`，轮询 `0x010B74D0`）构建接收任务，将其链接在 `manager+0x68`，并在 `state+0xB0`（`0x0100504C` 组）安装接收委托。

任务将数据汇存于 `job+0x60`（目标 `0x01005BC0`），进度回调在 `job+0xE0`（`0x01005C70`），其消息源为 `job+0x08` 处的会话对象（vtable `0x0250DAE0`）。它在搜索画面打开时出现，关闭时被释放。陷阱：重新进入画面会在新地址重建任务和汇存对象。

该汇存尾调用 `0x00FF0E00` -> `0x00FF1FB0` -> `0x00FF2170`，即导入器；导入器拒绝不是 0x2D0 字节记录整数倍的正文（720 字节，PKHeX 的第 8 代神秘卡片大小；`0x00ff22f4`）。每条记录在 `0x00FF2354` 处通过[一条记录必须携带的内容](#what-a-record-must-carry)中的检查，经 `0x01449820` 过滤，并由 `0x00FF3EC0` 落实。

导入器的第二个参数是路由；它成为卡片的 `+0x64`（`0x00FF3F5C`），并且当 `route != 0` 时，成为头部 `+0x0E`（`0x010B5FAC`）。每个调用方都是接收状态 vtable 中槽 16 里的 lambda：

| 状态 | 路由 | 调用点 |
|---|---|---|
| `StateReceiveLocal` | 0 | `0x01005bf8` |
| `StateReceiveInternet` | 1 | `0x01011588`、`0x010115f0` |
| `StateReceiveSerial` | 2 | `0x0100a268`、`0x0100a2d0` |
| `StateReceiveFromBall` | 2 | `0x0100fc78`、`0x0100fce0` |
| `StateReceiveRankMatch` | 3、4 | `0x01012458`、`0x010124c0` |

除 0 以外的任何路由都会覆盖记录的日期（[卡片的日期](#the-cards-date)）。路由 3 和 4 还会在块 `0xa83021c1` 和 `0xce07d358`（`0x00ff24e0..0x00ff26d4`）中设置字节；路由 0 两者都不触及。

## 卡片在信标广播数据中传输

分发者不加入任何网络。它广播一个网络，其广播数据携带卡片，接收方根据其 `Scan` 结果重新组装卡片。

礼物是 gflnet3 核心的使用方，与交换同步泵分离。核心管理器 `read_u64(read_u64(main+0x02616B80))` 自称为 `BeaconCommunication`（`0x02068858`），并驱动 `nn::ldn::Scan`、`GetNetworkInfo`、`SetAdvertiseData` 和 `OpenAccessPoint`（包装函数 `0x017978F0`、`0x01794C3C`/`0x01799BE0`、`0x017961B0`、`0x01794CF0`）。Pia mesh 加入不会在其中改变任何内容。

## 信标主体帧

LDN 广播数据的 0x180 字节由信标核心装帧，分为 0x18 字节的头部和 0x168 字节的主体。

| 主体内偏移 | 大小 | 字段 |
|---|---|---|
| `+0x00` | 2 | 对 `body[2:0x168]` 的 CRC-16/ARC，初始值 0，无最终异或 |
| `+0x02` | 12 位 | 网络 id，低 8 位在 `body[2]`，高 4 位在 `body[3]` 的低半字节 |
| `+0x03` 高半字节 | 4 位 | 每次捕获均为零 |
| `+0x04` | 1 | 每次捕获均为零 |
| `+0x05` | 最多 0x163 | 应用载荷 |

网络 id 在神秘礼物、连接交换和极巨团体战画面上为 `0xD70`。载荷上限是 `0x006c2174` 处的 `cmp x2, #0x163`。

校验和例程是 `0x0065dcb0`（表由 `0x0065def0` 构建），采用反射式 CRC-16/ARC，多项式 `0xA001`。

构建器 `0x006c1fa0` 清零主体，使用位打包写入器 `0x006c1830` 将网络 id 写入 `body+2`，将载荷复制到 `body+5`，并在 `body+0` 存放覆盖 `body+2` 起 0x166 字节的校验和；载荷缺失或过大时，则存放 `0xFFFF`（`0x006c21d4`）。

## 收到的信标通过的关口

`0x006c1be0` 返回 1 表示接受一个条目。收到的广播（`0x006bb9d4`、`0x006c4b38`、`0x006ca0dc`）只有在它接受时才会到达存储 `0x006c53b0`。任一测试失败都会拒绝：

1. `0x02616b80` 后面的核心对象存在；
2. `body+0` 等于在 `body[2:0x168]` 上重新计算的校验和；
3. body 的网络 ID 与 `0x02616b88` 后面的半字不同——那是在核心不存在时构建器的回退值；
4. 网络 ID 按半字节与核心自身的半字节一致（`0x006c1cf0`）：低半字节必须相等；第二个半字节不同也接受；否则第三个半字节必须相等。

校验和过期的信标会被扫描但永不存储。

陷阱：0x480 字节的 `NetworkInfo` 扫描结果槽，其中包括 `pia_obj+0x3C0`，会完整复制 0x180 字节的任何 body，无论其校验和如何；那里的标记仅证明已接收。

`0x006c53b0` 仅在新条目时才追加被接受的条目。存储的数组在 `+0x40`，数量在 `+0x48`，容量在 `+0x50`（0x32），互斥锁在 `+0x60`；一个条目为 0x180 字节，先是 vtable 指针，body 在 `+8`。两个存储通过 `0x006c5300` 交替。

`0x010f6600` 遍历存储，通过 `0x006c1d50` 读取网络 ID，通过 `0x006c1f80` 读取 payload（返回 `body+5`；唯一调用者是 `0x010f66c4`），然后将 payload 传给 `0x010f8cf0`，后者将其存入一个消息对象，供 `[gfl_job+0x68]` vtable `+0x38` 处的处理器使用。接收方的站点信息结构就是这个 payload，因此其偏移位于广播数据的 0x1d 字节处。

## 轮询重组出的消息

payload 的第 0 字节是消息类型。`0x010f6600` 为每个已知类型构建一个类型化视图，指向 `payload+1`：

| type | view | 去向 |
|---|---|---|
| 0 | `0x010f8730` | `0x0110f270`，以及 `0x02610958` 后面的对象；接收方自己的信标（站点信息） |
| 1 | `0x010f8830` | `[manager+0x68]` 处的任务，vtable 槽 `+0x38` |

在礼物画面中，该任务是接收任务，槽 `+0x38`（`0x0257dd88+0x48`；vtable 指针是组加 0x10）是它的轮询 `0x010b74d0`，因此类型 1 的 payload 会送入导入器。

轮询通过 `0x010f7bf0` 读取 `payload+1` 处的十字节头部（字段访问器 `0x010F7A40..0x010F7A80`；发送端在 `0x010F7C08` 布局）；分片跟在它后面：

| offset | size | 含义 |
|---|---|---|
| `+0` | 4 | 为零，否则轮询立即返回 |
| `+4` | 2 | 消息总长度 |
| `+6` | 1 | 分片数 |
| `+7` | 1 | 此分片的索引，除非小于分片数否则拒绝 |
| `+8` | 2 | 重组后消息的 CRC-16/ARC（`0x0065dcb0`） |

0x88 字节的重组上下文，每个在途消息一个，位于 `job+0x160` 到 `job+0x168` 之间，按除索引外的每个头部字段匹配（`0x010f7550`）。`0x010f7100` 将分片复制到 `index * 300`；超出缓冲区的索引或已经置位的位会被丢弃。一条消息最多 65535 字节和 256 个分片；720 字节的卡片是 300、300 和 120 的分片。

当 `0x010f7610` 报告每个位都已置位时，`0x010f7680` 将 `context+0x18` 与 `0x010f71e0`（经 `0x0065dcb0` 的缓冲区）比较，不匹配时返回 null。轮询在 null 时跳过接收处理（`0x010b77fc`），无论如何都会在同一次轮询内擦除上下文。

陷阱：校验和错误的消息不会留下任何痕迹；而空上下文列表也正是已完成消息留下的结果。

## 记录必须携带的内容

| 偏移 | 大小 | 字段 |
|---|---|---|
| `+0x00` | 8 | 日期（[卡片的日期](#the-cards-date)） |
| `+0x08` | 4 | 卡片 ID，u16，作为整个字比较：`+0x0A..+0x0B` 必须为零 |
| `+0x0C` | 2 | 未使用 |
| `+0x0E` | 2 | 游戏版本掩码 |
| `+0x10` | 1 | 标志：位 0 跳过每卡一次表，位 2 每卡日期一次 |
| `+0x11` | 1 | 礼物种类，1 到 5 |
| `+0x12` | 1 | 每卡一次限制 |
| `+0x13` | 1 | 每卡一次标记 |
| `+0x15` | 1 | 标题索引 |
| `+0x1C` | 1 | 保存在头部 `+0xf` |
| `+0x20` | | 种类的 payload |
| `+0x2CC` | 2 | 此字段清零后记录的 CRC-16/CCITT-FALSE |

版本掩码：导入器调用 `0x007d4270`（盾：`mov w0,#0x2d; ret`），当值为 `0x2D` 时用 `1 << 1` 测试掩码，否则用 `1 << 0`（`0x00ff2330..0x00ff2358`）。盾版取位 1；`0xFFFF` 可通过任一版本；零会被跳过。

每卡一次表：当 `+0x13` 非零时（`0x00ff236c`），如果 album `+0x1660` 处的表中的条目（块 `0x112D5141` 偏移 `0x1600`；50 个四字节条目，一个半字卡片 ID 和一个字节）与 `+8` 处的卡片 ID 以及 `+0x13` 的字节匹配，`0x01449820` 会拒绝该记录。保留时，当 `+0x12` 非零且 `+0x10` 的位 0 清零时（`0x00ff152c`），`0x00ff1544` 调用 `0x014494a0(album, record)`：它将 50 个条目下移，在 `+0x1724` 追加 `{card id, +0x13}`，并且当此 ID 的字节非零的条目数达到 `+0x12` 时，它会在前 49 个条目中将它们清零。当 `+0x13` 或 `+0x12` 为零，或 `+0x10` 的位 0 置位时，卡片每次都会被导入。

最近接收表：`+0x10` 的位 2 使保留路径调用 `0x01449560(album, record)`（`0x00ff1548`、`0x00ff1558`）：album `+0x15c0` 处有十个 16 字节条目，`+0` 处为 u64 日期，`+8` 处为 u16 卡片 ID。持有该 ID 的条目取记录的日期（`0x01449650`）；否则第一个日期更早的条目（`0x016cc1f0`，无符号）取 ID 和日期（`0x01449804`、`0x0144980c`）。空条目会被取用，因为它的零日期更早。

被接受的记录会复制到一个 `0x338` 字节的结构中（记录在 `+0x68`，`0x00ff2380`），然后交给验证器 `0x010b5de0`，后者将 `+0x2CC` 清零，并对全部 0x2D0 字节运行 CRC-16/CCITT-FALSE（多项式 `0x1021`，初值 `0xFFFF`，`0x010b5e60`、`0x010b5f54`）。对于空指针或长度非 `0x2D0` 返回 `0x80000000`，对于校验和不匹配返回 `0x80000001`（导入器将其映射为 1，`0x00ff23d0`），否则返回 0，包括 1..5 之外的种类。它会填充 `0x68` 字节的头部：卡片 ID 填入 `+8`，`+0x15` 填入 `+0xa`，`+0x11` 填入 `+0xc`，`route != 0` 填入 `+0xe`，`+0x1C` 填入 `+0xf`。卡片对象为 `0x3A8` 字节，结构保存在 `+0x70`。

卡片 ID：`0x00ff2f50` 将记录 `+0x08` 处的 u32（`0x00ff30c0`）与 16 位 ID 比较，因此 `+0x0A` 或 `+0x0B` 处任何非零值都匹配不到任何卡片，导入器报告 2（无法在此游戏中获得的礼物）。没有代码读取 `+0x0C`。

标题：`+0x15` 索引 PKHeX 附带的标题表 `text_wondercard8_<lang>.txt`，在接受卡片之前显示在列表中。构建器使用的索引：1 宝可梦蛋，3 道具名称，21 “{species} (Gigantamax Pokemon)”，34 零花钱，36 服装，39 对战点数。索引 0 仅为宝可梦种类名称；索引 11 是 “{species} de {original trainer}”。

种类：1 到 5 通过 `0x02067620` 分发；其他值返回成功但不构建任何内容。种类 3 和 5（`0x010b5fd8`）将 `+0x20` 处的字保存在头部 `+0x30` 中，并且不构建任何内容。种类 1 进入 `0x010b58f0`，种类 2 复制其道具对，种类 4 进入 `0x010b5bb0`。

解析器不读取等级或相遇等级；这两个偏移都来自领取的卡片。

等级 0：构建器抽取 `r = random & 0x7f` 直到 `r <= 99`，然后取 `r + 1`，在 1..100 上均匀（`0x010b6218`），相遇等级为 0。蛋无论怎样都得到等级 1（`0x010b6400`）。经验值与种类的成长组一致。

IV：构建器按 HP、攻击、防御、特攻、特防、速度的顺序测试六个字节；在 `0xFC..0xFE` 范围内的第一个字节会存储一个无瑕计数 `byte - 0xFB`（1 到 3）到 `[sp+0x110]`，并将全部六个指定 IV 设为 `0xFFFF`，丢弃其余字节（`0x010b6300..0x010b63c4`）。否则 32 或更大的字节变为 `0xFFFF`，低于 32 的字节保留。`0x00766660` 将等级上限设为 100，并向该数量的不同随机位置写入 31（`0x00766a50..0x00766b04`）；每个仍为 `0xFFFF` 的 IV 会随机生成 0..31（`0x00766de8`）。因此任何 IV 字节中的 `0xFC`、`0xFD` 或 `0xFE` 恰好给出 1、2 或 3 个随机 31 IV。

一条留零的记录会给出雄性、勤奋性格、第一特性和 IV 为 0 的宝可梦。`pokeldn.swsh.wc8.pokemon_card` 会写入性别 3、性格 `0xFF`、特性 3，以及每个 IV 字节 `0xFF`，除非给出了字段，这样游戏会各自随机。

性别 3 每次构建都会随机一次，而一次领取会构建两次：预览 `0x00fe3720`（`0x00fe3a50`）和兑换 `0x010159d0`（`0x01015a0c`），因此预览显示的性别可能与队伍收到的不同。性别 0、1 或 2 会跳过随机（`0x00766d94`）。应用和 `bin/swsh_gift_host.py` 在构建卡片时只抽取一次性别（当 `r + 1 < ratio` 时为雌性，`r` 低于 253）；`--set gender=3` 恢复游戏自身的随机。

## 通过信标投递的卡片，端到端

一条来自合成信标的三个分片、共 720 字节的记录，在未修改的主机上到达导入器。导入器的结果位于 `bound+0x2C0`，其中 `bound` 是 `job+0x80`；`0x00ff1fb0` 在其非零时返回它，否则当卡片列表为空时返回 2（版本掩码为 0 给出 2，“无法在此游戏中获得”；校验和错误给出 1，“接收礼物失败”）。一条密封的 kind-3 记录日期为零时会显示 2070 年 1 月 1 日。

## 发送到零售主机的卡片

`bin/swsh_gift_host.py` 通过 LDN 向零售版《剑》发送所有类型。主机仅在 LDN 协议 1 上列出卡片，且广播数据以其自身礼物广播的 Pia 头开头（[剑的会话](swsh_session.md)）：随机网络 id、零密码 CRC、系统通信版本 5、头大小 0x18、随机会话参数和八个零字节。场景 id 和应用版本不参与过滤。标题仅来自 `+0x15`，与类型无关；类型决定发送的内容。

类型 2 记录只需要类型、物品对和数量。解析器从记录 `+0x20..+0x37` 将恰好六个 id/数量对复制到头部 `+0x30..+0x47`（`0x010b6024..0x010b6080`），并将头部 `+0x0D` 设为非零数量值的个数（`0x010b6084..0x010b60e4`）；兑换对每个非零数量调用 `Bag::AddItem`（`0x01015d00..0x01015dd0`）。1.3.2 物品表有 1607 项；名字在 `bin/message/<lang>/common/itemname.dat` 中以 `★` 开头的是占位项（其中 1279 到 1578）。PKHeX 将 1607 个 id 中的 51 个命名为 `???`；应用的物品选择器列出 `ItemStorage8SWSH.GetAllHeld()` 的 817 个 id，即其卡片检查接受的集合。

类型 4 是服装（[服装](#clothing)）。类型 3 和 5 将 `+0x20` 处的字加到状态对象 `[[0x2610798]+0x208]` 中带钳位的计数器上：

    kind 3  0x01015e00   [status+0x17c] = min(old + amount, 9999)                  0x014390fc
    kind 5  0x010160b0   [status+0x64]: an amount above 9,999,999 sets 9,999,999;
                         otherwise old + amount, clamped to 9,999,999              0x01438f2c

`status+0x64` 是零花钱（`AddPocketMoney_` `0x014ad5e0`、`GetPocketMoney_` `0x014ad700`）。两个兑换都从记录 `+0x20` 读取数量。

类型 1 的兑换 `0x010159d0` 构建宝可梦（`0x010b6110`；为 null 时返回 0）并提供给同行队伍（`0x01015b78`，虚地址 `+0x28`）。如果队伍拒绝，它会向盒子存储 `[[0x2610798]+0x220]` 请求空位（`0x01408000`、`0x01015bd0`），仅在存在空位时才放入（`0x01406b00`、`0x01015c08`）。其结果从不被检查；未通过房间测试的卡片不会到达这里（[菜单拒绝的内容](#what-the-menu-refuses)）。

## 作为礼物信标的开发板

`bin/swsh_gift_host.py --save-to-board`（应用的“保留在开发板”）将卡片的广播周期存储到 ESP32 开发板并退出。从任何 USB 充电器供电后，开发板会自行广播该卡片，按启动器的 `--dwell` 三个片段，直到有主机打开它（[便携式信标](hardware_esp32.md#portable-beacon)）。每次上电使用相同的网络和密钥；广播 nonce 每次从随机值开始。仅从开发板接收卡片的零售主机未经过测量。

### 宝可梦 HOME

该组包含图库中用于《剑／盾》的 `HOME Simulated WCs`（卡片 id 9000 及以上，PKHeX 的 `WC8.IsHOMEGift`），每张都与 PKHeX 事件数据库持有的一张卡片逐字节一致，并使用 projectpokemon 的标题。卡片 9000 至 9007 的第一版将每个 PID 固定为 0；保留的第二版让游戏随机生成一个。

从这种卡片接收的宝可梦不带有 HOME 追踪器，而 PKHeX 要求 HOME 发放的礼物具有该追踪器：主机生成宝可梦，因此无论 HOME 追踪器设置如何，PKHeX 都会标记缺失的追踪器（[HOME 追踪器设置](gui.md#the-home-tracker-setting)），而宝可梦 HOME 目前接受它。应用以琥珀色轮廓标出这些卡片并说明这一点。

`+0x10` 处的标志设置了主机接收卡片的频率（[菜单拒绝的内容](#what-the-menu-refuses)）：

| flags | cards | receipt |

| bit 2 | 13 | 每个卡片日期一次，每天最多十次 |
| 均无 | 46 | 每次 |

两张宝可梦卡片带有版本掩码 1 或 2，会被另一版本跳过。

## 服装

类型 4 的记录从 `+0x20` 起携带十二对 u32，每对先类别后索引：前六对（`+0x20..+0x4F`）用于状态字节 `+0x105` 为零的玩家，后六对（`+0x50..+0x7F`）用于其他情况。该字节由 `0x01424c20` 在状态对象 `[[0x2610798]+0x1e8]` 上读取。PKHeX 的 `MyStatus8` 将玩家性别保存在块偏移 `0xA5`，比它低 `0x60`；对象在 `+0x60` 处保存该块这一点未经验证。

解析器 `0x010b5bb0` 将玩家的六对复制到头部 `+0x30..+0x5F`，并将索引不为 `0xFFFFFFFF` 的对数写入头部 `+0x0D`。兑换 `0x01015eb0` 用相同测试再次读取记录中的对（`0x01015f14`；记录 `+0x20` 是头部加记录 `+0x88`），并为每个索引不为 `0xFFFFFFFF` 的对在衣柜 `[[0x2610798]+0x218]` 上调用 `0x0143a450(wardrobe, category, index, 1)`。该设置器拒绝类别超过 14 或索引超过 1023 的情况，否则设置字节 `wardrobe + 0x68 + category * 0x80 + index / 8` 的位 `index & 7`。对 `(0, 0)` 设置类别 0 的位 0；用索引 `0xFFFFFFFF` 跳过槽位。

## 菜单拒绝的情况

在领取选定卡片之前，`0x01014a60` 会读取 kind 字段 `card[+0x7c]`（`0x01014bcc`）、`w25 = 0x00ff1750(card) - 1`（`0x01014bd4`、`0x01014be4`）以及记录标志 `[card+0xe8]` 的位 2（`0x01014be8 ubfx w24,w8,#2,#1`），并且对于 kind 1 会运行房间测试 `0x013adee0`（`0x01014d68`）。依次为：

    0x00ff1750 returned 1, 2 or 3    message 7, 0x10 or 0x11     0x01014d9c cmp w25,#3; table 0x02065360 = 7, 16, 17
    kind 1 and no room               message 8                   0x01014c14 mov w21,#8
    flag bit 2 set                   message 0xF, then state 3   0x01014d38 mov w1,#0xf; continuation 0x010156f0
    otherwise                        state 3, the redemption     0x01014e70

`0x02064f80` 保存 `mystery.tbl` 标签散列，每个消息索引一个 u64；来自 `0x01000718` 的初始化程序将条目 k 解析为 `owner+0x5f8+8k`，并由 `0x01002da0` 读回。以下摘自 1.3.2 英文版 `mystery.dat`：

| message | label | text |
|---|---|---|
| 7 | `msg_o_mystery_win_13` | 你无法获得该礼物，因为你之前已经获得过相同的礼物。 |
| 8 | `msg_o_mystery_win_14` | 没有存放其他宝可梦的空间。请在同行队伍或宝可梦盒中腾出空间后再试一次。 |
| 0xF | `msg_o_mystery_win_34` | 这个礼物每天只能接收一次。接收之后，要等到第二天才能再领取。 |
| 0x10 | `msg_o_mystery_win_35` | 这个礼物每天只能接收一次。你已经领取了今天的份，明天再来看吧。 |
| 0x11 | `msg_o_mystery_win_36` | 每天只能接收 10 个礼物。你今天已经领取了 10 个，明天再来领取更多吧。 |

拒绝后的继续流程 `0x01015740` 会在 `+0x80` 处存入 0，即菜单的第一个状态。被拒绝的卡片既不会放置，也不会保留，一旦原因消失就可以再次领取。

`0x013adee0` 在盒存储没有空位（`0x013adfb4 cset w20,eq`）且队伍报告已满（队伍 vtable `+0x60`，slot 12，`0x013adfc4`；`0x013adfd0 and`）时返回 1（没有空间）。

`0x00ff1750` 仅由 `0x01014bd4` 调用，是领取检查。当 `[card+0x60]` 或 `[card+0x68]` 为零时，它会立即返回 1（`0x00ff1750..0x00ff1770`）；对于路线 0 到 2，它会继续经 `0x00ff17b4` 执行到 `0x00ff1a30`：

    data = album+0x60 (0x014480e0)
    record flag bit 0, and the card id's bit set in the bitmap at data+0x1450 (album +0x14b0)   -> 1
    record flag bit 2 clear (0x00ff1ab0)                                                       -> 0
    the record's day invalid (0x00ff1b84)                                                      -> 3
    ten entries of 0x10 bytes from data+0x1560 (album +0x15c0), 0x00ff1b88..0x00ff1c70:
        entry id == card id and card day <= entry day (0x016cc210, cset ls)                   -> 2
        card day > entry day (0x016cc1f0, cset hi): a free entry
    a free entry                                                                               -> 0
    none                                                                                       -> 3

位图读取取 `id >> 3` 字节（`0x00ff1a8c ubfx x9, x23, #3, #0xd`），没有边界检查：位图是 0x100 字节（id 0 至 2047），因此记录若设置了标志位 0 且 id 为 2048 或更大，就会读到位图之后；从 id 13000 开始则会读到该块 0x17C8 字节之后。标志位 0 未设置的记录永远不会读取它。该位在领取时被设置；其写入者未知。

这些条目仅由 `0x01449560` 写入，而其唯一调用者 `0x00ff1558` 位于 `[card+0xe8]` 上的 `0x00ff154c tbz w8,#2` 之后；它们保存记录自身的日期（`0x01449570`、`0x01449648`），而不是领取时间。设置了标志位 2 的卡片每个卡片日期只能领取一次，且每天最多十个；用未更改的日期重新发送时，它会被消息 0x10 拒绝，而其条目仍然保留。

保留路径 `0x00ff13f0`（唯一调用者 `0x01014f74`，在宝可梦被放置之前）会更新上述表，对于路线 1 至 4 将领取时间写入 `card+0x70`（对于路线 0 则写入记录日期），并将卡片归档（`0x014480f0`）。它不检查合法性。

构建和兑换检查不会核对招式、回忆招式、性格、球种、携带物品或形态是否与物种匹配。构建器 `0x010b6110` 只有一个出口且不会拒绝：它按给定值存储四个招式和四个回忆招式（`0x77bfb0`、`0x77b9a0`；存储位于 `0x770c7c`），而招式 id 超过 826 只会改变 PP 查找（`0x00781490`）。兑换 `0x010159d0` 仅检查 kind 字节、非空构建，以及同行队伍中有位置（`0x7840f0` 会拒绝物种 0 或满队伍）或盒子中有空位（`0x1406b00` 需要一个空槽）。

唯一的物种测试位于 PokemonParam 构造函数 `0x777f40`（`0x778118..0x778148`）：如果某物种的个人条目的字节 0x21 的第 6 位为 0（`0x764990`、`0x77f530`），则记录 `+0x04` 字的坏蛋位 2（`0x76eb40`）会被设置，之后每个访问器都会读取物种 0x383（`0x776c50`）的静态替身，名为“蛋”。菜单路径上没有任何环节会拒绝它：卡片会以该物种名称列出并展示，而同行队伍会收到一个空白的“蛋”。物种编号超过 898 时会读取个人条目 0，而该条目存在，因此不会被标记。切勿发送《剑／盾》中不存在的物种；桌面应用的 PKHeX 检查会拒绝它。

性别是构建会纠正的唯一字段（`0x777490`，个人字段 0x14 在 `0x7774a4` 读取）：比例为 0、254 和 255 时强制为雄性、雌性和无性别（表 `0x1c4d2d0`）；在任何其他比例下，请求的 2 会变为 0（`0x7774d8`）。构建器会将记录性别 3 转换为 0xFF，即随机（`0x010b62ac`）。

## 卡片的日期

记录的前八个字节是相册显示的日期，即绝对 UTC 时间的小端 u64 位域。没有公开的内存映射为其命名；PKHeX 的 `WC8.cs` 从 `+0x08` 处开始读取卡片 id。

| bits | field |
|---|---|
| 0-5 | 秒 |
| 6-11 | 分 |
| 12-16 | 小时 |
| 17-21 | 当月日期 |
| 22-25 | 月，1 到 12 |
| 26-39 | 年，绝对年份 |

`0x016cc5e0` 通过 days-from-civil 算法（其中包含 `146097`、`1461` 和除以 100 的常数）将其转换为 POSIX 时间，并在该值等于 `main+0x2616900` 后面的哨兵值时返回 0。相册绘制 `0x00ffbaa0` 会将其传给 `nn::time::ToCalendarTime`（`0x00ffbaf0`），因此会应用主机时区，并回退到 `ToCalendarTimeInUtc`。年份以两位数字绘制。

零日期会显示为 01/01/2070。

只有本地无线卡片会保留其日期。其他所有路线都会用 `nn::time::StandardNetworkSystemClock::GetCurrentTime`（`0x00ff3f8c` -> `0x01449ca0`；PLT `0x01900050`，GOT `0x0260fbb8`）覆盖这八个字节，并由 `0x016cbfd0` 和 `0x016cc1d0` 打包。

分发器在发送前会用计算机当前的 UTC 时间填充空日期，并重新密封校验和；非零日期会被保留，导出的文件也保留其原始日期。宝可梦的相遇日期与相册日期是分开的。

## 相册保存卡片的位置

相册是存档块 `0x112D5141`（PKHeX 的 `KMysteryGift`），大小 `0x17C8` 字节，由 `0x01447eb0` 加载到相册对象的 `+0x60` 处，并由 `0x01449d90` 写回。它保存的是重新编码后的标头，从不保存 720 字节的传输记录或其字符串。`tools/switch/swsh_save.py` 将一个 `main` 读入其块中（PKHeX 的 SwishCrypto：对整个文件使用静态 xorpad；每个块使用以其键为种子的 XorShift32 流；对两个常量之间的加密主体计算 SHA-256）；`--key 112d5141 --out FILE` 会将此块写出，而 `--patch KEY OFF HEX --write OUT` 会重写某个块的字节并重新密封文件。

    0x0000  50 slots of 0x68 bytes, newest in slot 0; an insert moves every slot down one
            (0x01449880 indexes them, cmp w1, #0x31; a slot is in use when its +0x0C is non-zero)
    0x1450  0x378 bytes, zero in every save read; the last-receipt table is 0x1560..0x15FF
            (album +0x15c0) and the once-per-card table 0x1600..0x16C8 (album +0x1660)

一个槽位是导入器根据记录填充的 `0x68` 字节标头：

    +0x00  8    the record's date bitfield (zero draws 1 January 2070)
    +0x08  u16  card id
    +0x0A  u16  the record's byte at +0x15 (0 on Pokemon cards, 1 on kind-3, 3 on an item card)
    +0x0C  u8   kind: 1 Pokemon, 2 item, 3 the empty kind
    +0x0D  u8   kind 2: how many of the six item quantities are non-zero; 0 otherwise
    +0x0E  u8   1 when the card came by any route but local wireless
    +0x0F  u8   the record's byte at +0x1C (1 on kind-3 cards)
    +0x12  u16  level (kind 1)
    +0x30  u32  species (kind 1); kind 2: the item pairs (u16 id, u16 quantity) as at record +0x20
    +0x38  4 x u32  moves (kind 1)
    +0x48  26   nickname, UTF-16 (kind 1)
    +0x62  u8   3 on every Pokemon card

将槽位的 `+0x0C..+0x62` 清零会从相册中移除卡片；它已交付的物品仍保留在 `MyItem`（`0x1177C2C4`）中。

## 清空存储的每帧更新

`0x010f65a0` 是 gfl 网络管理器的每帧更新（管理器来自 `0x0261cba8`）：它通过 `0x006c5300` 排空 `manager+0x60` 处的接收器，遍历条目，并在每次发现存储非空时给 `manager+0x80` 打上标记。它的唯一调用者是 `0x01109240`，位于 `0x00f1df30` 内部，而后者是通过注册的回调到达的。

陷阱：在某些会话中，存储从不会被排空，`manager+0x80` 保持不变；在读取任何 beacon 结果之前，请先检查它是否在递增。原因未知。
