# 朱／紫

宝可梦朱（`0100a3d008c5c000`）与紫（`01008f6008c5e000`）是原生 Switch 标题，Pia 链接进 `main`。两者都能以两种角色与零售主机交换：`bin/sv_host.py` 为主机，供控制台的离线连接交换搜索；`bin/sv_join.py` 加入控制台的网络。零售版紫会加入一个通告朱本地通信 ID 的主机，其自身的搜索网络也通告朱的 ID（`0x0100a3d008c5c000`，应用版本 21，场景 4）。

两个启动器也都能以任一角色跑本地太晶团体战（[太晶团体战](sv_raid.md)）；主机还能把官方赠礼宝可梦交给控制台（[模拟神秘礼物](gift_simulated.md)）。[联合环](sv_union_circle.md) 以访客身份加入控制台的环，向其主机上报蓝莓学院任务通关，并在主机玩家周围生成用户指定的野生宝可梦。

地址是更新 4.0.0 解压后 `main` 的偏移（`tools/switch/nso_read.py`）：text `0x0..0x343fc90`，rodata 自 `0x3440000`，data 自 `0x4383000`。

## 搜索中的控制台通告什么

连接交换搜索在主持（每次新 SSID）与扫描之间交替，在信道 1、6、11 间跳；一次主持大约五秒。

    local_communication_id  0x0100a3d008c5c000，朱的，两个版本都用
    ldn protocol            1            advertisement version 4
    scene_id                4            app_version 21
    security_mode           1            accept_policy ALL
    participants            1/2
    application_data        132 bytes

应用数据是 0x5C 字节的 Pia 系统属性块再加 40 字节游戏数据：

| 字段 | 值 |
|---|---|
| 系统通信版本 | 0x15 |
| 应用通信版本 | 0x15 |
| 用户密码 | 十六个零字节，无链接码 |
| 玩家上限启用 | 1，玩家数 1，有站点入座后变为 2 |
| 玩家名 | 一个字节，一个空格，UTF-8 |
| 那 40 字节游戏数据 | 全零，或游戏 `+0x21` 处非零（见过 `fb149700`），每隔几秒交替；第二台控制台在任一状态下都能关联 |

`pokeldn.sv.build_advertise_data` 能逐字节复现两种信标。

## 游戏跑的协议

对零售对的被动捕获显示 Net、RTT、0x80 与 0x81，都发往会话 `/24` 的广播地址，明文页脚里带接收方的变量 ID。另外六种是单播（两台 Switch 2 之间的 802.11ax），捕获里没有。

游戏的 setup `0x17ff030` 按序创建：端口 0 上的 Reliable `0x7C` 与 BroadcastReliable `0x80`，Unreliable `0x68`，端口 1 与 2 上的 Reliable 与 BroadcastReliable，`[0x44dfcd0]` StreamBroadcastReliable `0x81` 端口（线上八个），Clone Clock `0x77` 与 Clone Atomic `0x74`。Pia 再加上 Net、RTT、Session `0x98` 与 MonitoringData `0xA4`；NatTraversalResult `0xA0` 仅在网络工厂启用 NAT 穿越时出现（`0x6d3138`），本地网络不会。

| id | 协议 | 版本 |
|---|---|---|
| `0x2C` | Net | 0 |
| `0x58` | RTT | 3 |
| `0x68` | Unreliable | 1 |
| `0x74` | Clone Atomic | 0 |
| `0x77` | Clone Clock | 0 |
| `0x7C` | Reliable | 2 |
| `0x80` | BroadcastReliable | 3 |
| `0x81` | StreamBroadcastReliable | 3 |
| `0x98` | Session | 0 |
| `0xA4` | MonitoringData | 0 |

传说 阿尔宙斯列出同样十个版本。零售对开局：

    +0.00   加入方关联
    +0.06   主机：Net 0x11（站点列表），0.12 s 后 Net 0x50
    +0.14   主机：确认全部十一路流，打开两路
    +0.89   加入方：RTT 请求，确认全部十一路，打开两路
    +0.97   主机：0x81 端口 0 上的首批记录
    +1.26   加入方：0x81 端口 1 上的首批记录

### Net 0x11，站点列表

布局与传说 阿尔宙斯相同，四个站点槽各 21 字节：

    01 11 0054          版本 1，类型 0x11，有效载荷大小 0x54
    00000002            序列 ID
    9141                主机变量 ID，每会话刷新
    eb9b2220f1480000    主机常量 ID，LDN MAC 重排
    0000000097392e8a    网络 ID，低四字节 crc32(ssid[1:16])
    01                  网络是否开放
    0004                站点槽数
    00                  是否正在迁移主机
    ...                 四个站点：迁移状态、排名（主机 0，加入方 1，空 0xff）、
                        一字节、16 字节地址、大端 u16 端口 (12345)

`01 40 00 00` 是裸的 NetStartHostMigration，由交出角色的主机发送。零售朱从搜索主持时，会在交给加入方的席位上重复它（[什么决定席位](#什么决定席位)）。

主机写入四个站点槽——Pia 的数量；游戏上限是两个。只有两个槽时，加入方游戏什么都不发，对 Net 0x11 以 ICMP 端口 12345 不可达应答，并在关联后约 5 s 断开（49 次加入里 4.98 到 5.01 s）；四个槽时它应答 Net 0x12 并发送 Session 加入请求。

### 十一路流

    0x80  BroadcastReliable         端口 0、1、2
    0x81  StreamBroadcastReliable   端口 0 到 7

两端大约每秒用 `pokeldn.ldn.reliable5` 的批量确认确认全部十一路：四个条目，站点字节为零，条目 *k* 是站点 *k* 最高序列加一，destination-bit 计数 3，位图里有对端的位。站点用十一字节的 INITIALIZED 消息打开两路流，并在其站点索引对应的端口上发送记录（同 `pokeldn.pla.data_exchange`）。

| 站点 | 打开 | 在其上发送记录 |
|---|---|---|
| 主机，索引 0 | 0x81 端口 1 与 5 | 0x81 端口 0 |
| 加入方，索引 1 | 0x81 端口 0 与 4 | 0x81 端口 1 |

打开载荷在端口 0 与 1 上是 `0000000000f38800000000`，在 4 与 5 上是 `00 <port> 00 00 0ff0 0800000000`：StreamData kind 0，登记接收 0xF388（传输 0）或 0xFF008（4 与 5）。0xFF008 传输在交换中从不发送。`pokeldn.sv.streams` 构建全部这些；`tests/test_sv.py` 把它钉到零售字节。

### Pia 消息标志

两个零售站点都发送（阿尔宙斯主机的建立标志未用）：

| 消息 | 标志 |
|---|---|
| RTT、流打开、记录的首次发送 | 0x00 |
| 再次发送的记录 | 0x40 |
| 批量确认 | 0xA0 |
| 主机的 Net 0x11 与 0x50 | 0x31 |
| NetStartHostMigration | 0x11 |

消息目标字段始终为零。标志 0x40 是 `ReliableSlidingWindow` 发送循环 `0x6f0638` 的 `w4 = 1`（发送计数 `[slot+0x14]` 为零时为 0，`0x6f0908`；重发 `0x6f0a9c` 或提前发送 `0x6f0c38` 时为 1），由 `0x6e7250` 存为包写入器选项块的字节 0。

### RTT

十一字节：kind、大端 u64 时钟、大端 u16 目标。请求是 kind 0、目标 0；应答是 kind 1，同一时钟与请求方的变量 ID，零售上 20 ms 内。

RttProtocol（vtable `0x43e5a28`）在 `[proto+0x60] + index*0x40` 为每站点保留 0x40 字节记录：样本数 `+0`，环头 `+4`，容量 9 在 `+0x10`，环内联其后，中位数缓存于 `+0x3c`，对应 `+0x38` 的计数。样本是当前时钟减回显时钟（`0x6f34b4`）；零或更小的样本丢弃（`0x6f34e0`）。请求按间隔 `[0x46d1528]` 发出，直到每个环满，然后按 `[0x46d1520]` = 500（写于 `0x6f2fcc`，游戏在 `0x1e7c2bc` 也写）。站点事件 0 或 1 清除该站点的记录（vfunc11 `0x6f3bd8`）：新席位没有样本。

GetRtt（`0x6f4498`；带计数 *n* 的 `0x6f44bc`）在无样本时返回 -1，否则返回最近 min(count, *n*) 个样本的中位数；min `0x6f44e4`、max `0x6f4508` 与样本数 `0x6f452c` 在旁。唯一调用者是 SessionTransportAnalyzer 的监控拷贝（`0x6f9ab0`..`0x6f9ad4`）与 `ReliableSlidingWindow` 重传截止 `0x6f0d14`，从发送循环 `0x6f073c` 调用：

    deadline = now + [window+0x80] + 1.4 * (对目标 GetRtt(count) 的最大值)

无样本时，`0x6f0d14` 返回未调度标记 `[window+0x5c]`：消息入队时发一次（`0x6f1bbc`..`0x6f1bd4`），在 `0x6f0a18` 被跳过，直到有样本重新武装（`0x6f09f4`..`0x6f0a08`）。没有 RTT 样本的窗口永不重传。

构造函数 `0x6eeea8`（调用者 `0x6e69f8`、`0x1800038`）把 `[window+0x80]` 设为 `ticks_per_second * 33 / 1000`（`0x6eef34`..`0x6eef74`；633,600 tick，19.2 MHz 下 33.0 ms），标记 `[+0x5c]` 为 0，基序列 `[+0x30]` 为 1，自身索引 `[+0x10]` 为 0xfd，压缩 `[+0xa4]` 为 1，提前发送上限 `[+0x88]`、`[+0x89]` 为 0。之后唯一写入者是 vfunc17 `0x6f1f98` 里的 `0x6f1fc8`（来自 `ReliableProtocol::vfunc17` `0x6eebbc` 与 `BroadcastReliableProtocol::vfunc17` `0x6e6818`，无已知调用者）。发送循环每 16.7 ms 帧跑一次，因此重发在达到或超过 `33 + int(1.4 * RTT)` ms 的第一帧离开：RTT 34 ms 时 83 ms，358 ms 时 550 ms。

### 记录

一条记录是一条带 ZLIB 标志的可靠消息，zlib 流窗口 4 KB（`484b`），解压为 1395 字节，`[window+0x70]`：Pia StreamData 标头下 0x81 传输的一块（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）：

    +0x00  1   StreamData kind：1 为本块首块，2 为后续块
    +0x01  1   传输 id，0
    +0x02  1   本块交付后的块百分比
    +0x03  4   零，kind 0 的容量字段
    +0x07  4   大端 u32 0x00000568，随后 1384 字节

站点的块是 0xF388（62,344）字节：45 个 1384 字节块加一个 64 字节块，id 1 到 46，百分比字节 `floor(k * 1384 * 100 / 62344)`（2、4、6、8、0x0b、…、25 处 0x37、37 处 0x52、46 处 0x64）。首块携带屏幕上显示的搭档：

    +0x0b  4   训练家 ID，然后秘密 ID
    +0x0f  1   版本：50 朱，51 紫
    +0x10  1   性别
    +0x11  1   语言
    +0x12  1   投球风格，1 为原始
    +0x13  26  玩家名，UTF-16 小端，NUL 填充；两个启动器都有 --trainer-name
    +0x2d  22  账号标识符，ASCII，`u-` 加二十个字符
    +0x53  8   剧情进度，小端：1 主线通关，4 靛蓝圆盘通关

块在栈上于 `0xa52f88`..`0xa530a0` 构建：训练家来自存档，然后投球风格来自另一存档块（`0xa53054`），然后账号标识符（`0x1a61a00`），最后是进度字——游戏保存在 `0x473a040` 的脚本函数返回值（在 `0xa5309c` 调用）。原生 `f20A702BD`（`0x877560`）安装它；在 3.0.1 脚本转储里，`BattleNetworkNetReceiver` 传入一个从 0 开始的函数，当 `FSYS_SCENARIO_GAME_CLEAR` 置位时设 1，当 `FSYS_SCENARIO_GAME_CLEAR_SU2` 置位时或入 4。`pokeldn.sv.reference` 发送 1；账号标识符全零的零售紫发送 0。

游戏脚本通过按此顺序注册的原生 getter 读取站点玩家：`PlayerId`、`RomCode`、`Sex`、`LanguageId`、投球风格、`NameStrBuf`（`RegisterPlayerData` 与 3.0.1 脚本转储里的对战设置；投球风格是存档自身 `ballThrowId` 填入的槽）。在零售存档上，ID 对、版本、语言与名字是存档自身捕获宝可梦的那些，与它提供哪只宝可梦无关。为接收玩家制作的赠礼会读取它们（`reference.identity_trainer`，[为接收玩家制作](gift_simulated.md#made-for-the-receiving-player)）。

块 2 到 24 是高熵；25 到 46 为零。站点一次发出整套，通常第一包是 id 1、25、26 到 36 与 46，第二包是 2、37 与 38 到 45，然后 3 到 24 每包一个（48 套零售里有 41 套如此），52 次里有 46 次在 0.19 s 内。相同的零块跟在存在字节 0x00 之后，每个标头字段继承（[消息帧格式](pia.md#message-framing)）。`pokeldn.sv.streams.decompress` 读取它们。

`pokeldn.sv.reference` 附带站点的 44 条记录及其在 0x7C 端口 0 上的两段身份片段，录自模拟朱，玩家为 `Player`，账号标识符未设。`bin/sv_host.py` 与 `bin/sv_join.py` 会发送它们，除非给定 `--record-set`、`--send-on-open` 或 `--no-identity`。

### 零售确认，以及重传洪泛

零售站点用 ack id 为连续段加一、字段 0x50 与之相等、以及掩码（字节 *k* 的位 *b* 表示 id `ack_id + 1 + 8k + b`）来确认对端的记录流：主机持有 id 1 到 4 与 7 到 38 时发送 `0005 0005 feffffff01`。低于对端自身 `lowest_pending` 的 id 视为已持有。`pokeldn.sv.streams.ack_position` 构建它；`bin/sv_join.py --ack-highest` 改为发送所见最高 id 加一。

主机每轮重发每条未确认记录，标志 0x40，最低 id 优先，每包一轮。轮间隔是 `[window+0x80] + 1.4 x RTT` 向上取整到帧：RTT 0.015 s 时 0.065 s，0.36 s 时 0.53 s。小 RTT 下每秒数百条记录，足以填满板子的串行线（[串行上限](hardware_esp32.md#the-serial-ceiling)）。主机的 `lowest_pending` 在整套发出约 0.5 到 1.0 s 后离开 1，与确认延迟无关，因此此前的 RTT 应答会让它重发加入方已持有的记录。`--rtt-delay 0.3` 把 RTT 应答推迟 0.3 s，使轮间隔高于该延迟并止住重发。

`--leave-on-migration N` 在 Session 类型 7 后 N 秒结束席位，`--announce-timeout SECONDS` 离开未公告的席位；两者都会再次扫描。`bin/sv_join.py` 对新记录立即确认，对重复记录每流最多每 50 ms 一次（`--repeat-ack-gap`）。

没有 RTT 样本时，0x81 流永不重传（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）：丢失的记录一直挂起，对端永不被公告。公告任务没有 RTT 门。缺失的身份记录把 BoxTrade 任务停在状态 1（`+0xb8`），`0x1e51ae8` 处的完成槽计数为 1 对 2。两个启动器都会重试挂起的身份记录（[Lowest pending 与 5、6 处的缺口](#lowest-pending-与-5、6-处的缺口)）；`tests/test_sv_identity_loss.py` 覆盖它。

### 捕获中的 A-MSDU 帧

两台控制台都把多个 MSDU 打进一个 A-MSDU 帧。被动捕获必须拆分子帧，否则会丢掉大部分 Pia 包（一次捕获里不拆 313 可读，拆后 3667）。

## LAN 模式

朱 4.0.0 从脚本启动 LAN 模式。选择器 `0x17fde60` 接受模式 1（本地，`0x17fe5c0`）、2（`0x26894f0`）或 3（`0x2689600`，LAN 服务）；模式是全局 `0x475ea40`，由 `0x17fddc0` 从网络任务的 `+0x50` 设置（构造函数 `0x188f488`）。`0x188e998(.., mode)` 创建该任务，并以 1（`0x18871a4`）、2（`0x1de28a4`）与 3（`0x1de6650`）调用。模式 3 的调用者 `0x1de653c` 跑 NetworkUse、InitializeSocket 与 InitializePia，是表 `0x4430500` 里的 Lua 绑定 `f6597D2A6`。

游戏的 Lua（`arc/scriptluabinrelease*.blua.trpak` 里六个块；`be21e654` 是 `main`）从对战菜单到达它。网络对战接待菜单（类 `C6A68AA55EC501641`，状态 `SET_STATE_NETWORK_VS_RECEPTION`，更新 `0.25603`）在选中条目时清除其 LAN 标志，当条目为 1 或 2 且输入测试 `fFCB9D967`（原生 `0xc60480`，输入 vfunc `+0x70`）对 `UI_ZL` 与 `UI_ZR` 都为真时置位。它把该标志作为 `LanMode` 传给匹配参数（`0.25605`：条目 2 时 MatchingType 2，否则 1）。匹配任务 `0.25585` 然后调用 `f9C74F2CA`（MatchingType 1）或 `f671B3A6A`（MatchingType 2），而不是本地的 `f40B78205` 或 `fA775C8D9`；两个 LAN 绑定返回的回调，其工作 `0xa41c8c` 调用 `0x1de653c`。

交换菜单（类 `CCEC7DC2C9A179FC0`，`SET_STATE_NETWORK_TRADE`，`0.25609`）在 `0.25611` 以 MatchingType 0 与 `LanMode` false 构建匹配参数；没有输入会置位。带 StartLan 方法（`FDF107F292AE61465`）的请求运行器 `0.28742` 属于类 `CD876458B95753AFF`，没有 Lua 构造它。

| 在零售朱 4.0.0 上测得（Switch 2 在 Wi-Fi 上） | 结果 |
|---|---|
| Combats en réseau，Combat solo，ZL 与 ZR 在按 A 与是／否时按住 | 搜索开始；控制台留在 Wi-Fi（ping 4/4，重复时 6/6） |
| 同样但不按 ZL 或 ZR | 搜索期间控制台离开 Wi-Fi（ping 0/6） |
| ZL + ZR 搜索期间控制台发出的帧，按 IP 与 MAC 捕获 | 约 4 分钟内无，含 IPv4、IPv6、广播与组播 |

在模拟朱 4.0.0 上，同样的搜索会发起网络连接请求（nifm；无网络时游戏显示错误 11），在 49152 与 35000 打开 UDP 套接字，向子网广播地址的 35000 端口广播一个 317 字节的 browse 请求，然后以主机等待。向它的 35000 发送 browse 请求会得到 620 字节应答，命名主机的 IPv4 地址与 Pia 端口 49152（`c0a8011f`，`0xc000`）。开头那一次广播解释了静默的零售捕获——捕获是在它之后开始的。

| 消息 | 首字节，如捕获；其后布局未读 |
|---|---|
| browse 请求，317 字节 | `00 00000000 0e000000 00000000 01000200 02000f03 01000000 00000000 01` |
| browse 应答，620 字节 | `01 0000022d 00000000 1f01a8c0 007c0a00 15` |

停止搜索会关闭三个套接字并把游戏带回离线模式；网络启动 `0x17fddc0` 会保留运行中的模式，但拆卸 `0x1813740` 先清除 `0x475ea40`，因此交换菜单不会继承 LAN 网络。

Pia 6 把 browse 端口从剑的 30000 改到 35000，并改了两种布局（[LAN 模式](pia.md#lan-mode)）。两台控制台用 ZL + ZR 搜索能否找到彼此尚未测量。

## 链接码

链接码在广告里出现两次；场景 id 仍为 4。用户密码是该码，NUL 填充到十六字节，再与 `e5ab19ed742b6d40885998bf968aa166` 异或——传说 阿尔宙斯在同一游戏密钥下的掩码（[docs/pla.md](pla.md)）。游戏字节在 +0x00 明文携带该码，在 +0x24 以 u32 携带其长度。`pokeldn.sv.build_advertise_data(code=...)` 能逐字节复现零售控制台以 12345678 搜索的结果。

搜索中的控制台只加入通告其码的主机（`bin/sv_host.py --code`）。零售控制台在码下主持时，接受了通告无码的加入方。`bin/sv_join.py --code` 只加入以该码搜索的控制台。

只有搜索中的控制台检查码，且只在它扫描的网络上。其选择器 `0x26e955c`（在加入前从 `0x272d838` 调用）在有码搜索时跳过无密码的网络（`0x26e95f4`），在无码搜索时跳过有密码的网络（`0x26e960c`）。然后它用 FNV-1a 64（素数 `0x100000001b3`，偏移基 `0xcbf29ce484222645` 在 `0x26e96c8` 加载，不是标准基）对游戏字节从 +0x00 到首个 NUL 以及自身的码求哈希，两不相等则跳过该网络（`0x26e972c`）。它既不读密码的值，也不读 +0x24 处的长度。

主机不比较加入方发送的任何内容。LDN 关联使用固定密码，Session 加入请求没有密码字段。Pia 对连接站点的密码检查——Net 0x32 处理器 `0x69ec50` 里的结果 7（`0x69ee5c`、`0x69ee70`）——需要 Net 0x32，而其唯一发送者 `0x69d42c` 受协议 vfunc 48 门控：`LdnProtocol` 里为 0（`0x6a2fac`），`LanProtocol` 里为 1（`0x6ba278`）。加入方一侧，LDN 连接跑 Pia 的网络检查 `0x6a22c4`，其密码比较（`0x6a24a4`）被关掉（`0x6b0d90`）。

已加入的控制台不再检查码。Net 0x50 处理器 `0x69ea3c` 校验系统属性大小（0x5c）、应用数据大小（至多 0x124）以及四个 Pia 身份字段（`0x69d9d8`），把字节拷进网络属性（`0x69d8a4`）并以 Net 0x51 确认；它不比较系统属性或游戏字节的任何字节。在 LDN 上，拷贝落入缓存的广告数据，下一次 `nn::ldn::GetNetworkInfo`（`0x6b30d4`）会覆盖它。游戏只在选择器与 UpdateSessionSetting（`0x26e63b8`，重写自身会话）里读会话的前 0x28 游戏字节；另外两个读取者（`0x268e988`、`0x268e9bc`）只读 +0x28 之后。加入方控制台把其码保留为自身的 Pia 站点密码（加入对象 vfunc `0x274bdb8`，setter `0x6a208c`），仅在它主持时通告。连接交换的端口 2 类型 1 来自 BoxTrade 任务的状态 2（`0x1e51b68`）：kind 1，静态空名 `[0x46d3e30]`，无数据。

## Session 协议

`nn::pia::session::SessionProtocol`（id vfunc `0x6d9f3c` 返回 0x98）与 `JoinMeshJob`、`CreateMeshJob`、`LeaveMeshJob`、`JoinSessionJob` 以及 `SessionPacketReader`/`Writer` 相邻；网状加入与传说 阿尔宙斯相同。Session 消息在包标头携带对端变量 ID，无页脚，因此走单播。加入方在加入请求的源位置 id 里声明其变量 ID；主机在关联后 0.14 s 命名它。

### Session 加入请求

写入器 `0x6d5464`..`0x6d58b0`，主机解析器 `0x6d5aa4`。布局是零售传说 阿尔宙斯的（`docs/pla.md`，The Session join request；`tests/test_pla_session_v11.py` 里 115 字节），由 `pokeldn.ldn.pia6.build_session_join` 构建：

    +0    1    类型 0
    +1    1    协议数，十
    +2    2n   (id, version) 对，从协议管理器列表遍历
    +22   4    随机，xorshift128 由系统 tick 播种（`0x6c70a8`、`0x6c7184`）
    +26   12   源位置 id：u64 常量 ID，两零字节，u16 变量 ID，大端
    +38   1    NAT 映射，两位
    +39   1    私有 IPv6 标志
    +40   32   识别令牌
    +72   1    地址种类，IPv4 为 0（1 则用 18 字节 IPv6 地址替换那六字节）
    +73   4    源 IPv4 地址
    +77   2    源端口，大端
    +79   12   目标位置 id，主机的
    +91   1    玩家数
    +92   1    任务置为 1 的标志
    +93   ..   玩家记录：16 字节 id（两个大端 u64 的 `1` 然后 `0`）、大端 u32
               名长度、kind 字节 (1)、名字

零售加入方的一个玩家名为单个空格。包标头携带目标变量 ID 0，源为加入方的 id；每次重复消息标志 `0x01`（跳过源检查）。主机按序检查：

1. 协议数等于自身的；否则什么都不发。
2. 每个版本等于主机的（`0x6ed1b8`）；否则状态 3，带 id 与主机版本。
3. 目标位置 id 是主机的常量与变量 ID；否则丢弃。
4. 源常量 ID 与地址不是主机的。
5. 已知常量 ID 再次得到状态 1；关闭的会话得状态 5；主机侧监听器可以以状态 4 拒绝。

加入应答（类型 2，43 字节，`0x6d6390`）是阿尔宙斯布局：类型、协议 id、版本、状态、大端 u32、四随机字节、两个位置 id、路由字节 A 与 B、站点索引、加入顺序、站点更新必须到达的序列 ID。加入方以 13 字节类型 6（`0x6d80a4`）应答类型 5 更新：类型、常量 ID、两零字节、已应用序列（`pokeldn.ldn.pia_connect`）。

## 席位，及其上的身份洪泛

零售朱主机在 16 ms 内接受加入请求，发送 41 字节加入应答（状态 1，无路由字节）与无路由的站点更新，并在 0x81 端口 0 上流式发送其身份。不接受加入方确认的主机，会重发每条记录直到席位结束，零售上约每秒 350 条。主机也可能改发 Session 类型 7，把角色交给加入方（[什么决定席位](#什么决定席位)）。

### 让主机把确认算进去的标志

带标志位 5、ZLIB（`[msg+0x29]`，`0x6efc80`）的消息在站点解析前于 `0x6e9984`（`0x69804c`，zlib inflate `0x2801d0`）解压；失败返回 0x2C03（`0x6efd5c`）。标志 0xA0 下的明文批量确认会在那里失败（模拟控制台上 600/600）。零售 0xA0 确认携带解压为 99 字节的 zlib 体（记录的 4 KB 窗口，level-5 sync-flush 帧）。标志 0x00 下同样 99 字节也会被计入：主机每条记录只发一次（每秒 6.3 条，然后没有，对照明文 0xA0 下每秒 115 到 257 条）。两个零售站点都把批量确认标为 0xA0，并发往其 /24 的 LDN 广播；`bin/sv_join.py` 在设置位 5 时压缩体（`--ack-flags`、`--ack-entries`、`--ack-dest-bits`、`--ack-sweep`）。

### 流上的首条记录携带 INITIALIZED

站点的首条记录携带 INITIALIZED，带 START、END 与 ZLIB，标志 0x1F；后续记录 0x17。以 0x17 发送的首条记录永不被确认。主机随后把整套确认到 47（掩码 `feffffffff01`），发送一次其记录，并发出列出两端站点的类型 5 站点更新。

四十字节游戏广告每会话会变：全零，或 +0x21 处非零（见过 `648cf4`、`8170f0` 与 `fb149700`）。用 `--channel 6`、`--player-name RyuPlayer` 与 `--host-player-id 00000000000000010000000000000000` 时，NetworkInfo 与模拟朱主机的一致，除会话 id。席位之上失败的会话会引出重复加入（测得 16 到 57）。

### Lowest pending 与 5、6 处的缺口

站点的 id 5 与 6 从不发送（线上 44 条记录），其余乱序发出（一对的主机：1、2、3、46、4、7、8、19、9、15、10、16…）。每条记录声明 `lowest_pending` 1、destination bits 3、位图 `[2]`、流 id 0。缺口由发送方在同一流上的下一次批量确认关闭，其 `lowest_pending` 从 1 步进到 47；对端随后以空掩码把整套确认到 47。若留在 1，对端应答 `ack_id` 5、掩码 `feffffffff01`，整段会话如此。无缺口的 id 1 到 44 也被接受；没有零售发送方用它们。

发送方可以只把 `lowest_pending` 推进到已确认记录之后。在初始突发后直接推进到 47 可能藏起丢失的身份块：对端确认 47，而 StreamData 块仍不完整，站点永不被公告。

两个 SV 启动器为身份集保留 `reliable5.SendWindow`。对应的批量确认条目释放低于其 `ack_id` 的记录，以及其选择性掩码点名的记录。每 250 ms，未确认记录以其原始序列 ID 与 Pia 消息标志 `0x40` 重发。发出的数据与批量确认标头声明仍挂起的最低记录，或整套完全确认时为 47。这保留了刻意的缺口 5 与 6，同时保留真实丢失。

丢失首条 INITIALIZED 记录会使全部 44 条记录未确认，需整套重试。缺失的中间记录单独重试。

## 游戏自身的协议，来自一对

测自两台互相交换的模拟朱 4.0.0 实例，各自记录发出的每个数据报。交换跑在 Reliable 0x7C 上；广播流只承载身份交换。

### 端口 2：公告、加入与应答

Reliable 0x7C（一个站点）与 BroadcastReliable 0x80（每个站点）的端口 2 承载游戏的会话消息。轮询器 `0x1954978` 读 `[0x475ea70]`（`0x19549e4`）与 `[0x475ea7c]`（`0x1954a54`）进分发器 `0x1954aec`：首字节，类型 1 到 0xD，表 `0x3c68988`。三种类型打开一次交换：

| 时间 | 站点 | 线路 | 类型 | 字节 |
|---|---|---|---|---|
| 0.00 | 主机 | 0x80 端口 2，zlib | 7 | 167 解压：`07b901b905b906010200bc09`，九零字节，`bc8080`，128 零字节，`000000b90183`，主机站点 id，`00` |
| 0.09 | 加入方 | 0x7C 端口 2 | 3 | `03b90200bc09` 与九零字节 |
| 0.15 | 主机 | 0x80 端口 2 | 9 | `09b9030000b90183` 与加入方站点 id |

编码是通道表的（`pokeldn.ldn.channel_table`）加上标签 `0xbc`，字节串：标签、作为整数的长度、字节。类型 7 是一元组，内含五元组（写入器 `0xe464fc`）：

    b9 06 ...   类型 1 体作为六元组：kind、容量、一零字节、九字节字符串的名字、
                128 字节字符串的数据、数据长度
    key         体 +0x8e，步进前中继的计数器 +0x1c4
    index       体 +0x8f，步进前中继的计数器 +0x1c0 掩到七位
    b9 01 ...   一元组 u64，类型 1 发送方的站点 id
    0           体 +0x98

类型 9 是加入的槽 key、结果字节与一元组 u64 的元组。

类型 7 是中继后的类型 1：类型 1 处理器 `0x18ceb70` 无条件拷贝 0x8e 字节体，盖上 key 与 index，步进两个计数器，追加发送方站点 id，并排队给类型 7 组装器（队列 `+0x200`，步长 0xa8）。`0x18d5a58` 向一个站点发送端口 2 消息，目标是自身时经 `0x1954aec` 分发，因此主机中继自身的类型 1。

类型 1 体（`0x18ab760`）：

    +0x00  kind
    +0x01  槽的容量：kind 1 到 3 为 2，kind 4 到 8 与 12 为 4，kind 9 到 11 为 0
    +0x02  零
    +0x03  至多八字符的名字，九字节内 NUL 终止
    +0x0c  至多 128 字节数据
    +0x8c  数据长度

交换的类型 1 是 kind 1、容量 2、空名、无数据。槽把体放在槽 `+0xd0`（构造函数 `0x18b73a0`），因此其 key `0x12fcabc`（槽 `+0x15e`）是体 `+0x8e`。每条中继的类型 1——自身的或对端的——都步进 key；只有 `0x12fbef0` 把计数器清零。命名 key 0 的加入，如 `03b90200bc09` 所做，只匹配计数器清零后的首次公告。

类型 3 处理器 `0x1981e94` 把加入的首字段与槽 key 比较（`0x1981ed4`），接受时排队类型 9（`+0x270`），否则在 `+0x350` 排队类型 0x0D：`0d b9 01` 与一个码：

| 码 | 拒绝原因 |
|---|---|
| 1 | 没有槽有该加入的 key（`0x1981ffc`），或 `0x279c8fc` 拒绝 |
| 2 | 槽已满：`0x18f80c8` 对照 `0x1e64914` 读到的容量，或 `0x279c9a0` 返回 0xfd |
| 3 | 加入名的 FNV-1a 64 哈希与槽的不同（`0x1e648a0`） |
| 4 | 槽已关闭（`0x1e64924`，槽 `+0x160`，创建槽时清除） |

类型 0x0D 进入 `0x1954f3c`，它要求 `0xb9`，解码一元组（`0x279c0e8`）并调用接收者 `0x279c1ac`（`0x1954f78`）：

    0x279c1b8  ldr  x8, [x0, #0xb8]     挂起的请求
    0x279c1bc  cbz  x8, ret             无：什么都不发生
    0x279c1d0  strb w9, [x8, #0x43]     result = 该码
    0x279c1d8  strb #1, [x8, #0x42]     done
    0x279c1dc  bl   0xc8e6c4            唤醒请求在 +0x48 的等待者

它既不检查请求类型 `+0x40`，也不检查 done 字节，因此来自加入方的 0x0D 会以该码完成控制台持有的任何请求。类型 9 接收者 `0x18b65c8` 按槽字节选对象、应用消息，除非 u64 是站点自身 id `[[0x46d0a08]] + 0xb8` 否则丢弃。

站点 id 是作为大端 u64 的 Pia 常量 ID（MAC `02:00:7f:00:00:02` 为 `7f00020000020000`）；对零售控制台，类型 9 携带其 Session 加入请求里的常量 ID。`pokeldn.sv.port2` 构建这三种（钉在 `tests/test_sv.py`）；`bin/sv_host.py --announce` 在席位后发送类型 7，并以类型 9 应答类型 3。

### 发送公告的交换任务

连接交换在 `0x1e2ea54` 创建任务：配置 `BoxTrade`（`0x3aefac8`），工厂 `0x1e2f3d4`，模式 4，需要 2。两个脚本绑定到达它：`0x1e2e9bc`（GOT `0x46d6608`，由 `0x1b9c8c4` 存入 `0x4717068`，尾调用）与 `0x1e2ec84`（GOT `0x46d6610`，`0x1e2ee40` 处 `bl`）。任务（构造函数 `0x1e3bd10`，vtable `0x44568a8`，Update `0x1e51a04`）：结果 `+0x40`，状态 `+0xb8`，会话句柄 `+0xc0`，模式与需要作为 u16 在 `+0xc8` 与 `+0xca`，槽对象 `+0xd0`，请求句柄 `+0xf8`。

| 状态 | 地址 | 做什么 |
|---|---|---|
| 1 | `0x1e51a84` | 若站点计数 `[[0x46d0a08]]+0xe0` 低于 need 则结果 3；若 `0x18ab520` 拒绝模式（0、5、大于 8）则结果 1；否则无超时等待 `need` 个完成的身份块（`0x1e52004` 遍历 `[[job+0xd0]+0x10] - 0x28`），然后主控上状态 2（`0x1639910`：自身 id `+0xb8` 等于主控 id `+0xc0`），客户端上状态 4 |
| 2，主控 | `0x1e51b2c` | kind `0x18ab550(mode)`（模式 1 到 8 给出 2、3、4、1、0、5、5、8），然后请求 `0x18ab658`；null 以结果 8 结束 |
| 3，主控 | `0x1e51ca8` | 无超时等待请求；结果 0 进入状态 6，否则经 `0x1e5086c` 结束任务 |
| 4、5，客户端 | `0x1e51b8c`、`0x1e51c74` | 同样等待，15 s 上限 |

| 结果 | 含义 |
|---|---|
| 1 | 成功，或模式被拒 |
| 2 | 状态 3 中的会话 |
| 3 | 站点少于 need |
| 4 | 客户端 15 s 超时 |
| 8 | 无会话，或请求被拒 |

请求 `0x18ab658` 构建类型 1 体并经 `0x18ab83c` 发送；当中继的挂起请求 `[relay+0xb8]` 的 done 字节 `+0x42` 仍为 0（`0x18ab860`、`0x18ab8e8`）或发送失败时返回 null。否则它清除 `+0xb8`（`0x18ab894`），存入新请求（`0x18ab8a8`；`0x18abec0`：`+0x40` 类型，公告为 0，`+0x42` done，`+0x43` result），并把类型 1 发给主控 id（`0x18d58b8`），主控上是自身；发送失败则清除 `+0xb8`（`0x18ab900`）。

`0x18ab658` 有四个调用者：`0x1e51b68`（BoxTrade 状态 2）、`0x18ab34c`（兄弟任务里同样，vtable `0x4456490`）、`0xa188f0`（vtable `0x4452e68`）与 `0x1d99568`（vtable `0x44536d8`）。只有这四个请求创建者写 `+0xb8`；`0x18ab83c` 与 `0x2799b10` 在有请求挂起时拒绝：

|---|---|---|---|
| `0x18ab83c` | 0，公告 | `0x18ab8a8` | `0x18ab6bc`，在 `0x18ab658` 中 |
| `0x2799b10` | 2，客户端加入 | `0x2799bd8`（守卫 `0x2799b2c`..`0x2799b40`） | `0x1e635fc` |
| `0x2799c44` | | `0x2799cfc` | `0x1e639ec` |
| `0x2799d6c` | | `0x2799e30` | `0x1e63c88` |

后三个调用者各自位于唯一调用者在 `0x1d98xxx` 的函数中（`0x1d986d8`、`0x1d98990`、`0x1d98c20`）。

在连接交换中，类型 2 创建者从 BoxTrade 状态 4 的 `0x1e51c40`，经 `0x1d986d8` 与 `0x1e635fc` 到达。它只在主控的槽已存在后于客户端运行（`0x1d999f4`、`0x18c7a40`），把请求保留在任务 `+0xf8`，并进入状态 5。`0x1d98698` 的其他调用者属于其他任务类。

排空 `0xe44cf0` 按序遍历队列 `+0x1c8`、`+0x200`、`+0x238`、`+0x270`、`+0x2a8`、`+0x2e0`、`+0x318`、`+0x350`；组装器返回 false 会结束本帧排空，因此卡住的类型 7 会把类型 9 与 0x0D 挡在后面。类型 7 组装器 `0xe45740` 在站点计数为 1 时只本地分发；否则询问 `BroadcastReliableProtocol::vfunc20`（`0x6e6638`）0x80 端口 2 能否发送，用 `0x107e060` 发送，仅当两者都成功时才本地分发。vfunc20 在目标列表 `[window+0x40]` 无条目时以 0x2c27 拒绝（`0x6efb98`），窗口放不下分片时以 0x4c0d（`0x6f1ef8`），无会话或窗口时以 0x10408。Pia 在站点加入事件填充目标列表（[窗口发给谁](pia.md#who-a-window-sends-to-pia-6)）。

类型 7 接收者 `0x18b566c` 创建并应用槽，并对挂起的类型 0 请求与控制台自身站点 id（体 `+0x90`）以结果 0 完成它：主控留在状态 3，直到自身的类型 7 已上线。中继与线路之间没有任何东西读 RTT 或定时器。

0x81 身份是每站点一块，在其索引端口上（句柄 `0x475ea48 + 4*index`），由流发送 API `0xe22188` 与接收 API `0xe22458` 为三种同布局对象搬运：

|---|---|---|---|
| `0xe21104`，`0x4455ec0` 槽 13 | `0xe21a44`，`0xe21dc4` 处 `bl`，`0xe21db8` 处 `w2 = 0xf388` | `0xe2150c`、`0xe2170c`，`0xe21708` 处 `w3 = 0xf388` | 0xF388 = 62,344 |
| | `0xa62c5c`，`w2 = 0xff008` | `0xa64ddc`，`w3 = 0xff008` | 0xFF008 = 1,044,488 |
| `0x1e5f87c`，`0x4458698` 槽 13 | `0x1e617a8`、`0x1e61980`，`w2 = 0x97e08` | `0x1e61a74`、`0x1e61c0c`，`w3 = 0x97e08` | 0x97E08 = 622,088 |

交换中只有 0xF388 块上线，因此任务的 `+0xd0` 对象属于该类（实例未追踪；经 `0x1e34b6c` -> `0x1e35e88` 构建）。

`0x1e52004` 计数 `+0xd0 + 0x30*k`（四个）处持有对端指针且字节 `+0xd8` 置位的槽。控制台自身槽在 `0xe21154` 得到它（`0xe21248` 处 `memcpy(slot, [+0x90], 0xf388)`，`0xe21258` 处 `+0xd8 = 1`；从 `0xa536e0`、`0xd6dc88`、`0xe21128`、`0x195160c` 调用）。对端槽在 `0xe212b8`（从 `0xa536f0`、`0xd6dc98`、`0xe21138` 调用）得到它，仅当发往对端（`+0xda`）与从对端接收（`+0xd9`）已开始、自身 0x81 流处于状态 3（`0xe2144c`，自身每块已确认）且对端处于状态 6（`0xe21404`，对端每块已收）时；状态 7 清除一个标志（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）。0x97E08 类有同样的一对，`0x1e60284` 与 `0x1e615e8`。

线上，类型 7 通常在控制台自身整套最后一条记录后 0.11 s 内跟上。

中继是 0x388 字节对象（vtable `0x44e56f8`），单例 `[0x46da9c0]` = `0x4739430`，仅在不存在时由 `0x165a200` 从 `0x1659b70` 创建（`0x1659b18`）。其站点事件处理器是 `0x12fbb90`，经 thunk `0x2b71650`：

| 事件 | 效果 |
|---|---|
| 0，站点加入，在主控上 | `0x12fbf8c` 向它发送当前槽，除非它是主控 |
| 1，自身 id | 未完成的挂起请求以结果 5 完成（`+0x42` 处 `0x501`），然后 `0x12fbef0` |
| 1，主控的 id | `0x12fbef0` |
| 1，任意站点，在主控上 | 然后 `0x12fcebc` 丢掉它中继过的元素 |

`0x12fbef0` 经 `0x12fc644` 移除每个槽（完成 key 匹配的挂起类型 1 请求），清空七个队列（除 `+0x1c8` 外全部）并清零 `+0x1c0` 与 `+0x1c4`；它留下 `+0xb8` 的请求。类型 0 请求只由类型 7 接收者、类型 0x0D 接收者与自身离开事件完成；类型 2 由类型 9 接收者 `0x18b6710`，类型 3 由类型 0xA 接收者 `0x1945404`，类型 4 由类型 0xB 接收者 `0x279be18`。

自身离开路径 `0x12fbc3c..0x12fbc4c` 以结果 5 完成客户端挂起的类型 2 请求（`+0x40..+0x43 = 02 00 01 05`），因此下一个创建者可以替换它。仅针对主控 id 的离开事件只调用 `0x12fbef0`。客户端的 BoxTrade 任务在 15 s 以结果 4 结束（状态 5 的时钟测试 `0x1e51c74`，基 `+0x108`），但其超时路径 `0x1e51d50` 与析构 `0x1e51740` 都不碰中继的请求：它留在 `+0xb8` 挂起，`0x2799b10` 与 `0x18ab83c` 拒绝，直到类型 9、类型 0x0D 或客户端自身离开事件完成它。

中继活到应用退出，因此 `+0xb8` 挂起的请求会跨过每个席位、搜索与菜单，直到有完成者跑。其持有者 `0x4739430`（GOT `0x46da9c0`）只由创建者（`0x165a2b4`）、从中继自身销毁槽到达的重置 `0x279d610`（`0x279d5ac`、`0x2b71660`）以及静态析构 `0xa15f74` 写入。vtable `0x44e56f8`：槽 0 `0x279a7b0`，3 `0x279d5ac`，4 `0x12fbb90`；接口 `+0x28` 是监听器 thunk `0x2b71650`。创建者以 `0xf0ba9c` 把它注册进 `0x4763a18` 的终结器列表，仅在应用 finalize 时遍历（`0x20e9c78`，止于 `nn::account::CloseUser`）。

| 时间 | 站点 | 端口 | 字节 | |
|---|---|---|---|---|

| 1.84 | 加入方 | 1 | 31，INITIALIZED | 同样 31 字节 |
| 2.43 | 加入方 | 2 | 15，INITIALIZED | `03b90200bc09000000000000000000` |
| 9.00 | 主机 | 1 | 11 | `b90101b902b90280800001`，加入方回发相同内容 |

端口 1 是通道表（阿尔宙斯机制）：站点只有在对端已通告某 key 后才在该 key 上发送。加入方的表与主机的逐字节相同；到达之前主机停在搜索画面。主机的 key-0x80 打开必须先到：加入方若在它之前画出交换画面，就永不发送首条游戏消息，对宝可梦按 A 也没有菜单。0x7C 可靠标头是九字节，无位图，序列与 lowest pending 都是消息自身的；打开是标志 0x0F，后续更新 0x07。

较晚的打开会让模拟朱 4.0.0 的交换箱没有选择光标。截止取决于对端：零售控制台在席位后 9.15 s 打开自身 key 0x80 时，对主机在 6.0 s 的打开画出菜单，在 11.0 s 则否。

对 `bin/sv_host.py`，主机的交换流消息编号为 5（提供）、6（确认）、7（提交）、8 到 15（步骤）；控制台的为 5、6、7 与 8 到 11，其 key-0x180 打开与关闭是端口 1 消息 3 与 4；其对主机提供的确认读作 `ack_id` 6、`lowest_pending` 5。两个相同的训练家可以交换。

### 在站点自身提供之前发送的确认

切勿在提供 `80000200` 仍排队时发送确认 `80000300`：零售控制台按该顺序收到会以系统错误崩溃。两个启动器上的 `--offer-after-open` 把提供挂在对端的 key-0x80 通告上，且都不会在同一站点与端口已有排队消息时再排一条交换消息。

交换动画跟在控制台最后一步 `8001010e` 之后，不携带交换消息。在其状态 `b90101b902b90280800100` 之后，控制台直到玩家退出才发送应用数据。

### 同一席位上的多次交换

Key 0x0080 保持打开；key 0x0180 每次交换打开再关闭。第二次交换重复该周期，序列继续（主机提供 16、确认 17、提交 18、步骤 19 到 26），无新关联、Session 交换或身份。`TradeStage` 与 `JoinerTradeStage` 接受记录列表，每次交换一条；`--trade-offer` 可重复。席位能否扛住控制台的主机迁移请求未知。

### 首条游戏消息，以及它携带什么

`80 00 01 00` 与 2557 字节，两个可靠分片，先 START 后 END（一对主机 238 压缩字节，零售控制台 195），各自独立 zlib 流（`484b`）；消息是两次解压的拼接：

    b9 02          两字段的元组
    bc 81 f6 09    blob，0x9f6 = 2550 字节
    ...            2550 字节
    04

blob 是 850 个小端三字节值，多为 1，其余是位掩码（`0x0fffff`、`0x0002ff`、`0x00003f`、0），每站点不同（零售控制台与一对主机之间 38 个条目不同；条目 36：`0x040000` 对 `0x0fffff`）。索引计什么未知。它不携带任何训练家字段：零售控制台的里既无 id 对也无名字。一对主机的四个分片重放后被零售控制台接受。

### 交换消息携带的记录

`80 00 02 00` 消息的 348 字节体是常量 `bc 81 58 01` 与一条 344 字节 Gen-9 队伍记录（PKHeX 的 PK9），在 Gen 8 加密下（`pokeldn/gen8.py`）：自 0x08 起四个 0x50 字节块由 `(EC >> 13) & 31` 置换，LCG `seed = seed * 0x41C64E6D + 0x6073` 扫过 16 位字，以及解密体至 0x148 的 16 位校验和。0x148 处的队伍尾在置换与校验和之外，并从加密常量重新播种 LCG。

    0x000  u32  加密常量，明文
    0x004  u16  sanity，测得每条记录为 0
    0x006  u16  校验和，明文
    0x008       四个 0x50 字节块，加密并置换        -> 0x148
    0x148       等级、一填充字节与六项能力值，加密       -> 0x158

字段图是 PK9 的 [`PKHeX.Core/PKM/PK9.cs`]；`pokeldn/gen9.py` 读写它。

从 344 零字节与 `read` 报告的字段重建的记录会逐字节一致（`tests/test_sv_pokemon.py`）。种类是内部索引，自全国图鉴 917 起与之分离 [`PKHeX.Core/PKM/Util/Conversion/SpeciesConverter.cs:92`]。错误的块顺序能通过校验和；读作连贯宝可梦的记录才能钉住它。`bin/sv_host.py` 打印双方提供，`--offer-out FILE` 写入控制台的（首次之后的提供 N 写到扩展名前带 `-N` 的 `FILE`），`--trade-offer` 接受 344 字节记录（明文或加密）、348 字节体或 352 字节消息。

### 组合的记录

由 `pokemon.build` 从零字节组合的记录，或用 `bin/sv_host.py --offer-set`（昵称、昵称标志、个性值、个体值）编辑的记录，会以组合时的每个摘要字段进入零售朱存档。交换画面绘制组合记录时不做合法性检查；主机写校验和。摘要的训练家 ID 是 `(TID16 | SID16 << 16) % 1000000`（12345 与 54321 显示为 993401，8131 与 64817 为 855043）；特征行来自加密常量与个体值。

等级跟随经验：0x148 字节为 100 而经验为零时到达为等级 1，经验 1,000,000 为等级 100。六条成长曲线（`PKHeX.Core/PKM/Util/Experience.cs`）在等级 100 需要 1,000,000、600,000、1,640,000、1,059,860、800,000 与 1,250,000。种类表 `personal_sv`（每种形态 0x50 字节，`PersonalInfo9SV.cs`）在 0x00 持有基础能力，性别比 0x0C，成长曲线 0x0F，三个特性 0x12（种类 132：曲线 0，特性 7、7、150）。接收游戏重算队伍能力：

    HP    = (2 * base + IV + EV/4) * level / 100 + level + 10
    other = ((2 * base + IV + EV/4) * level / 100 + 5) * nature

完美个体值、无努力值、中性性格的百变怪在等级 1 显示 12 与 6×5，等级 100 显示 237 与 132×5，来自零能力字段；等级 1 发送的 HP 99/99 到达为 12。

### 加入方按序发送什么

一对的加入方在游戏首条消息之前，时间来自一次捕获：

| 时间 | 消息 |
|---|---|
| 0.04 | Session 加入请求 |
| 0.17 | Net 0x12，回显主机 0x11 的序列 |
| 0.38 | Net 0x51，回显主机 0x50 的序列 |
| 1.63 | Session 类型 6，确认站点更新 |
| 1.68 | 十一路批量确认，以及 0x81 端口 0 与 4 上的流打开 |
| 1.68 | 0x7C 端口 1 上的通道表 |
| 1.82 | Clone Clock 0x77，十八零字节；主机应答 1、十六字节、一尾字节 |
| 2.03 | 自身 44 条记录在 0x81 端口 1 |
| 2.43 | 0x7C 端口 2 上的打开 |

无应答时，控制台重复 Net 0x11 与 0x50；0x12 与 0x51 会止住它们（无时席位内 212 条 Net 消息，有时 2 条）。

### 加入方一侧的交换

一对加入方的整段 0x7C 脚本，带每条消息在其端口上的序列：

| 端口 | 序列 | 消息 |
|---|---|---|
| 1 | 1 | 通道表，主机的四个 key，INITIALIZED |
| 2 | 1 | 类型 3 加入，`03b90200bc09` 与九零字节 |
| 0 | 1 到 4 | 首条游戏消息，两遍 |
| 1 | 2 | `b90101b902b90280800001`，key 0x80 打开，在第四分片之后 |
| 0 | 5 | 提供的宝可梦 |
| 0 | 6 | 确认 |
| 0 | 7 | 提交，先发 |
| 1 | 3 | `b90101b902b90280800101`，key 0x0180 打开，在主机自身的之后 |
| 0 | 8 到 11 | 每步 `8001 01 SS` 的回显（03、06、0B、0E）；对 `8001 02 SS` 无 |
| 1 | 4 | `b90101b902b90280800100`，关闭 |

身份在主机 key-0x80 打开后 0.15 s，加入方自身打开再晚 0.21 s。

`lowest_pending` 规则同样约束加入方：0x7C 上是自身下一序列，0x81 批量确认上是最高记录 id 加一。来自主机编号的数字会把主机的接收基推过加入方的后续消息，后者在 `0x6f03cc` 被丢弃。

`pokeldn.sv.trade.JoinerTradeStage` 是这一侧的状态机，由 `bin/sv_join.py --trade-offer` 运行（`--send-on-open` 把身份片段门控在 key-0x80 打开上）。`tests/test_sv.py` 用一对消息的主机半边驱动它，并钉住加入方半边。

### 交换会改写什么

组合记录交换到零售控制台再提供回来时，有 27 字节、七个字段不同：

| 字段 | 发送时 | 回来时 |
|---|---|---|
| `current_handler` | 0 | 1 |
| `ht_name` | 空 | 控制台玩家名 |
| `ht_language` | 0 | 接收控制台的语言（3，法语） |
| `ht_friendship` | 0 | 50 |
| `nickname` | 空 | 控制台语言下的种类名 |
| `current_hp` | 0 | 计算出的最大 HP（237，等级 100 百变怪） |
| `stats` | 零 | 游戏计算的六项 |

其余全部按发送保留。空名回来是种类名，与剑神秘礼物记录一样（`docs/swsh_gift.md`）。

原训练家是接收存档的记录保持处理者 0 且无处理者名，与传说 Z-A 一样（[交换写入接收记录什么](za.md#what-the-trade-writes-into-a-received-record)）。为零售紫训练家制作的神秘礼物宝可梦——来自该存档捕获的宝可梦（[为接收玩家制作](gift_simulated.md#made-for-the-receiving-player)）——从它回来时也如此。

### 加入搜索中的控制台：一次交换，以及什么决定席位

`bin/sv_join.py` 与从连接交换搜索主持的零售朱交换，编号如一对加入方。它把站点更新当作席位，以类型 3 加入应答控制台的公告，在控制台打开 key 0x80 后发送四条身份消息，并应用上述 `lowest_pending` 规则。

#### 什么决定席位

从搜索主持的零售控制台要么跑游戏，要么把主机角色交给加入方。游戏在 3 到 7 次 browse 尝试后主持一次（`RandomMatchingSeq` `0x26e182c`，计数器 `rand%5+4`），并等待成员 3000 + rand%1000 ms，每有一个成员加入再加 5000 ms（WaitMember，`0x26df898`）。超时的等待止于 JoinRandomRecover `0x26f507c`，它经 `LeaveMeshWithHostMigrationJob` 离开会话（[离开](#离开)），把角色交给 Net 排名最低的站点（`0x6a012c`）。在 WaitMember 内接受的加入会看到游戏运行；之后接受的得到类型 7。控制台玩家在公告后退出也会发送它。

交出角色的控制台销毁其网络并再次 browse。`--take-host`（默认）让 `bin/sv_join.py` 在公告前收到类型 7 时，在该席位的信道与码上以应用的主机标志跑 `bin/sv_host.py`，同 `bin/pla_join.py` 对传说 阿尔宙斯所做。

跑游戏时，控制台按序发送：

| | |
|---|---|
| 席位 | 命名加入方变量 ID 及其请求声明的玩家 id 的类型 5 站点更新，然后 41 字节加入应答 |
| 开场 | 全部十一路流上的批量确认，0x81 端口 1 上一条 11 字节记录，端口 5 上另一条 |
| 身份 | 0x81 端口 0 上 46 条记录，并把加入方的 44 确认到 47 |
| 通道表 | 在 0x7C 端口 1，key `0x007b`、`0x0132`、`0x0232`、`0x0332` |
| `0db90101` | 在 0x7C 端口 2，码 1，仅应答公告前发送的类型 3 加入 |
| 公告 | 在 0x80 端口 2，zlib，167 字节解压：类型 7，kind 1、容量 2 与控制台站点 id |

加入方以类型 3 加入应答公告（`--port2-now` 改为与通道表一起发送）。单靠站点更新就是席位：切勿等待加入应答。

## 离开

退出席位的控制台按角色跑两种 Pia 任务之一。各自等待对端，并在定时器上放弃。

已加入的控制台跑 `LeaveMeshJob`。SendLeaveRequest `0x6db590` 发送 Session 类型 3 离开请求（布局见 [docs/pla.md](pla.md#leaving)）并设 500 ms 截止（`0x6db6a0`）；WaitLeaveResponse `0x6db7b0` 到期重发，第四次发送后完成（`[job+0x6c]` 过 2，`0x6db8e8`），或一旦 `[job+0x69]` 置位即完成。Session 分发器（`0x6d4960`，表 `0x3c0cd3b`，类型 0 到 0xA）把类型 4 交给 `0x6d7b10`，对 17 字节消息（字节 5 到 16 是站点自身位置 id）置 `[job+0x69]`：

    04 | u32 随机 | 位置 id (12)，从请求拷贝

主机的类型 3 处理器 `0x6d7894` 在按常量 ID 与变量 ID 找到站点后，正好写出这些（`0x6d7a50` 处类型字节，来自 `0x6c70a8` 的新 xorshift 抽取，在 `0x6d7ad8` 发送）。无应答时，零售控制台大约每隔 0.5 s 发四次离开请求，并在首次后约 2 s 去认证；有应答时，在那一次后 0.04 s。`bin/sv_host.py` 应答第一次（`--no-leave-response` 保持无应答）；`tests/test_sv_departure.py` 在 unicorn 下经 `0x6d7b10` 跑该应答。

从搜索主持的控制台把主机角色交出去。`LeaveMeshWithHostMigrationJob` 向下一主机发送 Session 类型 7，并每秒重发（`0x6df050`），直到类型 8 命名该站点（`0x6ded94`），5 s 后放弃（`0x6defb8`）。类型 7（写入器 `0x6d8de0`）是 34 字节：

    07 | 主机位置 id (12) | 00 | 主机 IPv4、端口 | 下一主机的位置 id (12) | u16

最后的 u16 是任务的 `+0xe0`（`0x6d8ea8`）。然后 `NetDestroyNetworkJob` 以其主机迁移形式，等到每个客户端都收到连接状态更新（最多 4 s，`0x6ac68c`），每 300 ms 发送 NetStartHostMigration `01400000`（仅由 `0x69d310` 写出，仅从 `0x6aca54` 调用）（`0x6aca98`），直到网络站点计数为 1（`0x6acaf4`）或截止过去（4 s，或更新等待超时时 2 s，`0x6ac984`），并销毁 LDN 网络。线上更新是 is-migrating 置位的 Net 0x11；加入方的 Net 0x12 后，首次 NetStartHostMigration 在 45 ms 后跟上。客户端在 NetStartHostMigration 上启动哪个任务未追踪；`NetHostMigrationJob` 以 DisconnectNetwork 或 EmulateDisconnection（`0x6a93c4`）打开。

持有席位的加入方会收到约 4 s 的 NetStartHostMigration。`bin/sv_join.py` 在第一个时离开（`--stay-on-host-migration` 保持席位）。

完成交换后，两个启动器在控制台离开时退出。未完成交换的席位让 `bin/sv_join.py` 恢复扫描（[结束一次运行](architecture.md#ending-a-run)）。
