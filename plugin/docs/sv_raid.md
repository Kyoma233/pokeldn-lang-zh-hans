# 太晶团体战

一场本地太晶团体战是朱／紫会话，最多四个站点，位于 LDN 场景 7。主机管理大厅，然后向每位参与者发送一条引导消息，其中包含四名玩家的宝可梦、Boss 及其 RaidPoint；之后各台主机各自进行战斗。`bin/sv_host.py --raid-seed` 主办一场供零售主机加入的团体战，`bin/sv_join.py --raid-pokemon` 加入一台主机主办的团体战；两者中，程序里的玩家在战斗开始时离开，其宝可梦继续作为控制台的 AI 伙伴战斗。地址是朱 4.0.0 解压后 `main` 中的偏移；紫 4.0.0 在相同偏移处有相同代码（[docs/sv.md](sv.md)）。

## 主办

主机广播场景 7、四名参与者与连接码 4970。控制台从 X、宝可梦传送点、太晶团体战、离线搜索加入。`--raid-seed` 配合四个上下文标志选定团体战（[种子](#the-seed)），`--raid-pokemon` 是我方玩家携带的队伍记录（由 PKHeX 检查），重复的 `--raid-reward ITEM:QUANTITY` 用朱／紫背包可持有的物品行替换种子的奖励（PKHeX 助手的 `bag` 列表：除关键道具外的所有口袋，未发布物品除外）。`--raid-partner TRAINER` 最多对每个控制台空出的槽位使用一次（一台控制台时两个、两台时一个），按槽位顺序安置这些 NPC 伙伴，`--raid-partner-progress STAGE` 选定它们所属的阶段（[伙伴](#partners)）。应用的「太晶团体战（主办）」工具携带下列标志。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

在团体战模式下，主机与交换主机在寻址对象与时机上不同：

| | 团体战主机 |
|---|---|
| 网状寻址消息（RTT、0x80、0x81）、Session 站点列表 | 发往子网广播；经 ldn_mitm 单播，该路径不会把广播带给对端 |
| Net 0x11 | 一个序号，重复直到收到 0x12 |
| 站点列表中的控制台条目 | 控制台加入请求所点名的玩家；使用占位玩家时，控制台已入座但不出现在大厅中 |
| 站点列表 | 每 2 秒重发，直到控制台的 type 6 |
| 开场 | 仅在该 type 6 之后：前十一个批量 ack、同一包中的 0x81 端口 5 打开与一次 RTT 请求；0x81 端口 1 打开、信道表与端口 2 的 type 6；20 ms 后发送身份，每 3 ms 一条记录 |
| 端口 2 的 type 3 | 用两条 type 9 回答：主机站点 code 0，控制台 code 1 |

开场的 0x7C、0x81 端口 5 与 0x80 端口 2 消息每 0.25 秒重发直到被确认，主机发出的每条 ack 都声明该流中最低的未确认序号。

### 多台控制台

`--raid-players N`（1 到 3，应用中的「加入的控制台」）在同一大厅中安置最多三台控制台，各取最低的空闲站点索引。它们共享大厅与开战；从第一回合起，各自与自己的 NPC 伙伴和奖励进行战斗（[哪个站点运行服务器](#which-station-runs-the-server)）。主机为每台控制台保留一套流，在单控制台团体战使用 1 的地方改用该控制台的索引 *k*：

| | 索引 *k* 的控制台 |
|---|---|
| 加入响应 | 站点索引与加入顺序 *k* |
| 站点列表 | 每个已入座站点，我方在前；每次座位变更以下一序号发给每台已入座控制台，重发直到各自的 type 6 |
| Net 0x11 | 我方站点、按索引排列的已入座控制台，然后是加入者 |
| 目标位图 | 三个目标位下的 `1 << k` |
| 批量 ack | 条目 *k* |
| 开场 | 0x81 端口 *k* 与 4 + *k* |
| 端口 2 的 type 6 | 我方与已入座成员，按加入顺序，带 code 与计数 |
| 端口 2 的 type 9 | 我方 code 0，每个已入座成员用其 code，控制台最后用 code *k*；每个已入座成员收到控制台的那条 |
| 引导 | 其宝可梦在槽位 *k*；空闲座位为空槽 |

若加入时座位已满，或开战之后才加入，则不予应答。主机丢弃报头与页脚未点名其 variable id 的每个包，以及位图中缺少站点 0 的每条可靠消息，因为同一大厅中的控制台通过同一广播互相寻址。

端口 2 的槽位在槽位 `+0x170` 以 u8 code 与 u64 站点 id 保存成员；`0x138d208` 返回站点的 code，非成员为 0xfd。主机的 type-3 处理程序 `0x1981e94` 取 0 到 7 中最低且无成员持有、也无排队 type 9 点名的 code（`0x279c9a0`），然后为每个成员广播一条 type 9，并为加入者再广播一条。接收方 `0x18b68fc` 追加尚未列出的 `(code, id)`，且从不更改已列出的 code。type 6（`0x12fbf8c`，组装器 `0xe457cc`）在 `+0xa0` 携带成员 id、`+0xc0` 携带 code、`+0xc4` 为计数、`+0xc5` 为关闭字节；其接收方 `0x279b9c4` 为每个成员重放一条 type 9。Lua 大厅（chunk `be21e654`，接收方 `0.15829`；`0.N` 是主函数的原型 N）按发送方的 code 归档每条消息，无 code 时为 253。进入大厅的控制台发送状态 0x18 及其宝可梦；收到 0x18 的站点以其 Ready 状态与宝可梦作答。

可靠报头的接收检查（`0x6f0410`..`0x6f0430`）对任意目标计数 1 到 23，测试接收方位 `index & 31`（字 `index >> 5`）；零售发送方写入三，即站点容量 4（`0x44dfcb0`）减一（`0x6e71c4`）。

主机把网络交给仍在线上的最低索引。其他控制台仅在下一主机的 type 8 之后才收到 is-migrating 的 Net 0x11（对每个已入座站点排序），然后在每台控制台都回答 0x12 后发送 NetStartHostMigration，且无 Session type 7。使控制台保持在同一战斗中的条件：

| 条件 | 代码 |
|---|---|
| 一台控制台看到另一台离开时，仅在迁移中才保留它：`[net+0x249]` 由 is-migrating 的 0x11 设置，或 `[net+0x1c0]` 由 NetStartHostMigration 设置 | 站点离开处理程序 `0x69d08c`、`0x69d174` |
| 带有更新序号的 Net 0x11 丢弃每个标为已离开的站点 | `0x69e008`、`0x6b5074` |
| 下一主机最多等待 8000 ms 让每个 Net 站点到达状态 2，丢弃其余，发送 Net 0x11，等待每个 0x12 并发送 Session type 5 | NetHostMigrationJob `0x6a9cd4`、`0x6aa2a8`；`0x6d44f0` |
| 另一台控制台等待该 type 5 最多 10000 ms，然后失败 | `0x6dc024`、`0x6dc124` |
| type 7 的最后 u16 至多为下一主机已应用的列表序号 | `0x6d9164` |

Pia 主机在每次 LDN 参与者变化时向每个站点发送 Net 0x11（`0x69c310`，`0x69c79c` 递增 `[NetProtocol+0x60]`，按升序 IPv4 排名 `0x6a05ec`）。在 LDN 上，加入者的 0x11 接收方 `0x69db14` 不创建站点（`0x6a2fac` 返回 0）；其站点来自 `nn::ldn::GetNetworkInfo`（`0x6b43a8`），端口 12345。type-5 接收方 `0x6d7f8c` 仅当其地址在该节点列表中（`0x6a8320`）时才创建列出的站点（`0x6d840c`）；否则不发送 type 6，并将其已应用序号重置为 0xffff（`0x6d81a4`）。Session type 9（`0x6d4ef0`），`09 | constant id | count | constant ids`，每 3000 ms 点名加入者尚未听说过的站点（`0x6d4a60`）；主机的接收方 `0x6d940c` 把单个被点名的站点交给踢出任务（`0x6dc878`）。

控制台加入后，团体战主机发送 packet id 0：已入座控制台会丢弃更高 id 之后的内容（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）。站点列表中的玩家 id 是匿名的 `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）；随机 id 不会引出 type 6。

## 大厅

团体战消息是 0x80 端口 0 上的游戏消息（[交换](sv.md#the-trade)）：

| 字节 | 字段 |
|---|---|
| 0 | 处理程序键，u16 |
| 2 | kind、step：一个 u16 消息 id（0x012f 为引导，0x0193 为战斗开始） |
| 4 | 每发送方计数器，u16，由 `0xa583fc` 递增 |
| 6 | 压缩，u32：0 无，2 LZ4 |
| 10 | 载荷明文大小，u32 |
| 14 | 网络对象 id，u16，除非 `0x14ede48` 找到一个，否则为零 |
| 16 | 构造函数从不写入的两个填充字节 |
| 18 | 载荷 |

| 键 | kind | 内容 |
|---|---|---|
| 0x3380 | 0x2c | 团体战描述符：物种（DevID）、形态、星级、太晶属性、性别、遭遇记录编号 |
| 0x3380 | 0x2d | 参与者状态：0x00 未就绪，0x01 就绪，0x0c 主机开战，0x0d 访客应答，0x18 进入大厅，0x1e 主机拒绝迟到站点（`0.30822`） |
| 0x3380 | 0x2e | 参与者的宝可梦，其加密的 344 字节队伍记录 |
| 0x3380 | 0x2f | 战斗引导 |
| 0x3380 | 0x30 | 大厅计时器，剩余秒数 |
| 0x0132 | 0x6e、0x73 | 控制台正在加载战斗，然后已加载 |
| 0x3480 | 0x93 | 战斗开始 |
| 0x007b | 0x13 | 主机在 0x3480 之后发送的战斗开始消息 |

接收路径 `0x18bec54` 将报头复制到消息对象 `+0x40..+0x4f` 且不比较其中任何内容；它忽略 LZ4 返回值，仅将明文大小用作输出容量。

键 0x007b 上的战斗开始帧是 12 字节端口地址（三个 u32）、一个 u32 长度以及载荷；载荷前 32 字节是由 `0x1227714` 复制的报头：u32 类型 0x00、u64 0x08 与 0x10、u8 0x18 与 0x19，填充在 0x04 与 0x1a..0x1f。没有读取方比较填充（`0xf5a2fc`、`0xe10088`、`0xe0fd68`、`0xe106a4`、`0xf5a810`、`0xf5bc10`；18 字节报头的最后两个字节由 `0x18bece4` 存于 `+0x4e`，仅由序列化器 `0x290b150`、`0x14c7904` 读取）。一台零售朱访客在消息 15 与 16 的字节 0x1a..0x1f 以及 18 字节报头最后两字节清零的情况下开战并获胜。`0x14ab234` 除非接收方端口已注册其地址，否则丢弃帧：消息 15 寻址为 (0x2713, 1, 2)，消息 16 到 20 为 (0x2713, 3, 5)；0x2713 是设置中的 u32 `+0x2c`。

战斗通过 `0xe0fd68` 读取消息 16（类型 0x46）：当 +0x08 处的 u64 为零时按类型切换（`0xe10088`），`0x2897afc` 设置每帧更新 `0x289358c` 的对象的 `+0x71`（由 `0xfa4bb4` 用 `0x28950c8` 构建，存于 `[sm+0x148]`）。当 `+0x71` 为 0 时，更新泵送读取器（`0xe0f014`）并调用 `0xfc363c([+0x48], 0)`；为 1 时每帧调用 `0xfc363c([+0x48], 1)` 直到其返回 true（`0x28935b8` 清除它）。

团体战主机在 0x7C 端口 1 上宣布的信道表持有六个键：连接交换的四个（`0x007b`、`0x0132`、`0x0232`、`0x0332`）以及 `0x3380`、`0x3480`。零售访客先宣布四个，0.79 秒后再宣布团体战的两个。端口 2 携带主机的 type 6：kind 5、容量 4 下的 type 7 会话块，然后四个槽位，主机站点 id 在前（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` 按顺序向一台控制台释放主机消息，每条都在控制台的上一步之后；`RaidGroup` 持有同一大厅中各控制台共享的内容：

| 序号 | 消息 | 由……释放 |
|---|---|---|
| 1 | 描述符（zlib，INITIALIZED） | 控制台的大厅宝可梦（0x2e） |
| 2、3 | 状态 0x18、我方宝可梦 | |
| | 计时器，每次下降时 | 从第一台控制台应答后 0.73 秒起每秒一步 |
| | 状态 0x01 | 3.19 秒 |
| | 状态 0x0c，开战 | 一旦 `--raid-players` 台控制台已入座且都发送了 0x01，或计时器到 0 |
| | Net 0x50，属性状态 7 | 控制台的 0x0d |
| | Session 站点列表，下一序号 | 控制台的 Net 0x51 |
| | 引导，两个分片 | 控制台的 type 6 |
| | 已加载，`0x320173` | 控制台的 0x6e 或 0x73 |
| | 战斗开始，`0x803493` | 控制台的 0x73 |
| | 六条战斗开始消息 | 控制台的 0x93；然后 0、0.10、0.12、0.16、0.18 秒 |

零售主机打开 180 秒大厅并每秒发送一次计时器（`0.27104`）；pokeldn 主机的计时器在第一台控制台应答时从 180 开始。控制台的 0x00 或 0x18 会撤回其 0x01。访客立即以 0x0d 回答 0x0c，不做 Ready 检查，且只有主机开启战斗（`Raid_Start_Ready`，`0.27137`）。在主机上，`Raid_Start_Ready` 仅在每位访客都就绪时启用开战项；计时器到 0 时，若无就绪成员则解散大厅，否则开战。`Raid_Start_Go`（`0.27140`）重发 0x0c 直到每个成员回答 0x0d，然后发送引导，槽位 *k* 为 code *k* 成员的宝可梦。

门控消息在其里程碑后 50 ms 发出；Net 0x50 与站点列表每 0.5 秒重发直到被应答，团体战消息每 0.5 秒重发直到被确认。Net 0x50 是交换主机的属性体，序号 1，字节 27 设为 7，+38 处有 132 个应用字节，在标志 0x31 下 zlib 压缩；未压缩则不会引出 0x51。

最后一台控制台的消息 20 之后五秒，主机像离开中的零售主机一样把网络交给该控制台（[docs/sv.md](sv.md#leaving)）：每秒 Session type 7 直到 type 8，每 0.5 秒 is-migrating 的 Net 0x11 直到 0x12，每 0.3 秒 NetStartHostMigration 最多 4 秒。切勿改为销毁网络：零售控制台可能在战斗开场显示 2318-0006。

## 战斗引导

消息 0x2f 携带 0xaa0 字节记录，LZ4 压缩（块格式，`pokeldn.sv.lz4`）：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000 | 4 x 0x158 | 四名参与者的队伍记录，已加密，主机在槽位 0 |
| 0x560 | 0x158 | Boss 的队伍记录 |
| 0x6b8 | 0x3e8 | RaidPoint |

序列化器 `0xe327fc` 从消息对象 `+0x440`..`+0x458` 与 `+0x50`（`0xe329b4`）写入五条记录，然后从 `+0x58` 写入四个四字，从 `+0x78` 写入 0x3c8 字节；`0x1592b7c` 选择压缩，`0x71d940` 运行 LZ4。RaidPoint 被整块复制（`0x1bae670` -> `0x1bae760`，getter `0x1baff98`）。零售主机在 1395 字节处拆分消息。

空参与者槽位持有等级 1 的物种 0，昵称 `Egg`，太晶属性 19，语言 2，当前 HP 11，能力值 11/5/5/5/5/5。切勿发送全零空槽：零售控制台会在战斗开始时崩溃。

| RaidPoint 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000 | 24 | 名称，ASCII，`RaidPoint_` 与后缀（`RaidPoint_POKELDN_0` 可被接受） |
| 0x018 | u32 | 0x40 |
| 0x020 | 4 x u32 | 星级、结晶（0 标准，1 黑色，[2 与 3 为活动](#event-raids)）、`captureRate`、`captureLv` |
| 0x030 | 7 x u32 | `raidTimeData`：active、`gameLimit`、`clientLimit`、`commandLimit`、`pokeReviveTime`、`aiIntervalTime`、`aiIntervalRand` |
| 0x04c | 37 x u32 | Boss 的行动配置（`bossDesc`）：HP 系数、护盾的九个值、六个额外行动（行动、时机、值、招式）、双重行动的三个值 |
| 0x0e4 | 45 x 16 | 奖励行：物品、数量、稀有物品标志、主体 |
| 0x3b4 | u8 | 零售标准点中为 0，黑色点中为 1 |
| 0x3b8 | 7 x u32 | 星级、物种（DevID）、形态、性别、等级、0、太晶属性 |
| 0x3d8 | u64 | `randSeed`，伙伴种子（[伙伴](#partners)）与战斗种子（[战斗的随机数](#the-battles-random-numbers)） |
| 0x3e0 | u32 | `raidNpcGroupID`，主机的团体战解锁阶段（[伙伴](#partners)） |

六星记录的 `raidTimeData` 为 active，`gameLimit` 450、`commandLimit` 60；一星记录为 inactive，`gameLimit` 300，其余为零。在 inactive 时，计时器初始化器 `C2D7F486425487755.F0C64BA9B6853E61A` 使用游戏限制 300、命令限制 60、复活时间 30、AI 间隔 17 与随机性 6。行动为 0 无、1 重置 Boss 的能力变化、2 重置玩家的、3 招式、4 抽空太晶珠；时机为 0 无、1 时间、2 HP；值为触发它的 HP 或时间份额。P 百分比的 HP 触发在整数除法下 100 × Boss 的 HP / 其 HP 池 ≤ P 时触发一次：在 816 HP 中的 414 时，50% 行动触发。一至六星的 HP 系数为 500、500、800、1200、2000 与 2500。

零售点的奖励行是种子的固定行（主体 = 表的 `SubjectType`：0 每位玩家，1 主机，2 访客，3 一次），其抽奖在主体 0 下，再三次抽奖在主体 4 下，以及主体 5 下 Boss 的太晶碎块，数量为 `RaidGemItemRewardBoost` 的计数（一至七星为 0、0、2、5、10、12、0）且为正时。奖励界面先列出稀有物品行。

Lua 奖励过滤器 `C07C34FC3B976E5A7.F316609DEA110601D` 对所有人保留主体 0，对主机保留 1，对访客保留 2，在一次性资格下保留 3，保留前 N 行主体 4（N 为匹配 Boss 太晶属性的最高活跃团体战之力等级，用餐种类 5；属性 18 匹配全部），以及玩家持有闪闪护符（物品 2481）时保留主体 5。活跃用餐之力为 u32 种类、u32 属性、u32 等级与剩余秒数的 f32（食用时为 1800）。两个函数都在 Lua chunk `be21e65463b9a98f` 中，SHA-256 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`。

`raid_point` 以同样方式构建行；对种子 7B741233 与 09F3E337，其 45 行等于零售点的字节。选定奖励（`--raid-reward`）放在主体 0 下，无奖励加成行。

## 伙伴

每台控制台用相同的 NPC 训练家填满无大厅成员占据的参与者槽位，从两个 RaidPoint 字抽取：`randSeed`（0x3d8 处 u64）与 `raidNpcGroupID`（0x3e0 处 u32）（`0.4453`；getter `0x1be5ac0`、`0x1be5c20`）。零售主机在每次开战时抽取新的 `randSeed`（`Raid_Start_Go`，`0.27140`）。该 u64 以 `0x82A2B175229D6A5B` 为第二字播种 xoroshiro128+（`0x17ebec0`）。抽取三名训练家（`0.7804`），每次对池中仍剩的 n 做 `next_int(n)`（掩码到 n − 1 的位宽，当 ≥ n 时重抽）并移除。空槽按槽位顺序取抽取结果（`0.4455`）。

伙伴的记录从同一 `randSeed` 再取五次抽取，由一场战斗的每位伙伴共享（`raid_partners.identity`）：加密常量（在 0xffffffff 时重抽）、TID | SID << 16、PID（闪光时翻转第 28 位）、身高与体重，各为 0x30 + next_int(0xa0)。其余来自训练家条目，语言 2，物种基础亲密度。绑定 `f92C18AA6`（`0x1905a10`）构建以 `randSeed` 播种的 pml InitialSpec（`0x1905ce0`，转换器 `0x160ffd0`，创建 `0xdef2b8`，抽取顺序 `0xdf011c`）；其第三参数使随机体型为 M 级（SizeType 3，`0x1611cc4`）。`sex` 为 0 的条目在物种雌性百分比至少 15 时为雌性，否则为雄性（`0x1611d1c`）。`gemType` 为 0 时从键为 species × 10000 + form 的表 `0xe78418` 取太晶属性。

池为 `world/data/raid/raid_trainer_01`（16 行，阶段 0 与 1）、`_02`（18，阶段 2）与 `_03`（18，阶段 3 与 4），字段 `difficulty_0`*N+1*（`0.7797`）。一行持有训练家 id `raid_assist_NPC_*`、`npcPresetIndex` 与 `nameTextLabel`；训练家的宝可梦是其 `trdata_array` 条目的 `poke1`：特性槽 1、2 或隐藏，三个招式，`gemType`，个体值 31/10/31/31/10/31，努力值 252 HP、128 防御、128 特防，勤奋，精灵球，体型 128，无持有物。`scripts/gen_sv_partner_data.py` 将它们解码到 `pokeldn/sv/data/raid_partners.json`。伙伴等级为 int(0.8 × 战斗槽位 0 宝可梦的等级)，即主机的（`0.4455`、`0.4901`）。阶段 5 给出以 Boss 命名的皮卡丘伙伴并崩溃，因此 `raid_point` 拒绝超过 4 的阶段。

## 种子

一场团体战由 32 位种子与控制台状态抽取：版本、地区（帕底亚、菊草叶、蓝莓，表前缀 `""`、`su1_`、`su2_`）、剧情进度与结晶。xoroshiro128+ 从种子与常量 `0x82A2B175229D6A5B`（`0xe29340`）开始；其第一次抽取（一百个值）按剧情阶段边界选定标准结晶的星级（黑色结晶为六星），第二次按该星级与版本内的概率选定遭遇。`0xe29404` 用 `%sdifficulty_%02d` 构建表名，并将记录传给读取其 `raidEnemyInfo` 的 `0x1eab5e4`；`0x2935b68` 遍历全部三个前缀与六个等级。再用同一种子新建 xoroshiro，然后抽取 Boss：EC（种子低半部加 `0x229D6A5B`，因此 Boss 记录可还原其种子）、假训练家 id、PID、完美个体值、个体值、特性、性别、性格（毒电婴灵从其形态列表）、身高、体重与体型，与 PKHeX 的 `Encounter9RNG.GenerateData` 相同；太晶属性与奖励抽奖各另起一个新生成器。

`pokeldn.sv.raid_encounter` 基于 `pokeldn/sv/data/raid_base.json` 实现，该文件由 `scripts/gen_sv_raid_data.py` 从 Tera-Finder 的遭遇列表与奖励表、PKHeX 的种族表以及游戏 RomFS 的十八张 `raid_enemy_XX_array` 表构建（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，带各自 `.bfbs` 架构的 FlatBuffers）。在每种上下文中超过 12600 个种子上，其 Boss 与 PKHeX.Core 26.8.26 逐字段相等，包括六场帕底亚遭遇（记录 5094 到 5099），其零售表给出太晶规则 0（物种自身属性），而 PKHeX 记为规则 1（任意属性）。结晶构建器 `0xe26ff0` 读取 `gemType`，对 0 与 1 都从 18 种中抽取任意一种（`0xe27414` 处 `cmp w9, #2`，重抽直到值小于 18），与 PKHeX 一致；通用转换器 `0x160e108` 将 0 视为物种属性，但不在团体战路径上。由种子 `BD13FB43`（紫，帕底亚，四星）构建的 Boss 记录与零售引导字节对字节相等；由 `7B741233`（朱，帕底亚，五星）构建的与法语零售朱相等，仅昵称与语言不同：零售主机写入自身语言及该语言的物种名（`Embrylex`，3），生成器为英语（2）。无论哪种情况，控制台都以自身语言的名称显示 Boss。

团体战表中的物种是游戏的 DevID：到 916 为止为全国图鉴编号，从 917 起为游戏自有顺序（小锻匠 957 为 1000），即 `gen9.internal_index`。描述符与 RaidPoint 也携带 DevID：向零售朱展示物种 1000 的描述符与 RaidPoint 时，它列出并战斗小锻匠。
黑色结晶记录持有战斗等级 90 与努力值（例如 128 防御与 128 特防）以及捕获等级 75；标准记录的两个等级一致且努力值为零。引导的 Boss 记录与 RaidPoint 摘要携带战斗等级与努力值，RaidPoint 的 `+0x2c` 为捕获等级：由 `09F3E337`（朱，帕底亚）构建的黑色 Boss 与法语零售朱相等，仅昵称与语言不同。

## 活动团体战

宝可梦传送点新闻投递持有 `raid_enemy_array`、`fixed_reward_item_array`、`lottery_reward_item_array`、`raid_priority_array`（与基础表布局相同的 FlatBuffers）以及 `event_raid_identifier`（等于优先级表 `VersionNo` 的 u32）。后续投递在补丁后缀下重复每个文件（`_1_3_0`、`_2_0_0`、`_3_0_0`）；读取最新者。记录增加 `RomVer`（0 两者，1 朱，2 紫）、`DeliveryGroupID`、`Difficulty`（七星为 7）、`CaptureRate`（0 永不，1，2 每个存档一次）及其自身奖励表；其 `BossPokePara` 固定：

| 字段 | 活动记录 |
|---|---|
| `Sex` | 0 抽取；1 雄性，2 雌性，不抽取 |
| `Seikaku` | 0 抽取；性格加 1，不抽取 |
| `TalentType` | 1：`TalentVnum` 完美个体值；2：`TalentValue` 的六个个体值，不抽取 |
| `RareType` | 0 抽取；1 永不闪光（翻转第 28 位）；2 总是：PID 高半部改写为异色异或 0 |
| `ScaleType` | 0 两次抽取；1 到 5 各在 0-15、16-47、48-207、208-239、240-255 中抽一次；6 `ScaleValue` |
| `Item`、`EffortValue` | Boss 的持有物与战斗努力值 |

`TimeDesc` 是记录的 `raidTimeData`（RaidPoint 0x030）：每个七星记录为 active（`gameLimit` 450 到 900，`commandLimit` 60），以及五个五星记录。

巢穴属于投递组 1 到 10。从种子起的 xoroshiro 抽取并丢弃标准星级掷骰，然后在该组、控制台版本与允许星级的记录总概率下取一个值，并取跨度包含该值的记录 [PKHeX `EncounterDist9.GetIsPossibleSlot`]：

| 进度 | 阶段 | 抽取的星级 |
|---|---|---|
| 开局，太晶团体战 | 0 | 1、2 |
| 三星 | 1 | 1 到 3 |
| 四星 | 2 | 1 到 4 |
| 五星、六星 | 3 | 3 到 7 |

概率为 0 的记录永不被抽取。奖励为记录的固定表，然后从投递表抽奖（七星按六星计数）。空或数量为 0 的抽奖槽不给予任何东西；垒磊石的第一轮朱只有此类槽。

`pokeldn.sv.raid_event` 读取投递文件夹（[EventsGallery](https://github.com/projectpokemon/EventsGallery) 活动或其 `Files`）：

    ./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
        --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
        --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]

RaidPoint 携带记录的捕获率，结晶为活动时 2、七星活动时 3（Tera-Finder `RaidContent`）。应用的「太晶团体战（主办）」工具下载图库，并将版本、进度与结晶收窄到该活动会生成的内容（[团体战活动](gui.md#raid-events)，`raid_event.dens`）。

捕获率为 2 表示每个存档捕捉一次。存档列出已捕捉的记录编号（块 `0x8B14392F`；击败标志 `0xA4BA4848`，PKHeX `RaidSevenStar9`），重跑共享编号，因此一次捕捉关闭每一轮。控制台按大厅描述符的记录编号检查该列表；已列出的编号无论 RaidPoint 携带何种捕获率都会阻止捕捉。`--raid-catch-normal` 将一次性捕捉记录作为普通捕捉提供：捕获率 1，描述符中用替身记录编号，即记录日期加后缀 99（`raid_event.stand_in`），无投递使用且捕捉后存档不列出。没有 PK9 字段或 PKHeX 遭遇持有该记录编号，因此合法性不依赖它；主机发送的 Boss 在 331 场一次性捕捉团体战上等于 PKHeX 对该团体战的捕捉。七星捕捉仅在有最强之证时合法，由控制台给予。

固定行的主体 3（七星招式学习器与特性补丁）由每台控制台的奖励过滤器应用。团体战 Boss 之外的物种数据来自 `pokeldn/sv/data/species.json`（`scripts/gen_sv_species_data.py`）。在 EventsGallery 的 153 次投递上，pkNX 的遭遇等于 PKHeX.Core 26.8.26 的，20 080 个生成的 Boss 等于 PKHeX 的 `GenerateSeed32`，且 `scripts/check_sv_raid_events.py` 与每份 `Encounters.txt` 一致。

## 查找种子

应用的团体战种子字段显示该种子在工具上下文中给出的 Boss 与奖励，而「查找团体战」从第一个种子（键入或随机选取）起，在过滤器留下的每种上下文中搜索种子（`pokeldn.sv.raid_search`），按物种、星级、太晶属性、性格、性别、闪光、体型之证与个体值范围。它按 Boss 能力值分数（HP 乘以防御之和、仅防御、较强攻击项或其总和）或按想要的奖励（下方「最想要的奖励」）对结果排名。除非选定物种，否则每个物种只保留一个结果。

### 体型之证

PKHeX 在体型 0 时允许迷你之证、在体型 255 时允许巨大之证（`MarkRules`）；查找器的体型之证过滤器要其中任一。体型在身高与体重之后抽取：

| 体型规则 | 体型 | 得到 0 或 255 的概率 |
|---|---|---|
| 两次抽取（规则 0），每个标准与黑色 Boss | `next_int(0x81) + next_int(0x80)` | 各为 1/16512 |
| 活动区间从 0（规则 1）或从 240（规则 5） | `next_int(16) + low` | 触及的一端为 1/16 |
| 活动自有值（规则 6） | 记录的 `scale` | 总是或永不 |

`raid_search.size_marks` 点名活动 Boss 可取得的之证；查找器将其余变灰。

### 想要的奖励

奖励区段要的是物品行与团体战必须至少给出的该物品数量，同一物品数量相加。提供的物品与数量是被搜索团体战能给出的（`raid_search.reward_choices`）。搜索跳过无法给出所要内容的遭遇，然后在 Boss 之前抽取种子的奖励。

最想要的奖励按想要物品的顺序对结果排名。团体战某物品的总量计为一位数字，其位次在被搜索团体战能给出的总量之中（`raid_search.ranked_rewards`）；靠前物品的数字组成一个小于 2^31 的分数，与种子一起保存在 64 位排名中。五个物品可装入每个已知团体战。

### 助手的扫描

PKHeX 助手在每个核心上扫描种子（`services/pkhex/RaidScan.cs`，由 `pokeldn.sv.raid_scan` 驱动）：遭遇、Boss 直到体型、分数、过滤器与奖励。它点名某上下文的最佳种子，`search` 在 Python 中重建其团体战，因此结果与平局是 Python 扫描的（`tests/test_sv_raid.py` 比较两者）。每个遭遇行的最佳可能排名在每次请求中计算一次，其行无法击败已保留排名的种子在此停止。

一次请求持有 16 777 216 个种子，然后是助手在约 0.25 秒内扫描的数量，最多 268 435 456。一次搜索每个上下文最多覆盖 2^32 个种子（`most_seeds`）；查找器提供一亿，或全部种子。在首次匹配处停止（`stop_at_first`）返回最早匹配的种子。没有助手时，Python 每秒扫描约 22 000 个种子，查找器提供 100 000。

| 搜索，Apple M4，助手已热身 | 时间 |
|---|---|
| 42 种上下文各 100 000 000 个种子，查找器默认 | 5.2 秒 |
| 一种上下文的全部种子 | 6.1 秒 |
| 42 种上下文的全部种子 | 4 分 3 秒 |

## 控制台之间的战斗

在两台模拟的朱 4.0.0 之间测量，一台主办四星结晶，一台从宝可梦传送点加入，空闲座位上有两名 NPC 伙伴。主办控制台在整场战斗中留在会话内。每条战斗消息都是键 0x007b 上寻址为 (0x2713, x, y) 的战斗开始帧，其 32 字节报头的类型在 +0x00，u64 步计数器在 +0x08，u64 回合在 +0x10，然后是 5 与 +0x18、+0x19 处的战斗者或站点字节：

| 类型 | 来自 | 大小 | 内容 |
|---|---|---|---|
| 0x01、0x05、0x11、0x15、0x25、0x29、0x47、0x49 | 主机，地址 (0x2713, 1, 2) | 50 到 20626 | 一步；每位访客在相同计数器下以类型 + 1 作答 |
| 0x02、0x12、0x16、0x26、0x2a、0x48、0x4a | 每个站点，地址 (0x2713, 3, 5) 或 (0x2713, 2, 2) | 50 | 对一步的应答 |
| 0x06 | 站点为其自身战斗者；主机为其自身、每个 NPC 的以及再次为访客的 | 250 | 一名战斗者的命令；+0x19 为战斗者槽位（0 主机，2 访客，3 与 4 为 NPC） |
| 0x15 | 主机，每个行动中的战斗者一条，含 Boss | 20626 | 回合：+0x20 处五个 0x70 字节行动块（槽位 0 主机、1 Boss、2 访客、3 与 4 NPC），+0x250 处每槽一位字节计其块中的行动（[行动](#actions)），+0x258 处服务器命令队列长度，从 +0x25c 起为队列；压缩后 123 到 802 字节 |
| 0x46 | 主机，开战时 62 次 | 54 | |
| 0x51 | 主机 | 86 | |

战斗分服务器与客户端。主机的构建器 `0x113c8a0`（`0x113c908` 处类型 0x15）复制行动块，运行回合（`0x113e3d0`）并追加它产生的服务器命令队列；主机的 AI 生成 NPC 的命令，Boss 的行动仅在 0x15 内到达访客。访客播放队列，对类型 0x13、0x15、0x17、0x19、0x1f、0x23、0x25 与 0x4d，它用同一构建器从主机的行动块重建正文并比较大小与字节（`0xf5cfa4`）；不匹配则转到 `0xf5bfd4`，即接收超时处理程序。主办战斗的站点必须从相同状态产生朱引擎自身产生的队列。

### 哪个站点运行服务器

战斗服务器是每台控制台从大厅主机的 Session type 6 与 type 9 构建的端口 2 成员列表的第一条目；`pokeldn.sv.port2.build_session` 把主机放在第一位。

| 步骤 | 代码 |
|---|---|
| 团体战开战 `0.4455` 将服务器槽设为 0：`setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`，setup `+0x94` |
| 成员 i 映射到槽位 0、2、3、4；其 code 到 `+0x99+slot`，对自身 code 则槽位到 `+0x90` | 端口 2 `+0x170` 上的 `0x1ccd15c`；`0x2d363a0`、`0x130ea2c` |
| `0x2a1cd74` 在战斗开始时将 setup `+0x94` 复制到 `net+0x58`，`+0x90` 到 `net+0x5c` | 来自 `0x18915c4` |
| 当 `!setup.710 && slot == net+0x58` 时控制台是服务器 | net vf `+0x78` = `0x2a1d994` |
| 0x15 检查器仅安装在非服务器上 | `0xfb0ee8` |
| 接收超时或检查失败调用 net vf `+0x70` = `0x2a1d920`；在团体战中 `0x18e217c` 将 `net+0x58` 设为控制台自身槽位 | `0xf5bfd4` |

Setup `+0x710` 仅由 `0x7faed0`（Lua `f3AF42713`）设置，从不由团体战开战设置。失去服务器的控制台使自己成为服务器，因此当大厅主机停止发送时，每台控制台各自战斗。成员向量仅追加，通过 `0x18b65c8` -> `0x18b68fc` 由 type 6 或 7 会话块（`0x18b566c`，先追加）、type-6 重放（`0x279ba2c`）与 type 9（`0x1954bac`）写入；任何块之前的 type 9 被丢弃（`0x18b65e4`）。引导参与者 k 属于 code k 的成员；点名空参与者的成员 code 会中止加载（2162-0001）。故障转移的控制台用自身 AI 运行每个其他战斗者（`0xfa52b0`、`0xfa5314`）。其 code 是带有其站点的第一个向量条目的 code（`0xd5f3b4`）；Lua 槽位循环无 break，因此最后一个匹配条目设置其槽位。

### 战斗的随机数

每回合的每次随机抽取来自一个 0x28 字节的 xoroshiro128+ 对象（vtable `0x4500bd0`）：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x00 | 8 | vtable |
| 0x08 | 2 x u64 | 状态 |
| 0x18 | u64 | 种子 |
| 0x20 | u64 | 已做抽取次数 |

服务器的主模块（0x378 字节，构造函数 `0x12742d0`）在 `+0x10` 持有它；回合代码以 `[[x+0x10]+0x10]`（`0x11440e8`）到达它。模块的初始化器 `0x127d824` 将状态设为种子与 `0x82A2B175229D6A5B`，计数为 0（`0x127d9a8`），从参数块的 `+0x20` 取种子。访客的检查器从战斗设置的 `+0x718`（`0x2891748`）填充该字；团体战开战 `0.4455`（@1152..@1157）通过 Lua 绑定 `fAF4A81E0`（setter `0x7faf1c`）将 `+0x718` 设为 RaidPoint 的 `randSeed`。伙伴种子也是战斗种子，由写入引导的站点选定。服务器构建的每槽模块（`0x126ba88`，来自 `0xfa9f90`）以种子 0 初始化。

一次抽取加上 `s0 + s1` 并步进状态；计数每次调用加一，而非每次重抽：

| 函数 | 抽取 |
|---|---|
| `0x11440f0(rand, n)` | 小于 n 的 u64：`s0 + s1` 掩码到 n − 1 的位宽，≥ n 时重抽；n 小于 2 返回 0 且不抽取 |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f`，≥ 100 时重抽；小于 p 时为真 |

许多回合函数内联步进而不调用这些。

### 每次招式的伤害与抽取

一次招式使用按此顺序抽取：

| 抽取 | 何时 | 决定什么 |
|---|---|---|
| `chance(25)` | 使用者麻痹 | 完全麻痹 |
| `chance(33)` | 使用者混乱 | 击中自己，其掷骰是替换招式抽取的 `below(16)` |
| `chance(accuracy)` | 招式有命中率；100 仍抽取 | 命中；命中率为招式命中率乘以 (3 + n) / 3，或 n 小于 0 时为 3 / (3 − n)，截断，n 为使用者命中等级减目标闪避等级（±6 内），再经特性修正 |
| `below(24)`、`below(8)`、`below(2)` | 伤害招式，按会心等级 0、1、2；对总会心的招式无（冰息、邪恶抽打、花伎俩、水流连打） | 为 0 时会心 |
| `below(16)` | 伤害招式 | 掷骰 r：伤害乘以 (100 − r) / 100 |
| `chance(p)` | 概率为 p 的追加效果（泰山压顶的 30） | 该效果；火焰牙、冰冻牙与雷电牙先抽畏缩再抽状态，与 Showdown 列表相反 |

对 Boss 的畏缩追加效果不抽取任何东西（[回合队列中的招式](#a-move-in-the-round-queue) 有规则）。混乱追加效果在其 `chance(p)` 之前通过 `below` 与 `chance` 之外的调用将生成器步进一次：在记录每次抽取的情况下，20 次混乱抽取中的 20 次（精神干扰、幻象光线、水之波动、神奇蒸汽、魔法扭力）无论该步进输出如何。落地的混乱不抽取持续时间。100% 降低能力的追加效果（精神击破、重踏）在某些回合抽取 `chance(0)`，在另一些回合不抽取。速度相等的战斗者在速度排序中抽取 `below(2)`（[速度平手](#speed-ties)）。对 Boss 或持有精神力（特性 39）的目标，畏缩追加效果不抽取任何东西，除非使用者有破格、涡轮火焰或兆级电压（104、163、164）；对已在本回合行动过的玩家，它抽取其 `chance(p)`，且在那里落地的畏缩不向队列添加任何东西。接触招式碰上静电、毒刺、火焰之躯或迷人之躯（特性 9、38、49、56），或来自持有毒手（143）的使用者，在招式追加效果之后抽取 `chance(30)`；碰上迷人之躯仅在雌雄之间。提升使用者自身的追加效果（蓄能焰袭、钢翼）抽取其概率，并在命中的 `0x42` 之后、击倒命令之前添加提升，即使命中击倒目标时也是如此。降低使用者能力的招式（近身战、臂锤、冰锤）在其掷骰后抽取 `chance(100)`，并在命中的 `0x42` 之后为每项能力添加 `0x0d (A, stat, n)`、`0x93` 与 `0xcb (A, 31 + stat, A, stat)`（记录每次抽取的战斗显示该抽取）。落地的静电、毒刺或火焰之躯在目标的特性激活内、追加效果命令之后麻痹、中毒或灼伤攻击者：`0x25 (T)`、`0xc7 (T, 0)`、来自 T 的施加（[状态](#statuses)）、`0xc8 (T)`；已异常或免疫的攻击者什么也不显示。粗糙皮肤与铁刺（24、160）以激活内的 `0x01 (A, T, A 最大 HP 的八分之一, 20)`、`0x9a (A, -damage)` 与 `0xcb (A, 143, A)` 回应接触，也包括击倒持有者的接触；黏滑与纠缠之发（183、221）使攻击者速度降一级。吸取招式的回复紧接在命中的 `0x42` 之后、追加效果与接触回应之前，并读取它们之前的 HP。击倒 Boss 的命中不抽取追加效果与接触概率。在记录每次抽取的 156 场神谕战斗中，插件构建的每回合抽取等于所记录的。

战斗在第一回合前抽取一次 `below(100)`。伤害为 Showdown 的第九世代公式（数据来自 Pokémon Showdown 的 `moves.json` 与 `typechart`），使用队伍记录的能力值，Boss 仅按其太晶属性防御：能力变化前对 Boss 的 1346 次命中中有 921 次符合，且在记录每次抽取的 140 次命中中有 137 次，所记录的掷骰与会心抽取给出所记录的伤害。不符合的命中发生在 Boss 护盾期间（约公式的 0.45）、来自有自身规则的招式（扑击、电力上升、多段击）或被截断到剩余 HP。

特性按 Showdown 改变公式，各自单独应用，带自身的 4096 分之几修正（链式合成一个修正的一对未测量）：活力（55）将物理招式的攻击提高 1.5 倍并将命中率降至 3277/4096；复眼（14）将命中率提高 5325/4096，上限 100；厚脂肪（47）对火与冰将攻击者能力减半，洁净之盐（272）对幽灵，且洁净之盐持有者不从追加效果获得状态；秘剑击中防御能力，踢倒、圣剑与暗黑爆破忽略目标的防御与闪避等级；强壮之颚（173）将啃咬招式威力提高 1.5 倍，舍身（120）将反冲招式提高 4915/4096；有色眼镜（110）在属性倍率之后将效果绝佳以外的命中翻倍；冰鳞粉（246）在灼伤减半之后将特殊命中减半，除非攻击者有破格、涡轮火焰或兆级电压；过滤与坚硬岩石（111、116，均被破格打破）以及棱镜装甲（232）在那里将效果绝佳命中乘以 0.75。连续攻击（92）给出五击并仍抽取击数掷骰。天恩（32）使每个追加效果概率翻倍；恶臭（1）在招式自身追加效果之前添加 10% 畏缩抽取；目标上的鳞粉（19）移除追加效果及其抽取。坚硬脑袋（69）不受反冲。贪吃鬼、顺手牵羊、共生、熟成与反刍（82、124、180、247、291）在无战斗者持有物品时什么也不做。

大晴天将火系命中基础伤害提高 1.5 倍并将水系减半，下雨相反，在会心之前（Showdown 的 `onWeatherModifyDamage`；语料中 125 回合带此类命中构建相等）。悠游自如、叶绿素、拨沙与拨雪（33、34、146、202）在其天气中使速度翻倍，对顺序键、排序与 `0x5a` 皆然；沙隐与雪隐（8、81）在其天气中将对其持有者的招式命中率降至 3277/4096（语料中 83 回合带六者之一在其天气中构建相等）。沙隐、防尘、拨沙与沙之力（8、142、146、159）不受沙暴伤害。下雪将冰属性对物理命中的防御提高 1.5 倍，如同沙子将岩石属性的特防提高。

绝处求生与挣扎按使用者 HP 的四十八分之几取威力（Showdown 表：小于 2 为 200，小于 5 为 150，小于 10 为 100，小于 17 为 80，小于 33 为 40，否则 20）。持有适应力（91）的 Boss 对其既是自身属性又是太晶属性的招式取 2.25 STAB，对其他太晶属性招式取 2.0，对其自身属性的其他招式取普通 1.5。

有自身威力规则的招式遵循 Showdown 的 `moves.ts`：以牙还牙在目标已于本回合更早行动时翻倍（护盾打破所丢弃的 Boss 回应不计），祸不单行对异常目标，电力上升对电气场地中着地的目标；硬撑在睡眠以外的异常下翻倍，毒液冲击对中毒目标，电光双星与碰撞课程在效果绝佳时在属性倍率之后的伤害上取 5461/4096，广域战力在精神场地中由着地使用者取 1.5。翻倍的电力上升在其 `0x8b` 的第五参数携带 1；翻倍的以牙还牙携带 0。在构建相等的语料回合中，以牙还牙与电力上升各出现一次提高；祸不单行、硬撑、毒液冲击与电光双星仅以未提高出现。

场地（青草 1、薄雾 2、电气 3、精神 4）改变招式威力：着地使用者发出其属性招式时为 5325/4096（草、电、超；薄雾场地不增强任何），对薄雾场地中着地目标的龙系招式以及对青草场地中着地目标的地震或重踏为一半。战斗者除非是飞行、持有飘浮或持有气球，否则着地。语料中电气、精神或薄雾场地下的 151 回合（42、57、52）按这些规则构建相等。

Boss 的 HP 池为其记录 HP 乘以 RaidPoint 的 HP 系数再除以 100（[战斗引导](#the-battle-bootstrap)）：在获胜的神谕战斗中，一星 78 场、二星 84 场、三星 125 场与四星 35 场在 `0x37 (2, 2, damage)` 中恰好累计 5、5、8 与 12 倍记录 HP 后结束；其余因护盾与有自身规则的招式而更少。

### 状态

落地的主要状态追加效果在命中记录之后运行：`0x13 (T, condition, 0, value, A)`、`0x90 (T, condition)`、`0xa7 (T 的位置, code)` 与 `0xcb (A, text, T)`：

| 状态 | condition | value | code | text |
|---|---|---|---|---|
| 麻痹 | 1 | 1 | 46 | 92 |
| 睡眠 | 2 | turns << 3 \| 2 | 42 | 103 |
| 冰冻 | 3 | 1 | 45 | 97 |
| 灼伤 | 4 | 1 | 44 | 86 |
| 中毒 | 5 | 1 | 43 | 79 |
| 剧毒 | 5 | 7801 | 43 | 80 |

### 速度平手

战斗用交换排序按速度排列战斗者与行动：每个条目与每个更后的条目比较，当更后条目的键更大时它前移。相等键抽取 `below(2)`，1 使更后条目前移，因此平手在两个平手条目的每次比较中抽取一次。战斗者 id 为 1 到 5，Boss 为 2。在 142 场强迫两名战斗者为同一速度的神谕战斗中，按 id 顺序对五名战斗者的排序在开战时给出所记录的抽取次数为 142。

| 何时 | 对象，按此输入顺序 | 排序次数 | 什么读取结果 |
|---|---|---|---|
| 开战，在复制抽取之前 | 五名战斗者，id 顺序 | 1 | 入场事件 |
| 回合开始 | 回合的行动，命令顺序；键为优先度，然后非慢出，然后速度 | 3，各基于前一次结果 | 第一次：第二次 `0x51` 遍；第三次：招式顺序 |
| 除最后一次外每次招式之后 | 行动 | 1 | 队列中无 |
| 回合结束 | 仍站立的战斗者，每次 id 顺序 | 3 | 第二次：`0x43` |
| Boss 倒下的那一回合结束 | 仍站立的战斗者 | 无：不抽取 | `0x43` 按速度顺序，平手按 id 顺序（语料中 5 场带平手的胜利） |
| 回合结束（每第四回合） | 仍站立的战斗者，每次 id 顺序 | 8 | 第四次：沙暴、吃剩的东西与 `0x19` 顺序；第七次，在回合结束之后：`0x43` |

回合结束的 `0x43` 顺序在 123 场中有 109 场匹配第二次排序；另外 14 场有战斗者速度被该回合招式改变。链式行动排序在 27 场两名行动者平手的回合中匹配 `0x51` 与招式顺序，且第一次招式后的抽取在到达两次招式的 3 场回合中出现。第四次排序在前五次排序不一致的 12 场语料回合结束中给出残留顺序；第一、二、三或五次在其中一些上失败。

Boss 的复制对它能复制其特性的玩家按 id 顺序抽取 `below(N)`：一名玩家持有具现化时为 `below(3)`。进入硬壳盔甲（特性 75）的招式不抽取会心。

持有变身者的 Boss 在开战时变身为战斗者 1，并以该战斗者的能力值（但 HP、招式、属性与能力等级除外；其太晶属性不变）战斗。站点仍命令它变身，然后每次失败：`0xc9 (2, 0, 144, P, 1)`、`0x7b`、五个零组、`0xca (2, 567)`、`0x1d (2, P, 0, 1, 0, 144, 144)`、两次 `0x5b (2, 144)` 与 `0x1e (2, 0)`，在其处理程序的 `0x5a` 之后。键上平手且旁有处理程序招式的行动像任何平手一样排序与抽取（11 场语料战斗）。

未通过命中率抽取的变化招式作为伤害未命中运行（消息 73 与 `0x52 (A, 1)`）。目标属性免疫其状态的变化招式（电磁波进入电）作为免疫招式运行，带 `0xcb (A, 72, T)` 且无 `0x52 (A, 3)`，无抽取；对已中毒目标的中毒招式以 `0xcb (A, 84, T)` 同样方式。睡眠招式在其命中率之前通过抽取日志不显示的调用抽取其回合数。

天气招式（大晴天、求雨、雪景、沙暴）作为带场地类别（10）的能力等级变化招式运行，并以天气的开始代替能力变化：`0x6a (0)`、`0x69 (0, w)`、`0x79 (w, 5, 0, A, 0)` 与 `0x88 (w, A, 0)`，w 为 1 大晴天、2 下雨、3 下雪、4 沙子；施加状态的变化招式（电磁波、磷火、剧毒、蘑菇孢子）在那里运行施加（[状态](#statuses)）。喷沙（245）被伤害招式命中后在命中的 `0x42` 及其追加效果命令之后升起沙暴：`0x25 (b)`、`0xc7 (b, 0)`、w 为 4 的天气开始、`0xc8 (b)`，无消息，在命中击倒持有者时的击倒命令之前；若沙暴已起则什么也不显示。盖过另一天气升起的天气（天气招式或喷沙）仅显示自身开始并替换旧的，其结束什么也不显示。场地招式以同样方式运行，带场地的开始：`0x32 (t, 0, 42, A)`、`0x6a (8)`、`0xb2 (0)`、`0xaa (t)`、`0x69 (8, t)` 与 `0xca (A, text)`，开始文本青草 704、薄雾 706、电气 708、精神 828；已有场地时以文本 567 失败。场地招式的 `0x8b` 无论命令了什么位置都携带位置 10。天气是 `0x6a`、`0x69` 与 `0x44` 中的场地槽 0，场地是场地槽 8。

戏法空间（433）作为天气招式运行，其 `0x8b` 中位置为 10，效果为 `0x69 (1, 0)`、`0x30 (1, 0, 42, A)` 与 `0xcb (A, 275, A)`（场地槽 1）。在其升起时，顺序键与排序读取的每个速度都是 Showdown 的 10000 − Speed，含运行的处理程序键（其下 32 场语料回合构建相等；其结束未出现）。

顺风（366）在其使用者一侧（0 为玩家侧，1 为 Boss 侧）升起侧方条件 4，持续四个回合结束，升起的那一回合计为第一个。它作为带侧方类别（12）的天气招式运行，`0x8b` 中位置为 10（`0xc9` 保留命令的位置），然后 `0x4a (side, 4, 0, 34, A)`（34 为其四个回合 << 3 | 2）、带相同参数的 `0x65` 与 `0xca (A, 643, side)`。它在顺序键与排序中使该侧战斗者的速度翻倍，但不在处理程序的 `0x5a` 中。每个它升起的回合结束在最后的 `0x19` 之后、`0x44 (1)` 之前添加 `0x4c (side, 4)`；在其第四个时出现 `0x4b (side, 4)`、`0x66 (side, 4)` 与 `0xca (A, 645, side)`，A 为升起它的战斗者。反射壁、光墙与神秘守护是持续五个回合结束的侧方条件 0、1 与 2，以同样方式升起，带 `0x4a (side, c, 0, 42, A)` 与开始文本 623、627 与 635，结束文本 625、629 与 637。反射壁将该侧物理命中、光墙将特殊命中在最终伤害上乘以 2732/4096，除非是会心，任一侧皆然（Showdown 在多名战斗者旁的因子；语料中 Boss 自身的墙符合）。顺风侧持有风力发电（277）的战斗者在开始文本之后立刻蓄电：`0x25 (b)`、`0xc7 (b, 0)`、`0xcb (b, 1024, b, 366)`、`0xc8 (b)`、`0x1e (b, 20)`、`0x7d (20, b, 0, 0)`；顺风旁的乘风（274）未测量。语料中 47 回合带顺风升起、三回合带其结束，构建相等。

二到五击招式在命中率抽取之后立刻掷其击数（`0x19d4f2c`）：战斗生成器低 7 位的一次抽取，≥ 100 时重抽，小于 35 为 2 击、小于 70 为 3、小于 85 为 4，否则 5；固定次数（二连踢的 2、三连坠击的 3）不抽取。每次命中抽取其会心与掷骰，并在 20 字节零组之后运行其自身的 `0x7e` 三元组、以击数索引为第六参数、击数为第十参数的 `0x8b`、仅带 `0x8e (1, e, M)` 的伤害命令、`0x42` 与 `0xd1`；击倒目标的命中结束运行，其击倒命令不携带倒下消息。每次命中的 `0x8b` 第十参数是落地的击数，因此击数在其命令发出前被计数。最后一击之后出现效果消息 `0xca (A, 574 或 575)`（非普通时）、`0xca (A, 516, hits)`、效果绝佳时每次命中一次 `0x20 (A, 24)`、`0xa6 (96)`，然后是招式的通常结束，对 Boss 带 `0x85 (7, total damage)`；龙箭不显示消息 516。击倒 Boss 的多段击在 `0xa6 (96)` 之后添加其倒下消息 `0xcb (A, 0, 2)`；击倒玩家的则不。语料中每个二到五击回合都按此方式构建相等。

反冲招式在命中的 `0xd1` 之后、任何击倒命令之后添加 `0x01 (A, A, r, 4)`、`0x9a (A, -r)`、`0xcb (A, 127, A)` 与 `0x37 (A, 4, r)`，r 为造成的伤害（至多目标当时有的 HP）乘以招式比例，四舍五入，至少 1。叶绿爆以使用者最大 HP 的一半同样结束。铁辉炮在其 `0x8b` 之后、伤害命令之前立刻支付使用者最大 HP 的一半：`0x01 (A, A, cost, 0)` 与 `0x9a (A, -cost)`，无消息。持有生命宝珠（物品 270）的玩家在造成伤害的招式之后、命中的 `0xd1` 之后失去最大 HP 的十分之一：`0x01 (A, A, cost, 29)`、`0x9a (A, -cost)`、`0xcb (A, 328, A)`；其对 Boss 的命中不带 1.3 伤害加成（9 次命中构建相等，且 7 场在第一次此类命中因加成而分歧的战斗）。

聚气作为对自身的变化招式（类别 7）运行，效果为 `0x1e (A, 9)`、`0x7d (9, A, 0, 0)` 与 `0xcb (0, 336, A)`；此后使用者的会心等级高两级（等级 0 招式为 `below(2)`）。蓄力的第一层以同样方式运行，带 `0x35 (A, 0, 1)`、`0xcb (0, 236, A, 1)`、防御提升、`0x35 (A, 1, 1)`、特防提升与 `0x35 (A, 2, 1)`（语料中 18 中的 18；未出现第二层）。

唯一效果为能力等级的变化招式运行 `0x05`（玩家的）、`0x07 (A, 0)`、`0xc9 (A, 0, M, P, 0)`（P 为命令的位置）、`0x7b (M, n, A)`、一个 20 零字节的 `0xcf` 组、`0x7e (0, 0, 0, 0, 0, 0)`、`0x7e (1, 0, 0, 0, 0, 0)`、`0x7e (2, 7, 7, 7, 7, 7)`、`0x8b (A 的位置, T 的位置, M, type, 0, 0, 0, 0, class, 0)`（对自身的招式 T 为 A，类别 7）、能力变化，然后 `0x7c ()`、`0x08 (A, 0)`、`0x1d (A, P, type, 1, 0, M, M)`、两次 `0x5b (A, M)` 与 `0x1e (A, 0)`。提升为 `0x0c (b, stat, n)`、`0x92 (b, stat, n, 0)` 与 `0xcb (b, text, b)`；降低为 `0x0d (b, stat, n)`、`0x93 (b, stat, n, 0)` 与 `0xcb (A, text, b, stat)`。文本为提升 1、2 或 3 级时 10、17 或 24 加能力，降低 1 或 2 级时 31 或 38 加能力（能力 1 攻击到 7 闪避），按 Showdown 的源顺序，即能力顺序（盘蜷提升攻击、防御，然后命中），但换挡（速度，然后攻击）与 V 热火（速度、防御、特防）除外，覆盖神谕语料中每次能力变化。不能未命中的招式（Showdown 命中率 `true`）不抽取命中率。洁净之躯、白色烟雾与金属防护（29、73、230）以无命令无消息阻止伤害招式的追加降低，如同 -6 的能力的追加降低（其概率仍抽取）。不服与好胜（128、172）在对手降低一项能力的消息之后回应：`0x25 (b)`、`0xc7 (b, 0)`、`0x0c (b, 1 或 3, 2)`、`0x92`、`0xcb (b, 18 或 20, b)`、`0xc8 (b)`。

扩散招式（Showdown 目标 `allAdjacent` 或 `allAdjacentFoes`）仅命中其命令点名的位置，带单目标伤害且无扩散修正：每个持有一个的神谕回合都作为单目标命中构建相等，`class` 为 4 或 5。招式按优先度档顺序运行，然后按能力等级处的速度：Boss 的水流喷射或暗影偷袭在更快的玩家之前行动。

击倒 Boss 的命中赢得战斗。在其 `0x42` 之后出现 `0x49 (2, A, M)`、`0x09 (A, slot)`（`slot` 为 M 在 A 招式组中的索引，383 次神谕击倒中有 382）、`0x37 (2, 1, 1)`、`0xcb (2, 0, 2)`、`0x94 (2, 0)`、`0x37 (2, 8, 1)`、`0x5f (2)`、`0x62 (2)`、`0x6c (2)`、`0x5d (2)`、按 id 顺序每个玩家的 `0x41 (b, 2)`、k 为 0 到 13 的 `0x33 (2, k)`（仅当地场升起时有 8）、`0x80 (2)`、`0x29 (2)` 与 `0x38 (A)`，然后是招式的通常结束。此后无人行动，回合仅以仍站立战斗者的 `0x43`、`0x23` 列表与 `0x2d (0)` 结束。`0x85 (7, damage)` 与伤害命令携带 Boss 当时剩余的 HP。

前缀以 `0xb5 (0)` 开始，然后按 id 顺序对回合行动者运行一次 `0x51 (b, 1)`，再按第一次行动排序的顺序运行一次；在第二次运行中，持有慢出（特性 100）的战斗者携带 `0x51 (b, 0)`，此后其行动在其档中排最后；回合的第一次排序仍计其为 1。菌丝之力（298）对仅变化招式以同样方式携带 `0x51 (b, 0)`，恶作剧之心（158）将变化招式的优先度提高 1。每次行动排序（[速度平手](#speed-ties)）先按列表顺序计算每个招式行动的顺序键，注册自身处理程序的招式显示为 `0x5a (b, M, speed)`（速度在其能力等级）与 `0x5b (b, M)`。回合第一个运行的招式再次计算每个招式行动的键，且其招式注册处理程序的行动者在其 `0x05` 之前添加 `0x5a (b, M, key)`，键为 (优先度 + 7) << 16、其 `0x51` 值 << 13，加上其速度（优先度 0 招式为 `0x72000 + speed`；慢出的 `0x70000`）。排序的 `0x5a` 仅携带能力等级处的速度能力；运行的携带顺风与麻痹。（神谕的命令日志与其排序及行动运行交错。）631 个招式中有 347 个注册一个（硬撑与泰山压顶在其中，暗袭要害不在）。

Boss 从一开始就太晶化：其太晶属性的伤害招式在基础威力修正后威力低于 60、无优先度且单次命中时，以 60 命中，即第九世代的太晶规则（迷你芙的太晶一般撞击造成 4，而 40 基础威力给出 2；对抗心 Boss 的太晶恶咬住进入另一性别玩家造成 25，即未修正的 60 威力伤害，而对抗心的 45 最多给出 21）。招式的追加效果各按 Showdown 顺序抽取 `chance(n)`，但对 Boss 的畏缩除外，它不抽取任何东西：玩家对 Boss 的冰冻牙仅抽取其冰冻概率（冰冻显示为 `0x13 (2, 3, 0, 1, 4)` 带消息 97 与 98，且 Boss 在行动前抽取 `chance(20)` 解冻），Boss 对玩家的冰冻牙两者都抽。击倒 Boss 的命中先抽取 `chance(0)`，无论有无追加效果。

按此方式从 Showdown 的招式数据与第九世代伤害公式构建，554 场神谕战斗的第一回合中有 56 场与神谕字节对字节相等且无一不同（其余持有被拒绝的内容）；20 场完整战斗在每回合与神谕相等，且对脚本控制台服务时 19 中的 19 在相同帧发送神谕服务器发送的每一帧。
当行动或被命中的战斗者持有其 Showdown 回调可改变回合的特性或物品时（活力的攻击、对抗心的威力、友情防守的 0.75、胆怯在恶命中后的速度提升、疾风之翼的优先度），回合被拒绝，除非语料测得该特性或物品空闲，或当战斗持有入场时作用的特性（威吓在第一回合前降低攻击者的攻击）。

### 行动

回合的行动报头（请求块，0x238 字节）是五个 0x70 字节块，每个客户端槽位一个，每个最多七个 16 字节行动（一个 u64 行动字、一个 u32 行动者战斗者 id、4 个无代码写入的字节），且在 +0x230 处每槽一位字节计其块中的行动。服务器按槽位顺序将它们解码为 0x8c 字节行动条目（`0x1145e40`，解码器 `0x11461b4`）。行动字的低四位是种类：

| 种类 | 条目种类 | 字的字段 |
|---|---|---|
| 1 | 1，招式 | 位 4..7 目标的战斗位置，8..23 招式，位 25 一个标志 |
| 2 | 2 | 位 4..19 与 20..27；下一个 u32 |
| 3 | 3，替换 | 位 4..7 队伍索引（行动者是该队伍成员），8..11，位 12 |
| 4 | 6 | 位 4..11、12..15 与 16..23 |
| 5 | 4 | 位 4 |
| 6 | 5 | 位 4..11 |
| 7、10、11 | 7、8、9 | 无 |
| 9 | 10 | 位 4..11 |
| 12 | 11 | 位 4..11；下一个 u32 |
| 13 | 14 | 位 4..7、8..11、12..15、16..27、32..43、44..55、56..59、60..63 |

位 0..3 为 3 且位 12 置位的字被跳过，种类 0、8、14 与 15 亦然。记录的玩家行动 `41 67 03 00 ...` 是招式（种类 1），目标位置 4，招式 871（炬火颂）。

团体战中的战斗者 id：1 为槽位 0 的宝可梦，2 为 Boss，3 为槽位 2，4 为槽位 3，5 为槽位 4。站点的类型 0x06 命令为 0xe8 字节：0x20 字节报头（+0x19 为槽位）、+0x20 处的计数字节，然后从 +0x28 起的 (u64 word, u64 actor) 对。它携带该槽位自身的行动以及 Boss 对该槽位的回应：访客对槽位 2 的命令持有 `战斗者 3 在位置 4 使用招式 871` 与 `战斗者 2 在位置 1 使用招式 204`。站点选择 Boss 对其自身宝可梦的招式。

服务器为每个行动中的槽位填充一回合的请求块：

| 步骤 | 代码 |
|---|---|
| 发布者栈上的 0x240 字节块：每个行动的字与行动者清零，计数清零，种类（0x15）在 +0x238 | 每槽读取器步骤 `0xf6df44` 中的 `0xf6e6a8`；其他种类用 `0xf71d10` |
| 槽位的类型 6 消息（读取器 +0x30 为存储，u32 +0x38 为槽位）被复制入：计数字节清除，每对的 u64 字与行动者的低 u32 追加，计数提高；无边界，计数超过 7 会跑进下一槽 | `0xf702ec` -> `0xf7065c`（键 6，0xe8 字节消息）；键 0x10 到 `0xf72038`（单行动的 0x30 字节消息，在槽位持有至多六个时取） |

### 服务器命令队列

类型 0x15 记录的队列（正文的 +0x23c，长度在 +0x238）是一串命令。命令是大端 u16 id，然后按其 id 格式打包的参数作为一条大端位流，前端填充到整字节（写入器 `0x119bf58`，跳转表 `0x3c6aa7c`）。id 到格式的映射由 `0x3c6abe4` 处 208 行 (u16 id, u8 format, u8 0) 构建，同一 id 的更后行胜出；id 为 0 到 205。id 0xce 到 0xd4 由读取器 `0xe515f0` 自身读取（跳转表 `0x3c6a90c`）：

| id | 正文 |
|---|---|
| 0xce | 无：队列结束 |
| 0xcf、0xd2 | 一组：u8 字节计数，然后那么多字节 |
| 0xd0 | u8 计数，然后那么多字节：每个被命中目标一对 (战斗者, 效果)，四个目标上 8 字节 |
| 0xd1 | 两字节 |
| 0xd3 | 一字节 |
| 0xd4 | 无 |

### Boss 的行动

团体战 Boss 的额外行动等待在四个列表中（u8 种类在 +0x5c + 8i，u32 值在 +0x60 + 8i，计数 +0x7c），在 +0x10 处 RaidPoint 行动配置的副本之后。回合引擎的列表是 `[module+0x1b0]`（`0x16e5c90`），每回合重置；服务器的每帧机保留其自身的。

|---|---|---|
| 1 | 护盾（`0xf6f87c`）：时间在配置 +0x14 百分比及以下，或 HP 在 +0x12 及以下，在它开始之前 | 按时间为计时器的 `0xf70af0`，按 HP 为 0 |
| 2 | 护盾结束（`0xf6f87c`，对 +0x18 的 `0xf70010`） | 1 |

回合结束按列表的最后顺序为列表的每个条目（无论是否运行）放一个 `0x37 (b, 7, 1)`：护盾、额外 Boss 重置以及其三个条目被护盾再次排队的额外招式为 7。`0x75 (3, n)` 仅计有玩家条目的回合，且团体战行动回合仍计入 `0x7b (M, n, A)`。团体战行动回合否则作为命令回合结束：三次战斗者排序、按第二次顺序的 `0x43` 与 `0x23 (2)`。

### 战斗计时器

战斗计时器是服务器上下文 +0x38 处的 0x28 字节对象（每帧机与每个任务的 `[+0x40]`，它还在 +8 持有 N、在 +0x10 持有服务器模块、在 +0x18 持有服务器）：

| 偏移 | 字段 |
|---|---|
| +0x00 | u64 开始，`nn::os::GetSystemTick` 的纳秒；暂停时为 0 |
| +0x08 | u64 上次暂停前累积的纳秒 |
| +0x10 | u64 上次暂停的时间 |
| +0x18 | u8 已开始 |
| +0x19、+0x1a | u8 暂停原因；两者都为 0 时计时器运行 |
| +0x20 | 创建它时的限制 |

| 事件 | 代码 |
|---|---|
| 创建、开始并立刻因原因 0 暂停，在限制 N+0x8a 不为 0 时与战斗的第一个任务一起 | `0xf70864`、`0xf70a58` |
| Wild::Setup 结束时因原因 0 恢复（从未开始的计时器在那里开始） | `0x2a1fbfc`，`0xe63a6c` 的步骤 |
| 从团体战行动的消息 0x47 到其回合因原因 0 暂停 | `0x18c9a68`、`0xe63ac4` |
| 读取：限制加 `[[module+0x1b0]+8]` 处的 i16，减去自开始以来运行的整秒与累积的整秒；暂停时为限制减累积秒；零限制为 1 | `0xf91070` |

每帧机仅在计时器已开始（+0x18）且 setup +0x499 位 2 置位时检查时间触发（`0xf6d538`）。时间 P 百分比的触发在整数除法下 100 × 剩余时间 / 限制 ≤ P 时触发：在 300 秒计时器上，80% 触发在剩余 242 秒时触发，即运行 58 秒后。在下方服务的战斗中，计时器在最后一台站点对消息 0x11 的应答到达服务器时开始，80% 行动在 58.1 秒后发出。

### 战斗计时器耗尽

每帧顶部，每帧机（`0xf6d538`）读取战斗计时器（`0xf91070`）；结果为 0 或更少时走时间到分支 `0xf6d830`：

| 否则：带种类 0 的 AddExpBattleEnd | `0x16e5230`（哈希 `0x23607a0597b3a656`） |

机仅在无任务运行时运行，因此在回合期间耗尽的计时器在任务结束后才被看到。团体战时间到不发送 0x25：Boss 的最后计时回合，然后正文 `00 00 00 00 02 00` 的 0x2b、0x35 与 0x37（[战斗的结束](#the-battles-end)）。Boss 获胜的团体战以同样方式结束：主机或控制台的宝可梦每次倒下（非 NPC 伙伴的）从计时器减去 n 秒（`[[module+0x1b0]+8]` 处的 i16，`0x287f3d4`）：n 为时间限制乘以 0.125 乘以四名玩家的平均等级对 Boss 等级，float32，截断（339 场神谕战斗中的 339；300 秒计时器上 28 到 61 秒），且击倒的队列携带 `0x81 (-n)`。

| 消息 | 到 | 内容 |

### 服务器的流程

在控制台上，步骤是任务：Wild::Setup、ServerRequest（`0x138d178`，消息 5 到一个槽位）、ServerCommand（`0x16e4f10`，作为回合发布的请求块）、RaidAction 与战斗的结束。Wild::Setup（`0x2a1f54c`，跳转表 `0x3c61c1e`）发送消息 1，等待每个应答，发送 0x11，等待，清除每个槽位发送的内容（`0xe0f5f8`），仅当开始标志 [[o+0x40]+0x28] 为 1 时发送消息 3（仅由 `0x2840fac` 设置；团体战留其为 0），并启动战斗计时器。团体战的 setup +0x30 为种类 0。每帧机（`0xf6d538`）步进五个每槽读取器（`0xf6df44`）与 Boss 的列表：

| 读取器状态 | 何时 | 然后 |
|---|---|---|
| 0 | 槽位的已发送条目不持有 5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d 中任何一个 | 对该槽位的 ServerRequest（`0xf70078`），状态 1 |
| 0 | 否则 | 每个已应答对擦除（`0xf6edf4`） |
| 1 | 槽位被发送 5 并发送了 6 | 带该槽位命令的块（`0xf6e6a8`、`0xf702ec`）作为 ServerCommand 发布，状态 2 |
| 2 | 槽位应答了回合（0x15 / 0x16） | 状态 0 |

服务器按到达顺序为每槽保留它发送的消息与槽位发送的消息；`0xf6edf4` 擦除某类型的第一条已发送消息与第一条已接收应答，每次调用一对，状态 0 对每对 (0x15, 0x16)、(0x23, 0x24)、(0x11, 0x12)、(0x13, 0x14)、(0x17, 0x18)、(0x19, 0x1a)、(0x1b, 0x1c)、(0x1d, 0x1e)、(0x25, 0x26) 与 (0x1f, 0x20) 每帧调用一次。因此读取器在回合发出时被挂起的槽位（倒下的槽位）在再次被询问前每帧擦除一回合的积压：复活后 12 回合为 12 帧。Wild::Setup 的结束清除两个列表。

Boss 的槽位（对 N+0x95 的表 `0x3c6a45a`）仅擦除已应答对。其他读取器路径：发送了 4 的槽位得到种类 0x13 块；在团体战中 N 的一侧，读取器+9 处的子状态处理倒下的槽位（[战斗计时器耗尽](#the-battle-timer-running-out)）；0xd/0xe 发布种类 0x1b；7/8、0xb/0xc、0xf/0x10 与收到的 0xa 发布种类 0x17、0x19、0x15 与 0x17。

每帧，运行步骤 `0x2d383b8(N)` 步进服务器的入站链路（`0xe0f040`、`0xe0fd68`、[N+0xb0] 上的 `0xe0f854`），然后是任务图 `0xfc363c(G, 1)`，G = [N+0xa8]（vtable `0x44ee6e8`）：

| G+ | 对象 | |
|---|---|---|
| 0x98 | 请求工厂 | 发布的请求是 0x50 字节对象：任务类型哈希、计数器、载荷 |
| 0xa0 | 调度器（vtable `0x44eea68`） | 发布的请求在 +0x40..+0x50，由 `0x1479b10` 追加 |
| 0xa8 | 来源（vtable `0x44947d8`） | vf 0x68 `0x14641ec` 选定要开始的请求 |
| 0xb0 | 每帧机（vtable `0x4493530`） | vf 0x68 `0xf6d538` |
| 0xb8 | 执行器（vtable `0x4493688`） | 任务栈 |

`0xfc363c(G, 1)` 在执行器持有任务时单独运行它。否则它运行机，然后是来源的选定：在团体战中，第一个发布的团体战行动（哈希 `0x5c307d44ea569b63`），在模块开始第一个 Wild::Setup（哈希 `0x2e9e7a3009002c36`）之前，否则第一个发布的。执行器（`0xfc38dc`）运行顶任务的 vf 0x68：0 结束帧；2 弹出它，推入其继续 [job+0x70] 并结束帧；其他任何东西再次运行它。每帧开始一个发布的请求，团体战行动插队。

机的计时检查将其 Boss 列表的副本作为消息 0x51 发送到服务器自身的入站链路（`0xe0f440(server, N+0x95)`）；下一帧 `0x2016290` 将其 0x24 字节复制到机的 Boss 列表，后者发布团体战行动。没有该步骤，计时行动永不触发。机的 vf 0x70 `0x20162bc` 还接受 `0x0ab4bce035f3012b`（发布到 `0x201665c`）与 `0xde3856ecc4fe200c`（一个种类 14 行动，作为 ServerCommand 发布）。

在无任务的帧上，机（`0xf6d538`）先读取战斗计时器，剩余时间为 0 或更少时发布时间到；然后，在武装时（`+0x118`，0x51 发出时清除，团体战行动发布时再设置），若其 Boss 列表持有行动则结束帧，或对副本评估时间触发，当一个触发时发送 0x51 并结束帧；持有行动的 Boss 列表作为团体战行动发布且帧结束；仅在那时步进读取器。Boss 列表持有护盾的回合先自行发布团体战行动（`0x16e5ad0`）；团体战行动插入发布队列。在语料的 794 场神谕战斗上，按此构建的服务器在相同服务器时间发送神谕发送的每条消息，直到它拒绝的第一回合（31581 条消息；25 场经过倒下，8 场经过复活，5 场经过护盾的 0x47）。

机的时钟是 19.2 MHz 系统滴答：每帧若该帧时间更晚则将其移到该帧时间，每次 `nn::os::GetSystemTick` 读取加 256 滴答。在同一时间再次运行的帧（主机在上一轮结束的时间开始每轮帧）因此读得稍晚。整秒恰好在某帧时间结束的计时器仅当其检查在该帧时间内不早于其开始读取时钟时在该帧结束；否则晚一帧结束。

读取按顺序：

| 何时 | 读取 | 代码 |
|---|---|---|
| 创建计时器 | 两次，第二次暂停它 | `0xf70a58` |
| 暂停的计时器恢复 | 一次，其开始 | `0xe63ac4` |
| Wild::Setup 结束，每个槽位应答 0x11 后的帧 | 一次，战斗计时器的开始 | `0xe63ac4` |
| 每个机帧，战斗计时器运行 | 一次用于时间到 | 来自 `0xf6d538` 的 `0xf91070` |
| 时间触发，武装且列表为空 | 护盾未升起且低时间行动未运行时一次用于护盾；低时间行动未运行时一次用于它；每个尚未触发的基于时间的额外行动一次 | `0xf6f87c`、`0xf6dd84`、`0xf6fa5c` |
| 每个机帧 | 按槽位顺序，每个等待其复活计时器的倒下槽位一次 | `0xf71020` |

倒下槽位的计时器在其 0x22 被擦除时创建并恢复，因此其开始是那些读取中的第三次。

`Server`，此流程的 Python 移植，在机的时钟上以每秒 30 帧运行；不能跳过任何帧，因为等待倒下槽位计时器的读取器每帧都移动机。主机将其服务器读取的每条消息在一个队列中中继给访客，因此该队列的顺序是服务器读取它们的顺序。从模拟主机的引导与中继的消息，该移植在未写入字节之外字节对字节发送控制台全部 24 帧，且在 unicorn 下游戏对全部 216 个移植函数的自身代码留下相同页面，包括时间到与 Boss 获胜。

### 复现一回合

一回合在 unicorn 下从停在构建器 `0x113c8a0`、类型 0x15 的模拟控制台精确重放：内存从 GDB stub 每次取一页，`tpidrro_el0` 后的线程本地页是其 `+0x1f8` 点名假线程的替身，SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d 与 0x1e 返回 0。一回合触及 159 到 353 页。

服务器的 Python 移植为每个游戏函数运行一个函数，以其距 main 的偏移为键：种类 1、5、17 与 21 的构建器，回合驱动器 `0x113e3d0`（伤害 `0xf7c344`、倒下 `0x1144df8`、回合结束 `0x114a094`），战斗开始 `0x113dca8`，构建步骤 `0x2891748`、`0x2892ac0`、`0x2d381a4` 与 `0x2892dd4`，以及带其线程缓存与 TinyMT32 键（`0x525f448`）的 SDK 的 `nn::mem::StandardAllocator`。在 86 个停住的控制台上，它留下与游戏相同的正文与内存页。`__cxa_guard_acquire`（`0x53c49a0`）在字节 0 与字节 1 都未设置时返回 1 并将 guard 的字节 1 设为 2。

### 服务器的流程，实测

这些对 [服务战斗](#serving-the-battle) 的脚本控制台上的神谕服务器成立，且按它们构建的服务器在玩家获胜的九场完整战斗上向控制台发送相同帧，含通知：

| 规则 | 实测 |
|---|---|
| 报头计数器 | `step` 每次发送加一，广播或一次请求；消息 1 时 `round` 为 0，从 0x11 起为 1，并随每个 0x15 与 0x25 提高 |
| 每帧一个任务 | 消息 1 开始 Wild::Setup，它在每个槽位应答 1 后发送一次 0x11，并在每个槽位应答 0x11 后一帧结束 |
| 请求 | 在无任务运行的帧上，无未应答内容的槽位被发布请求（5）；请求每帧开始一个，按槽位顺序 0、2、3、4 |
| 命令 | 槽位的 6 作为向每个槽位发送回合（0x15）的任务发布 |
| 再次询问 | 已应答发给它的每个回合的槽位在下一帧再次被询问 |
| 获胜 | 获胜的回合之后，在下一帧跟一个空回合 0x25（20576 零字节），然后正文 `00 00 01 00 01 00` 的 0x29、0x49、0x35 与 0x37，各在每个槽位应答前一条之后发送一次：在对 0x25 与对 0x49 的最后应答后 2 帧，其余在同一帧 |
| 时间到 | 正文 `00 00 00 00 02 00` 的 0x2b（233 场战斗中的 63） |
| 通知 0x46 | 每个任务开始的帧一个，或在无任务运行时读取回合应答（0x16）的帧一个 |

### 服务战斗

`bin/sv_host.py --raid-serve [NAME]` 在战斗期间保持网络，并用 `pokeldn.sv.raid_battle.RaidBattle` 从主机站点服务它：从引导与两名 NPC 伙伴构建的插件战斗服务器（[战斗服务器](plugins.md#a-battle-server)），以及控制台主机为自己保留的站点。pokeldn 不附带战斗服务器；没有添加一个的插件时，该标志被拒绝。被服务的会话安置我方宝可梦、Boss、站点索引 1 处的一台控制台（引导参与者 1，槽位 2）与两名 NPC 伙伴，因此该标志接受一台控制台。

| 部分 | 主机发送什么 |
|---|---|
| 服务器到控制台的消息 | 寻址为 (0x2713, 1, 2) 的帧 |
| 槽位 0、1、3 与 4 | 每个奇数步在 0.05 秒后以类型 + 1 应答；对槽位 0、3 与 4 的请求（5）带类型 6 命令，其中该槽位的宝可梦对 Boss 使用其第一招式，Boss 对该宝可梦使用其第一招式（[行动](#actions)） |
| 服务器读取的每条消息，含控制台自身的 | 中继给控制台，寻址为 (0x2713, 3, 5) |
| 每个移动了战斗的服务器帧 | 在该帧的消息之后，来自槽位 0 的通知 0x46（步 0，4 字节零正文），寻址为 (0x2713, 3, 5) |

每帧在 0x80 端口 0 上作为一条压缩的可靠消息发出（标志 `COMPLETE_ZLIB`）；所见最大压缩到 903 字节。复现朱 4.0.0 发送的服务器，作为其前六帧，发送零售主机发送的六条战斗开始消息（`raid.HANDOFF`），在其栈填充的报头字节之外，顺序相同，因此 `--raid-serve` 用它们代替 `HANDOFF`。

一旦控制台应答 0x37，或 0x37 发送后 5 秒，主机停止服务并关闭网络。自身应答 0x37 会在服务器上重跑时间到（[服务器的流程](#the-servers-flow)），因此本地站点不应答它。失败（服务器抛出，或构建失败）停止服务并像无该标志的主机一样移交网络；控制台然后故障转移并自行战斗（[哪个站点运行服务器](#which-station-runs-the-server)）。

## 加入

`bin/sv_join.py --raid-pokemon FILE` 加入场景 7 网络并作为访客参与。控制台的玩家打开结晶，选择多人挑战并等待；应用的「太晶团体战（加入）」工具运行它。`pokeldn.sv.raid.RaidGuest` 与加入者按顺序做：

| 步骤 | 访客 |
|---|---|
| Net | 在消息标志 0x11 下应答 0x11 与 0x50 |
| Session | 对加入响应附带的站点列表不应答，至少 1 秒后确认其重传，然后确认之后每个列表，并发送字节 9 置位的时钟请求 |
| 信道 | 将主机的六键表拆成四个与团体战的两个，宣布四个，0.24 秒后加入端口 2，并在表后 0.79 秒宣布团体战的键；将其 0x7C ack 延迟 0.25 秒 |
| 身份 | 标准记录集（`pokeldn.sv.reference`）在入座后 0.44 秒，记录 1 在训练家名下 |
| 大厅 | 在那之后 0.27 秒状态 0x18 及其宝可梦；2 秒后状态 0x01 |
| 开战 | 主机的状态 0x0c 到达时状态 0x0d；将 0x0d 作为其就绪发送的访客被确认且从不显示就绪 |
| 战斗 | 确认主机的 0x3480 0x93，每 0.5 秒发送 Session type-3 离开直到 type 4（最多四次发送）并离开网络；战斗中的零售朱对四次都不应答 |
