# 太晶团体战

本地太晶团体战是《朱／紫》在 LDN 场景 7 中最多四个站点的一场会话。房主运行大厅，然后向每位参与者发送一条引导消息，其中包含四位玩家的宝可梦、首领及其 RaidPoint；每台主机各自进行战斗。`bin/sv_host.py --raid-seed` 主持一场由实机加入的团体战，`bin/sv_join.py --raid-pokemon` 加入一场由实机主持的团体战；两者中，程序玩家在战斗开始时离开，其宝可梦作为该主机的 AI 搭档继续战斗。地址是 Scarlet 4.0.0 解包 `main` 的偏移；Violet 4.0.0 在相同偏移处具有相同代码（[docs/sv.md](sv.md)）。

## 主持

房主广播场景 7、四名参与者和连接码 4970。主机从 X、宝可入口站、太晶团体战、离线搜索加入。`--raid-seed` 与四个上下文标志一起选择团体战（[种子](#the-seed)），`--raid-pokemon` 是我们玩家携带的同行宝可梦记录（PKHeX 会检查它），`--raid-reward ITEM:QUANTITY` 可重复，用《朱／紫》包包持有的物品行替换种子奖励（PKHeX 助手的 `bag` 列表：除重要物品外的每个口袋，未发售物品除外）。`--raid-partner TRAINER` 每个主机留空的栏位最多一次（一台主机时空两个，两台时一个），按栏位顺序让这些 NPC 搭档入座，`--raid-partner-progress STAGE` 选择他们来自哪个阶段（[搭档](#partners)）。应用的太晶团体战（主持）工具携带以下标志。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

在团体战模式中，房主与交换房主的不同之处在于寻址对象和时机：

| | 团体战房主 |
|---|---|
| mesh-addressed 消息（RTT、0x80、0x81）、Session 站点列表 | 发往子网广播；在 ldn_mitm 上单播，因为 ldn_mitm 不会向对等方传送广播 |
| Net 0x11 | 一个序列，重复直到 0x12 |
| 站点列表的主机条目 | 主机加入请求所指定的玩家；若为占位玩家，主机已入座但不在大厅中 |
| 站点列表 | 每 2 秒重发一次，直到主机的 type 6 |
| 开场 | 仅在该 type 6 之后：首先十一个 bulk ack、0x81 端口 5 打开和一个 RTT 请求合在一个数据包中；然后是 0x81 端口 1 打开、频道表和端口 2 type 6；身份在 20 ms 后发送，每 3 ms 一条记录 |
| 端口 2 type 3 | 用两个 type 9 应答：房主的站点 code 0，主机的站点 code 1 |

开场中的 0x7C、0x81 端口 5 和 0x80 端口 2 消息每 0.25 秒重复发送，直到被确认；房主发送的每个 ack 都声明该流中最低的未确认序号。

### 多台主机

`--raid-players N`（1 到 3，应用中的 “Consoles joining”）在一个大厅中最多让三台主机入座，每台位于最低空闲站点索引。它们共享大厅和开始；从第一回合起，各自带着自己的 NPC 搭档和奖励进行自己的战斗（[哪个站点运行服务器](#which-station-runs-the-server)）。房主为每台主机维护一组流，使用该主机的索引 *k*，而单主机团体战的 *k* 为 1：

| | 索引 *k* 处的主机 |
|---|---|
| 加入响应 | 站点索引和加入顺序 *k* |
| 站点列表 | 每个已入座的站点，我们先；每次座位变化都会在下一个序号下发送给每台已入座主机，重发直到每台主机的 type 6 |
| Net 0x11 | 我们的站点、按索引排列的已入座主机，然后是加入者 |
| 目标位图 | `1 << k` 在三个目标位下 |
| bulk ack | 条目 *k* |
| 开场 | 0x81 端口 *k* 和 4 + *k* |
| 端口 2 type 6 | 我们的站点和已经入座的成员，按加入顺序，带代码和数量 |
| 端口 2 type 9s | 我们的在 code 0 下，每个已入座成员在其 code 下，该主机的最后一个在 code *k* 下；每个已入座成员收到该主机的 |
| 引导消息 | 其宝可梦在栏位 *k*；空位留给空闲座位 |

若加入时所有座位已满，或发生在开始之后，则不会得到应答。房主会丢弃所有头部和尾部未标明其 variable id 的数据包，以及所有位图中缺少站点 0 的可靠消息，因为同一大厅中的主机通过同一广播互相寻址。

端口 2 槽位将其成员保存在槽位 `+0x170` 处，作为 u8 code 和 u64 站点 id；`0x138d208` 返回站点的 code，非成员则为 0xfd。房主的 type-3 处理程序 `0x1981e94` 取出没有成员占用且没有排队 type 9 指定的最低 code 0 到 7（`0x279c9a0`），然后为每个成员广播一个 type 9，并为加入者广播一个。接收器 `0x18b68fc` 追加一个尚未列出的 `(code, id)`，并且绝不更改已列出的 code。type 6（`0x12fbf8c`，构造器 `0xe457cc`）在 `+0xa0` 携带成员 id，在 `+0xc0` 携带 code，在 `+0xc4` 携带 count，在 `+0xc5` 携带 closed 字节；其接收器 `0x279b9c4` 为每个成员重放一个 type 9。Lua 大厅（chunk `be21e654`，接收器 `0.15829`；`0.N` 是主函数的原型 N）将每条消息归档在其发送者的 code 下，无 code 则为 253。主机进入大厅时发送 state 0x18 和自己的宝可梦；收到 0x18 的站点用其 Ready 状态和宝可梦应答。

可靠头部的接收检查（`0x6f0410`..`0x6f0430`）对任何目标数量 1 到 23 测试接收者字 `index >> 5` 的 `index & 31` 位；零售发送方写三个，即站点容量 4（`0x44dfcb0`）减一（`0x6e71c4`）。

房主将网络交给仍在场的最低索引。其他主机只有在下一房主的 type 8 之后才会收到 is-migrating Net 0x11（为每个已入座站点排名），然后当每台主机都回答了 0x12 后收到 NetStartHostMigration，没有 Session type 7。让主机保持在同一场战斗中的因素：

| 条件 | 代码 |
|---|---|
| 一台主机看到另一台离开时，只有在迁移期间才保留它：由 is-migrating 0x11 设置 `[net+0x249]`，或由 NetStartHostMigration 设置 `[net+0x1c0]` | 站点离开处理程序 `0x69d08c`、`0x69d174` |
| 带有更新序号的 Net 0x11 会丢弃每个标记为已离开的站点 | `0x69e008`、`0x6b5074` |
| 下一房主最多等待 8000 ms，让每个 Net 站点达到 state 2，丢弃其余站点，发送 Net 0x11，等待每个 0x12 并发送 Session type 5 | NetHostMigrationJob `0x6a9cd4`、`0x6aa2a8`；`0x6d44f0` |
| 其他主机等待该 type 5 10000 ms，然后失败 | `0x6dc024`、`0x6dc124` |
| type 7 的最后一个 u16 至多等于下一房主的已应用列表序号 | `0x6d9164` |

Pia 房主在 LDN 参与者每次变化时向每个站点发送 Net 0x11（`0x69c310`、`0x69c79c` 递增 `[NetProtocol+0x60]`，排名按 IPv4 地址升序排列 `0x6a05ec`）。在 LDN 上，加入者的 0x11 接收器 `0x69db14` 不会创建站点（`0x6a2fac` 返回 0）；其站点来自 `nn::ldn::GetNetworkInfo`（`0x6b43a8`），端口 12345。type-5 接收器 `0x6d7f8c` 仅当其地址在该节点列表中时才创建列出的站点（`0x6d840c`）（`0x6a8320`）；否则它不发送 type 6 并将其已应用序号重置为 0xffff（`0x6d81a4`）。Session type 9（`0x6d4ef0`），`09 | constant id | count | constant ids`，每 3000 ms 指定一个加入者尚未收到消息的站点（`0x6d4a60`）；房主的接收器 `0x6d940c` 将单个被指定的站点交给踢出作业（`0x6dc878`）。

主机加入后，团体战房主发送 packet id 0：已入座主机会丢弃更高 id 之后的内容（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）。站点列表的玩家 id 是匿名 `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）；随机 id 不会触发 type 6。

## 大厅

团体战消息是 0x80 端口 0 上的一条游戏消息（[连接交换](sv.md#the-trade)）：

| 字节 | 字段 |
|---|---|
| 0 | 处理函数键，u16 |
| 2 | 种类、步骤：一个 u16 消息 ID（0x012f 引导，0x0193 战斗开始） |
| 4 | 每发送方计数器，u16，由 `0xa583fc` 递增 |
| 6 | 压缩，u32：0 无，2 LZ4 |
| 10 | 有效载荷明文大小，u32 |
| 14 | 网络对象 ID，u16，除非 `0x14ede48` 找到一个，否则为 0 |
| 16 | 构造函数从不写入的两个字节填充 |
| 18 | 有效载荷 |

| 键 | 种类 | 说明 |
|---|---|---|
| 0x3380 | 0x2c | 团体战的描述符：物种（DevID）、形态、星级、太晶属性、性别、遭遇记录的编号 |
| 0x3380 | 0x2d | 参与者的状态：0x00 未准备，0x01 已准备，0x0c 主持人开局，0x0d 来宾的回应，0x18 正在进入大厅，0x1e 主持人拒绝过晚的站点（`0.30822`） |
| 0x3380 | 0x2e | 参与者的宝可梦，其加密的 344 字节队伍记录 |
| 0x3380 | 0x2f | 战斗引导 |
| 0x3380 | 0x30 | 大厅计时器，剩余秒数 |
| 0x0132 | 0x6e, 0x73 | 主机正在加载战斗，然后已加载 |
| 0x3480 | 0x93 | 战斗开始 |
| 0x007b | 0x13 | 主持人在 0x3480 之后发送的战斗开始消息 |

接收路径 `0x18bec54` 将头部复制到消息对象 `+0x40..+0x4f`，且不比较其中任何内容；它忽略 LZ4 返回值，只将明文大小用作输出容量。

键 0x007b 上的战斗开始帧是一个 12 字节的端口地址（三个 u32）、一个 u32 长度和有效载荷；有效载荷的前 32 字节是由 `0x1227714` 复制的头部：u32 类型 0x00、u64 0x08 和 0x10、u8 0x18 和 0x19，填充在 0x04 和 0x1a..0x1f。没有读取者比较这些填充（`0xf5a2fc`、`0xe10088`、`0xe0fd68`、`0xe106a4`、`0xf5a810`、`0xf5bc10`；18 字节头部的最后两个字节由 `0x18bece4` 存储在 `+0x4e`，仅由序列化器 `0x290b150`、`0x14c7904` 读取）。`0x14ab234` 会丢弃帧，除非某个接收端口注册了其地址：消息 15 的地址为 (0x2713, 1, 2)，消息 16 到 20 为 (0x2713, 3, 5)；0x2713 是 setup 的 u32 `+0x2c`。

战斗通过 `0xe0fd68` 读取消息 16（类型 0x46）：当 +0x08 处的 u64 为零时，按类型（`0xe10088`）进行分支，并且 `0x2897afc` 设置每帧更新 `0x289358c` 的对象（由 `0xfa4bb4` 用 `0x28950c8` 构建，存储在 `[sm+0x148]`）的 `+0x71`。当 `+0x71` 为 0 时，该更新会驱动读取器（`0xe0f014`）并调用 `0xfc363c([+0x48], 0)`；当为 1 时，每帧调用 `0xfc363c([+0x48], 1)`，直到其返回 true（`0x28935b8` 将其清除）。

团体战主持人在 0x7C 端口 1 上通告的频道表包含六个键：连接交换的四个（`0x007b`、`0x0132`、`0x0232`、`0x0332`）以及 `0x3380`、`0x3480`。零售版来宾先通告这四个，再在 0.79 秒后通告团体战的两个。端口 2 承载主持人的类型 6：类型 7 的会话块位于种类 5、容量 4 之下，然后是四个槽位，主持人的站点 ID 放在首位（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` 按顺序向一台主机释放主持人的消息，每条都在该主机上一步之后；`RaidGroup` 保存同一个大厅中各主机共享的内容：

| 序号 | 消息 | 释放条件 |
|---|---|---|
| 1 | 描述符（zlib，INITIALIZED） | 该主机的大厅宝可梦（0x2e） |
| 2, 3 | 状态 0x18，我们的宝可梦 | |
| | 计时器，每次减少时 | 从第一个主机回应后的 0.73 秒起，每秒一步 |
| | 状态 0x01 | 3.19 秒 |
| | 状态 0x0c，开始 | 一旦 `--raid-players` 个主机入座且均已发送 0x01，或计时器归零时 |
| | Net 0x50，属性状态 7 | 该主机的 0x0d |
| | 会话站点列表，下一序列 | 该主机的 Net 0x51 |
| | 引导，两个分片 | 该主机的类型 6 |
| | 已加载，`0x320173` | 该主机的 0x6e 或 0x73 |
| | 战斗开始，`0x803493` | 该主机的 0x73 |
| | 六条战斗开始消息 | 该主机的 0x93；然后是 0、0.10、0.12、0.16、0.18 秒 |

零售版主持人会开设一个 180 秒的大厅，并每秒发送一次计时器（`0.27104`）；pokeldn 主持人的计时器在第一个主机回应时从 180 开始。一个主机的 0x00 或 0x18 会撤回其 0x01。来宾会立即用 0x0d 回应 0x0c，无需 Ready 检查，且只有主持人能开始战斗（`Raid_Start_Ready`、`0.27137`）。在主持人端，`Raid_Start_Ready` 仅当每位来宾都已准备时才启用开始项；计时器归零时，如果没有任何已准备成员就解散大厅，否则开始战斗。`Raid_Start_Go`（`0.27140`）会重新发送 0x0c，直到每位成员都回应 0x0d，然后发送引导，槽位 *k* 存放代码为 *k* 的成员的宝可梦。

被门控的消息在其里程碑后 50 毫秒离开；Net 0x50 和站点列表每 0.5 秒重复一次，直到得到回应；团体战消息每 0.5 秒重复一次，直到被确认。Net 0x50 是交换主持人的属性主体，序列为 1，字节 27 设为 7，132 个应用字节位于 +38，在标志 0x31 下经过 zlib 压缩；未压缩时它不会引来 0x51。

在最后一台主机的消息 20 之后五秒，主持人会像要离开的零售版主持人那样把网络交给该主机（[docs/sv.md](sv.md#leaving)）：每秒发送 Session 类型 7，直到类型 8；每 0.5 秒发送表示正在迁移的 Net 0x11，直到 0x12；每 0.3 秒发送 NetStartHostMigration，最多持续 4 秒。绝不要转而销毁网络：零售版主机可能会在战斗开场时显示 2318-0006。

## 战斗引导

消息 0x2f 携带一个 0xaa0 字节的记录，经 LZ4 压缩（块格式，`pokeldn.sv.lz4`）：

| 偏移 | 大小 | 说明 |
|---|---|---|
| 0x000 | 4 x 0x158 | 四个参与者的队伍记录，已加密，主持人的在槽位 0 |
| 0x560 | 0x158 | Boss 的队伍记录 |
| 0x6b8 | 0x3e8 | RaidPoint |

序列化器 `0xe327fc` 从消息对象的 `+0x440`..`+0x458` 和 `+0x50` 写入五个记录（`0xe329b4`），然后从 `+0x58` 写入四个四字，并从 `+0x78` 写入 0x3c8 字节；`0x1592b7c` 选择压缩方式，`0x71d940` 运行 LZ4。RaidPoint 被整体复制（`0x1bae670` -> `0x1bae760`，getter `0x1baff98`）。零售版主持人会在 1395 字节处拆分该消息。

空的参与者槽位存放物种 0、等级 1、昵称为 `Egg`、太晶属性 19、语言 2、当前 HP 11 和能力值 11/5/5/5/5/5。绝不要发送全零的空槽位：零售版主机在战斗开始时会发生崩溃。

| RaidPoint 偏移 | 大小 | 说明 |
|---|---|---|
| 0x000 | 24 | 名称，ASCII，`RaidPoint_` 和一个后缀（接受 `RaidPoint_POKELDN_0`） |
| 0x018 | u32 | 0x40 |
| 0x020 | 4 x u32 | 星级、水晶（0 标准，1 黑色，[2 和 3 为活动](#event-raids)）、`captureRate`、`captureLv` |
| 0x030 | 7 x u32 | `raidTimeData`：激活、`gameLimit`、`clientLimit`、`commandLimit`、`pokeReviveTime`、`aiIntervalTime`、`aiIntervalRand` |
| 0x04c | 37 x u32 | Boss 的动作配置（`bossDesc`）：HP 系数、护盾的九个数值、六个额外动作（动作、时机、数值、招式）、双动作的三个数值 |
| 0x0e4 | 45 x 16 | 奖励行：道具、数量、稀有道具标志、主体 |
| 0x3b4 | u8 | 零售标准 RaidPoint 中为 0，黑色 RaidPoint 中为 1 |
| 0x3b8 | 7 x u32 | 星级、物种（DevID）、形态、性别、等级、0、太晶属性 |
| 0x3d8 | u64 | `randSeed`，伙伴种子（[伙伴](#partners)）和战斗种子（[战斗的随机数](#the-battles-random-numbers)） |
| 0x3e0 | u32 | `raidNpcGroupID`，主持人的团体战解锁阶段（[伙伴](#partners)） |

六星记录的 `raidTimeData` 为激活状态，`gameLimit` 为 450，`commandLimit` 为 60；一星记录为非激活状态，`gameLimit` 为 300，其余为零。当它处于非激活状态时，计时器初始化器 `C2D7F486425487755.F0C64BA9B6853E61A` 使用游戏限制 300、指令限制 60、复活时间 30、AI 间隔 17 和随机性 6。动作：0 无，1 重置 Boss 的能力变化，2 重置玩家的能力变化，3 使用招式，4 吸取太晶珠能量；时机：0 无，1 时间，2 HP；数值是触发该动作的 HP 或时间比例。在 P% 触发的 HP 动作会在 100 × Boss 当前的 HP / 其 HP 池（整数除法）的结果小于或等于 P 时触发一次：例如在 816 HP 中的 414 HP 时，50% 动作触发。一星到六星的 HP 系数分别为 500、500、800、1200、2000 和 2500。

零售版 RaidPoint 的奖励行由种子对应的固定行（subject = 表中的 `SubjectType`：0 所有玩家，1 主持人，2 来宾，3 一次）、subject 0 下的抽奖、subject 4 下的三次额外抽奖，以及 subject 5 下 Boss 的太晶碎块（数量为 `RaidGemItemRewardBoost` 的值，对一星到七星分别是 0、0、2、5、10、12、0，仅当为正数时）组成。奖励画面会首先列出稀有道具行。

Lua 奖励过滤器 `C07C34FC3B976E5A7.F316609DEA110601D` 会保留：subject 0 给所有玩家，1 给主持人，2 给来宾，3 给有资格获得一次的玩家；subject 4 的前 N 行，其中 N 是与 Boss 太晶属性匹配的激活中的 `Raid Power`（食物种类 5）的最高等级（太晶属性 18 匹配所有属性）；以及 subject 5，当玩家持有 `Glimmering Charm`（道具 2481）时。一个激活的食物加成是 u32 种类、u32 类型、u32 等级和一个表示剩余秒数的 f32（食用时为 1800）。这两个函数都位于 Lua 块 `be21e65463b9a98f` 中，SHA-256 为 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`。

`raid_point` 以相同方式构建奖励行；对于种子 7B741233 和 09F3E337，其 45 行与零售版 RaidPoint 的字节完全相同。被选定的奖励（`--raid-reward`）放在 subject 0 下，没有加成行。

## 伙伴

每台主机都会用相同的 NPC 训练家填满没有大厅成员占用的参加者栏位，这些训练家来自两个 RaidPoint 字段：`randSeed`（u64，位于 0x3d8）和 `raidNpcGroupID`（u32，位于 0x3e0）（`0.4453`；读取函数 `0x1be5ac0`、`0x1be5c20`）。零售版主机每次开始时都会抽取新的 `randSeed`（`Raid_Start_Go`，`0.27140`）。该 u64 种子会用 `0x82A2B175229D6A5B` 作为第二个字来初始化 xoroshiro128+（`0x17ebec0`）。接着抽取三名训练家（`0.7804`），每位训练家对池中还剩余的 n 个执行 `next_int(n)`（掩码到 n - 1 的位数，若结果大于等于 n 则重新抽取）并将其移除。空栏位按栏位顺序采用这些抽取结果（`0.4455`）。

一名伙伴的记录会从同一个 `randSeed` 中抽取五次，同一场战斗的所有伙伴共享此种子（`raid_partners.identity`）：加密常数（若为 0xffffffff 则重新抽取）、TID | SID << 16、PID（异色时翻转第 28 位）、身高和体重，每项为 `0x30 + next_int(0xa0)`。其余数据来自该训练家的条目，语言为 2，亲密度使用该物种的基础亲密度。绑定 `f92C18AA6`（`0x1905a10`）会构建一个以 `randSeed` 为种子的 pml InitialSpec（`0x1905ce0`，转换器 `0x160ffd0`，创建 `0xdef2b8`，抽取顺序 `0xdf011c`）；其第三个参数会使随机体型为 M 级（SizeType 3，`0x1611cc4`）。当 `sex` 为 0 时，如果该物种的雌性比例至少为 15，则为雌性，否则为雄性（`0x1611d1c`）。`gemType` 为 0 时，会从表 `0xe78418` 中获取太晶属性，键为物种 × 10000 + 形态。

池为 `world/data/raid/raid_trainer_01`（16 行，阶段 0 和 1）、`_02`（18 行，阶段 2）和 `_03`（18 行，阶段 3 和 4），字段 `difficulty_0`*N+1*（`0.7797`）。一行保存训练家 id `raid_assist_NPC_*`、`npcPresetIndex` 和 `nameTextLabel`；训练家的宝可梦是其 `trdata_array` 条目中的 `poke1`：特性槽位 1、2 或隐藏特性，三个招式，`gemType`，个体值 31/10/31/31/10/31，基础点数 252 HP、128 防御、128 特防，性格勤奋，精灵球，体型 128，无携带道具。`scripts/gen_sv_partner_data.py` 会将它们解码到 `pokeldn/sv/data/raid_partners.json`。伙伴的等级构建为 `int(0.8 × 战斗栏位 0 宝可梦的等级)`，也就是房主的宝可梦等级（`0.4455`、`0.4901`）。阶段 5 会给出以 Boss 命名的皮卡丘伙伴并导致崩溃，因此 `raid_point` 拒绝 4 以后的阶段。

## 种子

一场太晶团体战由一个 32 位种子和主机状态决定：版本、地区（帕底亚、北上、蓝莓，表前缀分别为 `""`、`su1_`、`su2_`）、剧情进度和结晶。xoroshiro128+ 从种子和常数 `0x82A2B175229D6A5B`（`0xe29340`）开始；第一次抽取（一百个值）会根据剧情阶段边界来挑选标准结晶的星数（黑色结晶固定为六星），第二次抽取在该星级和版本内按概率挑选遭遇。`0xe29404` 用 `%sdifficulty_%02d` 构建表名，并将记录传递给 `0x1eab5e4`，后者读取其 `raidEnemyInfo`；`0x2935b68` 会遍历全部三个前缀和六个等级。

然后，从同一种子新建的 xoroshiro 会抽取 Boss：EC（种子的低半部分加上 `0x229D6A5B`，因此 Boss 记录能反向给出其种子）、虚假的训练家 id、PID、完美个体值、个体值、特性、性别、性格（颤弦蝾螈的性格来自其形态列表）、身高、体重和体型，就像 PKHeX 的 `Encounter9RNG.GenerateData` 所做的那样；太晶属性和奖励抽选各自使用另一个新生成器。

`pokeldn.sv.raid_encounter` 基于 `pokeldn/sv/data/raid_base.json` 实现该过程；此 JSON 由 `scripts/gen_sv_raid_data.py` 根据 Tera-Finder 的遭遇列表和奖励表、PKHeX 的个人数据表以及游戏 RomFS 中十八个 `raid_enemy_XX_array` 表（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，带有自己的 `.bfbs` schema 的 FlatBuffers）生成。在超过 12600 个种子、每种上下文中，其生成的 Boss 都与 PKHeX.Core 26.8.26 逐字段相等，包括六个帕底亚遭遇（记录 5094 至 5099），它们的零售表给出太晶规则 0（该物种自身的属性），而 PKHeX 将其视为规则 1（任意属性）。结晶构建器 `0xe26ff0` 读取 `gemType`，对 0 和 1 均可抽取 18 种属性中的任意一种（`0xe27414` 处的 `cmp w9, #2`，会一直重新抽取直到值小于 18），和 PKHeX 一致；通用转换器 `0x160e108` 会将 0 视为该物种自身的属性，但它不在团体战生成路径上。由种子 `BD13FB43`（紫，帕底亚，四星）构建的 Boss 记录与零售引导程序（bootstrap）生成的逐字节相等；由种子 `7B741233`（朱，帕底亚，五星）构建的则与法语零售《朱》相等，但昵称和语言不同：零售版主机会写入自己的语言和该语言下的物种名称（`Embrylex`、3），而生成器使用英语（2）。无论哪种方式，主机都会以自己语言下的名称显示 Boss。

团体战表中的物种使用的是游戏的 DevID：916 号前为全国图鉴编号，从 917 开始使用游戏自己的顺序（Tinkatink 的 957 是 1000），表现为 `gen9.internal_index`。描述符和 RaidPoint 也带有 DevID：一台零售《朱》在显示描述符和 RaidPoint 时列出了物种 1000，并且实际对战的是小锻匠。黑色结晶记录的战斗等级为 90，带有基础点数（例如 128 防御和 128 特防），捕获等级为 75；标准记录的两个等级一致，且基础点数为零。引导程序的 Boss 记录和 RaidPoint 摘要携带战斗等级和基础点数，RaidPoint 的 `+0x2c` 携带捕获等级：由 `09F3E337`（朱，帕底亚）构建的黑色 Boss 与法语零售《朱》相等，但昵称和语言不同。

## 活动团体战

宝可入口站新闻发布包含 `raid_enemy_array`、`fixed_reward_item_array`、
`lottery_reward_item_array`、`raid_priority_array`（基础表布局中的 FlatBuffers）和
`event_raid_identifier`（一个 u32，等于优先级表的 `VersionNo`）。后来的发布会在补丁后缀
（`_1_3_0`、`_2_0_0`、`_3_0_0`）下重复每个文件；读取最新的。记录会添加
`RomVer`（0 双版本，1 朱，2 紫）、`DeliveryGroupID`、`Difficulty`（七星为 7）、
`CaptureRate`（0 从不，1，2 每个存档一次）及其自身的报酬表；其 `BossPokePara` 固定如下：

| 字段 | 活动记录 |
|---|---|
| `Sex` | 0 随机；1 雄性，2 雌性，不随机 |
| `Seikaku` | 0 随机；性格加 1，不随机 |
| `TalentType` | 1：`TalentVnum` 完美个体值；2：`TalentValue` 的六项个体值，不随机 |
| `RareType` | 0 随机；1 永不异色（位 28 翻转）；2 总是：PID 高半部分重写为异色 xor 0 |
| `ScaleType` | 0 两次抽取；1 至 5 在 0-15、16-47、48-207、208-239、240-255 中一次抽取；6 `ScaleValue` |
| `Item`、`EffortValue` | 头目的携带物品和战斗基础点数 |

`TimeDesc` 是记录的 `raidTimeData`（RaidPoint 0x030）：在每一条七星记录
（`gameLimit` 450 至 900，`commandLimit` 60）和五条五星记录上激活。

巢穴属于发布组，编号 1 至 10。来自种子的 xoroshiro 会抽取并丢弃标准星级的掷数，
然后抽取一个数值，该数值小于该组中符合主机版本与允许星级记录的总概率，并取涵盖
该数值的记录 [PKHeX `EncounterDist9.GetIsPossibleSlot`]：

| 进度 | 阶段 | 抽取的星级 |
|---|---|---|
| 初始，太晶团体战 | 0 | 1、2 |
| 3 星 | 1 | 1 至 3 |
| 4 星 | 2 | 1 至 4 |
| 5 星、6 星 | 3 | 3 至 7 |

概率为 0 的记录永不被抽中。报酬先是记录的固定表，再从发布表进行抽奖抽取
（七星按六星计）。空或数量为 0 的抽奖栏位不会给出任何东西；索财灵的第一次
朱版活动只有此类栏位。

`pokeldn.sv.raid_event` 读取发布文件夹（一个 [EventsGallery](https://github.com/projectpokemon/EventsGallery)
活动或其 `Files`）：

    ./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
        --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
        --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]

RaidPoint 携带记录的捕获率，并且作为水晶，活动为 2，七星活动为 3
（Tera-Finder `RaidContent`）。应用的太晶团体战（主持）工具会下载图库，
并根据活动生成的内容缩小版本、进度和水晶范围
（[团体战活动](gui.md#raid-events)，`raid_event.dens`）。

捕获率为 2 表示每个存档只能捕获一次。存档会列出已捕获的记录号
（块 `0x8B14392F`；已击败标志 `0xA4BA4848`，PKHeX `RaidSevenStar9`），并且
重跑共用同一编号，因此一次捕获即结束所有轮次。主机根据大厅描述符中的记录号
检查列表；只要该编号已在列表中，无论 RaidPoint 携带的捕获率如何，都会阻止捕获。

`--raid-catch-normal` 会将捕获一次记录作为普通捕获提供：捕获率为 1，
并在描述符中使用替身记录号，即该记录日期加后缀 99（`raid_event.stand_in`），
任何发布都不会使用该编号，捕获后存档也不会列出它。任何 PK9 字段或 PKHeX
遭遇都不保存记录号，因此合法性不依赖于它；主持者发送的头目与 PKHeX 在
331 个捕获一次团体战中捕获该团体战的结果一致。七星捕获只有在带有最强之证
时才合法，该证章由主机授予。

固定行的 subject 3（七星招式学习器和特性膏药）由每个主机的报酬筛选器应用。
团体战头目以外的物种数据来自 `pokeldn/sv/data/species.json`
（`scripts/gen_sv_species_data.py`）。在 EventsGallery 的 153 次发布中，
pkNX 的遭遇与 PKHeX.Core 26.8.26 的遭遇一致，生成的 20 080 个头目与
PKHeX 的 `GenerateSeed32` 一致，且 `scripts/check_sv_raid_events.py` 与每个
`Encounters.txt` 一致。

## 寻找种子

应用的团体战种子字段会显示该种子在工具上下文中给出的头目和报酬，而
“寻找团体战”会从输入或随机选取的第一个种子开始，在筛选器保留的每个上下文
（`pokeldn.sv.raid_search`）中搜索满足物种、星级、太晶属性、性格、性别、
异色、尺寸证章和个体值范围的种子。它会按头目能力值评分（HP 乘以两防之和、
任一防御单独、其较强攻击能力值或总能力值）或按想要的报酬（下方
“最想要的报酬”）对结果排序。除非选择了某个物种，否则每个物种只保留一个结果。

### 尺寸证章

PKHeX 允许在体型值为 0 时获得小不点之证，在 255 时获得大个子之证
（`MarkRules`）；搜索器的尺寸证章筛选器想要其中之一。体型值在身高和体重之后抽取：

| 体型规则 | 体型值 | 得到 0 或 255 的几率 |
|---|---|---|
| 两次抽取（规则 0），每个普通和黑色头目 | `next_int(0x81) + next_int(0x80)` | 各为 1/16 512 |
| 从 0（规则 1）或从 240（规则 5）开始的活动区间 | `next_int(16) + low` | 触及端点时为 1/16 |
| 活动自身数值（规则 6） | 记录的 `scale` | 总是或从不 |

`raid_search.size_marks` 会列出活动头目可能获得的证章名称；搜索器会将其他证章灰显。

### 想要的报酬

报酬部分需要物品行以及团体战必须给出的该物品最低数量，同一物品的数量会加总。
提供的物品和数量是所搜索的团体战能够给出的（`raid_search.reward_choices`）。
搜索会跳过无法给出所需物品的遭遇，然后在抽取头目之前先抽取种子的报酬。

“最想要的报酬”会按想要物品的顺序对结果排名。团体战某物品的总数作为一个数位，
其位置在搜索的团体战可给出的总数中（`raid_search.ranked_rewards`）；靠前物品的
数位组成一个小于 2^31 的分数，以 64 位排名保存在种子旁。五个物品可容纳进所有
已知团体战。

### 助手的扫描

PKHeX 助手会在每个核心上扫描种子（`services/pkhex/RaidScan.cs`，由
`pokeldn.sv.raid_scan` 驱动）：遭遇、头目直到体型值、评分、筛选器和报酬。
它会指出某上下文的最佳种子，而 `search` 会在 Python 中重建它们的团体战，
因此结果和并列情况与 Python 扫描一致（`tests/test_sv_raid.py` 对两者进行比较）。
每个遭遇行的最佳可能排名在每次请求时计算一次；某行的种子若无法超过已保留排名，
就会在此停止。

一次请求包含 16 777 216 个种子，随后助手在约 0.25 秒内扫描的数量最多为
268 435 456 个。搜索每个上下文最多覆盖 2^32 个种子（`most_seeds`）；
搜索器提供一亿个或全部种子。在第一个匹配处停止（`stop_at_first`）会返回
最早匹配的种子。没有助手时，Python 每秒扫描约 22 000 个种子，搜索器提供
100 000 个。

| 搜索，Apple M4，助手已预热 | 时间 |
|---|---|
| 默认搜索器在 42 个上下文的每个中搜索 1 亿个种子 | 5.2 秒 |
| 一个上下文的全部种子 | 6.1 秒 |
| 42 个上下文的全部种子 | 4 分 3 秒 |

## 主机之间的对战

在模拟的两台《朱》4.0.0 之间测量：一台主办 4 星结晶，一台通过宝可入口站加入，两个空位是 NPC 伙伴。主办方主机在整个对战中始终留在会话里。每条战斗消息都是 key 0x007b 上的战斗开始帧，地址为 (0x2713, x, y)，其 32 字节头部：类型在 +0x00，u64 步数计数器在 +0x08，u64 回合数在 +0x10，然后是 +0x18 和 +0x19 处的 5 和战斗者/站位字节：

| 类型 | 来源 | 大小 | 内容 |
|---|---|---|---|
| 0x01, 0x05, 0x11, 0x15, 0x25, 0x29, 0x47, 0x49 | 房主，地址 (0x2713, 1, 2) | 50 到 20626 | 一步；每台客机在相同计数器下应答 type + 1 |
| 0x02, 0x12, 0x16, 0x26, 0x2a, 0x48, 0x4a | 每个站位，地址 (0x2713, 3, 5) 或 (0x2713, 2, 2) | 50 | 对一步的应答 |
| 0x06 | 站位为它自己的战斗者；房主为自己、每个 NPC 以及再为客机各一条 | 250 | 一个战斗者的指令；+0x19 是战斗者槽位（0 房主、2 客机、3 和 4 NPC） |
| 0x15 | 房主，每个行动的战斗者一条，包括 boss | 20626 | 该回合：+0x20 处五个 0x70 字节行动块（槽位 0 房主、1 boss、2 客机、3 和 4 NPC），+0x250 处每槽位一个字节，表示其块中行动数量（[行动](#actions)），+0x258 处服务器指令队列长度，队列从 +0x25c 开始；压缩后 123 到 802 字节 |
| 0x46 | 房主，开始时 62 次 | 54 | |
| 0x51 | 房主 | 86 | |

该对战是服务器/客户端结构。房主的构建器 `0x113c8a0`（类型 0x15 在 `0x113c908`）复制行动块、运行回合（`0x113e3d0`）并追加它生成的服务器指令队列；房主的 AI 生成 NPC 的指令，而 boss 的行动只通过 0x15 到达客机。客机播放该队列，并且对于类型 0x13、0x15、0x17、0x19、0x1f、0x23、0x25 和 0x4d，它会用同一个构建器根据房主的行动块重建正文，并比较大小和字节（`0xf5cfa4`）；不匹配则转到 `0xf5bfd4`，即接收超时处理器。主办一场对战的站位必须生成 Scarlet 自己的引擎在相同状态下生成的队列。

### 哪个站位运行服务器

对战服务器是每台主机根据大厅房主的 Session 类型 6 和类型 9 构建的 port-2 成员列表中的第一个条目；`pokeldn.sv.port2.build_session` 将房主放在第一位。

| 步骤 | 代码 |
|---|---|
| 团体战开始 `0.4455` 将服务器槽位设为 0：`setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`，setup `+0x94` |
| 成员 i 映射到槽位 0、2、3、4；其代码放到 `+0x99+slot`，对于自己的代码，槽位放到 `+0x90` | `0x1ccd15c` 遍历 port-2 `+0x170`；`0x2d363a0`、`0x130ea2c` |
| `0x2a1cd74` 在对战开始时将 setup `+0x94` 复制到 `net+0x58`，将 `+0x90` 复制到 `net+0x5c` | 来自 `0x18915c4` |
| 当 `!setup.710 && slot == net+0x58` 时该主机是服务器 | net vf `+0x78` = `0x2a1d994` |
| 0x15 检查器只安装在非服务器上 | `0xfb0ee8` |
| 接收超时或检查失败会调用 net vf `+0x70` = `0x2a1d920`；在团体战中 `0x18e217c` 将 `net+0x58` 设为该主机自己的槽位 | `0xf5bfd4` |

Setup `+0x710` 只由 `0x7faed0`（Lua `f3AF42713`）设置，团体战开始绝不会设置它。失去服务器的主机会把自己设为服务器，因此当大厅房主停止发送时，每台主机各自进行自己的对战。成员向量是只追加的，由类型 6 或 7 会话块（`0x18b566c`，先追加）、类型 6 重放（`0x279ba2c`）和类型 9（`0x1954bac`）通过 `0x18b65c8` -> `0x18b68fc` 写入；在任何块之前的类型 9 会被丢弃（`0x18b65e4`）。Bootstrap 参与者 k 属于代码为 k 的成员；指向空参与者的成员代码会中止加载（2162-0001）。故障转移后的主机用其自己的 AI 运行其他所有战斗者（`0xfa52b0`、`0xfa5314`）。其代码是第一个带有其站位的向量条目的代码（`0xd5f3b4`）；Lua 槽位循环没有 break，所以最后一个匹配条目设置其槽位。

### 对战的随机数

一轮中的每次随机抽取都来自一个 0x28 字节的 xoroshiro128+ 对象（vtable `0x4500bd0`）：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x00 | 8 | vtable |
| 0x08 | 2 x u64 | 状态 |
| 0x18 | u64 | 种子 |
| 0x20 | u64 | 已抽取次数 |

服务器主模块（0x378 字节，构造函数 `0x12742d0`）将它放在 `+0x10` 处；回合代码通过 `[[x+0x10]+0x10]`（`0x11440e8`）访问它。该模块的初始化器 `0x127d824` 将状态设为种子和 `0x82A2B175229D6A5B`，将计数设为 0（`0x127d9a8`），种子取自其参数块的 `+0x20`。客机的检查器从对战设置的 `+0x718`（`0x2891748`）填充该字；团体战开始 `0.4455`（@1152..@1157）通过 Lua 绑定 `fAF4A81E0`（设置器 `0x7faf1c`）把 `+0x718` 设为 RaidPoint 的 `randSeed`。伙伴种子也是对战的种子，写入 bootstrap 的站位会选择它。服务器构建的每槽位模块（`0x126ba88`，来自 `0xfa9f90`）用种子 0 初始化。

一次抽取会将 `s0 + s1` 相加并推进状态；计数每次调用增加一，而不是每次重抽增加一：

| 函数 | 抽取 |
|---|---|
| `0x11440f0(rand, n)` | 一个小于 n 的 u64：将 `s0 + s1` 按 n − 1 的位掩码，结果大于等于 n 时重抽；n 小于 2 返回 0 且不抽取 |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f`，结果大于等于 100 时重抽；结果小于 p 时为 true |

许多回合函数内联推进状态，而不是调用这些函数。

### 每招式的伤害与抽取

一次招式使用按以下顺序抽取：

| 抽取 | 条件 | 决定内容 |
|---|---|---|
| `chance(25)` | 使用者麻痹时 | 完全麻痹 |
| `chance(33)` | 使用者混乱时 | 击中自身，其掷骰是 `below(16)`，并代替该招式的抽取 |
| `chance(accuracy)` | 招式有命中率；100 仍会抽取 | 命中 |
| `below(24)`, `below(8)`, `below(2)` | 伤害招式，按会心等级 0、1、2 | 结果 0 时造成会心一击 |
| `below(16)` | 伤害招式 | 掷骰 r：伤害乘以 (100 − r) / 100 |
| `chance(p)` | 概率为 p 的追加效果（泰山压顶的 30） | 该效果 |

对 boss 的畏缩追加效果不抽取（[回合队列中的招式](#a-move-in-the-round-queue) 有该规则）。混乱追加效果会在其 `chance(p)` 之前通过一次 `below` 和 `chance` 之外的调用推进生成器一次：在记录每次抽取的 20 场混乱抽取中（念力、幻象光线、水之波动、怪异蒸汽、魔法转矩），无论该步输出如何，都是如此。命中的混乱不抽取持续时间。100% 的降低能力追加效果（灵魂冲击、重踏）在某些回合中抽取 `chance(0)`，在另一些回合中不抽取。速度相同的战斗者在速度排序中会抽取 `below(2)`（[速度并列](#speed-ties)）。对 boss 或拥有精神力（特性 39）的目标，畏缩追加效果不抽取；对已经在本回合行动过的玩家，它会抽取其 `chance(p)`，并且在那里命中的畏缩不会向队列添加任何东西。接触招式命中静电、毒刺、火焰之躯或迷人之躯（特性 9、38、49、56），或者使用者拥有毒手（143）时，在招式的追加效果之后抽取 `chance(30)`。在记录每次抽取的 156 场 oracle 对战中，插件构建的每个回合的抽取都与记录一致。

一场对战会在其第一个回合前抽取一次 `below(100)`。伤害使用 Showdown 的 Gen 9 公式（数据来自 Pokemon Showdown 的 `moves.json` 和 `typechart`），采用队伍记录的能力值，并且 boss 仅按太晶属性防御：在能力等级变化前，对 boss 的 1346 次命中有 921 次符合该公式；在记录每次抽取的 140 次命中有 137 次，记录到的骰数和会心抽取给出了记录的伤害。不符合的命中发生在 boss 的护盾期间（约为公式的 0.45）、来自有自身规则的招式（扑击、高压电场、多段招式）或被限制在剩余 HP 处。

boss 的 HP 池是其记录的 HP 乘以 RaidPoint 的 HP 系数再除以 100（[对战 bootstrap](#the-battle-bootstrap)）：在获胜的 oracle 对战中，一星 78 场、二星 84 场、三星 125 场、四星 35 场分别在 `0x37 (2, 2, damage)` 中记录到恰好 5、5、8 和 12 倍记录 HP 后结束；其余则因护盾和自身规则招式造成更少的伤害。

### 速度并列

对战使用交换排序按速度对战斗者和行动排序：每个条目与后面每个条目比较，当后者的键更大时后者移到前面。键相等时抽取 `below(2)`，抽到 1 将后者移到前面，因此两个并列条目每次比较抽取一次。战斗者 id 为 1 到 5，boss 为 2。在强制两个战斗者速度相同的 142 场 oracle 对战中，按 id 顺序对五个战斗者的排序在 142 场开始时给出的抽取次数与记录一致。

| 时机 | 按此输入顺序排序对象 | 排序次数 | 读取结果者 |
|---|---|---|---|
| 战斗开始时，在 Trace 的抽取之前 | 五个战斗者，id 顺序 | 1 | 换入事件 |
| 回合开始时 | 回合的行动，指令顺序；键为优先级、其次非 Stall、再速度 | 3，每次排序基于前一次结果 | 第一次：第二次 `0x51` 传递；第三次：招式顺序 |
| 除最后一招外，每招之后 | 行动 | 1 | 队列中无 |
| 回合结束时 | 五个战斗者，每次按 id 顺序 | 3 | 第二次：`0x43` |
| 轮次结束时（每四个回合） | 五个战斗者，每次按 id 顺序 | 8 | 第四次和第五次与 `0x19` 一致；第七次：`0x43` |

回合结束 `0x43` 的顺序在 123 场对战的 109 场中与第二次排序一致；其余 14 场有战斗者的速度在该回合被招式改变。链式行动排序在 27 个有两个行动者并列的回合中，与 `0x51` 和行动顺序一致；第一次行动后的抽取在 3 个进行到两个行动的回合中，3 个都出现了。轮次结束顺序在 8 个排序有分歧的轮次结束中 8 个都一致。

boss 的 Trace 会按 id 顺序对能复制其特性的玩家抽取 `below(N)`：若有一名玩家拥有 Embody Aspect，则为 `below(3)`。对硬壳盔甲（特性 75）使用的招式不抽会心判定。

一个伤害招式若目标的属性免疫，则没有任何效果，甚至不消耗命中率，并运行

0, 0, 0, 0, 0)`、`0x7e (1, 0, 0, 0, 0, 0)`、`0x7e (2, 7, 7, 7, 7, 7)`、`0x8b (A's position, T's position,
M, type, 0, 0, 0, 0, class, 0)`（若招式作用于自身则 T 为 A，class 为 7）、能力变化，然后 `0x7c ()`、

(b, stat, n)`、`0x92 (b, stat, n, 0)` 和 `0xcb (b, text, b)`；下降是 `0x0d (b, stat, n)`、`0x93 (b,
stat, n, 0)` 和 `0x0cb (A, text, b, stat)`。text 为提升 1、2 或 3 级时是 10、17 或 24 加上能力值；下降 1 或 2 级时是 31 或 38 加上能力值（能力 1 攻击到 7 闪避），覆盖 oracle 语料库中的每次能力变化。一个必中招式（Showdown 命中率 `true`）不消耗命中率。

一个范围招式（Showdown 目标 `allAdjacent` 或 `allAdjacentFoes`）只命中其指令指定的位置，伤害按单体目标计算且无范围修正：oracle 语料库中每个包含一个的回合都与单体目标命中构建得相同，`class` 为 4 或 5。招式按优先度档位顺序运行，然后按能力阶段修正后的速度：boss 的水流喷射或影子偷袭会在速度更快的玩家之前行动。

一次将 boss 击倒的命中会赢得战斗。在其 `0x42` 之后是 `0x49 (2, A, M)`、`0x09 (A, 0)`、
`0x37 (2, 1, 1)`、`0xcb (2, 0, 2)`、`0x94 (2, 0)`、`0x37 (2, 8, 1)`、`0x5f (2)`、`0x62 (2)`、`0x6c (2)`、
`0x5d (2)`、每个玩家按 id 顺序一个 `0x41 (b, 2)`、k 从 0 到 13 除 8 外的 `0x33 (2, k)`、`0x80 (2)`、
`0x29 (2)` 和 `0x38 (A)`，然后是招式通常的结束。之后没有其他对战者行动，回合结束只包含仍站着的对战者的 `0x43`、`0x23` 列表和 `0x2d (0)`。`0x85 (7, damage)`
和伤害命令携带 boss 剩余的 HP。

前缀始于 `0xb5 (0)`，然后对回合的行动者按 id 顺序运行一次 `0x51 (b, 1)`，再按他们行动的顺序运行一次；在第二轮中具有慢出（特性 100）的对战者最后行动并携带 `0x51 (b, 0)`。一个选择了注册自身处理器的招式的对战者在每次运行后添加 `0x5a (b, M, speed)`（speed 为其能力阶段速度）
和 `0x5b (b, M)`，按该运行顺序，然后再按行动顺序两次。在第一个对战者之后每个对战者行动前，每一个这样的对战者再重复这对一次，而一个行动者若其招式注册了处理器，则在其 `0x05` 之前添加 `0x5a (b, M, 0x72000 + speed)`。631 个招式中有 347 个注册了一个（硬撑和泰山压顶在其中，暗袭要害不在）。

boss 从一开始就太晶化：其太晶属性且基础威力低于 60、无优先度且单体命中的伤害招式按 60 威力命中，此为第 9 世代的太晶规则（一只迷你芙的太晶一般撞击造成 4，而 40 基础威力则应为 2）。招式的每个附加效果按 Showdown 的顺序各消耗一次 `chance(n)`，但对 boss 的畏缩除外，它不消耗任何：玩家对 boss 的冰冻牙只消耗其冰冻几率（冰冻显示为 `0x13 (2, 3, 0, 1, 4)` 并带消息 97 和 98，boss 在行动前消耗 `chance(20)` 解冻），boss 对玩家的冰冻牙则两者都消耗。将 boss 击倒的命中先消耗 `chance(0)`，无论有无附加效果。

按此方式从 Showdown 的招式数据和第 9 世代伤害公式构建，554 场 oracle 战斗中有 56 场的第一轮与 oracle 逐字节相等，其余无差异（其他场次包含某些被拒绝的内容）；
20 场整场战斗在每一轮都与 oracle 相等，并在与脚本控制台对战时 19 次中 19 次在每一帧都发送与 oracle 服务器相同的帧。
当一名行动中或被击中的对战者持有的特性或道具其 Showdown 回调可能改变回合时（活力的攻击、斗争心的威力、友情防守的 0.75、恶属性命中后胆小的速度提升、疾风之翼的优先度），除非语料库测得该特性或道具闲置，或者战斗中持有在换入时生效的特性（威吓在第一轮前降低攻击者的攻击），该回合会被拒绝。

### 战斗开始正文

消息 0x11 的正文是一个没有长度字的命令队列（[服务器命令队列](#the-server-command-queue)）。战斗者 ID 为：槽位 0 是 1，头目（槽位 1）是 2，槽位 2 是 3，槽位 3 和 4 是 4 和 5；战斗者位于 id − 1 的位置。该正文按 ID 顺序将各战斗者派出，然后运行入场事件，最后以 `0x2b (0)` 结束：

| 命令 | 说明 |
|---|---|
| `0x3d (pos)`、`0x16 (pos, 0, 0, 0)`、`0x5e (id, ability)`、`0x61 (id)`、`0x6b (id)`、`0x4e (id)` | 派出一名战斗者；`ability` 是其特性 ID |
| `0x25 (id)`、`0xc7 (id, 0)`、其效果、`0xc8 (id)` | 一次特性的发动 |
| `0xcb (id, text, params..., 0xffff0000)`，用零填充至 10 个参数 | 一条战斗消息 |

| 入场事件 | 效果 |
|---|---|
| 压迫感（46） | 围绕 `0xcb (id, 162, id)` 的发动 |
| 威吓（22） | 每个目标的发动围绕 `0x0d (target, 1, 1)`、`0x93 (target, 1, 1, 0)`、`0xcb (id, 32, target, 1)` |

| 紧张感（127） | `0x25 (id)`、`0xc7 (id, 127)`、`0xca (id, 679, side, 0xffff0000)`、`0xc8 (id)`，在所有其他事件之前；`side` 为 1 表示玩家的紧张感，为 0 表示头目的 |

### 服务器发送的消息

服务器发送的每条消息都是 `0x113bad8(server, kind, destination)` 的一个步骤：

| 步骤 | 代码 |

| 2 | 护盾结束（`0xf6f87c`，`0xf70010` 对照 +0x18） | 1 |
| 3 | 当时间检查发现剩余 10% 或更少时，`0xf6dd84` | 1 |
| 4 | 六个额外行动（`0xf6fa5c`：种类、时机 1 时间 / 2 HP、阈值、招式在 +0x24 + 8i），各一次（记录 +0x86 + i） | 行动的索引 |
| 5 | 双行动（`0xf6de7c`）：HP 达到或低于配置 +0x54 | 0 |

值为 0 的双行动会在一次攻击使头目的 HP 份额留在 0（2/2 场全零配置的 oracle 战斗），并且在该招式与下一招式之间触发。它们都不抽随机数：每个触发都是对头目 HP 份额或剩余时间的阈值（战斗计时器上的 `0xf91070`）。作为请求块行动（`0x114fb2c`），该字的种类为 12，位 4..11 为列表的种类，位 32..47 为其值，执行者为太晶团体战战斗者的 ID（`0x114fc70`）。

在一回合中，空列表从 HP 触发器（`0x11425b0`）填充；若其中没有护盾，行动在该回合运行（`0x1145be0`）。一回合后，结果的字节 `0xc4a5` 选择下一步骤；当构建器的 `0xc4a4` 置位时，ServerCommand（`0x16e4f6c`）改为传递 8，太晶团体战行动按原样传递该字节（`0x16e4ff0`，跳转表 `0x3c61c38`）：0 表示无，4 表示空回合（`0x16e5cac`），6 表示该回合的列表持有护盾（`0x16e5ad0`），7 表示战斗结束（[战斗结束](#the-battles-end)）。一次太晶团体战行动（`0x18c92a8`，负载由 `0x17b5f3c` 复制）按四个状态运行：

| 状态 | 服务器 |
|---|---|
| 0 | 向每个站发送消息 0x47；以原因 0 暂停战斗计时器（`0x18c9a68`） |
| 1 | 等待直到每个已入座槽位都发送了该步骤的消息（`0xe63380`） |
| 2 | 一个请求块，其槽位 1 持有这些行动（计数字节 +0x231）；战斗计时器以原因 0 恢复（`0xe63ac4`）；该块作为一回合（0x15）发送 |
| 3 | 该回合结果中的下一步骤，列表清空（`0xfaf024`），每个槽位的 0x47 及其应答 0x48 被擦除 |

没有护盾的列表从状态 2 开始。逐帧状态机在头目列表为空时，在一份列表副本上检查配置的时间触发器（`0xf6d62c`）；当某个触发器触发时，它把副本作为消息 0x51 发送（`0xf71b74`）。0x51 通过服务器自己的槽位回到状态机并填充其列表（[服务器的流程](#the-servers-flow)）；持有行动的状态机列表会发出太晶团体战行动（`0xf6d8d4`）。

一次太晶团体战行动的回合队列，覆盖 oracle 语料库的 547 个此类回合：`0xb5 (0)`、`0x51 (2, 1)`、`0x85 (kind, x)`、`0xc1 (kind, y)`、行动效果、`0xb2 (0)`、`0x37 (2, 7, 1)`（在一招或一次能力等级重置后出现两次）、`0xc5 (1)`、`0x43`、`0x23 (2)` 和 `0x2d (0)`。对于额外行动，`x` 是其索引（213/213），`y` 是配置行动的种类（1 到 4）；种类 3 的 `x` 和 `y` 为 0 且没有效果命令（121 回合）；护盾开始的这两项都等于其值（值为 0 的有 95 个，其余为计时器的值）。重置玩家能力等级变化的额外行动，在它对每个清零的玩家执行 `0x10 (b)` 和 `0x13 (b, 16, 0, w, 2)` 之后，以 `0xc2 (60, 2, 0)` 结束其效果；重置头目能力等级的则以 `0x0f (2)`、`0xc2 (3, 2, 2)` 结束。

### 战斗计时器

战斗计时器是服务器上下文 +0x38 处的一个 0x28 字节对象（逐帧状态机的以及每个 job 的 `[+0x40]`，它在 +8 处还保存 N，在 +0x10 处保存服务器模块，在 +0x18 处保存服务器）：

| 偏移 | 字段 |
|---|---|
| +0x00 | u64 start，`nn::os::GetSystemTick` 的纳秒；暂停时为 0 |
| +0x08 | 上次暂停前累积的纳秒 u64 |
| +0x10 | 上次暂停的时间 u64 |
| +0x18 | u8 已启动 |
| +0x19、+0x1a | u8 暂停原因；两者都为 0 时计时器运行 |
| +0x20 | 创建时使用的限制 |

| 事件 | 代码 |
|---|---|
| 创建、启动并立即以原因 0 暂停，当限制 N+0x8a 不为 0 时，随战斗的第一个 job 一起 | `0xf70864`、`0xf70a58` |
| 当 Wild::Setup 结束时以原因 0 恢复（从未启动的计时器在那里启动） | `0x2a1fbfc`、`0xe63a6c` 的步骤 |
| 从太晶团体战行动的消息 0x47 到其回合，以原因 0 暂停 | `0x18c9a68`、`0xe63ac4` |
| 读取：限制加上 `[[module+0x1b0]+8]` 处的 i16，减去自启动以来经过的整秒和累积的整秒；暂停时，为限制减去累积秒数；限制为零时为 1 | `0xf91070` |

逐帧状态机只有在计时器已启动（+0x18）且设置 +0x499 位 2 置位时才检查时间触发器（`0xf6d538`）。时间为 P 百分比的触发器在 100 × 剩余时间 / 限制（整数除法）小于或等于 P 时触发：在 300 秒计时器上，80% 触发器在剩余 242 秒时触发，即经过 58 秒运行时间之后。在下文服务的战斗中，计时器在最后一个站对消息 0x11 的应答到达服务器时启动，而 80% 行动在 58.1 秒后发出。

### 战斗结束

在一回合结果字节为 7（`0x16e4ff0`）之后，服务器执行：

| 步骤 | 代码 |

| 按设置 kind +0x30 选择退出消息：kind 0 中结果 1 为 0x29，0 或 2 为 0x2b，6 为 0x2d；kind 1 为 0x31，2 为 0x33，3 为 0x2f | `0x1882b14` |

| 当设置 +0x498 位 0x400 且为 0x29 时，RaidCapture：消息 0x49 | `0x186d680`、`0x1934808` |

joins (written only via message 0x1d, which a raid never sends). The judge `0xe7d58c` counts each
side's able members (side by battle mode, table `0x3c6a450`); the first deciding test gives the winner:

| 测试 | 代码 | N+0x94 |
|---|---|---|
| 有 setup +0x49c 第 1 位时：一方有可战斗成员则为第 1 方，否则为第 0 方 | | 0 或 1 |

### 战斗计时结束

At the top of each frame the per-frame machine (`0xf6d538`) reads the battle timer (`0xf91070`); a
result of 0 or less takes the time-up branch `0xf6d830`:

| step | code |
|---|---|
| result 0 with N+0x94 = 2 kept in N, unless a result is already there | `0xe7d570(N, 0, 2, 0)` |
| the 0x29 body at server+0x208: N's slot, the outcome (`0x166882c`), N+0x94 | `0xe7d4c8` |
| a raid (setup +0x499 bit 2): ExitBattleEnd with message 0x2b | `0x201602c` (hash `0x2da7b4584624a364`, constructor `0x1882dbc`) |
| otherwise: AddExpBattleEnd with kind 0 | `0x16e5230` (hash `0x23607a0597b3a656`) |

机器仅在没有任何作业运行时才运行，因此在一个回合期间耗尽的计时器会在作业结束后才被看到。团体战时间到不会发送 0x25：先进行首领的最后一个限时回合，然后发送 0x2b，正文为 `00 00 00 00 02 00`，随后是 0x35 和 0x37（[战斗结束](#the-battles-end)）。首领获胜的团体战也以相同方式结束：每只濒死的玩家宝可梦会使计时器减少 75 秒（`[[module+0x1b0]+8]` 处的 i16）。

|---|---|---|
| 0x21 | 濒死槽位，仅标头 | 当该槽位没有可战斗成员时；其应答 0x22 会启动 reader 的计时器（reader+0x50，限制来自 `0x1ffe4e8`） |
| 0x23 | 每个槽位，20608 字节 | 当该计时器耗尽时（`0x2016bc8`，该槽位单个动作的 kind 0x23 块，kind 8），由 kind 35（`0x1153350`）构建：HP 恢复（`0x288cde8`），命令 3（battler，HP），成员被送回场上（`0x2887044`，`0x11482a0`：命令 0x98） |

### 服务器流程

在主机上，这些步骤是作业：Wild::Setup、ServerRequest（`0x138d178`，向一个槽位发送消息 5）、
ServerCommand（`0x16e4f10`，一个作为一轮的已发布请求块）、RaidAction 和战斗结束。
Wild::Setup（`0x2a1f54c`，跳转表 `0x3c61c1e`）发送消息 1，等待所有应答，发送 0x11，
等待，清除每个槽位发送的内容（`0xe0f5f8`），仅当启动标志 [[o+0x40]+0x28] 为 1 时发送消息 3
（仅由 `0x2840fac` 设置；团体战会使其保持为 0），并启动战斗计时器。团体战的 setup +0x30 为 kind 0。
每帧状态机（`0xf6d538`）步进五个逐槽读取器（`0xf6df44`）和头目的列表：

| 读取器状态 | 条件 | 操作 |
|---|---|---|
| 0 | 该槽位的已发送条目不包含 5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d 中的任何一个 | 为该槽位（`0xf70078`）发送一个 ServerRequest，状态 1 |
| 0 | 否则 | 每个已应答对均被擦除（`0xf6edf4`） |
| 1 | 该槽位被发送了 5 和 6 | 将带有该槽位命令（`0xf6e6a8`、`0xf702ec`）的块作为 ServerCommand 发布，状态 2 |
| 2 | 该槽位应答了一轮（0x15 / 0x16） | 状态 0 |

The boss's slot (table `0x3c6a45a` against N+0x95) only erases answered pairs. Other reader paths: a
slot that sent 4 gets a kind 0x13 block; on N's side in a raid the sub-states at reader+9 handle a
fainted slot ([The battle timer running out](#the-battle-timer-running-out)); 0xd/0xe posts kind
0x1b; 7/8, 0xb/0xc, 0xf/0x10 and a received 0xa post kinds 0x17, 0x19, 0x15 and 0x17.

每帧，运行步骤 `0x2d383b8(N)` 会步进服务器的传入链接（[N+0xb0] 上的 `0xe0f040`、`0xe0fd68`、`0xe0f854`），然后步进作业图 `0xfc363c(G, 1)`，其中 G = [N+0xa8]（vtable `0x44ee6e8`）：

| G+ | object | |
|---|---|---|
| 0x98 | the request factory | a posted request is a 0x50-byte object: job type hash, counter, payload |
| 0xa0 | the scheduler (vtable `0x44eea68`) | posted requests at +0x40..+0x50, appended by `0x1479b10` |
| 0xa8 | the source (vtable `0x44947d8`) | vf 0x68 `0x14641ec` picks the request to start |
| 0xb0 | the per-frame machine (vtable `0x4493530`) | vf 0x68 `0xf6d538` |
| 0xb8 | the executor (vtable `0x4493688`) | a stack of jobs |

`0xfc363c(G, 1)` 在持有任务时单独运行执行器。否则它运行机器，然后运行源的选取：在团体战中，是第一个已发布的团体战动作（哈希 `0x5c307d44ea569b63`），在模块启动第一个 Wild::Setup（哈希 `0x2e9e7a3009002c36`）之前；否则是第一个已发布的动作。执行器（`0xfc38dc`）运行顶部任务的 vf 0x68：0 结束该帧；2 将其弹出，压入其续体 [job+0x70] 并结束该帧；其他值则再次运行它。每帧启动一个已发布请求，而团体战动作会插队。

机器的定时检查会将其头目列表副本作为消息 0x51 发送到服务器自身的传入链接（`0xe0f440(server, N+0x95)`）；下一帧 `0x2016290` 将其 0x24 字节复制到机器的头目列表，后者会发布团体战行动。如果没有该步骤，定时行动就永远不会触发。机器的 vf 0x70 `0x20162bc` 还会接收 `0x0ab4bce035f3012b`（发布到 `0x201665c`）和 `0xde3856ecc4fe200c`（一个 kind-14 行动，作为 ServerCommand 发布）。

`Server` 是该流程的 Python 移植版，按机器时钟以每秒 30 帧运行；无法跳过任何一帧，因为等待濒死槽位计时器的读取器每帧都会推进机器。宿主将其服务器读取到的每条消息都通过一个队列转发给客户机，因此该队列的顺序就是服务器读取它们的顺序。借助模拟宿主的引导程序和转发的消息，该移植版逐字节发送控制台的全部 24 帧（未写入的字节除外），并且在 unicorn 下，游戏自身针对全部 216 个移植函数的代码会留下相同的页面，包括超时和头目胜利。

### 复现一回合

在 unicorn 下，从在构建器 `0x113c8a0` 处停止且类型为 0x15 的模拟控制台开始，一轮可精确重放：内存从 GDB 存根逐页获取，`tpidrro_el0` 后面的线程本地页是一个替身，其 `+0x1f8` 指定了一个假线程，并且 SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d 和 0x1e 返回 0。一轮会触及 159 到 353 个页面。

该服务器的 Python 移植版为每个游戏函数运行一个函数，并以相对 `main` 的偏移量为键：种类 1、5、17 和 21 的构建器，回合驱动 `0x113e3d0`（伤害 `0xf7c344`、濒死 `0x1144df8`、回合结束 `0x114a094`），战斗开始 `0x113dca8`，构建步骤 `0x2891748`、`0x2892ac0`、`0x2d381a4` 和 `0x2892dd4`，以及 SDK 的 `nn::mem::StandardAllocator` 及其线程缓存和 TinyMT32 密钥（`0x525f448`）。在超过 86 台已停止的控制台上，它留下与游戏相同的主体和内存页。当字节 0 和字节 1 均未置位时，`__cxa_guard_acquire`（`0x53c49a0`）返回 1，并将该守卫的字节 1 置为 2。

| `0x47420d8` | `avalon/data/growTable.bin` | the FlatBuffers root, through vf +0x70 of [T+0x30] |
| `0x4742568` | `avalon/data/waza_array.bin` | map, key move (u16) |

### 实测的服务器流程

这些对于在[提供对战](#serving-the-battle)的脚本化控制台上运行的 oracle 服务器成立；由它们构建的服务器会在玩家获胜的整整九场对战中，向控制台发送相同的帧（包括通知）：

| 规则 | 实测 |
|---|---|
| 头部计数器 | `step` 每次发送（广播或一次请求）加一；`round` 在消息 1 中为 0，从 `0x11` 起为 1，并随每个 `0x15` 和每个 `0x25` 递增 |
| 每帧一个作业 | 消息 1 启动 `Wild::Setup`，每有一个槽位应答 1 就发送一次 `0x11`，并在每个槽位应答 `0x11` 后一帧结束 |
| 请求 | 在没有作业运行的帧上，会向没有未应答内容的槽位发布一个请求（5）；请求每帧启动一个，按槽位顺序 0、2、3、4 |
| 一个命令 | 该槽位的 `6` 作为作业发布，该作业将轮次（`0x15`）发送给每个槽位 |
| 再次询问 | 已应答发送给它的每一轮的槽位会在下一帧被再次询问 |
| 获胜 | 获胜的轮次在下一帧后跟一个空轮次 `0x25`（20576 个零字节），然后是带正文 `00 00 01 00 01 00` 的 `0x29`，接着是 `0x49`、`0x35` 和 `0x37`；这些命令均在每个槽位应答前一个之后发送一次：在最后一次应答 `0x25` 和 `0x49` 后 2 帧，其余命令之后在同一帧发送 |
| 时间到 | `0x2b` 带正文 `00 00 00 00 02 00`（233 场对战中 63 场） |
| 通知 `0x46` | 每个作业启动的帧，或在没有作业运行时读取轮次应答（`0x16`）的帧，各有一个 |

### 主持战斗
`bin/sv_host.py --raid-serve [NAME]` 会在整场对战中保持网络，并从主机站点用 `pokeldn.sv.raid_battle.RaidBattle` 提供服务：这是一个插件的对战服务器（[对战服务器](plugins.md#a-battle-server)），由 bootstrap、两个 NPC 伙伴以及控制台主机为自身保留的站点构建。pokeldn 不附带任何对战服务器；如果没有插件添加一个，该标志会被拒绝。被服务的会话安排我们的宝可梦、头目、位于站点索引 1 的一台控制台（bootstrap 参与者 1，槽位 2）和两个 NPC 伙伴，因此该标志占用一台控制台。

| 部分 | 主机发送的内容 |
|---|---|
| 服务器发给控制台的消息 | 地址为 (0x2713, 1, 2) 的帧 |
| 槽位 0、1、3 和 4 | 每个奇数步在 0.05 秒后以 type + 1 应答；对槽位 0、3 和 4 的请求(5)使用 type-6 命令，其中该槽位的宝可梦对头目使用它的第一个招式，头目对它使用第一个招式（[动作](#actions)） |
| 服务器读取的每条消息，包括控制台自己的消息 | 转发给控制台，地址为 (0x2713, 3, 5) |
| 每个推进对战的服务器帧 | 在该帧的消息之后，一条来自槽位 0 的 0x46 通知（step 0，4 字节全零正文），地址为 (0x2713, 3, 5) |

每一帧在 0x80 端口 0 上作为一条 deflate 压缩的可靠消息（标志 `COMPLETE_ZLIB`）发送；观察到的最大压缩后大小为 903 字节。复现《朱》4.0.0 发送的服务器会把零售主机发送的六条战斗开始消息（`raid.HANDOFF`）作为前六帧，放在其协议栈填充的头部字节之外，按相同顺序发送，因此 `--raid-serve` 会发送它们以代替 `HANDOFF`。

一旦控制台应答了 0x37，或在发送 0x37 后 5 秒，主机就停止服务并关闭网络。应答 0x37 本身会在服务器上重新运行超时流程（[服务器的流程](#the-servers-flow)），因此本地站点都不应答它。发生失败（服务器抛出异常或构建失败）会停止服务，并像没有该标志时的做法那样移交网络；随后控制台会故障切换，进行自己的战斗（[哪个站点运行服务器](#which-station-runs-the-server)）。

## 加入

`bin/sv_join.py --raid-pokemon FILE` 加入场景 7 网络并以访客身份参与。主机玩家打开太晶结晶，选择组队挑战并等待；应用中的太晶团体战（加入）工具会运行该脚本。`pokeldn.sv.raid.RaidGuest` 和加入器按顺序执行以下操作：

| 步骤 | 访客 |
|---|---|
| 网络 | 在消息标志 0x11 下应答 0x11 和 0x50 |
| 会话 | 对加入响应附带的站点列表不予应答，至少在 1 秒后确认其重传，之后确认每个后续列表，并发送字节 9 置位的时钟请求 |
| 频道 | 将主机的六键表拆分为四个和团战的两个，宣告这四个，0.24 秒后加入端口 2，并在收到表后 0.79 秒宣告团战键；将其 0x7C 确认延迟 0.25 秒 |
| 身份 | 在就座后 0.44 秒发送标准记录集（`pokeldn.sv.reference`），记录 1 放在训练家名称下 |
| 大厅 | 此后 0.27 秒发送状态 0x18 及其宝可梦；2 秒后发送状态 0x01 |
| 开始 | 主机的状态 0x0c 到达后即发送状态 0x0d；发送 0x0d 作为其就绪的访客会得到确认，但从未显示为就绪 |
| 对战 | 确认主机的 0x3480 0x93，每 0.5 秒发送一次会话类型 3 离开，直到类型 4（最多发送四次），然后离开网络；对战中的一台零售版《朱》没有应答这四次中的任何一次 |
