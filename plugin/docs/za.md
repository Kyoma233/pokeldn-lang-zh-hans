# 传说 Z-A

宝可梦传说：Z-A（标题 ID `0100f43008c44000`）是一款原生 Switch 标题，Pia 静态链接在 `main` 中。其数据包标头版本为 16，即 `pokeldn.ldn.crypto` 为 GBA 应用写入的那个版本。

## 转储

基础应用 `v0`（4.3 GB），更新 `0100f43008c44800` `v393216`（2.1 GB），超级维度 DLC `0100f43008c45002`。

| NCA | id | 容器偏移 | section key |
|---|---|---|---|
| Program（更新） | `4a70b3ff963bfe412681185cea68bf55` | `0x2085d0` | `b9de1a0334576634f8fdafdd703f7f9a` |
| Control | `3e7ba1cd223145fa4f299a8f4cafd4cb` | `0xbd0` | `a8cb59338ce785237048d52452eb6adf` |

Program NCA 在 section 0 有 exeFS，在 section 1 有 BKTR RomFS。exeFS 含 `main`（33,970,422 字节）、`main.npdm`（1,700）、`rtld`（8,550）和 `sdk`（6,247,676），没有 `subsdk0`。解压后，`main` 的 text 为 `0..0x3163f70`，rodata 从 `0x3164000`，data 从 `0x3bc2000`；本页地址均为该镜像内的偏移。Control RomFS 数据在 NCA `+0x14c00`，section 计数器 `0000000000000005`；`control.nacp` 给出显示版本 2.0.2，以及 `+0x30b0` 处的八个本地通信 ID，全部为 `0100f43008c44000`。

## 数据包标头

标头版本 16，对应 wiki 表中的 Pia 6.39 到 7.2。布局为 `pokeldn.ldn.crypto.PiaHeader`（29 字节，魔数 `32AB9864`，加密时版本字节带 `0x80`；见 [Pia](pia.md)）。

    0x24fadbc   初始化器：魔数在对象 +0x08，0x10 在 +0x0c，memset 随机数 +0x15（8）、标签 +0x1d（16）
    0x24faefc   校验器：魔数，(version & 0x7f) == 0x10，(length - 0x1d) >> 6 小于 0x71
    0x24fb1e0   接收路径，按版本字节的 bit 7 分支
    0x24fb4b0   发送路径，若未密封则把 0x10 写回 +0x0c
    0x24fb46c   填充大小设置器：OR 进对象 +0x0d 的 bits 4..7（线上字节 0x05）

对象把随机数和标签保存在比其线上偏移高八字节处，与传说 阿尔宙斯在 `pokeldn.ldn.pia6` 中的版本 11 标头做法相同。

## 广告

处于本地搜索画面的控制台会托管网络并广播 112 字节：0x5C 字节的 Pia 系统属性块与 20 字节游戏数据。不随链接码变化的字段：

| 字段 | 值 |
|---|---|
| 本地通信 ID | `0100f43008c44000` |
| LDN 协议 | 1 |
| 广告版本 | 4 |
| 场景 ID | 1 |
| 应用版本 | 6 |
| 安全模式 | 1 |
| 接受策略 | ALL |
| 参与者 | 1/2 |
| 系统 / 应用通信版本 | 22 / 6 |
| 玩家名称 | 一个字节，一个空格，UTF-8 |

SSID 与信道按会话变化。游戏字节是 ASCII 形式的链接码，NUL 填充到十六字节，再跟其长度的小端 `u32`。布局与密码字段同传说 阿尔宙斯（[pla.md](pla.md)，广告中的链接码）；Z-A 的游戏密钥给出掩码 `1068a742ac3a8787ab6066a161f5d5e1`。`pokeldn.za.build_advertise_data(code)` 仅凭代码即可复现每条广告；`tests/test_za.py` 固定两者。

## 入席

搜索中的控制台接受一个站点后立即讲 Pia：首个数据报（109 字节）在 0.02 s。数据包在 `AES_ECB(game_key, ssid)` 下认证，网络 ID 为 `CRC32(ssid[1:16])`（解密的 32 中之 32）。无人应答时，它从自身的变量 ID 向目标 0 在协议 1（Net）上发送：

| 消息 | |
|---|---|
| `01 11 ...`，118 字节 | 连接状态，序列 ID 2 与 3，每秒两次 |
| `01 40 00 00` | 开始主机迁移，一旦状态无人应答 |

连接状态即 `pokeldn.ldn.pia_connect.parse_net_conn_request` 读取的布局：四个槽位，两个已填，均在端口 12345，主机 `169.254.x.1`，加入者 `169.254.x.2`。大约 14 s 后停止，站点仍保持入席。

仿真对的开场：

| | |
|---|---|
| 首个数据包 | 主机的，109 字节，关联后 48 ms；加入者以 45 字节应答，再跟 125 |
| 标头随机数 | 每站点计数器，从随机 64 位基数起，每发一包 +1 |
| 加入者的首个数据包 | 源 0，目标 0，数据包 ID 0，无页脚，未压缩 |
| 加入者的第二个数据包 | 自有源 ID，zstd 压缩 |
| 主机的下一个数据包 | 发往该 ID，带两字节收件人页脚 |

LDN 连接成功但网络上没有 Pia 主机的加入者，会在 7.94 s 后断开，即 8000 ms 的 Net 连接截止减去 LDN 连接耗时：

    0x251b1bc   LdnProtocol vtable 0x3c8aef8 slot 0x1d8：mov w0, #0x1f40
    0x2513520   NetBackgroundProcessJob StartConnectNetwork：job+0xa0 = now + ticks_per_ms * 8000
    0x25141c4   WaitConnected 步骤 0x25140bc，主机未知时：截止时间对 now
    0x25143a0   到期：结果 0x647a，状态字节 +0x100 = 5，5000 ms 截止（slot 0x1e8），
                然后 StartDisconnectNetwork

LdnProtocol 的计时槽 0x1b0 到 0x1f8 返回 6000、1000、500、10500、4500、8000、20000、5000、5000 与 10000 ms；仅识别了 0x1d8 与 0x1e8。

## 零售控制台上的会话

向参考加入者发送 Session join 的站点会立刻被接纳。控制台的发送：

| 自入席起 | 控制台发送的内容 |
|---|---|
| 0.02 s | Net 连接状态，118 字节 |
| 0.05 s | Session 加入响应，类型 2，37 字节，发往加入者的变量 ID |
| 0.06 s | Reliable（协议 10），106 字节，以及两条 Broadcast Reliable（协议 11） |
| 0.08 s | Net 更新属性，类型 0x50，150 字节 |
| 自 0.5 s 起 | RTT 请求，约每秒三次 |
| 1.12 s，重复 | Session 更新会话，类型 5，185 字节 |

加入在 Net 确认之上欠下：十个协议（`1:0 3:5 5:1 6:0 9:1 10:3 11:4 12:4 13:7 15:0`），应用通信版本 6，身份令牌 `0x06` 再跟零，以及一个空格的 PlayerInfo 名称。对每条 Net、Session、RTT 与 Reliable 消息作答、且不发游戏消息的加入者（不带 `--game` 的 `bin/za_join.py`）会保持零售搜索的座位直到离开（测得 150 s）。

| 加入 | 控制台的回答 |
|---|---|
| 协议数量与主机不同 | 被类型 0 处理程序 `0x254a030`（`0x254a090`，对照 `0x256c9f0`）丢弃，无应答，无站点 |
| 协议或应用版本错误 | 37 字节类型 2，结果 3（`0x254a2e4`）或 4（`0x254a290`） |
| GBA 应用的六个协议，或十个中的九个 | 无 Session 消息；入席后 8 到 12 s 发 Net 0x40，然后在新 SSID 下开新网络，仍在搜索 |
| 十个协议，但其变量 ID 无 RTT 应答或其他流量 | 被踢出（[踢出](#the-kick)），入席约 27 s 后显示「找不到伙伴」 |

8 到 12 s 的路径是主机的 WaitMember，3000 ± 999 ms（随机 u64 按有符号读取）；到期时，若加入者在 Net 层却不在会话中，LeaveMeshWithHostMigration 轮询 8000 ms 等待下一主机（`0x255a520`），然后发 Net 0x11 序列 3 与 Net 0x40。踢出序列为自 14 s 起的 Session 类型 13，九条间隔 0.5 s；自 19 s 起每 0.5 s 一条 Net 0x11 序列 3；自 23 s 起每 0.3 s 一条 Net 0x40。

## 游戏自身的交换

在 Pia 之上，游戏运行在 Reliable（协议 10）与 Broadcast Reliable（协议 11）上，子标头由 `pokeldn.ldn.reliable` 解析。一笔交易携带下列应用有效载荷（参考捕获中二十种不同的），每条重发直至确认，除站点 ID 外两侧发送同一套。按消息 ID，以首次出现顺序：

| id | 字节 | 携带内容 |
|---|---|---|
| `1400` | 106 | 站点身份，玩家名称 UTF-16 |
| `1403` | 9 | 身份的校验和（SyncDataSet），见下 |
| `0100` | 1211 | 选择画面所绘的记录 |
| `0101` | 354 | 提供：九字节标头、344 字节宝可梦记录、一尾随字节 |
| `0102`、`0104` | 5 | 步骤消息 |
| `0200` | 5 | 确认步骤，末字节为 3、6、0x0b、0x0e |

`pokeldn.za.reference` 附带身份、其后续、协议 11 开场与选择记录，录自玩家为 `Player` 的仿真对；`bin/za_join.py` 与 `bin/za_host.py` 发送它们（`--game-dir` 指定另一套）。

身份是一个二元的 `b9` 元组：一个 u32，再一个单成员元组，内含 0x5d 字节的 `bc` blob。该 blob 是六元元组。前四个成员是存档的训练家 ID（高半为秘密 ID）、性别、语言与玩家名称。随后是 32 字节的零字段及其余。

游戏从存档的训练家块——PKHeX 的 `MyStatus9a`，位于玩家状态对象 +0x40——填充这四项：

| 成员 | 块偏移 | getter |
|---|---|---|
| 训练家 ID | +0x00 | `0x824b2c` |
| 性别 | +0x05 | `0x505c24` |
| 语言 | +0x07 | `0x23c398` |
| 名称，13 个字符 | +0x10 | 由 `0xc90ce4` 拷贝 |

构建器是 `0xc90b04`；它把值存到 GOT 在 `0x3ec7638` 所持名称条目下。

接收控制台按相同顺序解码成员（`0x9131ec`）。其名称框 `T_pname_%02d`（`0xb13fd4`）对照游戏语言表（`0x33a308c`）检查语言为 1 到 11；11 是拉丁美洲西班牙语。它把性别与名称一并传入文本（`0x6b9fb8`）。

录下的身份是女性、英语存档：`0x378913cf`（5071 与 14217，参考会话宝可梦的训练家）、1 与 2。为接收玩家制作的礼物读取全部四项（`reference.identity_trainer`，[为接收玩家制作](gift_simulated.md#made-for-the-receiving-player)）。

    1400 b902 82<u32> b901 bc5d b906 82<u32> 01 02 bc1a <name> bc20 <32 bytes> ...

名称是 26 字节，UTF-16LE，NUL 填充：最多十二个字符，在协议 10 消息偏移 0x18（协议 11 站点前缀之后 0x1c）。录下的 `Player` 在此，零售控制台显示交易伙伴为 `Player`。两个启动器都把 `--trainer-name`（默认 `POKELDN`）写入其中（`pokeldn.za.reference.named`）。

信道 0x14 携带游戏在站点间保持同步的键值存储（`gfa::network::p2p`，在 `0x7796a0` 构建；消息 ID `0x1400 | index`）：1400 是 UpdateValue（`0xc1bdf4`），1402 是 DeleteAllValues，1403 是 SyncDataSet（`0xc4b1b4`）。身份的外层 u32 `0x2abe85e2` 是该值的键，常量在 `0xdf1b30`：即 `UserData` 的 FNV-1a 32，游戏以此名存储身份。1403 携带按键排序的发送方各值之上的一个 u32，`h = crc32(le32(fnv1a32(value) + h))`，从 `h = 0` 起（`0xc4b270`，FNV-1a 在 `0xc4b31c`，标准 CRC-32 在 `0xc4b420`）；对身份而言，值是 `bc5d` 之后的 0x5d 字节。接收方重算之，仅当每个站点的匹配时才继续（`0xb8c724`，`0xb8c660`）。录下的 `Player` 身份给出 `1403b9018269fb308f`，即录下的消息。带着陈旧 1403 发送的已改名身份会让零售控制台停在搜索画面：它发送自己的 1400 与 1403，但永不发 0100。`pokeldn.za.reference.sync_message` 为所发身份构建 1403。

### 交易命令

交易会话设置 `0xca2928` 在会话的命令信道（session+0xc8）上订阅五种命令类型（由 ctti 字符串命名）。ID 为 `0x100 | index`，即类型在信道列表 +0x60 中的位置（`0x96129c`，一次 `strcmp` 遍历）。每个有效载荷是以 u16 round 开头的 `b9` 结构。

| id | 命令 | 处理程序 | 处理程序读取的有效载荷 | 处理程序做什么 |
|---|---|---|---|---|
| `0100` | CommandReady | `0x2dc4c7c` | round，1200 字节 | 将 1200 字节拷到 session+0x604，设置 session+0xf0 |
| `0101` | CommandSelectPokemon | `0xb2a44c` | round，344 字节记录，一字节 | 加载记录（所提供的宝可梦）；该字节 bit 0 清除表示选定 |
| `0102` | CommandConfirmTrade | `0xc8dda0` | round | 若 session+0x152 高于 round 则忽略；否则伙伴状态 +0x134 = 4 |
| `0103` | CommandCancelTrade | `0x2dc51ac` | round，u32 原因 | +0xab4 = 原因（1 与 2 对调），否则 0；+0x152 = round；+0x150 += 1；然后 `0x2dc41f8` |
| `0104` | CommandFinalAgreement | `0x2dc52b4` | round | 若 +0x152 高于 round，或自身状态 +0x130 不是 4 或 5，则忽略；否则伙伴状态 5 |

取消发送方 `0x964a60` 在自身状态 +0x130 为 2 或 5 时什么都不发；否则发送 round +0x150 + 1，设 +0x130 = 2，推进 +0x150 与 +0x152，并把伙伴状态从 3..5 降到 2（原因为 0 时为 3）。处理程序只拒绝严格低于 +0x152 的 round，因此取消后陈旧的 ConfirmTrade 或 FinalAgreement 被忽略，更高的 round 被接受。SelectPokemon 不读 round。

会话对象（0xab8 字节，由 `0xca2704` 构建，vtable `0x3e3a6e8`）把 +0x150..+0xab7 清零，因此两个 round 从 0 起，会话的首个 `0102` 与 `0104` 为 `b90100`。完成交易后 `0x964568`（自身状态 6）清除双方提供，把双方状态设为 2 并清零双方 round，因此座位上的下一笔交易从 round 0 开始。`pokeldn.za.host` 每笔交易重置其 round。

| 自身状态 | 写入者 | 何时 |
|---|---|---|
| 5 | 会话更新 `0x95f600`（`0x95f680`） | 自身状态 3 或 4，字节 +0x148 已设，计时器 +0x138 至少 1.5 s，伙伴状态 4 或 5，`0x963710` 为真 |
| 6 | 委托调用 `0xdfda8c`，在 `0x964e78` 填入 | 交换工作者的状态 6 委托 |
| 7 | `0x2dc4b94`，由 `0x964f0c` 安装 | 工作者的状态 7 委托；在 2.0.2 中不可达 |

在自身状态 5，`0x9610a4` 调用交易对象（session+0x48，由 `0xc8ad1c` 构建，vtable `0x3d8a0d0`），并把交换工作者（`0x966af0`，0xb0 字节）连同状态 6 与状态 7 委托（`0x9649e0`，`0x964a20`）建入 +0xd0。

工作者的 start `0x965660` 在 +0x14 存主机测试 `0x9157d0`，清 +0x15，在 +0x18 存 `0x34f2b0(rng, 0x12c) + 2`（2..302），清零 +0xc 与 +0x10，把 +9 设为 1。其 update `0x960c20`（唯一调用者 `0x95f750`）经表 `0x33a360d` 按 +9 切换。`0x962ac0(peer, step)` 在 peer+0x48 存 `0x100 | step` 并发送；等待比较伙伴在 +0x70 的步骤，当 +0x71 已设时有效。

| 5 | `0x960ce0` | 等待伙伴的 6 | 6 |
| 6 | `0x960da0` | `0x9628e8`：交易对象 +0x40 = 1，然后 vfunc +0x80（`0xcbc68c`，即「交易向收到的记录写入什么」中的处理程序更新） | 7 |

| 14 | `0x960de8` | +0x10 == 0：状态 6 委托（`0x963810`）；否则状态 7 委托（`0x9a0b00`）；然后 `0x9637b8` | 0x10 |

自身状态 6 是交换完成，双方都经过了 `0200b901XX` 步骤 3、6、0x0b 与 0x0e。处理程序 14 在工作者错误字 +0x10 非零时选状态 7 委托，而 2.0.2 中没有任何东西往那里写非零：其唯一的存储是清零，在构造函数 `0x966ba4`（`0x966bcc`）与 start `0x965660`（`0x9656a0`）。工作者的中止阶段 +0xc 由会话 tick `0x95f6e4`（`0x95f738`）读取：1 请求交易对象取消（`0x9636f8` 设交易对象 +0x44 = 1）并把工作者停在步骤 0xf；2 等待交易对象 +0x44 == 3，然后设步骤 14 与阶段 3（`0x95f7e0`）。没有代码存储 1，因此没有路径经工作者到达自身状态 7。经工作者指针的每一次存储（对 session+0xd0 的读取在 `0x95f608`、`0x95fc80`、`0x9610c8`、`0x961130`、`0x961a74`、`0x9645cc`，构造函数、处理程序及其被调者）都落在 +0x09、+0x0c、+0x14、+0x15、+0x18、+0xa0、+0xa8 或委托的存储（管理者 `0x965f54`、`0x4177c8`）；无一经过计算地址。+0x15 清除的站点会在随机的 2..302 次 update 后再发其 0x0b。`0xdd07cc` 返回什么、以及所存半字如何映射到 `b901XX` 字节，未知。

在交易提示上选取消的 Z-A 发送 `0103b9020100`（round 1，原因 0）；玩家再次选定后，它用主机先前的提供重绘提示，并以 `0102b90101` 与 `0104b90101` 确认。round 0 下的应答被忽略，控制台停在「通信中」。`pokeldn.za.host` 从控制台自己的 `0102`、`0103` 与 `0104` 取 round。

### 加入者在这些流上欠下的

对照参考对与仿真主机的确认测得：

- 协议 10 发往主机的变量 ID，协议 11 发往网状 ID 0x0001；两者都在两字节收件人页脚中携带主机的变量 ID；
- 每个游戏数据包都经 zstd 压缩；
- 纯确认走流的基座 0xfff0，消息标志 0x40；推进序列的那个被读作其后有空洞的数据。应用数据不带消息标志；
- 协议 11 上的确认是 74 字节：站点的四字节、一个流字节、计数四，然后四个条目——各一个下一期望半字与十六字节掩码，最后一个被截短。条目 1 是加入者的流；主机在其余三个报告空闲基座 0xfff0；
- 身份在 INIT 下发出，其后选择记录，再在新序列下反复发送，每次相同的 1211 字节（测得：约 0.5 s 后，然后约每秒四次）；
- 子标头的收件人计数在协议 11 为三，在协议 10 为零；
- 在协议 11 上，子标头长度统计四字节站点前缀之后的有效载荷，因此每帧都比其声明多带四字节：开场是 `00000001` 与 `1402 b900`，身份是前缀加整个协议 10 身份，九字节消息是 `1403b9018269fb308f`，确认是前缀加四个完整的 18 字节条目。按声明长度截断的帧被丢弃（主机约每秒重发开场十次）；末四字节错误的帧会被确认，但主机停在搜索画面。

LDN NodeInfo 本地通信版本（0x40 字节的 +0x2E）在参考站点上为 6；0 被同等对待。

### 保活

设置的 +0x290 是以 ms 计的发送静默上限（`0x257d12c` -> `0x256a238`；0 变为 1000）。`SessionPacketWriter` vfunc 7 `0x2544004` 在向已入席站点发送时在 +0xb0 盖戳，并经 `0x256a2d0` 向任何在上限内未被发送的站点额外发一包：一条协议 0、中间字节 0xfd、端口 0、空有效载荷的 Pia 消息（标头字节 `04 00`）。没有协议 ID 为 0；读取器在下一接收轮次开始时回收未读消息（`0x2566030`），因此这类消息不会堆积。字节 +0xa0 标记正在被踢出的站点（`0x2577094`）。

### 数据包 ID

数据包 ID 在每发送方两个计数器上运行：一个用于目标 0x0001，一个用于其他所有目标（0 与主机变量 ID 共用）。`nn::pia::session::SessionPacketReader::vfunc11` `0x2566920` 在任何协议之前检查：未知源或无站点则接受；否则目标选择控制器（0x0001 用 station+0x78，否则 station+0x50），`0x2576ad0` 检查数据包 ID（线上 0x0a）与大端随机数（线上 0x0d）：

    id == 0                                         接受，不记录
    last id == 0                                    last id = id - 1
    last nonce == 0 and nonce != 0                  last nonce = nonce - 1
    (s16)(id - last id) < 1                         拒绝
    nonce != 0 and (s64)(nonce - last nonce) < 1    拒绝
    otherwise                                       last id = id，若非零则 last nonce = nonce

被拒数据包到 `0x25655d8` 并被丢弃：重复的 ID，或超前 0x8000 及以上。为目标 0 使用独立计数器的加入者，其每条 Net 0x51 都会被丢弃，直到它通过主机 ID 计数器；主机重复其 Net 0x50 直至有一条通过（测得约 10 s），其更新序列 1 被推迟。Net 0x51 处理程序 `0x2504100` 不读任何标头字段。

### 加入的其余部分

- Net：连接状态 0x11 以 0x12 应答，更新属性 0x50 以 0x51 应答。
- Session：类型 5 更新会话以十五字节应答：类型、站点的 LDN 常量 ID、更新序列的大端 u32，以及 0x0001。GBA 应用的应答（原始 MAC，无序列）会让 Z-A 主机无限期地每两秒重复其更新。

接受更新序列 1 的主机约 50 ms 后发送其选择记录（测得入席后 1.2 与 1.25 s）并进入其交易盒。

### 协议 10 上的交易

各方在选择记录之后发送 354 字节的 `0101`（测得约 2.5 s 后）。提供的末字节在站点主动发送的预览上为 1（零售控制台每次在交易盒移动光标都会发一个），在玩家选定上为 0；主机按该字节键控，而非按计数。带着 1 发送的选定会被确认并画成空，伙伴停在「通信中」且槽位为空。

加入者以自己的选定应答主机的选定，并以 `0102b90100` 确认；主机以相同确认，双方发送 `0104b90100`（主机在加入者的 `0102` 后 1.5 s），加入者发送四个 `0200b901XX` 步骤，03 与 06 立刻，0b 与 0e 在交易动画与交换工作者的随机等待之后（[交易命令](#the-trade-commands)）。主机在协议 11 上发送 `0000000202`，并以带其前缀的 `0201b901XX` 应答每一步。`bin/za_join.py --trade-offer` 运行加入者。

### 加载收到的记录时检查什么

伙伴的 `0101` 到达 `0xb2a44c`，为 CommandSelectPokemon 注册（`0xca33d8`，从 `0xca2928` 调用）。反序列化器 `0xb4e248` 要求标签 0xb9 带三个成员（`0xb4e33c`），把第一个读作 u16（`0xa91178`），要求第二个为恰好 0x158 字节的标签 0xbc（`0xb4e4b8`），并把第三个留在 struct+0x15a；任何错误时不调用处理程序（`0xb4e1c8`）。处理程序分配 PokemonParam（`0x82713c`）并以 `0x270994` 加载 344 字节：

1. `0xe47e94` 把 0x148 字节拷到核心、16 字节到尾部，解密两者并比较校验和；不匹配则设坏蛋位。它清除快速模式，因此加载以重写校验和并重新加密结束：坏校验和被纠正保留，坏蛋位已设。
2. `0xe3f18c`：对非零物种，`0x2901a4(species, form)` 在个人表中查找该对（`0xe366b0`，键为 `species * 10000 + form`）并读 FlatBuffers 字段 1 的字节（vtable +6，`0xe3bbfc`），缺失为 0。零则设坏蛋位（`0xe51698(acc, 1)`）。缺失键回退到 map+0x80，即物种 0 条目，没有字段 1。
3. `0xe41750(pp, 1)` 从经验写等级到尾部，并从物种、形态、能力等级、个体值、超级训练位、努力值与能力性格重算最大 HP 与五项能力值。当前 HP 为 0 时保持 0，否则按最大 HP 增益上升。
4. `0xe42584` 把自槽 0 起计的非零招式的 PP 钳到带 PP 提升的最大值（`0xe6646c`）；蛋或坏蛋（`0xe4c950`，`0xe485f0`）被跳过，除非 `[0x3f0784()+0x380]` 已设或 `0xe483b4` 为真。
5. `0xb2a4a4` 以 PokemonParam 调用 session+0x88 处的可调用对象，忽略其结果，把它移入 session+0x128，并在第三成员 bit 0 清除时把伙伴状态 +0x134 设为 3（选定）。该可调用对象始终是 `0xad2c68`，即下方的名称检查（`0xca20a4` 在 `0xca2520`、`0xca25d8` 用它构建配置；没有其他东西引用它）。

没有东西对照学习集检查招式、球、遇见数据、训练家 ID、特性或尾部等级。组成的记录仅因校验和错误或个人表字段 1 为零而失败，两者都产生坏蛋，从不拒绝；被拒名称被改写。校验和错误的记录画成蛋图标、等级 0、雄性符号，在提供的昵称下，并提供「交换它」；交换后它以「蛋」落入箱子，摘要为空，游戏继续运行。

### 收到宝可梦时的名称检查

`0xad2c68` 对空记录返回（IsEmpty `0x13778`），否则运行 `0x89f250`（另一调用者 `0x89de34`）：它把 `nn::ngc::ProfanityFilter` 开进全局 `0x612d3d0`，带 0x20000 字节缓冲（`0x912e10`），用 `0x9138d4(str, len, language)` 检查三个名称并收尾（`0x912d80`）。

| 名称 | 传入的语言 | 失败时 |
|---|---|---|
| 昵称，0x58 | 记录的，0xd5 | `0x8a0370` 以该语言写物种名（`0xe33ca0`）并清除已昵称位（0x8c bit 31） |
| 原训练家的，0xf8 | 记录的，0xd5 | `0x3d8a248[language]`，以 `0xe579a0` 写入 |
| 持有者的，0xa8 | 持有者的，0xc3 | `0x3d8a248[language]`，以 `0xe5a190` 写入 |

语言 12 及以上把表索引为 0。`0x8a0370` 在 `[0x3f0784()]+0x380` 与 accessor+0x1a 均为 0 时，对蛋或坏蛋（`0xe4c950`，`0xe485f0`）什么都不写。替换表 `0x3d8a248` 持有十二个 UTF-16 字符串：0、1、6 `ゼット.`；2 `Z`；3 `Zed`；4、7、11 `Zeta`；5 `Zett`；8 `제트.`；9、10 `Z.`。

`0x9138d4` 在以下情况使名称失败：

- 长度为 0 或首个单元为 0；
- 长度 7 单元及以上，且任一单元在 0x3041..0x3090、0x30a1..0x30fa、0x4e00..0x9fcc 或 0xac00..0xd7a3（通道在 `0x3308840`、`0x33087b8`）；
- 语言为 1..5、7 或 11，且首个 0 前任一单元在 0x4e00..0x9fa0 中且不是 0x4edd；
- L（来自 `0x444330`）为 0、6 或大于 11；
- 过滤器的 vfunc +0x28，由 `0x913ad0` 以 `(&result, pattern, &str, 1)` 调用，模式为 `0x339f650[L - 1]`，留下非零结果。

### 交易向收到的记录写入什么

## 与零售控制台的交易

处于链接交换搜索的零售 Z-A 与 `bin/za_join.py` 交易并保留组成的记录。交易后控制台在同一座位回到其交易盒并可再交易：`0x964568` 把双方状态重置为 2、双方 round 重置为 0（[交易命令](#the-trade-commands)）。重复的 `--trade-offer` 按两种角色依次交易队列：第四步后 2.7 s 预览下一条记录，并在控制台的下一次选定下于 round 0 选定（`tests/test_za_host.py`）。

交易动画在第四步之后运行，不携带消息。自该步起：1.1 s 动画，约 26 s 收到的宝可梦上屏，30.2 s 控制台的下一预览（`0101`，354 字节），约 31.7 s 玩家可操作。

在控制台主机阶段晚期形成的座位被移交：首个数据报约在关联后 1.4 s，不跟更新序列 1，控制台每秒重复一次 Session 类型 9，直到重启其 Net（测得 6.5 s）。wiki 把该类型编号为开始主机迁移、踢出为 12，而 Z-A 用 13。其后的代码未追踪。

## 托管

搜索中的控制台也会扫描，并加入携带该标题广告及其链接码的网络。`bin/za_host.py` 托管一个；`pokeldn.za.host` 按字节固定对照仿真对的交易。

| 自入席起 | 主机发送的内容 |
|---|---|
| 0 s，每 0.46 s 直至应答 | Net 连接状态 0x11：序列 2，四个槽位，主机与加入者在 12345 |
| 在 Session 加入时 | 加入响应（类型 2，37 字节）发往加入者 ID，更新会话（类型 5，序列 0）发往 0x0001 |
| 随之 | 协议 10 上 INIT 下的身份；协议 11 上捆绑的身份与 `1403b9018269fb308f`，前缀 `00000002` |
| 随之 | Net 更新属性 0x50，每 0.5 s 直至 0x51 |
| 自 0.2 s 起 | 向 0x0001 的 RTT 请求，约每秒三次；对加入者的每一个作应答 |
| 更新 0 被确认后 1.15 s | 更新会话序列 1 |
| 一旦更新 1 被确认 | 1211 字节选择记录两次，间隔 60 ms |
| 2.7 s 后 | 预览 `0101` |

与 GBA 应用的主机不同：

- 更新会话中主机的站点条目携带身份令牌 `0x06`；
- 更新的序列写两次，在 +1 与 +21；
- 属性更新在场景 ID 之后携带 `02`，而 GBA 应用写 `01`（CloseParticipation，见下）；
- 广播确认在条目 1 报告加入者的流，其余三个为 0xfff0。

零售 Z-A 加入 `bin/za_host.py` 并在任意链接码下交易（`--code`）。主机在第四交易步之后保持会话，并在控制台以 B 离开时关闭。`--hold-after-trade` 选择定时关闭，自控制台交易后的首个预览起计；总体 `--seconds` 限制仍适用。在定时关闭、`--seconds` 限制与 Ctrl-C 上，主机先把会话交给已入席的控制台（[主机离开](#a-host-leaving)）；处于其盒子上的控制台随后显示「你的交换对象选择退出交换。链接交换现在结束。」并回到链接对战。

陷阱：交易存档后无移交即关闭网络，或在交易动画期间发送移交，会在控制台上画出「错误编号：6」（交易已保存）。

交易后回到盒子上，控制台预览光标下的宝可梦，因此 `--offer-out` 只保留选定。

Net 更新属性（类型 0x50）由 `0x2502960` 构建（序列在 NetProtocol+0x160，经 `0x250f5d0`），由 `0x250e414` 大端序列化。偏移自 0x26 字节 Net 消息起点：

| 线上 | 大小 | 字段 |
|---|---|---|
| 0x04 | 4 | 序列 ID，NetProtocol+0x160 |
| 0x08 | 8 | 网络 ID，会话属性 +0x90 |
| 0x10 | 2 | 参与者数量（`0x25050dc`） |
| 0x12 | 2 | 站点槽位，NetProtocol+0x1216 |
| 0x14 | 8 | 会话属性值（`vfunc +0x10`）；LDN 属性把场景 ID（NetworkInfo +0x0a）保存在 +0x98 |
| 0x1c | 1 | 接受状态（`0x2505ec0`） |
| 0x1d | 1 | 会话属性 `vfunc +0x80`，bit 0 |
| 0x1e | 4 | 系统属性大小（`0x24fe4dc`） |
| 0x22 | 4 | 游戏数据大小（`vfunc +0x50`） |

`0x2505ec0` 在主机地址（+0x1280）与站点自身（+0x1260）已设、或 +0x12d0 非零时返回 NetProtocol+0x340 处的字节；否则 0。其写入者：

| 写入者 | 值 |
|---|---|

| `0x2515434`，来自作业字节 +0xc0（由 `0x2515220` 存储） | 经 `0x250758c`（`NetFacade` vfunc 17）为 1，经 `0x2507828`（vfunc 19）为 2 |
| 主机迁移 `0x250b060` | 字节为 1 时重跑 1 路径，否则 2 路径 |
| 设置器 `0x2500a9c` | 来自 `0x25fdc90` 与 `0x25fe1ec` 为 1 |
| 接收 0x50 的站点（`0x25035bc`） | 消息的字节；`0x2502e70` 把自身 +0xa6 设为 `byte != 2` |

LDN 会话属性把 +0xa6 设为 `stationAcceptPolicy == 0`（NetworkInfo +0x62，`0x25234b8`）。1 表示接受全部；2 表示标志清除。

`nn::ldn::SetStationAcceptPolicy`（PLT `0x3163b60`）由 LdnProtocol 索引 23（0，接受全部）、24（1，拒绝）与 21（3，白名单）调用。游戏关闭参与，且策略 1 随之，仅当它是会话主机时，来自 CloseSession 任务的 update `0x1a25454`。

任务构建器 `0x1a228f0` 以 "CloseSession"（哈希 `0x0dd344f64c81e84d`）在两个会话驱动上被调用。网络管理器（vtable `0x3c16978`）在 +0x38 保持其驱动；其设置器 `0x199e850` 按模式安装：0 无，1 本地驱动（`0x199eaa0`），2 互联网驱动（`0x199ecc0`，排位对战使用），3 LAN 驱动（`0x199ef70`）。模式来自 "InitializePia" 任务，由到本地序列（链接交换、私人对战）以 1 构建，由到互联网序列以 2 构建；没有调用以 3 构建，因此 2.0.2 中从不安装 LAN 驱动。

| 构建器 | 驱动，槽 | 游戏功能 |
|---|---|---|
| `0x19d7a70` | 本地，13（RandomMatchingSeq 的 CloseSession 步） | 链接交换搜索 |
| `0x19a7590` | 本地，19 | 私人对战 |

槽 13 被调用一次，在 `0xc8a224`，来自链接交换（`0xc9f8ec`，会话 "BoxTrade"）与排位对战。链接交换搜索以第四参数常量 1（`0xc8a194` 处 `mov w3, #1`）运行本地驱动的槽 13（`0x19a1310`），因此其 CloseSession 步构建该任务。槽 19 的调用者仅私人对战页面。

在零售链接交换搜索上，广告在入席时持有策略 0；Pia 玩家数（广告数据 +0x16，`e1 01 01 00` 到 `e1 01 02 00`）在 0.6 s 内变为 2，然后策略 1 恰在控制台那一条 Net 0x50（150 字节，序列 1，接受状态 `02`）之前被广告，并在会话中保持 1。此前无主机迁移，因此 `02` 是 CloseParticipation 的，来自槽 13 步 `0x19d7a70`。在 2/2 参与者时，策略拒绝的容量本就不会接受。

## 离开

站点经两个 `nn::pia::session` 作业之一离开，每个都等待对方站点的回复。分发器 `0x2547490`（表 `0x336a9b7`，类型 0 到 17）读取的 Session 类型：

| 类型 | 大小 | 发送方 | 消息 |
|---|---|---|---|
| 3 | 22 | 离开的加入者 | 离开请求：类型，随机 u32，其常量 ID（8，大端），其变量 ID（2），地址类型 0，其 IPv4，端口 |
| 4 | 15 | 主机 | 离开响应：类型，随机 u32，从请求拷贝的离开者常量与变量 ID |
| 9 | 30 | 离开的主机 | 开始主机迁移：类型，主机常量与变量 ID，0，主机 IPv4 与端口，下一主机的常量与变量 ID，`00 01` |
| 10 | 21 | 类型 9 命名的站点 | 其确认：类型，自身常量与变量 ID，然后主机的 |

`pokeldn.za` 构建全部四个（`build_leave_request`、`build_leave_response`、`build_migration_ack`）。

### 加入者离开

`LeaveMeshJob::SendLeaveRequest`（`0x2557e54`）向主机发送类型 3 并设 500 ms 截止；`WaitLeaveResponse`（`0x2558098`）在类型 4 上完成，并在每个截止时重发，共四次发送（计数器 +0x9c，`0x25581e0` 处 `cmp w8, #2; b.gt`），然后无应答也完成。类型 4 仅在 15 字节且字节 5 到 14 为站点自身 ID（+0x1b8，+0x1c0）时由 `0x25474f8` 接受；它设作业的字节 +0x99。主机的类型 3 处理程序 `0x254c5ac`（22 或 34 字节，仅主机）在 `0x254c740` 写类型 4 并移除站点（`0x2548500`）。

主机不发类型 4 的零售 Z-A 发送四条类型 3，约间隔 0.5 s，并在第一条后 2.0 s 去认证。`bin/za_host.py` 以类型 4 应答每条类型 3；`bin/za_join.py` 在 `--hold` 或 `--hold-after-trade` 上离开时发送自己的类型 3，并在类型 4 上或第四次发送后继续。

### 主机离开

`LeaveMeshWithHostMigrationJob` 命名下一主机（`CalcNextHost` `0x255a6fc`），然后 `SendStartHostMigrationMessage`（`0x255a91c`）每秒发送一次类型 9，直到 5000 ms 截止（`0x255a8c8`），之后作业以 `0x6c0e` 失败。`WaitStartHostMigrationAck`（`0x255abb4`）一旦字节 +0xe0 已设即完成。类型 10 读取器 `0x2550a64` 仅在主机上接受 21 字节消息，且仅当字节 11 到 20 为主机自身 ID，并在字节 1 到 10 为所命名下一主机的时经 `0x255a630` 设 +0xe0。

| 加入者的应答 | 零售主机在其类型 9 之后 |
|---|---|
| 无 | 五条类型 9 间隔一秒，Net 0x11 序列 3 每 0.5 s 共 4 s，Net 0x40 共 2 s，10.8 s 静默，11.3 s 网络关闭 |
| 类型 10，然后 0x12 `0112000000000003` | 0.04 s 的 0x11，Net 0x40（`01 40 00 00`，源 0）每 0.3 s 共 4 s，同时加入者仍在 |

加入者的类型 10 与 0x12 以标头标志 2、目标 0、数据包 ID 0、无页脚发出。

Net 0x11 是离开主机在 `NetDestroyNetworkJob`（`0x2516444`，标志在 job+0xd8，当断开站点为主机时设，`0x2503c44`）迁移形式下的连接状态：`0x2501930` 递增序列（NetProtocol+0x15c），字节 29——正在迁移字节——在 NetHostMigration 状态 NetProtocol+0x12d0 为 1 时为 1（`0x250f084`）。它向每个客户端请求该序列的 Net 0x12；客户端存储序列，设 NetProtocol+0x308 并应答（`0x2503164`，`0x25035c0`）。主机最多等 4000 ms 等齐每个 0x12，然后每 300 ms 发 0x40 共 4000 ms，或等待到期时 2000 ms，直到只剩自己，并销毁其网络（`0x251693c`，`0x25169f8`）。

迁移形式与开场 0x11 在三处不同：序列、字节 26（开场形式为 1，迁移形式为 2；含义未读）与字节 29。零售与仿真主机从源 0、目标 0、数据包 ID 0、标头标志 `0x3`（建立中，压缩）、无页脚发送；0x40 以相同方式发出，标志 2。类型 9 从主机的发往所命名站点的变量 ID，带页脚。

0x40 在非主机站点上开始主机迁移（`0x2503d44` -> `0x25099a4`，`NetHostMigrationJob` `0x2509da0`）：下一主机开网络并等其余站点 6000 ms；客户端等 1000 ms 并重连。

链接交换在移交处结束：类型 9 处理程序 `0x2550684` 移除离开主机的站点，交易场景更新 `0x95f398` 一旦会话的站点计数（session+0x110）为 1，即以原因 3（`0x95f508`）结束交易。

两个仿真 Z-A 2.0.2 控制台入席在交易盒时，主机玩家退出（B，然后是）会跑类型 9、类型 10、带字节 29 的 Net 0x11 序列 3、0x12，然后在类型 9 后 0.12 s 的 0x40；另一站点在 0x40 后 4 ms 离开网络，不创建网络，并显示「你的交换对象选择退出交换。链接交换现在结束。」

`bin/za_join.py` 以类型 10 应答命名它的类型 9，并以 0x12 应答其后的 Net 0x11，并在首个 Net 0x40 上离开网络（或控制台静默一秒后）。

`pokeldn.za.host.HostSession.leave` 以相同时序运行相同离开；`tests/test_za_host.py` 固定类型 9 与两条 Net 消息。

## LAN 模式

传说 Z-A 2.0.2 有一条其代码从不走上的 LAN 路径。网络启动 `0x1911540` 为模式 1 构建本地服务、为 2 构建互联网、为 3 构建 LAN 服务（`0x2523710`）。模式来自网络任务的 `+0x50`（构造函数 `0xc5a5f4`），仅经 `0xc5a3e4(.., mode)` 创建，其两个调用者传 1（`0xc57600`）与 2（`0x2a0bcc4`）。朱／紫的模式 3 调用者在此无对应。
