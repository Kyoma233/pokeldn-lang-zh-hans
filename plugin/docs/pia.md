# Pia 层

Pia 是任天堂开发的点对点会话中间件，在所有被检查的游戏中均使用 UDP 端口 12345。每个数据报均以魔数 `32 AB 98 64` 开头。Pia 版本决定了头部布局：

| | 火红/叶绿（GBA 应用） | 晶灿钻石/明亮珍珠 | 剑/盾 |
|---|---|---|---|
| Pia 版本字节 | 15/16（6.32+） | 9（5.27-5.45） | 4 |
| 头部大小 | 0x1D | 0x20 | 0x20 |
| 变量 ID | 每个 2 字节 | 每个 4 字节 | 1 字节 + 1 个半字 |
| 线路上 GCM 标签 | | 8（截断自 16） | 所有 16 字节 |
| 模块 | `pokeldn/ldn/pia_connect.py` | `pokeldn/ldn/pia5.py` | `pokeldn/ldn/pia4.py` |

除非某个部分明确指定了其他构建，否则 `0x01...` 地址表示的是 Shield 1.3.2 的解压 `main`（如 `tools/switch/nso_read.py` 所布局），而 `main.bin 0x01...` 地址则表示的是 BDSP 1.3.0 的地址。

## 包头

### 版本 9（Pia 5.27-5.45）

来自 `nn::pia::common::Packet::Header`：

    0x00  4  魔数 0x32AB9864，大端序
    0x04  1  0x80（加密）| 版本（0x7F）
    0x05  4  目标变量 ID，大端序（0 表示广播到网络）
    0x09  4  源变量 ID，大端序
    0x0d  2  包 ID，大端序
    0x0f  1  页脚大小
    0x10  8  AES-GCM 随机数，一个单调计数器
    0x18  8  AES-GCM 标签，截断自 16 字节
    0x20     密文：填充到 16 字节倍数的明文

### 版本 4

来自反序列化器 `0x01774730`（需要超过 0x1f 字节）：

    0x00  4  魔数 0x32AB9864，大端序
    0x04  1  0x80（加密）| 版本（0x7F）= 4
    0x05  1  连接 ID
    0x06  2  包 ID，大端序
    0x08  8  AES-GCM 随机数，一个单调计数器
    0x10  16 AES-GCM 标签，不截断
    0x20     密文

这两个小字段是每个目标站点的，针对不特定站点的包中为 0。零售版的剑发送 0，这会通过所有接收路径。

- 连接 ID：接收者（`0x017bdbd0`）会丢弃 ID 为 2 或更多且与它持有的 ID 不同的 ID；0 和 1 通过。
- 包 ID：接收者（`0x0185dd20`）会通过 0 作为未排序的包 ID，并丢弃不大于该站点上次包 ID 的非零包 ID。

在头部以下，版本 4 与版本 9 共享会话密钥、IV 和帧格式。

### 版本 11：接收者会丢弃的包（火红 4.0.0）

`0x6e9744` 会在任何协议读取之前接受或丢弃整个包。当 `st` 是源地址处的站点，`V` 是接收者的变量 ID，`D` 是头部目标，`S` 是源时：

| 检查项 | 丢弃条件 |
|---|---|
| 发送者 | `st` 被标记（`+0x78`）或处于状态 3 |
| 目标 | `D >= 2` 且 `D != V` |
| 源 ID | `S != 0` 表示没有站点，当 `D == V` 时，或当 `D` 是 0 或 1 且有页脚时 |
| 包 ID，当 `D == 1` 时 | 不大于 `st` 在其目标-1 计数器（`st+0x60`）上的上次包 ID |
| 包 ID，其他 `D` | 不大于 `st` 在其另一个计数器（`st+0x48`）上的上次包 ID |

包 ID 0 总是通过且不存储；否则需要 `(int16)(id - last) >= 1`，因此相同 ID 的重传会被丢弃。当源地址处没有站点（加入）时，不检查包 ID。零售发送者使用一个计数器对目标-1 包进行编号，并使用每个接收者的计数器对单播包进行编号；两者都跳过 0。

## 消息帧格式

Pia 有效载荷承载一个或多个消息，每个消息以一个存在字节开头，表示哪些头部字段跟随。省略的字段从该包中的上一个消息继承（`0x01853050`）。遍历在 `0xFF` 时停止，且没有其他内容：`0x00` 是合法的一个字节头部，继承所有字段。

| 头部版本 | 标题读取 | 读取器 | 下一条消息开始位置 |
|---|---|---|---|
| 4 | 剑 | `0x01852da0` | 在四的倍数上 |
| 9（5.27-5.45） | 明亮珍珠 1.3.0 | `0x159b980` | 在四的倍数上 |
| 11（6.16-6.30） | 传说 阿尔宙斯 1.1.1 | `0x7484cc` | 在有效载荷结束处 |
| 11 | 火红 4.0.0 | `0x6ed2d0` | 在有效载荷结束处 |
| 16（6.39-7.2） | 传说 Z-A | `0x256e088`；没有 `0xFF` 停止，包头表示其填充 | 在有效载荷结束处 |

站点使用存在字节 0x00 打包等大小的消息运行（火红的零填充记录块，明亮珍珠的可靠消息，阿尔宙斯的第二个 24 字节记录）。永远不要在 0x00 处停止遍历。`tests/test_pia_bundled.py` 固定了每个标题的一个包。

版本 3（去吧！皮卡丘/伊布 1.0.2）没有存在字节：一个固定的 0x16 字节头部，其第二个字节必须为 1（`0x5ae7d0`），遍历在 `0xFF` 时停止。

版本 4 的头部是一个字节加上五个可选字段：

    位 0x01  +1  消息标志
    位 0x02  +2  有效载荷大小，大端序
    位 0x04  +4  协议 ID 和一个 3 字节端口
    位 0x08  +8  目标
    位 0x10  +8  发送者的站点常量 ID

存在 0x7F 给出 24 字节（版本 9：16）；位 0x20/0x40 没有添加任何内容。常量 ID 是 `station_protocol.ldn_constant_id`，基于发送者的 MAC，大端序在这里，小端序在本地协议主体中。

版本 16（Z-A）有一个字节的标志、协议（0x04）、端口（0x08）和位 0x10，两个字节的大小；位 0x10 字节位于协议和端口之间（`0x256df54`）。大小为 0x590 或以上会被拒绝。`pokeldn.ldn.reliable.parse_messages` 读取它。

在版本 4 和 9 中，每个消息都填充到四的倍数；包尾是 `0xFF`。`pia4.parse_packet()` 解析继承关系，`pia4.parse_messages()` 返回每个消息的原始头部。遍历正确当消耗的字节加上 `0xFF` 填充等于整个明文。

### 压缩

有效载荷可能是 zlib 流，在消息标志中标记：5.27-5.45 中为 0x20，版本 4 中为 0x10。版本 5 可靠头部有一个自己的 zlib 标志，0x10，BDSP 在某些游戏消息中设置（[BDSP 的协议](bdsp_protocol.md)）。BDSP 在会话中途切换压缩。zlib 流的第一个两个字节，作为大端序半字，是 31 的倍数。

### 页脚

发送到多个主机的包带有页脚：每个接收者一个大端序半字，低半字是其变量 ID，长度在头部字节 0x0f 中。GCM 标签不覆盖它：密文是 `data[0x20 : len(data) - footer_size]`（`pia5.ciphertext()`）。留在页脚中的内容会导致身份验证失败，没有其他症状。

## 会话密钥

| 网络类型 | 类 | 派生方式 |
|---|---|---|
| LDN（局域无线） | `nn::pia::local::LocalProtocol` | 在游戏密钥下使用 AES-128-ECB，基于从会话值中用 xorshift128 种子生成的 16 字节 |
| LAN | `nn::pia::lan::LanProtocol` | HMAC-SHA256（游戏密钥，一个参数，其最后一个字节递增）的第一个 16 字节（[LAN 模式](#lan-mode)） |
| NEX（互联网） | `nn::pia::nex::*` | 从匹配服务器获取的会话密钥 |

### 游戏密钥

    key = cryptoKeyDataSeed                     游戏自身的 16 字节常量
    key[1]  = (version >> 8) & 0xFF
    key[3]  = (version >> 4) & 0xFF             version = 局域通信版本，
    key[7]  = (version >> 1) & 0xFF                       由广告携带
    key[12] = (version >> 0) & 0xFF

`ldn_game_key()` 计算它。剑/盾的密钥是一个 16 字节的 ASCII 字面量，不变，没有种子和版本替换。

### LDN 会话密钥

对于 Pia 5.9-5.45：

    rnd = 四个 SEAD 抽取，种子是广告中的会话参数（+0x0c），
          小端序打包成 16 字节
    会话密钥 = AES-128-ECB（游戏密钥）。encrypt（rnd）

SEAD 种子 `s[i] = (prev ^ (prev >> 30)) * 0x6C078965 + i` 并运行一个 xorshift128，移位为 11、8 和 19（`pokeldn/ldn/sead.py`；`pia5.ldn_session_key()`）。对于 Pia 6.16+，会话密钥是游戏密钥下对 SSID 的 AES 加密（[无线层](ldn.md#hosting-for-an-emulator)）。

### AES-GCM IV

对于 Pia 5.27-5.45 和版本 4（`ldn_nonce_crc()`，`gcm_iv()`）：

    IV[0..2]  = crc32（网络 ID（小端序）||源 MAC 地址）的第一个三个字节
    IV[3]     = 源变量 ID & 0xFF        来自包头
    IV[4..11] = 包的 8 字节头部随机数

明文的 `0xFF` 填充是已知明文，用于在一个 AES 块中测试候选密钥。

## LAN 模式

LAN 模式通过普通 IP 网络上的 UDP 传输 Pia：一个站点通过广播查找会话，无需无线电和 LDN。`pokeldn/ldn/pia_lan.py` 实现 Pia 5.45 及更早版本；以下所有事实均通过模拟的 Shield 1.3.2 进行验证（`tests/test_swsh_lan.py` 将它们固定到其字节）。

| 端口 | 承载 |
|---|---|
| 30000 | 浏览请求（广播）和浏览回复（单播给请求者），未封装在 Pia 中 |
| 49152-49155 | 站点的 Pia 数据包；一个控制台取第一个空闲的 |
| 40000 | 站点发送到子网广播的可靠（0x80）消息 |

Scarlet 4.0.0（Pia 6）在 UDP 35000 上浏览，使用 317 字节的请求和 620 字节的回复，其站点端口为 49152（参见 [LAN mode](sv.md#lan-mode)）。

每个宝可梦标题都会链接 `nn::pia::lan` 并在某个模式值后面构建其 LAN 网络工厂；仅当某些代码传递该模式值时，标题才会进入 LAN 模式。从每个标题的 `main` 中读取：

| 标题 | LAN 模式值 | 其代码传递的值 | 页面 |
|---|---|---|---|
| Sword / Shield 1.3.2 | 3 | 0, 2, 3（Options 中按 L + R + 左摇杆） | [LAN mode](swsh_session.md#lan-mode) |
| Let's Go 1.0.2 | 2 | 0, 1 | [LAN mode](lgpe_session.md#lan-mode) |
| BDSP 1.3.0 | Pia 插件的 LAN 设置 | 无；LAN 设置从未被注册 | [LAN mode](bdsp_session.md#lan-mode) |
| Legends Arceus 1.1.1 | 3 | 1, 2 | [LAN mode](pla.md#lan-mode) |
| Scarlet 4.0.0 | 3 | 1, 2, 3（在 Combats en réseau 按住 ZL + ZR，已测量；从未从交易菜单） | [LAN mode](sv.md#lan-mode) |
| Legends Z-A 2.0.2 | 3 | 1, 2 | [LAN mode](za.md#lan-mode) |

### 浏览请求和回复

浏览请求为 `00`，后跟 u32 大小 `0x23A`，0x23A 字节的搜索条件和 0x12A 字节的加密挑战。回复为 `01`，后跟 u32 大小 `0x511`，会话信息和 0x3A 字节的挑战回复。

| 搜索条件偏移 | 字段 |
|---|---|
| 0x00 | 最小参与者，u16 的（最大值，最小值）对 |
| 0x04 | 最大参与者，相同的对 |
| 0x08 | 仅开启的，会话 |
| 0x0A | 结果偏移，结果大小（u32 各一个） |
| 0x12 | 游戏模式（u32） |
| 0x16 | 会话类型（u32） |
| 0x236 | 搜索标志：0x1 最小，0x2 最大，0x4 已开启，0x8 空缺，0x10 游戏模式，0x20 会话类型 |

| 会话信息偏移 | 字段 |
|---|---|
| 0x00 | 游戏模式，网络 id（u32 各一个） |
| 0x08 | 六个 u32 属性 |
| 0x20 | 参与者，最小值，最大值（u16 各一个） |
| 0x26 | 系统通信版本，应用程序通信版本（u8 各一个；在 Sword 中为 7 和 7） |
| 0x28 | 会话类型（u16） |
| 0x2A | 384 字节的应用程序数据，然后其 u32 大小位于 0x1AA |
| 0x1AE | 已开启 |
| 0x1AF | 主机地址：IPv4，12 个零字节，u16 端口 |
| 0x1C1 | 主机常量 id（u64），可变 id（u32），服务可变 id（u32） |
| 0x1D1 | 十六个 50 字节的站点：角色（1 主机，2 玩家），名称编码（1 UTF-8），40 字节名称，u64 常量 id |
| 0x4F1 | 32 字节的会话密钥参数 |

站点的 id 来自其地址：常量 id 是 IPv4 地址与端口的组合（`c0a8011f0000c001` 对应 192.168.1.31:49153），服务可变 id 是地址的低半部分与端口的组合，网络 id 等于主机的服务可变 id。

### 挑战

    challenge  = version 2, enabled 1, u64 counter, 16-byte challenge key, 16-byte tag,
                 256 random bytes under AES-GCM(AES-ECB(game key, challenge key),
                                                 nonce = receiver's broadcast address || counter)
    reply      = HMAC-SHA256(game key, the 256 bytes)[:16]
                 under AES-GCM(HMAC-SHA256(game key, reply key || request key)[:16], the same nonce)
    key param  = the first answered reply's challenge key || its request's challenge key
    session key = HMAC-SHA256(game key, key param with its last byte plus one)[:16]

nonce 以接收者子网的广播地址开头（`local | ~mask`）。主机为每个回复生成新的 16 字节挑战密钥，并在其下和它所回答的请求的挑战密钥下加密响应；密钥参数存储在会话信息 0x4F1 处，保留其首次回答的请求对（Shield 1.3.2 为 `0x0178b464`）。搜索站点在回复的挑战密钥和其自身最新请求的挑战密钥下检查回复，从不在密钥参数下（`0x0178ab2c`），并丢弃失败的回复。主机仅回答其会话匹配的请求（`0x0178e590`）：游戏模式，会话类型，两个参与者范围（0xFFFF 为开放），仅开启的和仅空缺的。

站点从其浏览回复中选择会话（`0x01778c80`）：搜索条件匹配，已开启，不是加入已失败的会话，相同的系统和应用程序通信版本，以及有足够空间加入的站点。若无符合条件的，则创建自己的会话。

### 主机请求和 AES-GCM IV

浏览后，加入者发送主机请求，协议 0x44 类型 3：`03`，11 个零字节，u32 网络 id。主机回复类型 4：`04`，11 个零字节，网络 id，其站点位置。随后进行的站点握手与通过 LDN 相同；没有 Local Protocol（0x24）。零售版 Shield 的主机请求携带源常量 id 0；其常量 id 是其地址与其站点端口的组合，而主机对任何其他 id 的连接请求都不会收到回复。

一旦进入网格，零售版 Shield 发送会话请求，类型 5：`05`，11 个零字节，u32 网络 id。主机以会话信息回复，使用会话消息，类型 6：`06`，11 个零字节，u32 值由分片共享，u16 序列 id，分片索引和计数（u8 各一个），u32 分片大小，然后最多 800 字节的会话信息。Shield 若未收到一个则在 5 秒后静默并离开网格。

站点每两秒发送一次 keep-alive，类型 7（`07` 和 11 个零字节），以明文形式在会话之外；接收者忽略它。

    IV[0..3]  = the sender's IPv4 address
    IV[4]     = the connection id from the packet header
    IV[5..11] = the last seven bytes of the header nonce

### 加入网格

站点通过更新会话（0x24）、连接请求（0x14）和加入请求（0x18）按顺序加入；每个都每 500 毫秒重传一次，直到收到确认。

网格消息在 0x14 上通过八字节类型 5 确认，格式为 `05 00 00 00` 和大端序的 ack id；ack id 是消息的最后四个字节（`mesh_protocol.ack_for()`）。主机在发送加入响应之前确认加入请求；接收者确认每个副本。

### 离开会话（Pia 6）

`Session::LeaveAsync` 运行 `LeaveSessionJob`，其 LeaveMesh 步骤在非主机上启动 `LeaveMeshJob`（在主机上为 `LeaveMeshWithHostMigrationJob`）。其 SendLeaveRequest 步骤发送 Session 类型的 3 离开请求，并等待 500 毫秒接收主机的类型 4 响应，最多发送四次。第一个类型 3 之前的任何延迟都属于游戏。

| | Legends Arceus 1.1.1 | GBA app (Pia 6.39) |
|---|---|---|
| `Session::LeaveAsync` | `0x72a6dc` | `0xb1060` |
| SendLeaveRequest | `0x73b898` | `0xcacf4` |

## Local Protocol（0x24）

主机每 100 毫秒广播一次更新会话（类型 0x11），直到每个站点确认为止：

    local message header  version 1, type 0x11, size 73
    sequence id
    network id            random, not the advertisement's network id
    host variable id      the packet header's source variable id
    host constant id
    allow participating
    node 0..7             address:port and a ranking byte each
    host migration state

Pia 消息头为大端序，这些字段为小端序，字段内的本地地址为大端序。`pokeldn/ldn/local_protocol.py` 解析它及版本 4 的。

### 确认

确认（类型 0x21）为 20 字节（`LocalAckMessage::Serialize`, `main.bin 0x016bc0f4`）：0 处为 `1`，1 处为类型，2 处为负载大小半字，六个零字节，0x0C 处为序列 id，四个零字节。它像更新会话一样被封装：presence `0x7F`，flags `0x11`，protocol 36，port 0，destination 0。客户端广播它；重新广播的停止是通过信号。

主机通过发送者的地址和端口属性确认（`0x016aec94`）。客户端的可变 id 用于 IV，因此在一次运行中必须稳定且非零。

## 网格站点协议（0x14）

第 0 字节为类型：1 为连接请求，2 为响应，3 和 4 为断开连接请求和响应，5 为确认，6 和 7 为中继连接请求和响应（调度程序：版本 4 `0x017c5f50`，BDSP `0x0154e848`）。

### 版本 9 的连接请求

按顺序检查：

| 偏移 | 字段 | 失败时 |
|---|---|---|
| | 大小 15..949 | 丢弃 |
| 0x0 | 消息类型、连接结果、平台 ID | 丢弃 |
| 0x3 | 目标常量 ID，大端序 u64，为本机所有 | 静默 |
| 0xB | 目标变量 ID，大端序 u32，为本机所有 | 静默 |
| 0xF | 协议数量，为本机所有 | 静默 |
| 0x10 | 那么多 (id, 版本) 对 | 版本过低 → 结果 2，过高 → 结果 3 |
| | 站点位置大小，大端序 u16，0x20..0x40 | 丢弃 |
| | 站点位置 | 丢弃 |

协议 ID 永远不会被检查。站点位置的地址大小字节必须为 2、6 或 18；格式错误的位置读取为变量 ID 0。

结果代码（`0x0154f5e8`）：

| 结果 | 含义 |
|---|---|
| 2 | 请求者版本过低 |
| 3 | 过高 |
| 7 | 所有版本都匹配但第二阶段拒绝，或变量 ID 已是本机站点之一（当站点离开或使用新 ID 时清除） |

大小：确认 8 字节，拒绝 15，断开连接响应 1。

### 版本 4 的连接请求

处理程序 `0x017c62a0`：

    [0]     消息类型            1
    [1]     NAT 标志
    [2]     平台 ID             必须为 9
    [3]     0 或 1；1 表示请求还指定了一个目标变量 ID
    [4]     目标常量 ID      大端序 u64，为本机所有
    [0xC]   目标变量 ID      大端序 u32，仅当 [3] 为 1 时检查
    [0x10]  NAT 位置 / 协议计数
    [0x11]  发送方的站点位置（反序列化器 `0x0185ee20`）

没有协议列表。当 [3] = 1 时，本机不回答。错误的平台会回复 `02 02 09 00` 和 13 个零字节（结果 2）；后续检查为静默。

握手过程，[3] 清零：

    ->   本机的连接请求
    <-   加入者的连接响应，结果 0，携带本机的常量和变量 ID
    ->   类型 5 的确认
    ->   自己的连接响应，约 600 字节，携带加入者的 ID 和玩家姓名，
         重复发送直到收到确认

发送本机请求的类型 5 确认会停止其重传（`--ack-request`）；在此之前也可以接受响应。

### 连接响应必须满足的条件才能被读取

类型 2 和 7 到达 `0x017c6e70`。除非结果不是 2，否则静默丢弃，除非：

| 字段 | 要求 |
|---|---|
| `[5]` 大端序 u64 | 接收方自己的常量 ID |
| `[0xD]` 大端序 u32 | 接收方自己的变量 ID |
| 站点位置 | 解析为其已知的站点 |
| `[0x37]`，仅结果 0 | 小于 5 |
| 站点状态 | 4，在发送确认后检查；接受时为 5 |

本机在 `[0x37]` 检查后对响应进行确认：一个从未被确认的响应失败了 ID、位置或 `[0x37]`。一个 17 字节的响应会在其末尾留下 stale 缓冲字节；`station4.build_connection_response(..., min_size=ACCEPTED_RESPONSE_SIZE)` 会填充到 0x38 并在其中写入 1。该层的接受不会启动其上的游戏（参见[抵达游戏层](swsh_session.md#reaching-the-game-layer)）。

本机自己的连接响应即为接受；其请求每 500 毫秒重传一次，附加相同的尾随计数器，表示拒绝；静默本身既不是接受也不是拒绝。

## 网格协议（0x18）

第 0 字节减 1 索引一个 129 项的表格（版本 4：`0x017c0c80`）；版本 4 缺少 BDSP 的 0x22 DUMMY_MESSAGE 和 0x23 DUMMY_ACK。

加入请求为六字节：类型 1，站点索引 253（"尚未加入网格")，一个确认 ID。Pia 大约每 10 秒重传一次。

加入响应头为十六字节。拒绝时 `[1] == 0`，`[2] == [3] == 0xFF`，原因在 [4]；否则 [1] 为站点数量，0xC 为大端序更新计数器。站点条目：

| 版本 | 条目 | 布局 |
|---|---|---|
| 5.31-5.45 | 68 字节 | 64 字节站点位置，站点索引，大端序加入顺序 |
| 4 | 64 字节 | 索引在 0x3E，无加入顺序，最多 32 个站点 |

版本 4 在未分段时遍历 `stations` 条目，在分段时遍历 [6] 项到槽 [7]；5.31-5.45 在两种情况下都取 [6]。`parse_join_response(version4=True)` 遵循这两种路径。

UPDATE_MESH（0x20），大约每秒一次，列出谁在网格中；BDSP 总是发送 556 字节，未使用的座位为零，因此遍历 `entries` 字节（`mesh_protocol.parse_update_mesh()`）。

### 主机迁移

0x18 端口 1 上的网格消息在可靠头部下到达。指定为下一个主机的站点必须回答。

| 消息 | 字节 | 处理程序要求 |
|---|---|---|
| MIGRATION_START (0x44) | `[0x44, 主机索引, 新主机索引]` | 大小 3，[1] 为网格的主机索引，[2] <= 0x1F 且不等于主机索引 (`0x017c1f00`) |
| MIGRATION_RESPONSE (0x48) | `[0x48, 自己的站点索引]` | 大小 2 (`0x017c10ac`) |
| MIGRATION_FINISH (0x41) | `[0x41, 主机索引, 标志 & 1]` | 大小 3，[1] 为主机索引 (`0x017c0fb0`) |

响应发送给新主机，新主机广播 MIGRATION_FINISH。`pokeldn/ldn/mesh_protocol.py` 构建并解析这三个消息。

## RTT 协议（0x58）

主机从每个站点加入网格开始计时。版本 9 的消息为十三个字节：

    u8   类型        0 = 请求，1 = 响应
    u64  时间戳   大端序，发送方自己的时钟
    u32  目标   大端序，此次回复针对谁；零被所有人接受

版本 4 读取固定的十六字节并忽略十三个字节的答案；
`rtt_protocol.response_for_v4()` 回显请求并仅设置类型。

站点以回显的时间戳回答类型 1。主机为每个站点维护一个九采样环，其中位数为 RTT；BDSP 时间戳以约 31.36 MHz 运行。静默的站点不会被丢弃，只是不再采样。BDSP 在未收到回复时每 410 毫秒发送一次请求，一旦环满则每 508 毫秒发送一次（`0x015ace54`）；可靠重传间隔遵循 RTT。

## 可靠滑动窗口（0x7c）

### 版本 9（Pia 5.29-5.43）

    0x0  1  标志     1 应用数据，2 消息开始，4 消息结束，8 已初始化，
                      16 zlib，32 重置，64 重置确认
    0x1  1  流 ID
    0x2  2  负载大小，大端序
    0x4  2  序列 ID，大端序
    0x6  2  待确认的最低序列 ID，大端序
    0x8  1  目标位数数量 (N)
    0x9  4 * ceil(N / 32)  目标位图字，大端序
            负载

N 大于等于 0x20 或负载大于等于 0x5a1 会被拒绝。

当应用数据标志清除时，负载为批量确认：

    0x0  1   位字段，所有捕获的确认中均为 0
    0x1  1   条目数量，0x21 或更多时拒绝
    0x2  21 * n  条目：u8 流 ID，u16be 确认 ID，u16be `确认 ID - 1`，16 字节确认掩码

零售机对序列 0 和 1 的确认：

    00 00 0017 ffff 0003 00   00 01   00 0002 0001  00 * 16

控制消息的序列 ID 为 0xFFFF。`ack id` 比收到的最高序列 ID 大 1。
`reliable5.build_ack_message()` 按字节还原它。带有序列 0 的数据消息不触发确认；序列 1 会触发。

### 接收方在静默中丢弃的内容

接收路径（Scarlet 4.0.0 `0x006f0330`，BDSP 1.3.0 `0x159fb98`) 在以下情况下丢弃消息但仍返回成功：

| 消息被丢弃时 | Scarlet | 确认仍发送 |
|---|---|---|
| 窗口未初始化且标志缺少 `is initialized` | `0x6f037c` | 否 |
| 序列 ID 低于窗口基 | `0x6f03cc` | 是 |
| 目标数量非零但位图缺少接收方的位 | `0x6f0430` | 否 |
| 流 ID 与初始化时锁存的不同 | `0x6f0454` | 否 |
| 环槽已被占用 | `0x6f0540` | 是 |

这两种被确认的情况会让发送方收到一条确认，但应用程序从未接收到该消息。窗口末尾之外的序列返回 `0x4c0d`，超过 `0x5a1` 字节的重组返回 `0x10407`，无法解压的 zlib 负载返回 `0x2c03`。

流上的第一条消息将基设置为其自身的序列 ID。接收方还会将基前进到发送方的 `lowest pending`（Scarlet `0x6eff24`）。声明 `lowest pending` 高于其下一个序列的发送方会让对等方在 Scarlet 和 BDSP 上丢弃这些消息并发送确认。确认携带发送方自己的未确认最低序列 ID，既在头部也在条目的第二个半字中。BDSP 在定时器上以及伴随数据向每个活跃对等方发送欠发送的确认。

### 窗口发送给谁（Pia 6）

`ReliableSlidingWindow` 的目标是按站点索引索引的站点指针，由 Pia 在站点加入和离开事件中填充，没有游戏代码（Scarlet 4.0.0：注册 `0x6ef588`）。仅在加入事件之前、离开之后、协议具有站点索引 0xfd，或注册拒绝时（索引已被占用或站点已注册），站点才会从列表中缺失。批量确认构建器 `0x6f2138` 读取同一个列表：确认中的一位显示窗口已注册该站点，与是否发送消息给它无关。

### 版本 4

一个标头类服务于 0x7C 和 0x80（`ReliableSlidingWindow::MessageHeader`，反序列化 `0x0184e390`）：

    0x0  1  标志
    0x1  1  流 ID
    0x2  2  负载大小，大端序    0x589 及以上拒绝
    0x4  2  序列 ID，大端序
    0x6  2  待确认的最低序列 ID，大端序
    0x8  1  目标数量           0x20 及以上拒绝
    0x9  8 * count  站点常量 ID，大端序

两种版本在 count 0 时一致，这是每一侧 0x7C 消息发送的共同点。

接收路径（`0x01859338`）在静默中拒绝负载超过 `0x57F - 8 * count` 的消息，拒绝消息长度不等于 `9 + 8 * count + size` 的消息，拒绝流 ID 与该站点的窗口不同的消息，拒绝目标列表中不包含接收方的消息，以及拒绝第一条消息缺少 FLAG_IS_INITIALIZED 的情况。标志位 5 为 RESET，位 6 为 RESET_ACK，位 0 为 APPLICATION_DATA；其他则为确认。

主机在其第一条消息上发送标志 0x0F，之后发送 0x07。
`reliable4.build_data_message(bytes.fromhex("610000000a00"))` 还原主机序列 1：
`0f0000060001000100610000000a00`。

确认负载恰好为 0x260 字节，32 个 19 字节条目：u8 流 ID，u16be 确认 ID，16 字节掩码（处理程序 `0x01859a84`；任何其他大小回复 0x2c03）。`reliable4.build_ack_payload` 用相同的条目填充每个槽。Shield 留下未使用的槽位为 stale 字节：仅读取被确认流的条目，否则发送方会超出主机的窗口并停止确认。

固定 `lowest_pending` 下的增长序列 ID 意味着积压的增长。

一条消息如果太长而无法放入单个负载，则分散在连续的序列 ID 上，第一条带标志 0x02，最后一条带标志 0x04，每个独立解压的片段带标志 0x10。Shield 主机的战斗回合日志（2074 到 2657 字节）分为两部分：标志 0x03 带 1407 字节未改变，随后标志 0x15 带剩余的 zlib 流；消息为第一部分后跟第二部分解压后的数据。在模拟回环上，3/11 的分段消息中关闭片段先于其开启片段到达：按序列顺序重新组装，绝不要按到达顺序。

## 协议 0x81：流式广播可靠传输（Pia 6）

`StreamBroadcastReliableProtocol` 将一个固定大小的数据块从一个站点传输到所有请求该数据的站点，并将其分块传输（Scarlet 4.0.0，更新 `0x6f5360`）。它与 0x7C 和 0x80 相同的时间限制内重传，但在没有任何目的地的 RTT 样本时不会重传。

每条消息都携带一个 11 字节的 StreamData 头部 (`0x6f60e8`)：

    +0  1  kind: 0 表示已接收到，1 表示第一个块，2 表示后续块，3 到 6 表示控制
    +1  1  传输 ID
    +2  1  本次块传输后已交付的块百分比
    +3  4  大端 u32：kind 0 时表示接收容量，块时为零
    +7  4  大端 u32：后续数据的长度
    +11    数据

已接收到的消息发送 kind 0，表示其容量；已发布的最小容量限制了发送 API 接受的块大小。对于大于该大小、ID 为 0xff 或没有站点为该 ID 发布接收的发送，发送将被拒绝。块的大小为 `[window+0x70] - 11` 字节。

| kind | 接收端的操作 |
|---|---|
| 0，接收已发布 | 记录发送者的 ID 和容量，或在忙碌时回复 kind 3 |
| 1，第一个块 | 重置已接收计数，然后按 kind 2 处理 |
| 2，块 | 如果数据适合，则复制数据；当百分比达到 100 时，接收完成 |
| 3，忙碌的发送者拒绝接收 | 重置传输 |
| 4，发送者取消 | 重置传输 |
| 5，接收者取消 | 删除该接收者；发送者回复 kind 6 |
| 6，发送者确认取消 | 重置 |

控制类型使用 ID 0xff。当每个目的地的窗口确认最后一个块时，发送完成。

## 协议 0x84：可靠广播传输

`nn::pia::transport::ReliableBroadcastProtocol` 用于承载 Sword/Shield 的交易快照：

| kind | 含义 |
|---|---|
| 0x11 / 0x12 | 数据片段；[4] 处有一个计数器，[10] 处有一个容量 |
| 0x19 | 传输完成 |
| 0x21 | 确认消息，包含连续的基数和早期到达的位掩码 |
| 0x28 | 对 0x19 的响应 |

如果接收者从未回复，发送者将持续重传最后三个消息（`pokeldn/ldn/broadcast4.py`）。一个控制台在端口 0 发送自己的传输，并在端口 1 确认对等方的传输。
